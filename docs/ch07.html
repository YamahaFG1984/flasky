第 7 章

大型应用的结构

单文件应用写起来方便，但越长越难改。和 Flask 一样，Hono 不强制任何目录结构，怎么组织完全由你决定。 这一章把 src/index.tsx 拆成一个结构清晰的项目：配置集中管理、用应用工厂创建应用、 用子应用分组路由（相当于蓝本），并且配上第一批单元测试。本书剩下的部分都会沿用这个结构。

本章目标

  • 知道项目里每个目录、每个文件的职责
  • 把配置集中到一个模块里，按“开发 / 测试 / 生产”切换，敏感信息只来自环境变量
  • 用应用工厂 createApp() 延迟创建应用，并通过中间件把依赖注入到每个请求
  • 用 new Hono() + app.route() 实现蓝本的效果
  • 用 npm scripts 代替 Flask 的自定义命令
  • 用 Vitest 写出并运行第一批单元测试

项目结构

四个最重要的约定：

  • src/ 放应用本身的所有代码（相当于原书的 app 包）。

配置

应用通常需要好几套配置，最典型的是数据库：开发、测试、生产要用三个不同的数据库，互不干扰 —— 你肯定不希望跑一遍单元测试就把开发时攒的数据清空了。 原书用一组配置类（Config、DevelopmentConfig、TestingConfig、ProductionConfig）加一个字典来实现。 TypeScript 里用一个接口描述“配置长什么样”，再用一个函数按名字生成对应的配置对象： 

export type ConfigName = 'development' | 'testing' | 'production'

export interface Config {
  name: ConfigName
  debug: boolean
  testing: boolean
  secretKey: string
  databaseUrl: string
  mail: { host: string; port: number; user?: string; password?: string }
  mailSubjectPrefix: string
  mailSender: string
  adminEmail?: string
  csrf: boolean
}

type Env = Record<string, string | undefined>

// 所有环境共用的部分（相当于原书的 Config 基类）
function baseConfig(env: Env) {
  return {
    debug: false,
    testing: false,
    secretKey: env.SECRET_KEY ?? 'hard to guess string',
    mail: {
      host: env.MAIL_SERVER ?? 'smtp.googlemail.com',
      port: Number(env.MAIL_PORT ?? 587),
      user: env.MAIL_USERNAME,
      password: env.MAIL_PASSWORD,
    },
    mailSubjectPrefix: '[Flasky]',
    mailSender: 'Flasky Admin <flasky@example.com>',
    adminEmail: env.FLASKY_ADMIN,
    csrf: true,
  }
}

export function loadConfig(name?: string, env: Env = process.env): Config {
  const configName = name ?? env.FLASKY_CONFIG ?? 'development'
  const base = baseConfig(env)

  switch (configName) {
    case 'development':
      return { ...base, name: 'development', debug: true, databaseUrl: env.DEV_DATABASE_URL ?? './data/dev' }
    case 'testing':
      return { ...base, name: 'testing', testing: true, csrf: false, databaseUrl: env.TEST_DATABASE_URL ?? 'memory://' }
    case 'production':
      if (!env.SECRET_KEY) throw new Error('生产环境必须设置 SECRET_KEY 环境变量')
      return { ...base, name: 'production', databaseUrl: env.DATABASE_URL ?? './data/prod' }
    default:
      throw new Error(`未知的配置名：${configName}`)
  }
}

和原书的写法相比，有几点值得注意：

  • 类型保证了“每套配置都完整”。如果给 Config 接口加了一个字段而某个分支忘了设置，TypeScript 会直接报错。
  • 生产环境没有 SECRET_KEY 就拒绝启动。原书给了一个默认值 'hard to guess string'，开发时方便，但如果忘了在生产环境设置， 所有人都能伪造你的会话。启动时就失败，比上线后出事好得多。
  • env 参数默认是 process.env。测试时可以传进一个假的环境，方便验证各种配置组合。
  • 原书每个配置类还有一个 init_app() 方法，用于“某个环境专属的初始化”（第 17 章用它配置日志）。我们会把这类逻辑放在 createApp() 里，按 config 的字段决定做不做。
⚠ 永远不要把密码等机密写进会提交到 Git 的配置文件

这是原书的原话，也是本书反复强调的规矩。机密一律通过环境变量传入。 开发时一个个 export 很烦，可以把它们写进项目根目录的 .env 文件（第 1 章已经把它加进了 .gitignore）： 

FLASKY_CONFIG=development
MAIL_USERNAME=你的测试邮箱
MAIL_PASSWORD=应用专用密码
FLASKY_ADMIN=你的邮箱

Node.js 20.12 起内置了 process.loadEnvFile()，调用一次就把 .env 读进 process.env，不需要装任何包（原书在第 17 章用 python-dotenv 做同样的事）。

应用工厂

到目前为止，app 是在模块顶层直接创建的。原书指出了这样做的问题：应用在模块被导入的那一刻就创建好了， 之后再想换一套配置已经来不及。这对单元测试尤其不利 —— 测试需要一个用测试配置、连测试数据库的应用。

解决方法是把创建应用的代码放进一个函数，需要的时候再调用，这个函数叫应用工厂（application factory）。 顺便把应用依赖的东西（配置、数据库、邮件发送器）都作为参数传进去： 

import { serveStatic } from '@hono/node-server/serve-static'
import { Hono } from 'hono'
import { csrf } from 'hono/csrf'
import { logger } from 'hono/logger'
import type { Config } from './config.js'
import type { Db } from './db/index.js'
import type { Mailer } from './lib/email.js'
import { session } from './lib/session.js'
import { main } from './routes/main.js'
import type { AppEnv } from './types.js'
import { renderer } from './views/layout.js'
import { ErrorPage } from './views/pages.js'

export interface AppDeps {
  config: Config
  db: Db
  mailer: Mailer
}

export function createApp({ config, db, mailer }: AppDeps) {
  const app = new Hono<AppEnv>()

  // 把“全局”依赖挂到每个请求的 c.var 上 —— 相当于 Flask 的 current_app
  app.use('*', async (c, next) => {
    c.set('config', config)
    c.set('db', db)
    c.set('mailer', mailer)
    await next()
  })

  if (config.debug) app.use('*', logger())
  app.use('/static/*', serveStatic({ root: './' }))
  app.use('*', renderer)
  if (config.csrf) app.use('*', csrf())
  app.use('*', session)

  app.route('/', main)          // 注册“蓝本”

  app.notFound((c) => { c.status(404); return c.render(<ErrorPage status={404} />) })
  app.onError((err, c) => {
    console.error(err)
    c.status(500)
    return c.render(<ErrorPage status={500} />)
  })

  return app
}

所有会出现在 c.var 上的东西，在一个地方声明类型：

import type { Config } from './config.js'
import type { Db } from './db/index.js'
import type { Mailer } from './lib/email.js'
import type { SessionData } from './lib/session.js'

export type AppEnv = {
  Variables: {
    config: Config
    db: Db
    mailer: Mailer
    session: SessionData
  }
}
🔎 深入：为什么不直接 import 一个全局的 db？

第 5 章我们在 db/index.ts 里直接 export const db = …，任何文件 import 进来就能用。这很方便， 但它和“模块顶层创建 app”有同样的问题：数据库在 import 的那一刻就连上了，测试没法换成内存数据库。 通过 c.var.db 取数据库，数据库是谁、连到哪里，完全由调用 createApp() 的人决定。 这就是依赖注入。在 Cloudflare Workers 上它还是必需的：那里的数据库连接只能在请求里从 c.env 拿到。

数据库模块也改成工厂

第 5 章的 db/index.ts 写死了 PGlite 的路径。现在改成根据 URL 决定连接谁：

import { mkdirSync } from 'node:fs'
import { dirname } from 'node:path'
import { PGlite } from '@electric-sql/pglite'
import { drizzle as drizzlePg, type NodePgDatabase } from 'drizzle-orm/node-postgres'
import { migrate } from 'drizzle-orm/node-postgres/migrator'
import { drizzle as drizzlePglite } from 'drizzle-orm/pglite'
import pg from 'pg'
import * as schema from './schema.js'

export type Db = NodePgDatabase<typeof schema>

// postgres:// 开头 → 真正的 PostgreSQL 服务器；其他 → PGlite（目录路径，或 memory://）
export function createDb(url: string): Db {
  if (/^postgres(ql)?:\/\//.test(url)) {
    return drizzlePg(new pg.Pool({ connectionString: url }), { schema })
  }
  if (!url.startsWith('memory://')) mkdirSync(dirname(url), { recursive: true })   // PGlite 不会自动建上级目录
  // 两种驱动的查询 API 完全相同，统一成一个类型，业务代码就不必关心底下是谁
  return drizzlePglite(new PGlite(url), { schema }) as unknown as Db
}

export async function migrateDb(db: Db, migrationsFolder = './drizzle') {
  await migrate(db, { migrationsFolder })
}

邮件模块同理

第 6 章的 transport 也是模块顶层创建的。改成一个 Mailer 接口，并且测试配置下根本不连 SMTP，只把邮件存进一个数组 —— 原书也提到，Flask-Mail 在测试配置下会把邮件记录下来而不真正发送： 

export interface MailMessage { to: string; subject: string; text: string; html: string }

export interface Mailer {
  send(message: MailMessage): Promise<void>
  outbox: MailMessage[]            // 测试时，“发出去”的邮件都留在这里
}

export function createMailer(config: Config): Mailer {
  const outbox: MailMessage[] = []
  if (config.testing) {
    return { outbox, async send(message) { outbox.push(message) } }
  }
  const transport = nodemailer.createTransport({
    host: config.mail.host,
    port: config.mail.port,
    secure: config.mail.port === 465,
    auth: config.mail.user ? { user: config.mail.user, pass: config.mail.password } : undefined,
  })
  return { outbox, async send(message) { await transport.sendMail({ from: config.mailSender, ...message }) } }
}

export function sendEmail<P>(
  c: Context<AppEnv>, to: string, subject: string, template: EmailTemplate<P>, props: P,
): Promise<void> {
  const { config, mailer } = c.var
  const task = (async () => {
    const { text, html } = template(props)
    await mailer.send({ to, subject: `${config.mailSubjectPrefix} ${subject}`, text, html: String(await html) })
  })().catch((err) => console.error('邮件发送失败：', err))

  // Cloudflare Workers 等环境需要 waitUntil；Node.js 没有 executionCtx，访问它会抛异常，忽略即可
  try { c.executionCtx.waitUntil(task) } catch { /* Node.js */ }
  return task
}

用子应用分组路由（蓝本）

应用工厂带来一个新问题：原来路由是用 app.get() 注册的，可现在 app 要等 createApp() 被调用时才存在， 路由写在哪？原书的答案是蓝本（blueprint）：它像一个“还没挂上去的小应用”，可以先定义路由，之后再注册到应用上。

Hono 里没有专门的“蓝本”类，因为任何一个 new Hono() 都可以挂到另一个上面：

Flask：app/main/__init__.py + views.py
from flask import Blueprint
main = Blueprint('main', __name__)
from . import views, errors

# views.py
@main.route('/', methods=['GET', 'POST'])
def index():
    ...

# app/__init__.py 的 create_app() 里
from .main import main as main_blueprint
app.register_blueprint(main_blueprint)
Hono：src/routes/main.tsx
import { Hono } from 'hono'
import type { AppEnv } from '../types.js'

export const main = new Hono<AppEnv>()

main.get('/', (c) => { … })
main.post('/', …)

// src/app.tsx 的 createApp() 里
import { main } from './routes/main.js'
app.route('/', main)

和原书对照几个细节：

  • 错误处理器。原书指出：在蓝本里用 errorhandler 只对本蓝本的路由生效，要全应用生效得用 app_errorhandler。 Hono 也有同样的两层：子应用上的 onError 只管自己的路由（第 14 章的 API 就会用它返回 JSON 错误），createApp() 里的 app.onError / app.notFound 管全局。
  • 循环导入。原书要把 from . import views 放在 __init__.py 的最后，以免循环导入出错。 在我们的结构里，路由模块不需要 import 应用，只有 app.tsx 去 import 路由，所以依赖是单向的，不存在这个问题。
  • url_for('main.index') 与命名空间。原书花了一段讲蓝本如何给端点名加前缀。Hono 没有端点名，页面里直接写路径（第 3 章讲过）。

第 4–6 章的首页路由，搬进 routes/main.tsx 后是这样的。注意它不再 import 任何全局的 db、transport，全部从 c.var 获取：

import { eq } from 'drizzle-orm'
import { Hono } from 'hono'
import { z } from 'zod'
import { users } from '../db/schema.js'
import { sendEmail } from '../lib/email.js'
import { validateForm } from '../lib/forms.js'
import type { AppEnv } from '../types.js'
import { newUserEmail } from '../views/emails.js'
import { IndexPage } from '../views/pages.js'

export const main = new Hono<AppEnv>()

const nameSchema = z.object({ name: z.string().trim().min(1, '请填写你的名字') })

main.get('/', (c) => {
  const { name, known } = c.var.session
  return c.render(<IndexPage name={name} known={known} />)
})

main.post(
  '/',
  validateForm(nameSchema, (c, values, errors) =>
    c.render(<IndexPage name={c.var.session.name} values={values} errors={errors} />)),
  async (c) => {
    const { db, config, session } = c.var
    const { name } = c.req.valid('form')
    const [user] = await db.select().from(users).where(eq(users.username, name)).limit(1)
    if (!user) {
      await db.insert(users).values({ username: name })
      session.known = false
      if (config.adminEmail) sendEmail(c, config.adminEmail, '新用户', newUserEmail, { username: name })
    } else {
      session.known = true
    }
    session.name = name
    return c.redirect('/')
  },
)

validateForm() 是把第 4 章那个“校验失败就带着错误重新渲染”的 zValidator 钩子提炼出来的小工具， 后面每个表单都会用到： 

import { zValidator } from '@hono/zod-validator'
import type { Context } from 'hono'
import { z } from 'zod'
import type { AppEnv } from '../types.js'

export type FormValues = Record<string, unknown>
export type FieldErrors = Record<string, string[] | undefined>

export function validateForm<S extends z.ZodType>(
  schema: S,
  onInvalid: (c: Context<AppEnv>, values: FormValues, errors: FieldErrors) => Response | Promise<Response>,
) {
  return zValidator('form', schema, async (result, c) => {
    if (!result.success) {
      const errors = z.flattenError(result.error).fieldErrors as FieldErrors
      return onInvalid(c as Context<AppEnv>, result.data as FormValues, errors)
    }
  })
}
ⓘ 为什么 import 路径要写 .js，明明文件是 .ts？

第 1 章的 tsconfig.json 用了 "module": "NodeNext"。在这个模式下，TypeScript 要求你写的是编译之后的文件名： routes/main.tsx 编译后是 routes/main.js，Node.js 运行时找的就是它。TypeScript 知道去找对应的 .ts/.tsx 做类型检查。 这是 Node.js 官方 ES Module 规范的要求（Node 不会帮你猜后缀），Hono 官方的 Node.js 模板也是这么写的。

单元测试

原书用 Python 标准库的 unittest 写了两个最简单的测试：应用存在、应用在用测试配置。 我们用 Vitest —— 速度快、原生支持 TypeScript，API 和流行的 Jest 一样： 

npm install -D vitest

import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: {
    include: ['tests/**/*.test.ts'],
    testTimeout: 20_000,     // PGlite 第一次启动要一两秒
  },
})

先写一个测试辅助函数：用测试配置、内存数据库和假邮件发送器组装一个应用。这正是应用工厂的价值所在：

import { createApp } from '../src/app.js'
import { loadConfig } from '../src/config.js'
import { createDb, migrateDb } from '../src/db/index.js'
import { createMailer } from '../src/lib/email.js'

export async function setupTestApp() {
  const config = loadConfig('testing')
  const db = createDb('memory://')      // 每次都是一个全新的空数据库
  await migrateDb(db)                   // 相当于原书 setUp() 里的 db.create_all()
  const mailer = createMailer(config)
  const app = createApp({ config, db, mailer })
  return { app, db, config, mailer }
}
unittest：tests/test_basics.py
class BasicsTestCase(unittest.TestCase):
    def setUp(self):
        self.app = create_app('testing')
        self.app_context = self.app.app_context()
        self.app_context.push()
        db.create_all()

    def tearDown(self):
        db.session.remove()
        db.drop_all()
        self.app_context.pop()

    def test_app_exists(self):
        self.assertFalse(current_app is None)

    def test_app_is_testing(self):
        self.assertTrue(current_app.config['TESTING'])
Vitest：tests/basics.test.ts
import { beforeAll, describe, expect, it } from 'vitest'
import { setupTestApp } from './helpers.js'

describe('基础', () => {
  let ctx: Awaited<ReturnType<typeof setupTestApp>>

  beforeAll(async () => {
    ctx = await setupTestApp()
  })

  it('应用存在', () => {
    expect(ctx.app).toBeDefined()
  })

  it('使用的是测试配置', () => {
    expect(ctx.config.testing).toBe(true)
    expect(ctx.config.databaseUrl).toBe('memory://')
  })
})

对照一下概念：

  • describe 把相关的测试分成一组（相当于 TestCase 类）；it 是一个测试（相当于 test_ 开头的方法）。
  • beforeAll / beforeEach / afterEach 相当于 setUpClass / setUp / tearDown。
  • expect(x).toBe(y) 相当于 assertEqual。
  • 不需要 tearDown 里的 drop_all()：内存数据库随着测试进程结束自然消失。
  • 也不需要 app_context.push()：我们没有上下文，所有东西都是显式传的。

数据库初始化与运行

重构后的应用用的是配置里的数据库地址（开发环境默认 ./data/dev），和第 5 章单文件版本用的不一定是同一个。 不管数据库在哪、是新是旧，一条命令就能把它升级到最新结构 —— 这正是迁移的好处： 

npm run db:migrate
npm run dev
# Flasky（development）运行在 http://localhost:3000

原书这一章的结尾说：你已经走完了第一部分，学到了构建 Web 应用的基本要素，但可能还不太清楚这些零件怎么拼成一个真正的应用。 第二部分就是来解决这个问题的：我们会用这些零件，一章一章地搭出完整的社交博客。

小结

  • 项目按职责分目录：routes（蓝本）、views（模板）、models（业务逻辑）、lib（工具）、db（数据库），命令放 scripts。
  • 配置集中在 config.ts，按 FLASKY_CONFIG 选择；机密只来自环境变量，开发时写在不提交的 .env 里，用 process.loadEnvFile() 读取。
  • 应用工厂 createApp({ config, db, mailer }) 让测试可以用不同的零件组装应用；依赖通过中间件放进 c.var。
  • 任何 new Hono() 都能用 app.route(前缀, 子应用) 挂载，这就是 Hono 版的蓝本。
  • npm scripts 代替 Flask CLI；dependencies / devDependencies 代替多个 requirements 文件。
  • Vitest 的 describe / it / expect 对应 unittest 的类、方法和断言；npm test 运行。

动手练习

  2. 新建一个 routes/about.tsx 子应用，里面有 GET / 和 GET /team，把它挂载到 /about，用 showRoutes(app) 确认最终路径。

  4. 把开发数据库删掉（rm -rf data），只用 npm run db:migrate 重建它，体会“迁移即文档”。
