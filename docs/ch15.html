第 15 章

测试

第三部分“最后一公里”从测试开始。写单元测试有两个理由：确认新写的代码按预期工作；更重要的是，每次修改之后都能确认旧的功能没有被改坏（也就是没有“回归”）。 这一章用覆盖率找出没被测到的代码，用 Hono 的 app.request() 测试网页和 API，最后用 Playwright 驱动真实的浏览器做端到端测试。

本章目标

  • 用 Vitest 的 V8 覆盖率报告找出测试的盲区
  • 理解 app.request()：不启动服务器，直接把请求送进应用
  • 写一个会记住 Cookie、会跟随重定向的测试客户端，模拟完整的注册登录流程
  • 测试 REST API 的认证、状态码和 JSON 内容
  • 用 Playwright 在真实浏览器里测试页面
  • 知道哪些测试值得写、代码应该怎样组织才好测

代码覆盖率

有一套测试很重要，知道这套测试“好不好”同样重要。覆盖率工具统计测试运行时执行了应用的哪些代码， 并给出一份报告，指出哪些部分从来没被测到 —— 这正是下一步该补测试的地方。

原书用 Python 的 coverage 包，而且为了让覆盖率从程序的第一行开始统计，在 flask test --coverage 里用了一个“设置环境变量后重新启动自己”的技巧。 Node.js 的 V8 引擎自带覆盖率统计，Vitest 直接调用它，一个参数就够了： 

npm install -D @vitest/coverage-v8

import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: {
    include: ['tests/**/*.test.ts'],
    testTimeout: 20_000,
    hookTimeout: 30_000,
    // 只统计 src/ 下的代码（相当于原书的 include='app/*'），测试代码和依赖包不算
    coverage: { provider: 'v8', include: ['src/**'] },
  },
})

npx vitest run --coverage

除了终端里的表格，Vitest 还会在 coverage/ 目录生成一份 HTML 报告，用浏览器打开 coverage/index.html， 可以看到每一行源代码被标成绿色（执行过）或红色（没执行过）。原书特别提到了分支覆盖率： 它不只看每一行有没有执行，还检查每个 if 的“真”和“假”两条路是不是都走过 —— 表格里的“分支”一列就是它。

ⓘ 覆盖率高不等于没有 bug

原书提醒：覆盖率说明不了项目里有多少代码是没有 bug 的，测试本身的质量同样重要。一行代码“被执行过”，不代表它的结果被检查过。 覆盖率最有用的地方，是告诉你哪里完全没有测试。

测试网页：app.request()

应用里有些代码离不开“正在处理请求”的环境。原书指出，你没法直接调用视图函数来测试它 —— 它需要请求上下文、表单数据、登录的用户…… Flask 为此提供了测试客户端：它模拟应用运行在 Web 服务器里的环境，让测试像客户端一样发请求。

Hono 在这方面有天然优势。应用本来就是一个 (Request) => Response 的函数，测试时根本不需要服务器： app.request() 构造一个标准的 Request，直接交给应用，拿回一个标准的 Response。

最简单的例子，对应原书的 test_home_page：

it('首页向陌生人问好', async () => {
  const res = await ctx.app.request('/')
  expect(res.status).toBe(200)
  expect(await res.text()).toContain('陌生人')
})

一个像浏览器一样的测试客户端

原书创建测试客户端时传了 use_cookies=True：让它像浏览器一样接收和发送 Cookie，这样依赖会话的功能（登录状态！）才能测试。 它还有 follow_redirects=True 选项，让客户端自动跟随重定向。app.request() 本身只发一次请求，我们在它外面包一个小类，补上这两个能力： 

type Fetchable = { request: (input: string, init?: RequestInit) => Response | Promise<Response> }

export class TestClient {
  cookies = new Map<string, string>()

  constructor(private app: Fetchable) {}

  async request(path: string, init: RequestInit & { followRedirects?: boolean } = {}): Promise<Response> {
    const { followRedirects = false, ...rest } = init
    const headers = new Headers(rest.headers)
    if (this.cookies.size) {
      headers.set('Cookie', [...this.cookies].map(([k, v]) => `${k}=${v}`).join('; '))   // ① 带上 Cookie
    }
    const res = await this.app.request(path, { ...rest, headers })
    this.storeCookies(res)                                                               // ② 记住 Cookie

    const location = res.headers.get('Location')
    if (followRedirects && res.status >= 300 && res.status < 400 && location) {
      const url = new URL(location, 'http://localhost')
      return this.request(url.pathname + url.search, { followRedirects: true })          // ③ 跟随重定向
    }
    return res
  }

  get(path: string, opts: { followRedirects?: boolean } = {}) {
    return this.request(path, opts)
  }

  post(path: string, form: Record<string, string>, opts: { followRedirects?: boolean } = {}) {
    return this.request(path, { method: 'POST', body: new URLSearchParams(form), ...opts })
  }

  private storeCookies(res: Response) {
    for (const line of res.headers.getSetCookie()) {
      const [pair, ...attrs] = line.split(';')
      const i = pair.indexOf('=')
      const name = pair.slice(0, i).trim()
      const value = pair.slice(i + 1).trim()
      const expired = attrs.some((a) => /^\s*max-age=0\s*$/i.test(a))   // deleteCookie 发的是 Max-Age=0
      if (expired || value === '') this.cookies.delete(name)
      else this.cookies.set(name, value)
    }
  }
}

注意 post() 用 URLSearchParams 作正文，和浏览器提交表单时的编码完全一样（application/x-www-form-urlencoded，第 4 章）。

CSRF 与测试配置

原书遇到一个小麻烦：Flask-WTF 的每个表单都有隐藏的 CSRF 令牌，测试要先请求页面、解析 HTML 取出令牌才能提交。于是原书在测试配置里关掉了 CSRF。 我们的 hono/csrf 检查的是 Origin 头，测试客户端不发这个头，同样会被拦截。第 7 章的测试配置里已经做了同样的事： 

case 'testing':
  return { ...base, name: 'testing', testing: true, csrf: false, databaseUrl: 'memory://' }
💡 也可以不关，测试里带上 Origin

因为我们的 CSRF 防护不需要令牌，其实只要在测试请求里加一个头 Origin: http://localhost 就能通过检查。 如果你想让测试覆盖 CSRF 中间件本身，这是个好办法：写一个专门的测试，断言“没有 Origin 的表单 POST 返回 403”。

模拟一个新用户的完整流程

原书例 15-4 模拟了一个新用户：注册、登录、确认账户、退出。翻译成我们的测试客户端：

it('注册 → 登录 → 确认 → 退出', async () => {
  // 注册：成功时重定向到登录页
  let res = await client.post('/auth/register', {
    email: 'john@example.com', username: 'john', password: 'cat', password2: 'cat',
  })
  expect(res.status).toBe(302)
  expect(ctx.mailer.outbox).toHaveLength(1)                       // 确认邮件“发”出去了
  expect(ctx.mailer.outbox[0].subject).toContain('确认你的账户')

  // 登录：会被带到“请先确认账户”页面
  res = await client.post('/auth/login', { email: 'john@example.com', password: 'cat' }, { followRedirects: true })
  expect(res.status).toBe(200)
  let html = await res.text()
  expect(html).toMatch(/你好，\s*john！/)
  expect(html).toContain('你还没有确认账户')

  // 模拟点击邮件里的确认链接
  const user = (await findUserByEmail(ctx.db, 'john@example.com'))!
  const token = await generateConfirmationToken(ctx.config.secretKey, user.id)
  res = await client.get(`/auth/confirm/${token}`, { followRedirects: true })
  expect(await res.text()).toContain('账户确认成功')

  // 退出（第 8 章把它改成了 POST）
  res = await client.post('/auth/logout', {}, { followRedirects: true })
  html = await res.text()
  expect(html).toContain('你已退出登录')
  expect(html).toContain('陌生人')
})

几个值得说说的细节，都来自原书的讨论：

  • 正则匹配问候语。原书发现 'Hello, john!' 搜不到，因为 Jinja2 模板在两个词之间留下了多余的空白，只好用正则。JSX 输出的 HTML 没有这种多余空白，但用 \s* 容错是好习惯，模板格式调整时测试不会莫名其妙地挂掉。
  • 确认令牌从哪来？令牌本来在邮件里。原书的做法是绕过邮件，直接用用户对象再生成一个。我们也这样做；另一种选择是从 ctx.mailer.outbox[0].text 里用正则把链接抠出来 —— 这样还顺便测试了邮件内容。
  • 每个测试都从干净的数据库开始。见下一节。

测试数据库的策略

原书在每个测试的 setUp() 里 create_all()、在 tearDown() 里 drop_all()。 每个测试都新建一个 PGlite 实例也可以，但它启动一次要零点几秒。更快的做法是每个测试文件建一次，每个测试前清空所有表： 

export async function resetDb(db: Db) {
  // TRUNCATE 比 DELETE 快得多；RESTART IDENTITY 让自增 id 从 1 重新开始；CASCADE 连带清空有外键引用的表
  await db.execute(sql`truncate table comments, posts, follows, users, roles restart identity cascade`)
  await insertRoles(db)
}

describe('网页端（测试客户端）', () => {
  let ctx: Awaited<ReturnType<typeof setupTestApp>>
  let client: TestClient

  beforeAll(async () => { ctx = await setupTestApp() })     // 每个文件一次：建库、迁移、建应用
  beforeEach(async () => {
    await resetDb(ctx.db)                                   // 每个测试一次：清空数据
    ctx.mailer.outbox.length = 0
    client = new TestClient(ctx.app)                        // 新的客户端 = 新的“浏览器”，没有 Cookie
  })
  // …各个 it(…)
})

Vitest 默认让不同的测试文件在不同的工作线程里并行运行，每个文件有自己的内存数据库，互不干扰。

测试 Web 服务

测试 API 同样用 app.request()，而且更简单：API 是无状态的，不需要 Cookie，每个请求自己带上认证头就行。原书写了一个辅助方法生成这些请求头： 

const basic = (email: string, password: string) => ({
  Authorization: `Basic ${btoa(`${email}:${password}`)}`,
  Accept: 'application/json',
  'Content-Type': 'application/json',
})

it('没带认证信息 → 401', async () => {
  const res = await ctx.app.request('/api/v1/posts/', { headers: { 'Content-Type': 'application/json' } })
  expect(res.status).toBe(401)
})

it('未确认的账户 → 403', async () => {
  await createUser(ctx.db, { email: 'john@example.com', username: 'john', password: 'cat', confirmed: false })
  const res = await ctx.app.request('/api/v1/posts/', { headers: basic('john@example.com', 'cat') })
  expect(res.status).toBe(403)
})

原书例 15-5 的 test_posts：先插入一个用户，然后通过 API 写一篇文章、再读回来检查：

it('文章：创建、读取、列表、时间线、修改', async () => {
  const u = await addUser('john@example.com', 'john', 'cat')
  const headers = basic('john@example.com', 'cat')

  // 空正文 → 400
  let res = await ctx.app.request('/api/v1/posts/', { method: 'POST', headers, body: JSON.stringify({ body: '' }) })
  expect(res.status).toBe(400)
  expect((await res.json()).message).toBe('post does not have a body')

  // 写一篇
  res = await ctx.app.request('/api/v1/posts/', {
    method: 'POST', headers, body: JSON.stringify({ body: 'body of the *blog* post' }),
  })
  expect(res.status).toBe(201)
  const url = res.headers.get('Location')!

  // 读回来
  res = await ctx.app.request(url, { headers })
  const post = await res.json()
  expect(post.url).toBe(url)
  expect(post.body_html).toBe('<p>body of the <em>blog</em> post</p>')   // Markdown 在服务器上渲染过了

  // 时间线里也有它（自己关注自己，第 12 章）
  res = await ctx.app.request(`/api/v1/users/${u.id}/timeline/`, { headers })
  expect((await res.json()).count).toBe(1)
})

原书提到，Flask 测试客户端不会自动把字典编码成 JSON，需要手动 json.dumps()，返回的正文也要 json.loads()。 标准的 Request / Response 也一样：请求正文用 JSON.stringify()，响应用 await res.json()。

ⓘ 类型安全的测试客户端：hono/testing

Hono 还提供了 testClient()（来自 hono/testing），它和第 14 章提到的 RPC 客户端 hc 一样， 能根据路由定义推断出路径和参数的类型，写成 client.posts[':id'].$get({ param: { id: '1' } }) 这样。 要享受这种类型推断，路由需要用链式写法（new Hono().get(…).post(…)）来定义。我们的项目用的是普通写法，所以本章用 app.request()，它适用于任何写法。

📌 原书检查点 15c：测试 Web 服务

用 Playwright 做端到端测试

测试客户端无法完全模拟真实的运行环境。原书举的例子：页面里的 JavaScript 根本不会被执行。Flasky 就有两段这样的脚本（第 3 章的本地化时间、第 11 章的 Markdown 预览）。 要测试这些，只能用真正的浏览器连接真正运行着的服务器。原书用的是 Selenium，今天 JavaScript 生态里最流行的是微软的 Playwright： 

npm install -D @playwright/test
npx playwright install chromium        # 下载一个测试专用的 Chromium

原书为 Selenium 测试做了不少准备工作：在后台线程里启动 Flask 服务器、写一个只在测试模式下可用的 /shutdown 路由来关闭它、测试结束后清理数据库…… Playwright 把这些都接管了：在配置里告诉它“怎么启动服务器、服务器在哪个地址”，它会在测试前启动、等服务器就绪、测试后关闭。 

import { defineConfig } from '@playwright/test'

export default defineConfig({
  testDir: './e2e',
  use: { baseURL: 'http://localhost:3100' },      // 默认就是无头模式（原书的 'headless' 参数）
  webServer: {
    command: 'npx tsx scripts/e2e-server.ts',     // 启动一个带测试数据的服务器
    url: 'http://localhost:3100',                 // 等这个地址能访问了才开始测试
  },
})

测试用的服务器：内存数据库，插入一些假数据和一个管理员（对应原书 setUpClass() 里做的事）：

和测试客户端的写法对比，原书指出了最大的不同：用 Selenium（Playwright 也一样）时，测试从不直接和应用打交道， 而是向浏览器发出命令，这些命令和真实用户用鼠标、键盘做的事一一对应。 Playwright 的定位方式也是按“用户看到的东西”来的：getByRole('link', { name: '登录' }) 找的是“文字为‘登录’的链接”， getByLabel('邮箱') 找的是“标签为‘邮箱’的输入框”——这也是第 4 章表单里 <label for> 要写对的另一个理由。

📌 原书检查点 15d：用 Selenium 做端到端测试

值得吗？

原书用一节来回答这个问题：写测试客户端和浏览器测试真的值得吗？它的回答很有分量： 无论你愿不愿意，你的应用一定会被测试。你不测，你的用户就会替你测 —— 他们会发现 bug，然后你得在压力之下修复。

原书的建议可以总结成两条：

  • 能脱离请求环境测试的部分，一定要测。比如模型里的逻辑，写起来成本很低，却保证了应用核心的正确性。本书从第 8 章起就一直在这么做。
  • 把业务逻辑从处理函数里挪出去。处理函数应该很薄：接收请求、调用 models/ 或 lib/ 里的函数、返回响应。 这样大部分逻辑都能用便宜的单元测试覆盖，只有少数“必须在真实环境里才能验证”的功能才需要写端到端测试。

回头看看我们的代码：createUser()、confirmUser()、getPostsPage()、can() 都是不依赖 c 的普通函数，所以测起来毫不费力； 第 7 章的应用工厂和依赖注入，让整个应用可以用内存数据库和假邮件发送器组装起来测试。好测的代码，往往也是结构好的代码。

小结

  • vitest run --coverage 用 V8 内置覆盖率生成报告，重点看“完全没测到”的地方；分支覆盖率检查每个 if 的两条路。
  • app.request() 不需要服务器，直接把标准 Request 交给应用；包一层 Cookie 管理和重定向跟随，就得到了 Flask 测试客户端的全部能力。
  • 测试配置关闭 CSRF（或者给请求带上 Origin 头）；测试邮件看 mailer.outbox。
  • 每个测试文件一个内存数据库，每个测试前 TRUNCATE 清空，又快又隔离。
