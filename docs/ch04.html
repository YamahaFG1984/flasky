第 4 章

Web 表单

到目前为止，信息只从服务器流向浏览器。表单让信息反过来流动：用户填写、提交，服务器接收、校验、处理。 这一章实现原书的“你叫什么名字”表单，顺带讲清楚三个贯穿全书的机制： POST/重定向/GET 模式、用户会话和 Flash 消息。

本章目标

  • 知道浏览器提交表单时到底发送了什么，以及如何在 Hono 里读取
  • 用 Zod 描述“什么样的输入才合格”，用 @hono/zod-validator 自动校验
  • 把表单渲染成 Bootstrap 样式，并在校验失败时显示错误提示
  • 理解 CSRF 攻击，以及 Hono 用什么办法防御它
  • 用签名 Cookie 实现会话，理解“签名”为什么能防篡改
  • 用 PRG 模式和 Flash 消息做出体验良好的表单

表单是怎么提交的

HTML 的 <form> 元素让用户输入数据。点击提交按钮时，浏览器把所有字段打包， 通常以 POST 请求发给服务器。原书提到：也可以用 GET 提交，但数据会出现在地址栏里，所以表单几乎都用 POST。

Hono 用 c.req.parseBody() 解析表单正文，结果是一个普通对象（相当于 Flask 的 request.form）：

app.post('/', async (c) => {
  const body = await c.req.parseBody()    // { name: 'Dave' }
  const name = body.name                  // 类型是 string | File
  return c.text(`收到：${name}`)
})

注意类型是 string | File：表单也可能上传文件。而且用户可能根本没填、填了一堆空格、填了一万个字…… 直接用 body.name 是在假设“用户一定会好好填”。原书说得对：表单处理里最繁琐的两件事， 就是生成表单的 HTML 和校验提交的数据。Flask 用 Flask-WTF 解决这两件事，我们分开解决。

用 Zod 定义表单

在 Flask-WTF 里，每个表单是一个类，每个字段带着一组验证器（validator）。 在 TypeScript 生态里，最流行的校验库是 Zod：你用它描述数据的“形状”，它负责检查真实数据是否符合。 

npm install zod @hono/zod-validator
Flask-WTF：表单类
from flask_wtf import FlaskForm
from wtforms import StringField, SubmitField
from wtforms.validators import DataRequired

class NameForm(FlaskForm):
    name = StringField('What is your name?',
                       validators=[DataRequired()])
    submit = SubmitField('Submit')
Zod：数据模式（schema）
import { z } from 'zod'

const nameSchema = z.object({
  name: z.string().trim().min(1, '请填写你的名字'),
})

// 顺便免费得到一个 TypeScript 类型：
type NameForm = z.infer<typeof nameSchema>
// → { name: string }

一个关键区别：WTForms 的表单类同时负责校验和生成 HTML（字段标签、提交按钮都写在类里）； Zod 只管校验。HTML 我们用 JSX 组件自己写 —— 分工更清楚，也更容易改样式。

原书表 4-1、4-2 列出了 WTForms 的字段类型和验证器。在我们的方案里，字段类型由 HTML 决定，验证器由 Zod 提供：

让 Hono 自动校验

@hono/zod-validator 把 Zod 包装成 Hono 中间件：请求到达处理函数之前，先按 schema 校验表单。 校验通过，处理函数里用 c.req.valid('form') 拿到已经校验过、类型确定的数据： 

import { zValidator } from '@hono/zod-validator'

app.post('/', zValidator('form', nameSchema), (c) => {
  const { name } = c.req.valid('form')   // name 的类型是 string，而且保证不是空的
  return c.text(`你好，${name}`)
})

默认情况下，校验失败会返回一个 400 状态码的 JSON —— 这很适合 API（第 14 章），但对网页表单不友好。 我们需要的是 Flask-WTF 那种效果：页面重新显示，出错的字段下面有红字提示。 zValidator 的第三个参数是一个钩子函数，校验结束后被调用，可以自己决定返回什么： 

app.post(
  '/',
  zValidator('form', nameSchema, (result, c) => {
    if (!result.success) {
      // 把 Zod 的错误整理成 { name: ['请填写你的名字'] } 这样的结构
      const errors = z.flattenError(result.error).fieldErrors
      return c.render(<IndexPage value={String(result.data.name ?? '')} errors={errors} />)
    }
  }),
  (c) => { /* 只有校验通过才会来到这里 */ },
)
ⓘ 钩子里的 c 类型比较“宽”

钩子函数收到的 c 不带我们自己声明的 Env 类型，所以在钩子里访问 c.var.session 这类自定义变量，TypeScript 会报错 （给参数手动标注 c: Context<Env> 也不行）。本章的钩子只用到 c.render()，不受影响； 第 7 章会写一个 validateForm() 小工具把这个问题一次性封装掉。

渲染表单

原书用 Flask-Bootstrap 的 wtf.quick_form(form) 一行渲染整个表单。 我们用 JSX 手写，Bootstrap 5 的表单样式只需要几个 class：form-label、form-control， 出错时加上 is-invalid，错误文字放在 invalid-feedback 里： 

type FieldErrors = Record<string, string[] | undefined>

function IndexPage({ name, value = '', errors }: { name?: string; value?: string; errors?: FieldErrors }) {
  return (
    <>
      <div class="page-header">
        <h1>你好，{name ?? '陌生人'}！</h1>
      </div>
      <form method="post">
        <div class="mb-3">
          <label class="form-label" for="name">你叫什么名字？</label>
          <input class={`form-control${errors?.name ? ' is-invalid' : ''}`} id="name" name="name" value={value} />
          {errors?.name && <div class="invalid-feedback">{errors.name[0]}</div>}
        </div>
        <button type="submit" class="btn btn-primary">提交</button>
      </form>
    </>
  )
}

对比 Jinja2 版本：{% if name %}{{ name }}{% else %}Stranger{% endif %} 变成了 {name ?? '陌生人'} （?? 的意思是“左边是 null 或 undefined 时用右边”）。

表单字段写多了会重复，后面几章我们会把它提炼成 <Field name label values errors /> 这样的小组件， 用起来就和 quick_form 一样省事了。

ⓘ name 属性是连接前后端的纽带

<input name="name"> 里的 name 属性，决定了提交的数据叫什么名字； 它必须和 Zod schema 里的键 name 对上。字段显示给用户看的文字写在 <label> 里，和 name 属性无关。

密钥与 CSRF 防护

原书这一章花了一段来讲 SECRET_KEY 和 CSRF。它们确实要从第一个表单开始就考虑。 CSRF（Cross-Site Request Forgery，跨站请求伪造）是这样一种攻击：

现代浏览器在每个 POST 请求上都会带 Origin 头（图 4-1 里见过），而且会给表单请求加上 Sec-Fetch-Site 头， 恶意网站无法伪造它们。Hono 内置的 csrf() 中间件就是检查这两个头： 对于表单类型的非 GET 请求，来源不是本站就直接返回 403。 

import { csrf } from 'hono/csrf'

app.use(csrf())   // 就这一行。不需要在每个表单里放隐藏字段

再加上会话 Cookie 的 SameSite=Lax 属性（下一节会设置），就构成了双重保险。 这也是 OWASP 目前推荐的做法之一。

⚠ 用 curl 或测试代码提交表单会被拦下

curl、测试脚本这类“非浏览器”客户端默认不发 Origin 头，所以会被 csrf() 拒绝（403）。 手动测试时加上 -H "Origin: http://localhost:3000"。 原书的做法是在测试配置里关掉 CSRF（WTF_CSRF_ENABLED = False），第 7 章我们也会这么做。

那 SECRET_KEY 呢？在 Flask 里它有两个用途：签名 CSRF 令牌、签名会话 Cookie。 我们的 CSRF 方案不需要它，但会话需要 —— 马上就会用到。先像原书那样定义它： 

// 开发时用一个默认值；上线时必须通过环境变量设置一个谁都猜不到的随机字符串（第 7 章）
const SECRET_KEY = process.env.SECRET_KEY ?? 'hard to guess string'

在处理函数里处理表单

Flask 用一个视图函数同时处理 GET（显示表单）和 POST（处理提交），靠 form.validate_on_submit() 区分。 Hono 里更自然的写法是两个路由：

Flask：一个函数两种方法
@app.route('/', methods=['GET', 'POST'])
def index():
    name = None
    form = NameForm()
    if form.validate_on_submit():
        name = form.name.data
        form.name.data = ''
    return render_template('index.html',
                           form=form, name=name)
Hono：GET 和 POST 各一个
app.get('/', (c) => {
  return c.render(<IndexPage />)
})

app.post('/', zValidator('form', nameSchema, hook), (c) => {
  const { name } = c.req.valid('form')
  return c.render(<IndexPage name={name} />)
})

重定向与用户会话

这个版本有个体验问题。提交名字后按 F5 刷新，浏览器会弹出一个奇怪的对话框：“确认重新提交表单？” 因为刷新的意思是“重复上一个请求”，而上一个请求是 POST。大多数用户看不懂这个提示，点了确认就会重复提交。

原书的解决办法是一个经典模式 —— POST / 重定向 / GET（简称 PRG）： 处理完 POST 后不直接返回页面，而是返回一个重定向，让浏览器用 GET 请求结果页。 这样浏览器的“上一个请求”永远是 GET，刷新就安全了。

但新问题来了：POST 请求里拿到了名字，重定向之后是一个全新的 GET 请求，名字到哪去了？ 需要一个能在请求之间记住东西的地方 —— 这就是用户会话（session）。

会话是怎么实现的

原书提到：Flask 默认把会话存在浏览器的 Cookie 里，并用 SECRET_KEY 做加密签名， 内容一旦被篡改，签名就对不上，会话随即作废。Hono 提供了现成的签名 Cookie 工具 setSignedCookie / getSignedCookie， 我们用它自己实现一个会话中间件，一共三十行左右，但每一行都值得理解： 

import { deleteCookie, getSignedCookie, setSignedCookie } from 'hono/cookie'
import { createMiddleware } from 'hono/factory'

type SessionData = { name?: string; flashes?: string[] }
type Env = { Variables: { session: SessionData } }

const session = createMiddleware<Env>(async (c, next) => {
  // ① 读：没有 → undefined；签名不对 → false；两种情况都当作空会话
  const raw = await getSignedCookie(c, SECRET_KEY, 'session')
  let data: SessionData = {}
  if (raw) {
    try { data = JSON.parse(raw) } catch { data = {} }
  }
  const before = JSON.stringify(data)
  c.set('session', data)                 // 处理函数通过 c.var.session 读写

  await next()                           // ② 处理函数在这里运行

  // ③ 写：只有内容变了才重新发 Cookie
  const after = JSON.stringify(c.var.session)
  if (after === before) return
  if (after === '{}') {
    deleteCookie(c, 'session', { path: '/' })
    return
  }
  await setSignedCookie(c, 'session', after, SECRET_KEY, {
    path: '/',
    httpOnly: true,     // 页面上的 JavaScript 读不到它，XSS 偷不走
    sameSite: 'Lax',    // 别的网站发起的 POST 不带它，防 CSRF
  })
})

const app = new Hono<Env>()
app.use(csrf())
app.use(session)

createMiddleware<Env> 是 Hono 提供的帮手，作用只是让中间件带上正确的类型； Env 里声明了 session 变量的类型，之后所有处理函数里的 c.var.session 都有自动补全。

有了会话，PRG 版本的处理函数就很简单了：

Flask
@app.route('/', methods=['GET', 'POST'])
def index():
    form = NameForm()
    if form.validate_on_submit():
        session['name'] = form.name.data
        return redirect(url_for('index'))
    return render_template('index.html',
        form=form, name=session.get('name'))
Hono
app.get('/', (c) => {
  return c.render(<IndexPage name={c.var.session.name} />)
})

app.post('/', zValidator('form', nameSchema, hook), (c) => {
  c.var.session.name = c.req.valid('form').name
  return c.redirect('/')
})

🔎 深入：Cookie 会话 vs 服务器端会话

把会话整个存在 Cookie 里（Flask 和我们都是这样），好处是服务器什么都不用存，多台服务器之间也不用同步。 缺点是 Cookie 有大小限制（约 4 KB），而且服务器无法主动让某个会话失效（比如“踢掉所有设备”）。 需要这些能力时，就改成“Cookie 里只存一个随机 ID，数据存在服务器的数据库或 Redis 里”。 原书第 18 章提到的 Flask-Session 就是做这个的。我们的中间件只要改“读”和“写”两段就能切换过去。

Flash 消息

很多时候需要在请求完成后给用户一个状态提示：“保存成功”、“密码错误”、“你已退出登录”。 问题是提示常常要在重定向之后的那个页面显示。Flask 内置了 flash() 来做这件事，原理是： 先把消息存进会话，下一次渲染页面时取出来显示，取完就删掉。

在会话之上实现它只需要两个小函数：

import type { Context } from 'hono'

function flash(c: Context<Env>, message: string) {
  const s = c.var.session
  s.flashes = [...(s.flashes ?? []), message]
}

function getFlashedMessages(c: Context<Env>): string[] {
  const s = c.var.session
  const messages = s.flashes ?? []
  delete s.flashes          // 取一次就没了
  return messages
}

处理函数里在名字变化时发一条消息：

Flask
if form.validate_on_submit():
    old_name = session.get('name')
    if old_name is not None and \
            old_name != form.name.data:
        flash('Looks like you have changed your name!')
    session['name'] = form.name.data
    return redirect(url_for('index'))
Hono
(c) => {
  const { name } = c.req.valid('form')
  const oldName = c.var.session.name
  if (oldName && oldName !== name) {
    flash(c, '看起来你改了名字！')
  }
  c.var.session.name = name
  return c.redirect('/')
}

原书说：显示 Flash 消息最好的地方是基础模板，这样所有页面都能显示。 我们的布局是用 jsxRenderer 注册的，布局组件里可以用 useRequestContext() 拿到当前请求的 c： 

import { jsxRenderer, useRequestContext } from 'hono/jsx-renderer'

app.use(jsxRenderer(({ children }) => {
  const c = useRequestContext<Env>()
  const messages = getFlashedMessages(c)
  return (
    <html lang="zh-CN">
      {/* …head、导航栏与第 3 章相同… */}
      <body>
        <main class="container">
          {messages.map((m) => (
            <div class="alert alert-warning alert-dismissible">
              {m}
              <button type="button" class="btn-close" data-bs-dismiss="alert"></button>
            </div>
          ))}
          {children}
        </main>
      </body>
    </html>
  )
}, { docType: true }))

这里用循环，是因为上一个请求可能调用了好几次 flash()。 注意中间件的顺序：session 必须在 jsxRenderer 之前注册，布局渲染时 c.var.session 才已经就绪； 而布局取走消息后会话内容变了，会话中间件在 await next() 之后会发现这一点，自动更新 Cookie。

小结

  • 表单数据以 application/x-www-form-urlencoded 编码放在 POST 正文里，c.req.parseBody() 读取。
  • Zod schema 描述“合格的输入”，zValidator('form', schema, hook) 在处理函数之前校验；钩子里带着错误重新渲染表单。
  • 表单 HTML 用 JSX 写，Bootstrap 的 is-invalid / invalid-feedback 显示错误。
  • CSRF 用 hono/csrf（检查 Origin / Sec-Fetch-Site）加 SameSite=Lax Cookie 防御。
  • 会话 = 用 SECRET_KEY 签名的 Cookie：内容可见但不可篡改；我们自己用中间件实现了它。
  • POST 处理完一律重定向（PRG），需要跨请求的数据存会话，提示用 Flash 消息。

动手练习

  1. 给名字加一条规则：最多 20 个字符，超出时提示“名字太长了”。试试提交一个很长的名字。
  2. 打开浏览器开发者工具的 Application → Cookies，找到 session，看看它的内容；手动改掉其中一个字母再刷新页面，会发生什么？
  3. 用 curl -X POST -d "name=Dave" http://localhost:3000/ 提交，确认被 CSRF 中间件拦截；再加上 -H "Origin: http://localhost:3000" 重试。
  4. 把 return c.redirect('/') 改回直接渲染页面，亲身体验一下刷新时的“重新提交”对话框，然后改回来。
  5. 给 flash() 增加一个“类别”参数（'success' | 'warning' | 'danger'），让布局根据类别使用不同颜色的 Bootstrap 提示框。
