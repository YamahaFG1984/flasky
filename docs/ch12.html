第 12 章

关注

社交网站让用户之间建立联系：有的叫关注，有的叫好友、联系人、人脉……名字不同，本质都是“用户与用户之间的有向链接”。 这一章实现关注功能，并让首页可以只显示关注的人写的文章。它会带你深入理解数据库里最复杂的一种关系 —— 多对多，以及 JOIN 查询。

本章目标

  • 理解四种关系类型，以及为什么多对多需要一张关联表
  • 理解“自引用”的多对多：两端都是用户
  • 给关联表加上自己的数据（关注时间），并用级联删除保持数据干净
  • 在资料页上实现关注 / 取消关注、粉丝列表、“关注了你”
  • 一步一步看懂 JOIN，用一条查询取出“我关注的人写的文章”
  • 理解“自己关注自己”这个技巧带来的方便与副作用

再谈数据库关系

第 5 章介绍过：关系型数据库用关系把记录链接起来，最常见的是一对多 —— “多”的那一方有一个外键，指向“一”的那一方。 目前的 Flasky 里就有两个一对多：角色 → 用户、用户 → 文章。其他关系类型大多是一对多的变体：

多对多关系

原书用的经典例子：学生和课程。一个学生选很多门课，一门课有很多学生。 在 students 表里放一个“课程外键”不够（一个学生不止一门课）；在 classes 表里放“学生外键”也不够。两边都需要一个外键列表。

解决办法是加第三张表，叫关联表（association table，也叫连接表 junction table）。于是一个多对多被拆成了两个一对多：

用 Drizzle 定义这三张表。关联表的主键由两列共同组成（复合主键），这样同一个学生不可能重复选同一门课：

export const students = pgTable('students', { id: serial('id').primaryKey(), name: text('name') })
export const classes = pgTable('classes', { id: serial('id').primaryKey(), name: text('name') })

export const registrations = pgTable('registrations', {
  studentId: integer('student_id').notNull().references(() => students.id),
  classId: integer('class_id').notNull().references(() => classes.id),
}, (t) => [primaryKey({ columns: [t.studentId, t.classId] })])

// 小明选了哪些课？一次 JOIN 查出来：
await db.select({ name: classes.name })
  .from(registrations)
  .innerJoin(classes, eq(registrations.classId, classes.id))
  .where(eq(registrations.studentId, 1))

原书里 SQLAlchemy 可以用 secondary=registrations 把关联表“藏”起来，让你写 s.classes.append(c) 这样的代码。 Drizzle 的哲学是不藏：关联表就是一张普通的表，选课就是往里插一行，退课就是删一行。多写一点点，但数据库里发生了什么一目了然。

自引用关系：用户关注用户

关注也是多对多：一个人关注很多人，也被很多人关注。但和学生/课程不同，两端都是用户 —— 这叫自引用关系。 概念上没有任何区别，只是更难在脑子里想清楚。原书把左边的用户叫“关注者”（follower），右边的叫“被关注者”（followed）：

带额外数据的关联表

原书还希望记录“什么时候开始关注的”，这样粉丝列表可以按时间排序。这个信息只能存在关联表里。 在 SQLAlchemy 里，要做到这一点得把关联表“升级”成一个完整的模型，再把多对多拆回两个一对多，配置相当繁琐。 在 Drizzle 里，关联表本来就是普通的表，直接加一列就行了：

Flask-SQLAlchemy
class Follow(db.Model):
    __tablename__ = 'follows'
    follower_id = db.Column(db.Integer,
        db.ForeignKey('users.id'), primary_key=True)
    followed_id = db.Column(db.Integer,
        db.ForeignKey('users.id'), primary_key=True)
    timestamp = db.Column(db.DateTime,
                          default=datetime.utcnow)

class User(UserMixin, db.Model):
    followed = db.relationship('Follow',
        foreign_keys=[Follow.follower_id],
        backref=db.backref('follower', lazy='joined'),
        lazy='dynamic', cascade='all, delete-orphan')
    followers = db.relationship('Follow',
        foreign_keys=[Follow.followed_id],
        backref=db.backref('followed', lazy='joined'),
        lazy='dynamic', cascade='all, delete-orphan')
Drizzle
export const follows = pgTable('follows', {
  followerId: integer('follower_id').notNull()
    .references(() => users.id, { onDelete: 'cascade' }),
  followedId: integer('followed_id').notNull()
    .references(() => users.id, { onDelete: 'cascade' }),
  timestamp: timestamp('timestamp', { withTimezone: true })
    .notNull().defaultNow(),
}, (t) => [primaryKey({ columns: [t.followerId, t.followedId] })])

原书花了不少篇幅解释 relationship() 的几个参数，在 Drizzle 里它们对应的是：

  • foreign_keys=[…]：两个外键都指向 users，SQLAlchemy 需要你说明每个关系用哪个。Drizzle 里查询时自己写 eq(follows.followerId, …) 还是 eq(follows.followedId, …)，天然就不会混淆。
  • lazy='joined' / lazy='dynamic'：控制关联数据什么时候加载、要不要生成一次查询。原书特别指出，如果用默认的 select 模式，列出 100 个关注的人需要额外 100 次查询 —— 又是第 11 章的 N+1 问题。Drizzle 不做任何自动加载，你写出来的 JOIN 就是实际执行的查询。
  • cascade='all, delete-orphan'：删除用户时，把指向他的关注记录也删掉，而不是留下指向不存在用户的“孤儿”行。这正是数据库外键的 ON DELETE CASCADE 做的事，由数据库保证，比 ORM 层面的级联更可靠。
  • 复合主键：(follower_id, followed_id) 作为主键，同一对用户不可能出现两条关注记录。

操作关注关系的函数

原书给 User 模型加了四个方法，我们写成四个函数。每个都只是对 follows 表的一次简单操作：

export async function follow(db: Db, followerId: number, followedId: number) {
  // 已经关注过就什么都不做（主键冲突时忽略），不用先查一遍
  await db.insert(follows).values({ followerId, followedId }).onConflictDoNothing()
}

export async function unfollow(db: Db, followerId: number, followedId: number) {
  await db.delete(follows).where(and(eq(follows.followerId, followerId), eq(follows.followedId, followedId)))
}

export async function isFollowing(db: Db, followerId: number, followedId: number) {
  const n = await db.$count(follows, and(eq(follows.followerId, followerId), eq(follows.followedId, followedId)))
  return n > 0
}

export const isFollowedBy = (db: Db, userId: number, otherId: number) => isFollowing(db, otherId, userId)

原书的 is_following() 还专门检查了 user.id is None 的情况 —— 在 SQLAlchemy 里，一个还没提交的用户对象没有 id。 我们的用户对象都是从数据库里查出来的，id 一定存在，不需要这个检查。

资料页上的关注功能

资料页需要显示：“关注”或“取消关注”按钮、粉丝数和关注数、以及当对方关注了你时显示“关注了你”。 这些数字一次算好传给页面： 

export async function getProfileStats(db: Db, userId: number, viewerId?: number) {
  const [postCount, commentCount, followerCount, followingCount] = await Promise.all([
    db.$count(posts, eq(posts.authorId, userId)),
    db.$count(comments, eq(comments.authorId, userId)),      // 第 13 章
    db.$count(follows, eq(follows.followedId, userId)),       // 有多少人关注他
    db.$count(follows, eq(follows.followerId, userId)),       // 他关注了多少人
  ])
  const isSelf = viewerId === userId
  return {
    postCount,
    commentCount,
    followers: followerCount - 1,       // 减掉“自己关注自己”那一条，见本章最后
    following: followingCount - 1,
    viewerFollows: viewerId !== undefined && !isSelf && await isFollowing(db, viewerId, userId),
    followsViewer: viewerId !== undefined && !isSelf && await isFollowing(db, userId, viewerId),
  }
}

Promise.all 让四个计数查询同时发出，而不是一个等一个。页面上的按钮是小表单（关注会改变数据，所以用 POST，理由见第 8 章的“退出登录”）：

粉丝列表和关注列表

点击资料页上的数字，进入粉丝列表或关注列表，两者都要分页。原书用 user.followers.paginate() 得到 Follow 对象， 再在 Python 里转换成 {user, timestamp} 的列表方便模板使用。我们直接用 JOIN 查出这个形状： 

function followList(direction: 'followers' | 'following') {
  return async (c: Context<AppEnv>) => {
    const db = c.var.db
    const profile = await findUserByUsername(db, c.req.param('username') ?? '')
    if (!profile) {
      flash(c, '用户不存在。')
      return c.redirect('/')
    }
    const isFollowers = direction === 'followers'
    const mine = isFollowers ? follows.followedId : follows.followerId     // 这一列 = 资料页的主人
    const theirs = isFollowers ? follows.followerId : follows.followedId   // 这一列 = 列表里要显示的人
    const where = and(eq(mine, profile.id), ne(theirs, profile.id))      // 顺便去掉“自己关注自己”
    const pagination = await paginate(
      pageParam(c),
      c.var.config.followersPerPage,
      () => db.$count(follows, where),
      (limit, offset) => db
        .select({
          user: { id: users.id, username: users.username, email: users.email, avatarHash: users.avatarHash },
          timestamp: follows.timestamp,
        })
        .from(follows)
        .innerJoin(users, eq(users.id, theirs))
        .where(where)
        .orderBy(desc(follows.timestamp))
        .limit(limit)
        .offset(offset),
    )
    const title = isFollowers ? `${profile.username} 的粉丝` : `${profile.username} 关注的人`
    return c.render(
      <FollowersPage title={title} profile={profile} pagination={pagination}
        basePath={isFollowers ? '/followers' : '/followed-by'} />,
      { title },
    )
  }
}

main.get('/followers/:username', followList('followers'))
main.get('/followed-by/:username', followList('following'))

两个路由逻辑几乎一样，所以写成一个返回处理函数的函数。原书也用同一个 followers.html 模板渲染两种列表，只是传入不同的标题和端点。 页面是一个两列的表格：左边头像和用户名，右边关注时间。

用 JOIN 查询关注的人的文章

现在首页显示的是所有人的文章。有了关注功能，用户会希望只看关注的人写的。 最直接的想法是：先查出我关注的人，再查每个人的文章，最后合并排序。原书指出这正是 N+1 问题，而且没法高效地分页。 正确的做法是用一条 JOIN 查询。原书用一组具体的数据一步步演示了 JOIN，我们照着走一遍。三张表：

要回答“susan 关注的人写了哪些文章”，数据库做了这样两步：

原书先写出了一个 “从 Follow 开始、再 JOIN Post” 的版本，然后指出把顺序反过来更简洁：从 posts 开始，JOIN follows，再按关注者过滤。 数据库会把两种写法优化成同样的执行计划。Drizzle 里就是在第 11 章的 getPostsPage 里加一个分支：

def followed_posts(self):

        Follow, Follow.followed_id == Post.author_id
    ).filter(Follow.follower_id == self.id)

它生成的 SQL（用 .toSQL() 可以看到）：

select "posts"."id", "posts"."body", …, "users"."username", …
from "posts"
inner join "users" on "posts"."author_id" = "users"."id"
inner join "follows" on "follows"."followed_id" = "posts"."author_id"
where "follows"."follower_id" = $1
order by "posts"."timestamp" desc, "posts"."id" desc
limit $2 offset $3

在首页显示关注的人的文章

首页顶部加两个标签页：“全部”和“关注的人”。用户的选择要被记住，原书把它存在一个名为 show_followed 的 Cookie 里，有效期 30 天。 两个新路由负责设置 Cookie，然后重定向回首页：

Flask

Hono
const THIRTY_DAYS = 60 * 60 * 24 * 30

main.get('/all', loginRequired, (c) => {

            { maxAge: THIRTY_DAYS, path: '/' })

  setCookie(c, 'show_followed', '1',

原书解释了为什么这里要 make_response()：Cookie 只能设置在响应对象上。Hono 的 setCookie(c, …) 先把 Cookie 记在 c 上，c.redirect() 生成响应时会自动带上，所以不需要额外的步骤。

ⓘ 为什么这里用普通 Cookie，而不是会话？

“只看关注的人”只是一个显示偏好，被人改了也无所谓，不需要签名；而且它应该在退出登录后依然保留，所以不放进会话。 这体现了一个原则：只有需要防篡改或需要和登录状态绑定的数据，才放进签名会话。

自己关注自己

切换到“关注的人”之后你会发现：自己写的文章不见了。查询没有错 —— 你并没有关注自己。但大多数用户会希望在好友动态里也看到自己的文章。 原书的解决办法很简单：让每个用户在创建时就关注自己。 

export async function createUser(db: Db, input: NewUser, adminEmail?: string): Promise<User> {
  // …确定角色、哈希密码…
  return db.transaction(async (tx) => {
    const [user] = await tx.insert(users).values({ /* … */ }).returning()
    await tx.insert(follows).values({ followerId: user.id, followedId: user.id })   // 关注自己
    return user
  })
}

两次插入包在一个事务里（第 5 章）：要么用户和“自己关注自己”都创建成功，要么都不创建，不会出现“有用户但没有自关注”的半成品。

那已经存在的老用户呢？原书写了一个 add_self_follows() 函数，循环所有用户逐个补上。和第 9 章补角色一样，SQL 可以一条语句搞定： 

export async function addSelfFollows(db: Db) {
  await db.execute(sql`
    insert into ${follows} (follower_id, followed_id)
    select id, id from ${users}
    on conflict do nothing`)          // 已经关注过自己的，跳过
}

INSERT … SELECT 把查询结果直接插入另一张表；ON CONFLICT DO NOTHING 让它可以反复执行。 原书提到，这种“修正数据的函数”会被放进部署脚本（第 17 章），每次部署都运行一次也不会出问题。

这些副作用我们在前面的代码里都已经处理了：getProfileStats 里的 - 1，粉丝列表查询里的 ne(theirs, profile.id)。对应的单元测试：

it('关注与取消关注', async () => {
  const u1 = await createUser(db, { email: 'john@example.com', username: 'john', password: 'cat' })
  const u2 = await createUser(db, { email: 'susan@example.org', username: 'susan', password: 'dog' })
  expect(await isFollowing(db, u1.id, u2.id)).toBe(false)

  await follow(db, u1.id, u2.id)
  expect(await isFollowing(db, u1.id, u2.id)).toBe(true)
  expect(await isFollowedBy(db, u2.id, u1.id)).toBe(true)
  expect(await isFollowedBy(db, u1.id, u2.id)).toBe(false)
  expect(await db.$count(follows, eq(follows.followerId, u1.id))).toBe(2)   // 自己 + susan

  await unfollow(db, u1.id, u2.id)
  expect(await db.$count(follows)).toBe(2)            // 只剩两条“自己关注自己”

  await follow(db, u2.id, u1.id)
  await db.delete(users).where(eq(users.id, u2.id))   // 删用户 → 相关关注被级联删除
  expect(await db.$count(follows)).toBe(1)
})
📌 原书检查点 12e：自己关注自己

小结

  • 多对多需要一张关联表，把它拆成两个一对多；复合主键防止重复关联。
  • 关注是自引用的多对多：follows 的两个外键都指向 users。Drizzle 里关联表就是普通表，加一列关注时间毫不费力。
  • ON DELETE CASCADE 相当于原书的 delete-orphan；onConflictDoNothing 让“关注”天然幂等。
  • 粉丝列表和关注列表用 follows 的不同列筛选和 JOIN；同一逻辑写成返回处理函数的函数。
  • “关注的人的文章”= posts JOIN follows ON followed_id = author_id WHERE follower_id = 我，一条查询，可以直接分页。
  • 显示偏好存普通 Cookie；自关注让时间线包含自己的文章，计数和列表要相应地排除自己。
