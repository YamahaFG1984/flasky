第 9 章

用户角色

并不是所有用户都一样。大多数应用里，有一小部分用户被赋予了额外的权力：管理员、内容协管员…… 这一章给 Flasky 加上角色和权限：用一个整数的各个二进制位表示权限，用中间件保护路由，在页面里按权限显示不同的按钮。

本章目标

  • 理解“角色 + 权限”的混合模型，以及为什么权限值要用 2 的幂
  • 用位运算组合、检查、增删权限
  • 写一个可以反复执行的 insertRoles()（upsert）
  • 注册时自动给用户分配角色，管理员邮箱自动成为管理员
  • 用 can(user, perm) 统一检查权限，匿名用户也不用特殊处理
  • 用 permissionRequired 中间件保护路由，返回 403 页面

角色与权限的数据表示

原书分析了几种实现方式：只有“普通用户”和“管理员”两种人时，一个 is_administrator 布尔字段就够了； 角色多、层次复杂时需要更灵活的方案；有的应用甚至不谈角色，直接给每个用户分配一组权限。

原书采用的是折中方案：每个用户属于一个角色，每个角色由一组权限定义。第 5 章已经建过一张简单的 roles 表，现在给它加两列：

Flask-SQLAlchemy
class Role(db.Model):
    __tablename__ = 'roles'
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(64), unique=True)
    default = db.Column(db.Boolean, default=False,
                        index=True)
    permissions = db.Column(db.Integer)

    def __init__(self, **kwargs):
        super(Role, self).__init__(**kwargs)
        if self.permissions is None:
            self.permissions = 0
Drizzle
export const roles = pgTable('roles', {
  id: serial('id').primaryKey(),
  name: varchar('name', { length: 64 }).notNull().unique(),
  default: boolean('default').notNull().default(false),
  permissions: integer('permissions').notNull().default(0),
}, (t) => [index('ix_roles_default').on(t.default)])
  • default：只有一个角色是 true，新用户注册时自动获得这个角色。应用要按它来查找角色，所以加了索引。
  • permissions：一个整数，用它的二进制位紧凑地记录这个角色有哪些权限。原书需要在构造函数里把 None 改成 0，我们直接在列上写 .notNull().default(0)，由数据库保证。

用二进制位表示权限

Flasky 需要的权限如下（原书表 9-1）。每个权限的值都是 2 的幂：

任务权限名值二进制
关注其他用户FOLLOW100001
评论别人的文章COMMENT200010
写文章WRITE400100
管理别人的评论MODERATE801000
管理员权限ADMIN1610000

为什么是 2 的幂？因为每个权限在二进制里正好占一个“位”，互不重叠。一个角色拥有哪几个权限，就把对应的位打开， 得到的整数就能唯一地表示这个组合。比如“能关注、能评论”就是 1 + 2 = 3，二进制 00011：

代码表示（原书例 9-2、9-3）。Python 的类常量换成一个 as const 对象，Role 上的方法换成几个纯函数：

export const Permission = {
  FOLLOW: 1,
  COMMENT: 2,
  WRITE: 4,
  MODERATE: 8,
  ADMIN: 16,
} as const        // as const：让这些值不可修改，类型也精确到具体数字

export const hasPermission = (permissions: number, perm: number) => (permissions & perm) === perm
export const addPermission = (permissions: number, perm: number) => permissions | perm
export const removePermission = (permissions: number, perm: number) => permissions & ~perm
ⓘ 为什么用 | 和 & ~，而不是原书的 + 和 −

原书的 add_permission 用加法、remove_permission 用减法，所以必须先检查“有没有”，否则重复添加会把 4 + 4 算成 8（变成了另一个权限！）。 按位或 | 和“与非” & ~ 天然就是幂等的：7 | 4 还是 7，3 & ~4 还是 3，不需要事先检查。

在 shell 里玩一下（对应原书在 flask shell 里的演示）：

flasky> let p = 0
flasky> p = models.addPermission(p, models.Permission.FOLLOW)
flasky> p = models.addPermission(p, models.Permission.WRITE)
flasky> models.hasPermission(p, models.Permission.FOLLOW)
true
flasky> models.hasPermission(p, models.Permission.ADMIN)
false

定义角色：可以反复执行的 insertRoles

Flasky 支持的角色（原书表 9-2）：

角色权限说明
（匿名）无没登录的访客，只能看。它不需要出现在数据库里
UserFOLLOW、COMMENT、WRITE写文章、写评论、关注别人。新用户的默认角色
Moderator+ MODERATE还能管理别人的评论
Administrator+ ADMIN全部权限，包括修改其他用户的角色

手动往数据库里插角色既费时又容易出错。原书写了一个 Role.insert_roles() 静态方法，它有一个重要特点： 不是直接插入，而是“有就更新，没有才插入”。这样以后要调整角色的权限，改一下代码里的表，再运行一次就行 —— 单元测试里、生产服务器上都能放心地反复调用。

“有就更新、没有就插入”在数据库里叫 upsert。原书需要先查一次再决定插入还是修改；PostgreSQL 一条 INSERT … ON CONFLICT DO UPDATE 就能完成，Drizzle 写作 onConflictDoUpdate： 

import type { Db } from '../db/index.js'
import { roles } from '../db/schema.js'

const P = Permission
export const ROLES: Record<string, number[]> = {
  User: [P.FOLLOW, P.COMMENT, P.WRITE],
  Moderator: [P.FOLLOW, P.COMMENT, P.WRITE, P.MODERATE],
  Administrator: [P.FOLLOW, P.COMMENT, P.WRITE, P.MODERATE, P.ADMIN],
}
export const DEFAULT_ROLE = 'User'

export async function insertRoles(db: Db) {
  for (const [name, perms] of Object.entries(ROLES)) {
    const permissions = perms.reduce(addPermission, 0)      // [1, 2, 4] → 7
    const isDefault = name === DEFAULT_ROLE
    await db.insert(roles)
      .values({ name, permissions, default: isDefault })
      .onConflictDoUpdate({ target: roles.name, set: { permissions, default: isDefault } })
  }
}

分配角色

新用户注册时应该得到默认角色 User。唯一的例外是管理员：原书用配置项 FLASKY_ADMIN 记录管理员的邮箱， 用这个邮箱注册的人一开始就是 Administrator。原书把这段逻辑写在 User 的构造函数里，我们放在 createUser() 里： 

export async function createUser(db: Db, input: NewUser, adminEmail?: string): Promise<User> {
  const email = input.email.toLowerCase()
  let roleId = input.roleId                         // 调用方可以直接指定角色（测试里常用）
  if (roleId === undefined) {
    const isAdmin = !!adminEmail && email === adminEmail.toLowerCase()
    const [role] = await db.select({ id: roles.id }).from(roles)
      .where(isAdmin ? eq(roles.name, 'Administrator') : eq(roles.default, true))
      .limit(1)
    roleId = role?.id
  }
  const [user] = await db.insert(users).values({
    email, username: input.username, roleId,
    passwordHash: await hashPassword(input.password),
  }).returning()
  return user
}

// 注册的处理函数里：
const user = await createUser(db, { email, username, password }, config.adminEmail)

检查权限

原书给 User 加了 can(perm) 和 is_administrator() 两个方法， 又专门写了一个 AnonymousUser 类实现同样的两个方法（永远返回 False）， 这样模板里可以直接写 current_user.can(...)，不用先判断是否登录。

我们的 c.var.user 是一个普通对象（或者 null），所以写成接收用户的函数更自然 —— 而且 null 天然就代表匿名用户： 

export type User = typeof users.$inferSelect
export type CurrentUser = User & { permissions: number }     // 用户 + 他所属角色的权限

export const can = (user: CurrentUser | null, perm: number) =>
  !!user && hasPermission(user.permissions, perm)             // 匿名用户（null）什么都不能做

export const isAdministrator = (user: CurrentUser | null) => can(user, Permission.ADMIN)

CurrentUser 多了一个 permissions 字段。它从哪来？每个请求加载当前用户时，顺手用一个 LEFT JOIN 把角色的权限一起查出来 —— 一次查询搞定，之后整个请求里检查权限都不用再访问数据库： 

async function findOne(db: Db, where: SQL): Promise<CurrentUser | null> {
  const [row] = await db
    .select({ user: users, permissions: roles.permissions })
    .from(users)
    .leftJoin(roles, eq(users.roleId, roles.id))     // 没有角色的用户也要查出来，所以是 LEFT JOIN
    .where(where)
    .limit(1)
  return row ? { ...row.user, permissions: row.permissions ?? 0 } : null
}

export const findUserById = (db: Db, id: number) => findOne(db, eq(users.id, id))
export const findUserByEmail = (db: Db, email: string) => findOne(db, eq(users.email, email.toLowerCase()))
export const findUserByUsername = (db: Db, username: string) => findOne(db, eq(users.username, username))

保护路由：permissionRequired 中间件

原书写了两个装饰器：@permission_required(perm) 和 @admin_required，权限不够时 abort(403)。 Hono 里它们是返回中间件的函数：

Flask：app/decorators.py
def permission_required(permission):
    def decorator(f):
        @wraps(f)
        def decorated_function(*args, **kwargs):
            if not current_user.can(permission):
                abort(403)
            return f(*args, **kwargs)
        return decorated_function
    return decorator

def admin_required(f):
    return permission_required(Permission.ADMIN)(f)
Hono：src/lib/auth.ts
export const permissionRequired = (permission: number) =>
  createMiddleware<AppEnv>(async (c, next) => {
    if (!can(c.var.user, permission)) {
      throw new HTTPException(403)
    }
    await next()
  })

export const adminRequired =
  permissionRequired(Permission.ADMIN)

三层嵌套的装饰器变成了“一个返回中间件的函数”，Python 的 functools.wraps 这类细节也不需要了。用法：

Flask
@main.route('/admin')
@login_required
@admin_required
def for_admins_only():
    return "For administrators!"

@main.route('/moderate')
@login_required
@permission_required(Permission.MODERATE)
def for_moderators_only():
    return "For comment moderators!"
Hono
main.get('/admin', loginRequired, adminRequired, (c) =>
  c.text('For administrators!'))

main.get(
  '/moderate',
  loginRequired,
  permissionRequired(Permission.MODERATE),
  (c) => c.text('For comment moderators!'),
)

原书强调了顺序：先检查登录状态，因为没登录的用户应该被送去登录页，而不是看到 403。Hono 里中间件从左到右执行，把 loginRequired 写在前面即可。

最后让 403 错误也显示一个像样的页面。在 createApp() 的 onError 里，按 HTTPException 的状态码分别处理：

app.onError((err, c) => {
  if (err instanceof HTTPException) {
    if (err.status === 403 || err.status === 404) return errorResponse(c, err.status)
    if (err.status < 500) return err.getResponse()          // 其他 4xx 原样返回
  }
  console.error(err)
  return errorResponse(c, 500)
})

function errorResponse(c: Context<AppEnv>, status: 403 | 404 | 500) {
  c.status(status)
  return c.render(<ErrorPage status={status} />)             // “禁止访问”“页面不存在”“服务器内部错误”
}

单元测试

原书给每个角色写了一个测试，外加匿名用户。我们把它们合在一起，用数组一次比较多个结果：

it('普通用户、协管员、管理员、匿名用户的权限', async () => {
  const [moderator] = await db.select().from(roles).where(eq(roles.name, 'Moderator'))
  const [admin] = await db.select().from(roles).where(eq(roles.name, 'Administrator'))

  const load = async (u: User) => (await findUserById(db, u.id))!    // 带上权限
  const u = await load(await createUser(db, { email: 'u@x.com', username: 'u', password: 'p' }))
  const m = await load(await createUser(db, { email: 'm@x.com', username: 'm', password: 'p', roleId: moderator.id }))
  const a = await load(await createUser(db, { email: 'a@x.com', username: 'a', password: 'p', roleId: admin.id }))

  expect([u, m, a].map((x) => can(x, Permission.WRITE))).toEqual([true, true, true])
  expect([u, m, a].map((x) => can(x, Permission.MODERATE))).toEqual([false, true, true])
  expect([u, m, a].map((x) => can(x, Permission.ADMIN))).toEqual([false, false, true])
  expect(can(null, Permission.FOLLOW)).toBe(false)                     // 匿名用户
})

it('FLASKY_ADMIN 邮箱注册时自动成为管理员', async () => {
  const u = await createUser(db, { email: 'Boss@Example.com', username: 'boss', password: 'p' }, 'boss@example.com')
  expect(can(await findUserById(db, u.id), Permission.ADMIN)).toBe(true)
})

测试依赖角色已经存在，所以每个测试开始前要清空数据库并调用 insertRoles() —— 这正是它必须能反复执行的原因：

export async function resetDb(db: Db) {
  await db.execute(sql`truncate table users, roles restart identity cascade`)
  await insertRoles(db)
}

// 测试文件里
beforeEach(async () => { await resetDb(db) })

给已有的用户补上角色

原书最后提醒：在加入角色功能之前注册的用户，role_id 都是空的，需要补上。它在 shell 里写了一个循环。 用 SQL 的思路，两条 UPDATE 就够了，不需要把用户一个个读出来： 

flasky> await models.insertRoles(db)
flasky> const [admin] = await db.select().from(roles).where(eq(roles.name, 'Administrator'))
flasky> const [dflt] = await db.select().from(roles).where(eq(roles.default, true))
flasky> await db.update(users).set({ roleId: admin.id }).where(and(isNull(users.roleId), eq(users.email, config.adminEmail)))
flasky> await db.update(users).set({ roleId: dflt.id }).where(isNull(users.roleId))
💡 用集合操作代替循环

原书的循环会对每个用户发一条 UPDATE，用户多了会非常慢。“把所有没有角色的用户设为默认角色”在 SQL 里是一条语句，数据库内部一次完成。 写数据库代码时，先想想“能不能用一条语句处理一整批数据”，这是写出高性能代码的重要习惯。第 17 章的部署脚本还会遇到同样的思路。

小结

  • 混合模型：用户属于一个角色，角色用一个整数的二进制位记录权限；权限值取 2 的幂，互不重叠。
  • 检查用 (p & perm) === perm，添加用 |，删除用 & ~，天然幂等。
  • insertRoles() 用 onConflictDoUpdate（upsert）实现“有则更新、无则插入”，可以放心地反复执行。
  • 加载当前用户时用 LEFT JOIN 带出权限；can(user, perm) 对 null（匿名用户）返回 false。
  • permissionRequired(perm) / adminRequired 中间件抛出 403；放在 loginRequired 之后。
  • JSX 里直接 import Permission，不需要上下文处理器。
