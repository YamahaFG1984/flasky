第 16 章

性能

没有人喜欢慢吞吞的应用。页面加载太久会让用户烦躁，所以性能问题一出现就要发现并解决。 和原书一样，这一章关注 Web 应用最重要的两类性能问题：慢的数据库查询和吃 CPU 的代码。

本章目标

  • 知道一个请求的时间都花在了哪里，用 Server-Timing 在浏览器里看到它
  • 自动记录超过阈值的慢查询，并在生产环境也保持开启
  • 用 EXPLAIN ANALYZE 分析查询，发现并补上缺失的索引
  • 用 Node.js 自带的 CPU 剖析器找出最耗时的函数

时间都去哪儿了

用 Server-Timing 看到每个请求的时间

开始优化之前，先要能看到时间。HTTP 有一个标准的响应头 Server-Timing，服务器可以用它报告各个阶段的耗时， 浏览器开发者工具的“网络”面板会把它画成时间条。Hono 内置了 hono/timing 中间件： 

import { timing } from 'hono/timing'

if (config.debug) app.use('*', logger(), timing())   // 开发环境打开；它会自动记录总耗时

想单独测量某一段代码（比如一次数据库查询），用 startTime / endTime 包起来：

import { endTime, setMetric, startTime, type TimingVariables } from 'hono/timing'

// types.ts：让 c 知道 timing 中间件用到的变量
export type AppEnv = { Variables: TimingVariables & { config: Config; db: Db; /* … */ } }

main.get('/', async (c) => {
  startTime(c, 'db', 'fetch posts')
  const pagination = await getPostsPage(c.var.db, pageParam(c), c.var.config.postsPerPage)
  endTime(c, 'db')
  setMetric(c, 'posts', pagination.items.length, 'post count')
  // …
})

// 响应头：Server-Timing: db;dur=31.2;desc="fetch posts", posts;dur=20;desc="post count", total;dur=48.5
⚠ 描述文字只能用英文

指标的名字和描述会原样写进 HTTP 响应头，而响应头只允许 Latin-1 字符。写成 startTime(c, 'db', '查询文章')， 请求会直接抛出异常（Cannot convert argument to a ByteString）。这是本教程在验证代码时真实踩到的坑。

ⓘ 生产环境要不要开

Server-Timing 会把内部的耗时信息暴露给任何访问者。开发时非常方便；生产环境通常关掉，或者只对管理员开放。 timing() 中间件也支持通过选项控制是否输出。

记录慢查询

原书指出：优化查询之前，得先知道哪些查询值得优化。一个请求可能发出好几条查询，很难凭感觉判断哪条慢。 原书借助 Flask-SQLAlchemy 记录每条查询的统计信息（SQL、参数、耗时……），然后在 after_app_request 钩子里把超过阈值的写进日志。

Drizzle 的 logger 选项可以打印每一条 SQL（开发时把 drizzle(client, { schema, logger: true }) 打开看看，很有启发）， 但它不记录耗时。所以我们在更底层动手：给数据库驱动的 query 方法包一层计时器。 PGlite 和 node-postgres 执行 SQL 最终都会调用这个方法： 

export interface SlowQuery { sql: string; params: unknown; ms: number }

export interface DbOptions {
  slowQueryMs?: number
  onSlowQuery?: (q: SlowQuery) => void
}

export function createDb(url: string, options: DbOptions = {}): Db {
  if (/^postgres(ql)?:\/\//.test(url)) {
    const pool = new pg.Pool({ connectionString: url })
    watchSlowQueries(pool, options)
    return drizzlePg(pool, { schema })
  }
  // …PGlite 同理：watchSlowQueries(client, options)
}

function watchSlowQueries(
  client: { query: (...args: any[]) => Promise<any> },
  { slowQueryMs, onSlowQuery }: DbOptions,
) {
  if (!slowQueryMs || !onSlowQuery) return
  const original = client.query.bind(client)
  client.query = async (...args: any[]) => {
    const start = performance.now()
    try {
      return await original(...args)
    } finally {
      const ms = performance.now() - start
      if (ms >= slowQueryMs) {
        const q = args[0]
        onSlowQuery({ sql: typeof q === 'string' ? q : q?.text, params: args[1] ?? q?.values, ms })
      }
    }
  }
}

阈值放进配置（原书的 FLASKY_SLOW_DB_QUERY_TIME = 0.5 秒），在入口文件里把慢查询写进日志：

const config = loadConfig()          // config.slowQueryMs = 500
const db = createDb(config.databaseUrl, {
  slowQueryMs: config.slowQueryMs,
  onSlowQuery: ({ sql, params, ms }) =>
    console.warn(`慢查询 ${ms.toFixed(0)}ms\n  SQL: ${sql}\n  参数: ${JSON.stringify(params)}`),
})
★ 在生产环境也要开着

原书特别强调：Flask-SQLAlchemy 默认只在调试模式下记录查询统计，但数据库性能问题很少在开发时出现，因为开发用的数据库小得多。 所以原书把记录功能在所有配置里都打开了。我们的计时器开销只是两次 performance.now()，完全可以在生产环境常开。 日志去了哪里、怎么保存，取决于部署平台，第 17 章会讲。

让数据库自己记录

应用这一侧的计时包括了网络往返。PostgreSQL 本身也能记录慢查询，而且更精确，生产环境里两者最好都用上： 

-- 执行超过 500 毫秒的语句都写进 PostgreSQL 的日志
ALTER SYSTEM SET log_min_duration_statement = '500ms';
SELECT pg_reload_conf();

-- 更进一步：开启 pg_stat_statements 扩展，按“哪类查询累计最耗时”排序
SELECT query, calls, mean_exec_time FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;
📌 原书检查点 16a：记录慢查询

用 EXPLAIN 分析查询

找到慢查询之后怎么办？原书提到，大多数数据库都有 EXPLAIN 语句，它会显示数据库执行一条查询的步骤，经常能暴露数据库或索引设计上的低效之处。 优化可能简单到加一个索引，也可能复杂到在应用和数据库之间加一层缓存。我们来实际分析一次。

打开 shell，先用第 11 章的脚本塞进大量数据，然后看看文章列表那条查询的执行计划： 

EXPLAIN ANALYZE
SELECT count(*) FROM comments WHERE comments.post_id = 42;

-- Seq Scan on comments  (actual time=0.012..8.431 rows=3 loops=1)
--   Filter: (post_id = 42)
--   Rows Removed by Filter: 99997

Seq Scan（顺序扫描）的意思是：为了找出 3 条评论，数据库把十万行从头到尾看了一遍。 而第 11 章的文章列表查询里，每篇文章都要算一次评论数 —— 一页 20 篇，就是 20 次全表扫描。

⚠ PostgreSQL 不会自动给外键建索引

很多人以为定义了外键就有了索引 —— 并没有。PostgreSQL 只会自动给主键和唯一约束建索引。 comments.post_id、comments.author_id、posts.author_id 都是外键，都经常出现在 WHERE 和 JOIN 里，却都没有索引。 还有一个更隐蔽的：follows 的主键是 (follower_id, followed_id)，这个复合索引能加速“按 follower_id 查”， 但“按 followed_id 查”（算粉丝数、第 12 章的 JOIN）用不上它，因为复合索引只能从第一列开始用。

给这些列补上索引：

export const posts = pgTable('posts', { /* … */ }, (t) => [
  index('ix_posts_timestamp').on(t.timestamp),
  index('ix_posts_author_id').on(t.authorId),
])

export const comments = pgTable('comments', { /* … */ }, (t) => [
  index('ix_comments_timestamp').on(t.timestamp),
  index('ix_comments_post_id').on(t.postId),
  index('ix_comments_author_id').on(t.authorId),
])

export const follows = pgTable('follows', { /* … */ }, (t) => [
  primaryKey({ columns: [t.followerId, t.followedId] }),
  index('ix_follows_followed_id').on(t.followedId),      // 反方向的查询也要快
])

npm run db:generate -- --name performance_indexes
npm run db:migrate

再看一次执行计划：

EXPLAIN ANALYZE
SELECT count(*) FROM comments WHERE comments.post_id = 42;

-- Index Only Scan using ix_comments_post_id on comments  (actual time=0.021..0.023 rows=3 loops=1)
--   Index Cond: (post_id = 42)

从 8 毫秒降到 0.02 毫秒。这类改进在开发时几乎感觉不到，在数据增长之后却是决定性的。

💡 索引不是越多越好

每个索引都会让 INSERT / UPDATE 变慢一点（索引也要跟着更新），还会占用磁盘。 原则是：经常出现在 WHERE、JOIN、ORDER BY 里的列才加索引，并且用 EXPLAIN 确认它真的被用上了。

剖析源代码

另一类性能问题是 CPU 占用过高，原因是某些函数做了繁重的计算。剖析器（profiler）观察运行中的应用， 记录每个函数被调用了多少次、花了多长时间，最后给出一份报告，指出最慢的函数。

原书用 Werkzeug 的 ProfilerMiddleware，写了一个 flask profile 命令，让开发服务器在剖析器下运行。 Node.js 的 V8 引擎自带剖析器，一个命令行参数就能打开： 

npm run build                                          # 剖析编译后的 JS，结果更接近线上
node --cpu-prof --cpu-prof-dir=./profiles dist/src/index.js
# …在浏览器里访问几个页面，或者用压测工具制造一些负载…
# 按 Ctrl+C 停止，profiles/ 目录下会生成一个 .cpuprofile 文件
⚠ Ctrl+C 之后没有生成剖析文件？

--cpu-prof 只在进程正常退出时写文件。服务器被 Ctrl+C（SIGINT 信号）直接杀掉时，文件不会生成。 解决办法是在入口文件里处理这个信号，先关闭服务器再正常退出。这段代码第 17 章部署到 Docker 时也需要（docker stop 发的是 SIGTERM）： 

const server = serve({ fetch: app.fetch, port }, …)

// 优雅退出：停止接收新请求，等正在处理的请求完成，再退出
for (const signal of ['SIGINT', 'SIGTERM'] as const) {
  process.on(signal, () => {
    console.log(`收到 ${signal}，正在关闭……`)
    server.close(() => process.exit(0))
  })
}

要制造负载，可以用压测工具 autocannon：20 个并发连接，持续 10 秒访问首页：

npx autocannon -c 20 -d 10 http://localhost:3000/

.cpuprofile 是 Chrome 开发者工具的标准格式。打开 Chrome 的开发者工具 → Performance 面板 → 加载这个文件， 或者直接在 VS Code 里打开它，就能看到火焰图：

比命令行参数更方便的几种方式：

  • 实时剖析：node --inspect dist/src/index.js，然后在 Chrome 地址栏打开 chrome://inspect，点“inspect”，在 Performance 面板里随时开始、停止录制。
  • 一键生成火焰图：npx 0x dist/src/index.js，停止后自动在浏览器里打开交互式火焰图。
  • 综合诊断：clinic 工具集（clinic doctor、clinic flame）会结合 CPU、事件循环延迟、内存给出诊断建议。
⚠ 剖析只在开发环境做

原书提醒：剖析器要实时观察、记录程序的一举一动，会让应用明显变慢，所以一般只在开发环境使用。 除非使用专门为生产环境设计的轻量级采样剖析器（很多 APM 监控服务都提供），否则不要在生产服务器上剖析。

📌 原书检查点 16b：源代码剖析
🔎 深入：Node.js 单线程带来的特殊问题

Node.js 用一个线程处理所有请求（第 2 章）。这意味着：一段 CPU 密集的同步代码运行时，其他所有请求都在等。 在多线程的 Flask 里，一个慢请求只拖慢自己；在 Node.js 里，它可能拖慢整个服务器。 所以要特别小心同步的重计算：比如我们用的是异步版本的 scrypt（它在线程池里执行，不阻塞主线程），而不是 scryptSync。 剖析器里如果看到一个很宽的同步函数，就要考虑把它挪到 worker_threads 里，或者干脆换个算法。

原书说：部署前的准备工作到这里就完成了。下一章，我们来看看把应用部署上线时会遇到什么。

小结

  • 先测量再优化：hono/timing 用 Server-Timing 头把耗时展示在浏览器开发者工具里。
  • 在数据库驱动的 query 方法外包一层计时器，超过阈值（500 毫秒）就记日志；生产环境也要开着，配合 PostgreSQL 自己的 log_min_duration_statement。
  • EXPLAIN ANALYZE 显示执行计划；Seq Scan 往往意味着缺索引。PostgreSQL 不会自动给外键建索引，复合索引只能从第一列开始用。
  • node --cpu-prof 生成 .cpuprofile，在 Chrome 或 VS Code 里看火焰图；进程要优雅退出才会写文件。
  • Node.js 单线程：同步的 CPU 密集代码会阻塞所有请求，尽量用异步 API 或 worker 线程。
