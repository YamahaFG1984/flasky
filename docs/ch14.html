第 14 章

应用编程接口

越来越多的应用把业务逻辑放在客户端：手机 App、单页应用（SPA）……服务器的角色变成了“只提供数据的存取服务”，也就是 API。 这一章给 Flasky 加上一套 REST API：用 JSON 交换数据、用令牌做无状态认证、统一的错误格式和分页。Hono 的轻量正是做 API 的理想选择。

本章目标

  • 理解 REST 的核心思想：资源、URL、方法、表示、无状态、版本
  • 把 API 放进一个独立的子应用，挂在 /api/v1 下，并让它的错误永远是 JSON
  • 用 HTTP Basic 认证和 Bearer 令牌实现无状态认证
  • 把数据库行“序列化”成对外的 JSON，把客户端的 JSON 校验后“反序列化”
  • 实现文章、用户、评论的资源接口，返回正确的状态码和 Location 头
  • 给集合资源分页，并用 curl / HTTPie 测试 API

REST 简介

客户端和 Web 服务之间有很多种通信协议。原书提到，早些年流行 XML-RPC、SOAP 这类“远程过程调用”协议； 后来 REST（Representational State Transfer，表述性状态转移）成了 Web 应用的首选，因为它就建立在大家熟悉的 Web 模型之上。 Roy Fielding 在他的博士论文里用六个特征定义了 REST：

🖥

客户端-服务器

两者职责分离：服务器管数据，客户端管界面。

🔄

无状态

每个请求都带齐所需的全部信息，服务器不在请求之间记住客户端。

💾

可缓存

响应要标明能不能缓存，客户端和中间节点据此优化。

🔗

统一接口

用 URL 标识资源、用标准方法操作、用自描述的消息和超链接。最复杂也最核心。

🧱

分层系统

客户端和服务器之间可以插入代理、缓存、网关，双方都不必知道。

📦

按需代码（可选）

客户端可以从服务器下载代码来执行，比如网页里的 JavaScript。

资源就是一切

REST 的核心概念是资源：应用领域里值得关注的东西。在 Flasky 里，用户、文章、评论都是资源。 每个资源有一个唯一的 URL；同一类资源的集合也有一个 URL；还可以定义表示“某个子集”的集合 URL：

请求方法

客户端在资源 URL 上用不同的 HTTP 方法表示要做什么（原书表 14-1）：

方法目标含义成功时的状态码
GET单个资源获取这个资源200
GET集合获取集合（或其中一页）200
POST集合新建一个资源加入集合。新资源的 URL 由服务器决定，放在 Location 响应头里201
PUT单个资源修改资源（客户端能决定 URL 时也可以用来创建）200 或 204
DELETE单个资源删除资源200 或 204
DELETE集合删除集合里的所有资源200 或 204
ⓘ 不支持的方法

REST 不要求每个资源都支持所有方法。原书说，客户端用了不支持的方法时应该返回 405（Method Not Allowed），Flask 会自动处理。 Hono 默认把“路径对了、方法不对”当作没匹配到路由，返回 404。对大多数 API 来说这无伤大雅；需要严格 405 时，可以给这些路径注册一个 app.all() 兜底路由返回 405。

请求和响应的正文

资源以某种格式在请求和响应的正文里来回传递，格式由 Content-Type 头说明。原书指出，Web 服务最常用的两种格式是 JSON 和 XML， 而 JSON 因为简洁、而且和 JavaScript 天然亲近而更受欢迎。一篇文章的 JSON 表示可能是这样： 

{
  "url": "http://localhost:3000/api/v1/posts/12345",
  "body": "…正文…",
  "author_url": "http://localhost:3000/api/v1/users/2",
  "comments_url": "http://localhost:3000/api/v1/posts/12345/comments/"
}

注意 url、author_url、comments_url 都是完整的网址。原书强调：设计良好的 API，客户端只需要知道少数几个入口 URL， 其余的都从响应里的链接“发现” —— 就像浏览网页时点链接发现新页面一样。

版本

传统网站更新时，服务器上换了新版本，所有用户立刻就用上了新版。API 不一样：手机 App 由用户决定什么时候升级，服务器没法强迫所有客户端同时更新。 所以 API 的改动必须非常小心，不兼容的改动会让旧客户端直接坏掉。常见的做法是在 URL 里带上版本号：

import { Hono } from 'hono'
import { HTTPException } from 'hono/http-exception'
import { ValidationError } from '../../lib/errors.js'
import type { AppEnv } from '../../types.js'
import { apiAuth, confirmedOnly, tokens } from './authentication.js'
import { commentsApi } from './comments.js'
import { badRequest } from './errors.js'
import { postsApi } from './posts.js'
import { usersApi } from './users.js'

export const api = new Hono<AppEnv>()

// 只管 /api/v1 下面的错误：永远返回 JSON，不返回 HTML 错误页
api.onError((err, c) => {
  if (err instanceof ValidationError) return badRequest(c, err.message)
  if (err instanceof HTTPException) {
    if (err.status === 404) return c.json({ error: 'not found' }, 404)
    return err.getResponse()
  }
  console.error(err)
  return c.json({ error: 'internal server error' }, 500)
})

// 相当于原书 api 蓝本上的 before_request + auth.login_required
api.use('*', apiAuth, confirmedOnly)

api.route('/', tokens)
api.route('/', postsApi)
api.route('/', usersApi)
api.route('/', commentsApi)

const app = new Hono<AppEnv>({ strict: false })     // strict: false → /posts 和 /posts/ 是同一个路由
// …
app.route('/api/v1', api)                              // 版本号只在这里写一次
ⓘ 结尾的斜杠

原书提醒：Flask 对结尾带斜杠的路由有特殊处理 —— 请求 /posts 会被自动重定向到 /posts/。 Hono 默认把两者当成不同的路径；创建应用时传入 strict: false，两种写法就都能匹配到同一个路由，不需要重定向。

错误处理

REST 服务通过状态码告诉客户端请求的结果，必要时在正文里附上说明（原书表 14-2）：

状态码名称含义
200OK请求成功
201Created请求成功，并创建了新资源
202Accepted已接受，但还在异步处理中
204No Content请求成功，没有要返回的数据
400Bad Request请求无效或不一致
401Unauthorized没有提供认证信息，或认证信息无效
403Forbidden认证通过了，但权限不够
404Not FoundURL 指向的资源不存在
405Method Not Allowed这个资源不支持该方法
500Internal Server Error处理请求时发生了意外错误

原书指出，404 和 500 有点特殊：它们通常由框架自己产生，默认返回 HTML，这会让期待 JSON 的 API 客户端很困惑。 原书的办法是内容协商：根据请求的 Accept 头，给 API 客户端返回 JSON，给浏览器返回 HTML。我们在全局的错误处理里做同样的事： 

// 请求头说“要 JSON、不要 HTML” → 是 API 客户端
function wantsJson(c: Context) {
  const accept = c.req.header('Accept') ?? ''
  return accept.includes('application/json') && !accept.includes('text/html')
}

const ERROR_NAMES = { 403: 'forbidden', 404: 'not found', 500: 'internal server error' } as const

function errorResponse(c: Context<AppEnv>, status: 403 | 404 | 500) {
  if (wantsJson(c)) return c.json({ error: ERROR_NAMES[status] }, status)
  c.status(status)
  return c.render(<ErrorPage status={status} />, { title: ERROR_NAMES[status] })
}

app.notFound((c) => errorResponse(c, 404))

其余状态码由 API 自己主动返回，写成几个辅助函数（原书例 14-5）：

import type { Context } from 'hono'

export const badRequest = (c: Context, message: string) => c.json({ error: 'bad request', message }, 400)
export const unauthorized = (c: Context, message: string) => c.json({ error: 'unauthorized', message }, 401)
export const forbidden = (c: Context, message: string) => c.json({ error: 'forbidden', message }, 403)

用户认证

API 和网页一样需要保护数据。但 REST 要求无状态：服务器不能在请求之间记住客户端，每个请求都必须带上全部必要的信息 —— 包括身份凭据。

原书讨论了一个微妙之处：网页用的 Flask-Login 把状态存在 Cookie 里，服务器其实也没存什么，看起来是符合无状态的。 但对于不是浏览器的客户端（手机 App、命令行脚本），处理 Cookie 很麻烦，所以一般认为在 API 里用 Cookie 不是好设计。 REST 建立在 HTTP 之上，那么首选就是 HTTP 自己的认证机制：凭据放在每个请求的 Authorization 头里。

★ 为什么无状态这么重要

原书的解释：无状态的服务器非常容易扩容。如果服务器记住了客户端的状态，就得保证同一个客户端的请求总是落到同一台服务器上，或者让所有服务器共享状态存储 —— 这两件事都很难做好。服务器什么都不记，就可以随意加机器，任何一台都能处理任何请求。

方式一：HTTP Basic 认证（邮箱 + 密码）

Basic 认证把 用户名:密码 用 Base64 编码后放进请求头：Authorization: Basic am9obkBleGFtcGxlLmNvbTpjYXQ=。 原书用 Flask-HTTPAuth 处理它；Hono 内置了 hono/basic-auth，同样让你提供一个验证函数：

Flask-HTTPAuth
auth = HTTPBasicAuth()

@auth.verify_password
def verify_password(email, password):
    if email == '':
        return False
    user = User.query.filter_by(email=email).first()
    if not user:
        return False
    g.current_user = user
    return user.verify_password(password)

@auth.error_handler
def auth_error():
    return unauthorized('Invalid credentials')
hono/basic-auth
import { basicAuth } from 'hono/basic-auth'

const passwordAuth = basicAuth({
  verifyUser: async (email, password, c) => {
    const user = await findUserByEmail(c.var.db, email)
    if (!user ||
        !(await verifyPassword(user.passwordHash, password))) {
      return false
    }
    c.set('user', user)            // 相当于 g.current_user
    c.set('tokenUsed', false)
    return true
  },
  // 认证失败时的响应正文（对象会被转成 JSON，状态码 401）
  invalidUserMessage: { error: 'unauthorized', message: 'Invalid credentials' },
})
⚠ API 必须走 HTTPS

原书特别强调：因为每个请求都带着凭据，API 路由必须通过 HTTPS 提供，让所有请求和响应在传输中加密。 Base64 只是编码，不是加密，任何人截获了请求都能直接解码出密码。

方式二：令牌认证

每个请求都发送密码，风险太大。原书的改进是令牌：客户端先用邮箱和密码换一个有时效的令牌，之后的请求都用令牌代替密码。 令牌就算泄露，一小时后也就失效了。生成令牌用第 8 章的 JWT 工具，只是 purpose 换成 'api'： 

export const generateAuthToken = (secret: string, userId: number, expiresIn: number) =>
  generateToken(secret, 'api', { id: userId }, expiresIn)

export async function verifyAuthToken(db: Db, secret: string, token: string) {
  const data = await readToken(secret, token, 'api')
  return data && typeof data.id === 'number' ? findUserById(db, data.id) : null
}

原书把令牌塞进 Basic 认证的“用户名”字段、密码留空来传递。现在更通行的做法是用专门的 Bearer 方案：Authorization: Bearer <令牌>。 我们的认证中间件两种都支持 —— 看到 Bearer 就按令牌验证，否则交给 Basic 认证： 

export const apiAuth = createMiddleware<AppEnv>(async (c, next) => {
  const header = c.req.header('Authorization') ?? ''
  if (header.startsWith('Bearer ')) {
    const user = await verifyAuthToken(c.var.db, c.var.config.secretKey, header.slice(7))
    if (!user) return unauthorized(c, 'Invalid credentials')
    c.set('user', user)
    c.set('tokenUsed', true)                 // 记下“这次是用令牌认证的”
    return next()
  }
  return passwordAuth(c, next)
})

// 认证通过但没有确认邮箱的账户，一律 403（原书的 before_request 也做了这个检查）
export const confirmedOnly = createMiddleware<AppEnv>(async (c, next) => {
  if (!c.var.user?.confirmed) return forbidden(c, 'Unconfirmed account')
  await next()
})

原书把 login_required 挂在蓝本的 before_request 上，让 API 的所有路由都自动受到保护。 我们在前面的 api/index.ts 里写的 api.use('*', apiAuth, confirmedOnly) 是同样的效果。

换取令牌的路由：

const EXPIRATION = 3600

tokens.post('/tokens', async (c) => {
  // 只能用邮箱+密码换令牌。如果允许“用旧令牌换新令牌”，令牌就等于永不过期了
  if (c.var.tokenUsed || !c.var.user) return unauthorized(c, 'Invalid credentials')
  const token = await generateAuthToken(c.var.config.secretKey, c.var.user.id, EXPIRATION)
  return c.json({ token, expiration: EXPIRATION })

资源与 JSON 的转换

序列化：数据库行 → JSON

把内部数据转换成传输格式，叫序列化。原书给每个模型加了 to_json() 方法；我们写成独立的函数，因为它需要 c 来生成完整网址： 

export function postJson(c: Context<AppEnv>, post: PostWithAuthor) {
  return {
    url: externalUrl(c, `/api/v1/posts/${post.id}`),
    body: post.body,
    body_html: post.bodyHtml,
    timestamp: post.timestamp,                                  // Date 会自动转成 ISO 8601 字符串
    author_url: externalUrl(c, `/api/v1/users/${post.authorId}`),
    comments_url: externalUrl(c, `/api/v1/posts/${post.id}/comments/`),
    comment_count: post.commentCount,                           // “编”出来的属性
  }
}

export function userJson(c: Context<AppEnv>, user: User, postCount: number) {
  return {
    url: externalUrl(c, `/api/v1/users/${user.id}`),
    username: user.username,                                    // 邮箱、角色、密码哈希一律不对外
    member_since: user.memberSince,
    last_seen: user.lastSeen,
    posts_url: externalUrl(c, `/api/v1/users/${user.id}/posts/`),
    followed_posts_url: externalUrl(c, `/api/v1/users/${user.id}/timeline/`),
    post_count: postCount,
  }
}

反序列化：JSON → 数据库

反过来，把客户端发来的 JSON 变成数据库里的数据，叫反序列化。原书指出这里的挑战是：客户端发来的数据可能无效、错误或多余。 原书的 Post.from_json() 只取 body 一个字段，其余的全部忽略：body_html 由服务器生成、作者只能是认证的用户、URL 由服务器决定……

我们用第 4 章的 Zod 做同样的事，只是这次校验的是 'json' 而不是 'form'。Zod 的 z.object() 默认会丢掉 schema 里没有的字段， 所以客户端就算发了 author_url，也根本到不了处理函数： 

// 校验失败 → 抛 ValidationError → API 的 onError 把它变成 400
const json = <S extends z.ZodType>(schema: S) =>
  zValidator('json', schema, (result) => {
    if (!result.success) throw new ValidationError(result.error.issues[0]?.message ?? 'invalid request')
  })

const newPostSchema = z.object({
  body: z.string('post does not have a body').min(1, 'post does not have a body'),
})

// 相当于原书的 app/exceptions.py
export class ValidationError extends Error {}

为什么要抛异常，而不是直接返回 400？原书解释：校验代码往往在很深的地方，它不知道该怎么处理错误，于是把错误“往上抛”，交给更高层的代码统一处理。 这样处理函数本身就可以写得非常干净，完全不用管错误检查。

实现资源接口

GET 请求最简单，只读取不修改（原书例 14-17）：

export const postsApi = new Hono<AppEnv>()

postsApi.get('/posts', async (c) => {
  const pagination = await getPostsPage(c.var.db, pageParam(c), c.var.config.postsPerPage)
  return c.json(pageJson(c, 'posts', pagination, '/api/v1/posts/', postJson))
})

postsApi.get('/posts/:id{[0-9]+}', async (c) => {
  const post = await getPost(c.var.db, Number(c.req.param('id')))
  if (!post) throw new HTTPException(404)                // API 的 onError 会把它变成 JSON 的 404
  return c.json(postJson(c, post))
})

POST 在集合上创建新文章。成功时返回 201，并在 Location 头里给出新文章的地址。原书还贴心地把新资源放在响应正文里，省得客户端再发一次 GET：

postsApi.post('/posts', apiPermission(Permission.WRITE), json(newPostSchema), async (c) => {
  const { body } = c.req.valid('json')
  const created = await createPost(c.var.db, requireUser(c).id, body)   // 作者 = 认证的用户，由服务器决定
  const post = await getPost(c.var.db, created.id)
  if (!post) throw new HTTPException(500)
  return c.json(postJson(c, post), 201, { Location: externalUrl(c, `/api/v1/posts/${post.id}`) })
})

检查权限的中间件和网页版的类似，但权限不足时返回 JSON 而不是 403 页面（原书例 14-19）：

export const apiPermission = (permission: number) =>
  createMiddleware<AppEnv>(async (c, next) => {
    if (!can(c.var.user, permission)) return forbidden(c, 'Insufficient permissions')
    await next()
  })

PUT 修改文章。除了要有写文章的权限，还必须是作者本人或管理员 —— 这个检查写在处理函数里：

const editPostSchema = z.object({ body: z.string().min(1).optional() })

postsApi.put('/posts/:id{[0-9]+}', apiPermission(Permission.WRITE), json(editPostSchema), async (c) => {
  const db = c.var.db
  const id = Number(c.req.param('id'))
  const post = await getPost(db, id)
  if (!post) throw new HTTPException(404)
  const user = requireUser(c)
  if (user.id !== post.authorId && !can(user, Permission.ADMIN)) return forbidden(c, 'Insufficient permissions')
  const { body } = c.req.valid('json')
  if (body !== undefined) await updatePost(db, id, body)      // 复用第 11 章的函数，body_html 自动更新
  return c.json(postJson(c, (await getPost(db, id))!))
})

给集合分页

返回整个集合的 GET 请求，数据量一大就会非常昂贵。API 也要分页。原书的格式是：当前页的数据、上一页和下一页的链接（没有就是 null）、以及总数。 所有集合资源都用同一种格式，所以写一个通用的函数： 

export function pageJson<T, K extends string>(
  c: Context<AppEnv>, key: K, pagination: Pagination<T>, path: string, toJson: (c: Context<AppEnv>, item: T) => unknown,
) {
  const link = (page: number | null) => (page === null ? null : externalUrl(c, `${path}?page=${page}`))
  return {
    [key]: pagination.items.map((item) => toJson(c, item)),
    prev: link(pagination.prevNum),
    next: link(pagination.nextNum),
    count: pagination.total,
  } as Record<K, unknown[]> & { prev: string | null; next: string | null; count: number }
}

{
  "posts": [ { "url": "http://localhost:3000/api/v1/posts/150", … }, … ],
  "prev": null,
  "next": "http://localhost:3000/api/v1/posts/?page=2",
  "count": 150
}

客户端不需要知道分页的规则，只要沿着 next 一直走，直到它变成 null。这就是前面说的“通过链接发现资源”。

用 curl 和 HTTPie 测试

测试 Web 服务需要一个 HTTP 客户端。原书推荐了两个命令行工具：几乎每台电脑都自带的 cURL，以及语法更简洁的 HTTPie。 启动开发服务器后，在另一个终端里： 

# 用邮箱和密码获取文章列表
curl -u john@example.com:cat http://localhost:3000/api/v1/posts/
# 或者用 HTTPie
http --auth john@example.com:cat GET http://localhost:3000/api/v1/posts/

# 发一篇新文章
curl -u john@example.com:cat -H "Content-Type: application/json" \
     -d '{"body": "从*命令行*发的文章"}' http://localhost:3000/api/v1/posts/
http --auth john@example.com:cat POST http://localhost:3000/api/v1/posts/ "body=从*命令行*发的文章"

发文章的响应：

HTTP/1.1 201 Created
Content-Type: application/json
Location: http://localhost:3000/api/v1/posts/151

{
  "url": "http://localhost:3000/api/v1/posts/151",
  "body": "从*命令行*发的文章",
  "body_html": "<p>从<em>命令行</em>发的文章</p>",
  "timestamp": "2025-03-06T02:30:27.000Z",
  "author_url": "http://localhost:3000/api/v1/users/1",
  "comments_url": "http://localhost:3000/api/v1/posts/151/comments/",
  "comment_count": 0
}

改用令牌：

# 1. 换取令牌
curl -u john@example.com:cat -X POST http://localhost:3000/api/v1/tokens/
# {"token":"eyJhbGciOiJIUzI1NiIs…","expiration":3600}

# 2. 之后一小时内都用令牌
curl -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIs…" http://localhost:3000/api/v1/posts/
http -A bearer -a eyJhbGciOiJIUzI1NiIs… GET http://localhost:3000/api/v1/posts/
💡 注意 CSRF 中间件不会拦截 API

第 4 章的 csrf() 只检查“表单类型”的请求（application/x-www-form-urlencoded、multipart/form-data、text/plain）。 API 请求用的是 application/json，浏览器里的恶意网页没法在不经过 CORS 预检的情况下跨站发送这种请求，所以 CSRF 中间件放行它们是安全的。

超越原书：Hono 生态里的 API 工具

原书的 API 到此就完整了。Hono 在做 API 方面还有几个特别好用的工具，值得了解：

🔗

RPC 客户端 hc

用 hc<typeof app>() 生成一个带完整类型的客户端：前端调用 API 时，路径、参数、返回值全都有类型检查，后端改了接口前端立刻报错。

📖

OpenAPI 文档

@hono/zod-openapi 用你已经写好的 Zod schema 自动生成 OpenAPI 规范，再配合 @hono/swagger-ui 得到一个可以在线调试的文档页。

🌐

CORS

如果 API 要给其他域名下的网页调用，加上 hono/cors 中间件，声明允许哪些来源。

⏳

限流

公开的 API 需要防止被刷。社区有基于内存或 Redis 的限流中间件，在认证之后按用户计数。

小结

  • REST：资源用 URL 标识，用 GET / POST / PUT / DELETE 操作，用 JSON 表示，每个请求无状态；URL 里带版本号。
  • API 是一个挂在 /api/v1 的子应用；它自己的 onError 保证错误永远是 JSON，全局错误处理按 Accept 头做内容协商。
  • 认证放在 Authorization 头里：Basic（hono/basic-auth）或 Bearer 令牌（JWT，一小时过期）；令牌不能用来换新令牌。
  • 序列化函数决定对外暴露什么（带上完整的资源链接，隐藏敏感字段）；反序列化用 zValidator('json')，只接受允许的字段。
  • POST 成功返回 201 + Location；权限不足 403、校验失败 400、找不到 404，全部是 JSON。
  • 集合资源统一分页格式 { items, prev, next, count }，客户端沿着 next 链接翻页。

动手练习

  1. 用 curl 走一遍完整流程：换令牌 → 发文章 → 读回来 → 修改 → 读评论。每一步都看看响应头里的状态码。
  2. 给 API 加一个 DELETE /posts/:id，只允许作者和管理员调用，成功返回 204（提示：c.body(null, 204)）。
  3. 加一个 GET /users/:id/followers/ 接口，返回分页的粉丝列表，格式和其他集合一致。
  4. 用 hc 写一个小脚本调用你的 API（提示：import { hc } from 'hono/client'），体会类型提示带来的便利。
