第 17 章

部署

开发时的 tsx watch 是为了方便改代码，不是为了上线。这一章把 Flasky 真正部署出去： 先写一个每次部署都能放心执行的部署脚本、处理好生产环境的错误日志， 然后依次介绍三种主流的部署方式 —— 平台即服务（PaaS）、Docker 容器、以及自己管理的传统服务器。

本章目标

  • 把“编译、迁移、初始化数据”变成一个可以重复执行的部署脚本
  • 让生产环境的错误被记录下来，并通知到管理员
  • 理解虚拟机、容器、PaaS 三种云部署模型的区别
  • 在 PaaS 上部署：配置环境变量、数据库、HTTPS 与反向代理
  • 用多阶段构建写 Dockerfile，用 Docker Compose 同时运行应用和 PostgreSQL
  • 在自己的服务器上用 systemd + Nginx 部署

部署流程

不管用哪种方式托管，每次安装或升级应用时，都有一系列任务要完成，比如创建或升级数据库的表。 原书指出，每次手动做这些事既容易出错又浪费时间，于是写了一个 flask deploy 命令把它们打包在一起。我们对应地写一个脚本： 

import { loadConfig } from '../src/config.js'
import { createDb, migrateDb } from '../src/db/index.js'
import { insertRoles } from '../src/models/permissions.js'
import { addSelfFollows } from '../src/models/users.js'

try { process.loadEnvFile() } catch { /* 没有 .env 也行 */ }

// 部署时要做的所有事，每一步都可以重复执行，不会出副作用
const config = loadConfig()
const db = createDb(config.databaseUrl)

await migrateDb(db)          // 1. 数据库结构升级到最新（第 5 章）
await insertRoles(db)        // 2. 创建或更新角色（第 9 章）
await addSelfFollows(db)     // 3. 确保每个用户都关注了自己（第 12 章）

console.log('部署任务完成')
process.exit(0)

原书强调了一个设计原则：这些函数执行多少次都不会出问题。迁移只执行还没执行过的；角色用 upsert；自关注用 ON CONFLICT DO NOTHING。 这样每次安装或升级时直接运行部署脚本就行，不用担心“某个函数在不该运行的时候运行了”。

另一件上线前必须做的事是编译。开发时 tsx 在内存里即时转换 TypeScript；生产环境应该提前编译成 JavaScript，启动更快，也不需要带着开发依赖。 编译时只需要 src 和 scripts，所以单独写一个构建用的 tsconfig： 

{
  "extends": "./tsconfig.json",
  "include": ["src", "scripts"]
}

"scripts": {
  "build": "tsc -p tsconfig.build.json",     // src/*.ts → dist/src/*.js，scripts/*.ts → dist/scripts/*.js
  "start": "node dist/src/index.js",
  "deploy": "node dist/scripts/deploy.js"
},
"engines": { "node": ">=24" }

记录生产环境的错误

开发时出了错，终端里马上能看到调用栈。生产环境里，用户只会看到一个 500 页面（第 3 章），错误详情去哪了？ 原书说，Flask 会把它们写进日志 —— 但生产模式下日志默认没有配置任何输出，不加处理器的话，日志就丢了。

Node.js 的约定比这简单：日志一律写到标准输出和标准错误（console.log / console.error）， 由运行它的平台负责收集 —— PaaS 有 logs 命令，Docker 有 docker logs，systemd 有 journalctl。 原书为 Heroku、Docker、Unix 各写了一个配置类来“把日志输出到 stderr / syslog”，在我们这里都不需要了。

原书还配置了一个把 ERROR 级别的日志通过邮件发给管理员的处理器。我们在全局的 onError 里做同样的事：

app.onError((err, c) => {
  if (err instanceof HTTPException) {
    if (err.status === 403 || err.status === 404) return errorResponse(c, err.status)
    if (err.status < 500) return err.getResponse()
  }
  console.error(err)                                   // 所有环境：写进标准错误
  if (!config.debug && !config.testing && config.adminEmail) {
    // 生产环境：再给管理员发一封邮件（原书的 SMTPHandler）
    sendEmail(c, config.adminEmail, '应用出错', ({ stack }: { stack: string }) => ({
      text: stack, html: `<pre>${stack.replace(/</g, '&lt;')}</pre>`,
    }), { stack: String((err as Error).stack ?? err) })
  }
  return errorResponse(c, 500)
})
💡 错误邮件的升级版

一个 bug 在高峰期可能每秒触发几十次，邮件会瞬间塞满管理员的收件箱。真实项目通常改用错误监控服务（Sentry 等）： 同样的错误会被自动归并、统计次数、附带请求信息，并且只在首次出现或频率异常时通知你。Hono 有现成的中间件 @hono/sentry。

云部署的几种方式

平台即服务（PaaS）

原书以 Heroku 为例讲 PaaS：开发者只需要把代码推送上去，平台自动完成安装、配置和启动，还能按需增减服务器数量。 Heroku 至今仍在运营（2022 年起取消了免费套餐），Render、Railway、Fly.io 等新平台的用法大同小异。下面以 Heroku 为例，关键在于理解每一步为什么要做。

创建应用和数据库

heroku login
heroku create <应用名>                      # 同时会给 Git 仓库加一个名为 heroku 的远程地址
heroku addons:create heroku-postgresql:essential-0
# 平台会自动设置 DATABASE_URL 环境变量 —— 我们的 config.ts 本来就读取它

配置环境变量

heroku config:set FLASKY_CONFIG=heroku
heroku config:set SECRET_KEY=$(openssl rand -hex 32)       # 一个谁都猜不到的随机密钥
heroku config:set MAIL_SERVER=… MAIL_USERNAME=… MAIL_PASSWORD=… FLASKY_ADMIN=你的邮箱
heroku config:set PGSSLMODE=no-verify                       # Heroku 的 Postgres 要求 SSL 连接，node-postgres 会读取这个变量
⚠ SECRET_KEY 必须设置

原书反复强调：开发时用默认的密钥没关系，但生产环境必须设置一个谁都不知道的随机字符串，否则攻击者可以伪造会话、生成有效的令牌。 第 7 章的 loadConfig 在生产配置下缺少 SECRET_KEY 时会直接拒绝启动，就是为了防止忘记。

HTTPS 与反向代理

Heroku 为 *.herokuapp.com 下的应用免费提供 HTTPS。原书用 Flask-SSLify 把所有 http:// 的请求重定向到 https://， 并指出了一个很容易忽视的细节：用户连接的并不是你的应用，而是 Heroku 的反向代理。加密连接在代理那里就结束了， 代理再用普通 HTTP 把请求转发给应用。于是应用看到的请求永远是 http:// —— 生成确认邮件里的链接时就会出错。 

// 生成完整网址（发邮件、API 里的链接都要用）
export function externalUrl(c: Context<AppEnv>, path: string): string {
  const url = new URL(path, c.req.url)
  if (c.var.config.trustProxy) {
    // 反向代理后面：真实的协议和域名在代理加的请求头里（相当于 ProxyFix）
    const proto = c.req.header('x-forwarded-proto')?.split(',')[0].trim()
    const host = c.req.header('x-forwarded-host')?.split(',')[0].trim()
    if (proto) url.protocol = `${proto}:`
    if (host) url.host = host
  }
  return url.href
}

// 相当于 Flask-SSLify：HTTP 请求一律 301 到 HTTPS
export const httpsRedirect = createMiddleware<AppEnv>(async (c, next) => {
  const proto = c.var.config.trustProxy
    ? c.req.header('x-forwarded-proto')?.split(',')[0].trim()
    : new URL(c.req.url).protocol.replace(':', '')
  if (proto === 'http') {
    const url = new URL(externalUrl(c, c.req.path + new URL(c.req.url).search))
    url.protocol = 'https:'
    return c.redirect(url.href, 301)
  }
  await next()
})

对应的配置：只有真正跑在 Heroku 上（存在 DYNO 环境变量）时才强制 HTTPS，这样用 Heroku 配置在本地测试时不会被重定向（原书同样的做法）：

case 'heroku': {
  // …先得到 production 配置…
  return { ...production, name: 'heroku', sslRedirect: Boolean(env.DYNO), trustProxy: true }
}

// createApp() 里
if (config.sslRedirect) app.use('*', httpsRedirect)
⚠ 不在代理后面时，不要相信 X-Forwarded-* 头

这些请求头任何客户端都可以随便伪造。只有确定应用前面有一个会覆盖它们的代理时，才把 trustProxy 打开。 所以它默认是关的，只在 Heroku 配置、或者设置了 TRUST_PROXY=1 环境变量时（自己的 Nginx 后面，见本章最后）才打开。

生产环境的 Web 服务器

原书说，Flask 自带的开发服务器性能差、不安全，生产环境要换成 Gunicorn 或 uWSGI（Windows 上用 Waitress）。 Node.js 不一样：@hono/node-server 基于 Node 内置的 http 模块，它本身就是生产级的服务器，不需要再套一层。 开发和生产的区别只在于：生产环境运行编译后的 dist/，而且不开 tsx watch。

平台会通过 PORT 环境变量告诉应用该监听哪个端口，第 2 章起我们的入口文件就在读它。

Procfile

Heroku 通过项目根目录的 Procfile 知道怎么启动应用：

release: node dist/scripts/deploy.js
web: node dist/src/index.js
  • web：启动 Web 服务器的命令，平台会给它设置 PORT。
  • release：Heroku 的“发布阶段”，在新版本上线之前自动执行。原书是部署完之后手动运行 heroku run flask deploy 再重启； 用发布阶段，部署脚本成为发布流程的一部分，脚本失败时新版本根本不会上线。

那 npm ci 和 npm run build 谁来执行？Heroku 的 Node.js 构建包看到 package.json 就会自动安装依赖、运行 build 脚本， 然后删掉开发依赖。原书需要专门准备一个顶层的 requirements.txt，我们什么都不用加。

本地测试、推送与升级

# 在本地按 Procfile 运行（从 .env 读取环境变量），上线前先试一试
npm run build
heroku local

# 部署：推送代码，平台自动构建、执行 release、启动 web
git push heroku main

# 查看日志（原书的 heroku logs -t）
heroku logs --tail

升级应用时，原书的流程是：打开维护模式 → 推送 → 运行 deploy → 重启 → 关闭维护模式。 有了发布阶段，大多数升级只需要 git push。如果某次迁移会让新旧代码无法同时运行（比如删除了旧代码还在用的列）， 仍然应该用 heroku maintenance:on / off 把升级过程包起来，期间用户会看到一个“马上回来”的静态页面。

Docker 容器

Heroku 是一种相当“高层”的部署方式。原书接着介绍了容器：它不像 PaaS 那样自动化，但更灵活，也不绑定任何一家云厂商。 容器是一种特殊的虚拟机，运行在宿主操作系统的内核之上 —— 虚拟化只到内核为止，所以比完整的虚拟机轻量高效得多。

编写 Dockerfile

容器从镜像启动，镜像是容器文件系统的一个快照。构建镜像的指令写在 Dockerfile 里。 和原书相比，我们多了一个“编译”步骤，所以用多阶段构建：第一阶段装全部依赖并编译，第二阶段只装生产依赖、只拷贝编译结果，得到的镜像更小： 

# ---------- 第一阶段：安装全部依赖，编译 TypeScript ----------
FROM node:24-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY tsconfig.json tsconfig.build.json ./
COPY src src
COPY scripts scripts
RUN npx tsc -p tsconfig.build.json

# ---------- 第二阶段：只装生产依赖，拷贝编译结果 ----------
FROM node:24-alpine
ENV NODE_ENV=production \
    FLASKY_CONFIG=production
WORKDIR /app

COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force

COPY --from=build /app/dist ./dist
COPY drizzle ./drizzle
COPY static ./static
COPY --chmod=755 boot.sh ./

# 没配 DATABASE_URL 时 PGlite 要往 ./data 写数据，先给普通用户准备好目录
RUN mkdir -p data && chown node:node data
USER node

EXPOSE 3000
ENTRYPOINT ["./boot.sh"]

对照原书逐条解释这些指令：

  • FROM：指定基础镜像。原书用 python:3.6-alpine，我们用 Docker Hub 上官方的 node:24-alpine。Alpine 是一个很小的 Linux 发行版，常用来做容器的基础。
  • ENV：定义运行时的环境变量。FLASKY_CONFIG=production 相当于原书的 FLASK_CONFIG docker。
  • USER：原书特别建议不要用 root 运行容器。官方的 Node 镜像里已经有一个叫 node 的普通用户，直接切换过去即可（原书需要自己 adduser）。
  • WORKDIR / COPY：设定工作目录，把文件拷进镜像。先拷 package.json 装依赖、再拷源码，这样只改源码时 Docker 可以复用“装依赖”那一层的缓存，构建快得多。
  • RUN：在构建时执行命令。原书在这里创建虚拟环境、pip install；我们 npm ci。
  • EXPOSE：声明应用在容器里监听的端口。
  • ENTRYPOINT：容器启动时执行的命令。

别忘了 .dockerignore，免得把本地的 node_modules、数据库文件和机密拷进镜像：

node_modules
dist
data
coverage
tests
.env
.env-*

容器的启动脚本（原书例 17-11 和 17-13），先运行部署脚本，再启动服务器：

#!/bin/sh
# 数据库容器可能还没准备好，部署任务失败就等 5 秒重试
until node dist/scripts/deploy.js; do
  echo "部署任务失败，5 秒后重试……"
  sleep 5
done

# exec：让 Node 进程接替 shell 成为容器的主进程，才能收到 docker stop 发出的 SIGTERM
exec node dist/src/index.js

原书解释了为什么要用 exec：Docker 特别关注启动容器的那个进程，它结束，容器就结束。exec 让 Node 进程替换掉 shell 进程。 这样 docker stop 发出的 SIGTERM 信号直接送到 Node，第 16 章写的优雅退出代码就能生效：先处理完正在进行的请求，再退出。

📌 原书检查点 17d：Docker 支持

构建和运行容器

docker build -t flasky:latest .          # -t 给镜像起名字和标签；最后的点表示“用当前目录构建”
docker images                            # 查看本地的镜像
# REPOSITORY   TAG       IMAGE ID       SIZE
# flasky       latest    a9d5c738aca2   ~320MB（压缩后约 70MB）

docker run --name flasky -d -p 8000:3000 \
  -e SECRET_KEY=$(openssl rand -hex 32) \
  flasky:latest
  • --name：给容器起名字（不给的话 Docker 会随机生成一个）。
  • -d：在后台运行（detached）。
  • -p 8000:3000：把宿主机的 8000 端口映射到容器里的 3000 端口。同一个镜像可以启动多个容器，映射到宿主机的不同端口。
  • -e：设置环境变量。

现在可以访问 http://localhost:8000 了。常用的管理命令：

docker ps                       # 正在运行的容器
docker logs -f flasky           # 查看（并持续跟踪）日志
docker exec -it flasky sh       # 在运行中的容器里打开一个 shell，排查问题
docker stop flasky              # 停止（会收到 SIGTERM，优雅退出）
docker rm flasky                # 删除已停止的容器
docker rm -f flasky             # 停止并删除

要把镜像分享给别人（或者给服务器使用），推送到镜像仓库，比如 Docker Hub 或 GitHub Container Registry：

docker login
docker tag flasky:latest <你的用户名>/flasky:latest
docker push <你的用户名>/flasky:latest

使用外部数据库

原书指出了上面这种部署方式的一个缺点：数据库（原书是 SQLite，我们是 PGlite）就在应用容器里，容器一旦删除，数据就跟着没了，升级应用变得很麻烦。 更好的做法是让数据库在单独的容器里运行，应用容器随时可以替换。Docker Hub 上有官方的 PostgreSQL 镜像。 原书用 docker run --link 把两个容器连起来，这个参数现在已经不推荐使用了，更好的办法是直接用下一节的 Docker Compose。

📌 原书检查点 17e：为 Docker 使用外部数据库（原书用 MySQL，我们用 PostgreSQL）

用 Docker Compose 编排容器

一个应用往往由好几个容器组成：应用本身、数据库，将来可能还有缓存、队列……原书介绍了 Docker 自带的编排工具 Compose： 在一个 docker-compose.yml 文件里描述所有容器，一条命令全部启动： 

services:
  flasky:
    build: .                    # 用当前目录的 Dockerfile 构建
    ports:
      - "8000:3000"
    env_file: .env              # 应用的环境变量
    restart: always             # 意外退出时自动重启
    depends_on:
      - postgres                # 先启动 postgres

  postgres:
    image: postgres:17-alpine   # 直接用官方镜像，不需要构建
    env_file: .env-postgres
    volumes:
      - pgdata:/var/lib/postgresql/data   # 数据存在命名卷里，删掉容器数据也还在
    restart: always

volumes:
  pgdata:

两个环境变量文件。原书特意把数据库的变量放在单独的文件里：好习惯是别让一个容器能看到另一个容器的机密：

FLASKY_CONFIG=production
SECRET_KEY=3128b4588e7f4305b5501025c13ceca5
DATABASE_URL=postgres://flasky:<数据库密码>@postgres:5432/flasky
MAIL_USERNAME=…
MAIL_PASSWORD=…
FLASKY_ADMIN=你的邮箱

POSTGRES_USER=flasky
POSTGRES_PASSWORD=<数据库密码>
POSTGRES_DB=flasky
⚠ 这两个文件永远不要提交到 Git

它们包含密码和其他敏感信息。.gitignore 和 .dockerignore 里都要排除 .env 和 .env-*。

原书讨论了编排系统的一个典型问题：容器启动的顺序。depends_on 保证 postgres 先启动，但不会等它真正准备好接受连接（PostgreSQL 初始化要几秒钟）。 原书的建议是：连接外部服务时总要考虑重试。这正是 boot.sh 里那个重试循环的用途 —— 部署脚本连不上数据库就等 5 秒再试： 

docker compose up -d --build      # 构建镜像（--build），按依赖顺序启动所有容器（-d 后台运行）
docker compose logs -f            # 所有容器的日志合在一起看
docker compose ps                 # 各容器的状态
docker compose down               # 停止并删除容器（数据卷保留）

升级应用：改完代码后再执行一次 docker compose up -d --build，Compose 会重新构建有变化的镜像，用新容器替换旧容器，启动时 boot.sh 自动完成迁移。

📌 原书检查点 17f：Docker Compose 支持

清理旧的容器和镜像

docker ps -a                      # 包括已停止的容器
docker rm -f <名字或ID> …
docker images
docker rmi <镜像>
docker volume ls
docker system prune               # 一次性清理停止的容器、无用的镜像和网络
⚠ 小心 --volumes

原书提到 docker system prune --volumes 可以连同没用的数据卷一起清理。但数据库的数据就存在卷里 —— 如果那一刻数据库容器恰好是停止状态，它的卷就会被当成“没用的”删掉。清理卷之前，务必确认里面没有你需要的数据。

在生产环境使用 Docker

原书列出了只用 Docker 本身部署生产环境的几个局限，今天依然成立：

🚨

监控与告警

Docker 能在容器崩溃时重启它，但不会监控它的健康状况，也不会在异常时通知你。

📜

日志

每个容器有自己的日志流，缺乏长期存储、搜索和过滤。

🔑

机密管理

通过环境变量传递密码并不安全，docker inspect 就能看到。

📈

可靠性与扩容

要容错和扩容，需要在多台主机上运行多个实例，前面再放负载均衡器。

这些问题通常交给更高级的编排系统解决：原书提到了 Docker Swarm、Apache Mesos 和 Kubernetes。 今天更常见的是直接使用云厂商托管的容器服务（AWS ECS、Google Cloud Run、Fly.io 等），你只需要提供镜像。

传统部署：自己的服务器

最后一种方式：买或租一台服务器（物理机或虚拟机），手动装好所有组件。这是最费力的方式，但当你能直接登录生产服务器时，它也最直接。 原书列出了服务器上要做的准备工作，我们逐条对应到今天的 Node.js 生态：

原书的清单本教程的做法
安装数据库（MySQL / Postgres）PostgreSQL（或者用云厂商托管的数据库，省去备份和升级的麻烦）
安装邮件传输代理（Sendmail / Postfix）自己搭邮件服务器很难保证送达率，推荐用事务性邮件服务（第 6 章）
安装生产级 Web 服务器（Gunicorn / uWSGI）不需要：Node.js 本身就是（前面“生产环境的 Web 服务器”一节）
安装进程监控工具（Supervisor）systemd（现代 Linux 发行版自带），或者 pm2
配置 SSL 证书Let's Encrypt 免费证书（certbot 自动续期），或者用会自动申请证书的 Caddy
（强烈推荐）前置反向代理（Nginx / Apache），由它直接提供静态文件Nginx 或 Caddy
加固服务器：防火墙、移除无用软件……防火墙只开 22/80/443、SSH 只允许密钥登录、开启自动安全更新
💡 用脚本自动化这些步骤

原书建议：不要手动执行这些配置，而是用 Ansible、Chef、Puppet 这样的自动化工具写成脚本。这样换一台服务器、或者出了问题要重建时，几分钟就能恢复。

导入环境变量

和 Heroku、Docker 一样，应用在服务器上也依赖环境变量来获取数据库地址、邮件密码等配置。原书在 flasky.py 里用 python-dotenv 读取 .env 文件。 我们从第 7 章起就在入口文件和所有脚本里调用了 Node 内置的 process.loadEnvFile()，所以只要在服务器上的项目目录里放一个 .env 就行： 

FLASKY_CONFIG=production
SECRET_KEY=…
DATABASE_URL=postgres://flasky:…@localhost:5432/flasky
TRUST_PROXY=1
MAIL_SERVER=… MAIL_USERNAME=… MAIL_PASSWORD=…
FLASKY_ADMIN=…

TRUST_PROXY=1 告诉应用：前面有 Nginx，可以相信它加上的 X-Forwarded-* 请求头（图 17-3）。

用 systemd 守护进程

原书推荐用 Supervisor 这样的进程监控工具，在应用崩溃或服务器重启后自动把它拉起来。现代 Linux 自带的 systemd 就能做到： 

[Unit]
Description=Flasky (Hono)
After=network.target postgresql.service

[Service]
Type=simple
User=flasky
WorkingDirectory=/home/flasky/flasky
ExecStartPre=/usr/bin/node dist/scripts/deploy.js
ExecStart=/usr/bin/node dist/src/index.js
Restart=always
Environment=PORT=3000

[Install]
WantedBy=multi-user.target
  • ExecStartPre：每次启动前先运行部署脚本（相当于容器里的 boot.sh）。
  • Restart=always：进程退出就自动重启，服务器重启后也会自动启动（配合下面的 enable）。
  • systemctl stop 会发送 SIGTERM，第 16 章的优雅退出代码同样生效。
sudo systemctl daemon-reload
sudo systemctl enable --now flasky       # 开机自启，并立即启动

# 升级：拉代码 → 装依赖 → 编译 → 重启（重启时会自动跑部署脚本）
git pull && npm ci && npm run build && npm prune --omit=dev && sudo systemctl restart flasky

日志

原书为 Unix 服务器写了一个 UnixConfig，把日志发给 syslog 守护进程。用 systemd 运行的程序，写到标准输出和标准错误的内容会自动进入 systemd 的日志系统 journald，所以什么都不用配置： 

journalctl -u flasky -f              # 实时跟踪 Flasky 的日志
journalctl -u flasky --since today   # 今天的日志

Nginx 反向代理

server {
    listen 80;
    server_name flasky.example.com;
    return 301 https://$host$request_uri;          # HTTP 一律跳转到 HTTPS
}

server {
    listen 443 ssl;
    server_name flasky.example.com;
    ssl_certificate     /etc/letsencrypt/live/flasky.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/flasky.example.com/privkey.pem;

    location /static/ {                            # 静态文件由 Nginx 直接提供，不经过 Node
        alias /home/flasky/flasky/static/;
        expires 7d;
    }

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;          # 应用靠它知道用户用的是 HTTPS
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

小结

  • 部署流水线：npm ci → npm run build → 部署脚本（迁移、角色、自关注，全部可重复执行）→ node dist/src/index.js。
  • 日志一律写标准输出 / 标准错误，由平台收集；生产环境的错误额外通知管理员，更好的做法是用错误监控服务。
  • PaaS：平台装依赖、跑 build；Procfile 的 release 自动执行部署脚本；在反向代理后面要通过 X-Forwarded-Proto 判断 HTTPS。
  • @hono/node-server 本身就是生产级服务器，不需要 Gunicorn 那样的额外一层。
  • Docker：多阶段构建让镜像只包含运行所需；boot.sh 用重试等待数据库、用 exec 让 Node 接收信号；Compose 用服务名互联、用卷持久化数据。
  • 自己的服务器：Nginx（TLS、静态文件、反向代理）+ systemd（守护、自动重启、journald 日志）+ PostgreSQL；设置 TRUST_PROXY=1。

动手练习

  1. 用 Docker Compose 在本地把 Flasky 和 PostgreSQL 跑起来，注册一个账号，然后 docker compose down 再 up，确认数据还在。
  2. 给 postgres 服务加上 healthcheck（提示：pg_isready -U flasky），把 depends_on 改成 condition: service_healthy，观察 flasky 容器还需不需要重试。
  3. 在 docker compose up 运行时执行 docker compose stop flasky，在日志里找到“收到 SIGTERM，正在关闭……”。再把 boot.sh 里的 exec 去掉重试一次，比较有什么不同。
  4. 选一个 PaaS（Heroku、Render、Railway 或 Fly.io），把 Flasky 部署上去，通过“找回密码”邮件里的链接确认它生成的是 https:// 地址。
