密码安全

原书指出，用户信息的安全经常被忽视。如果攻击者拿到了你的用户表，风险远不止你的网站 —— 大多数人在很多网站用同一个密码，泄露一个就等于泄露一串。

所以数据库里绝不能存密码本身，只存密码的哈希值。哈希函数把密码变成一串看不出规律的字符，而且无法反推回去； 但同样的输入永远得到同样的输出，所以登录时对用户输入的密码再算一次哈希，和存着的比一比就知道对不对。

三个关键点：

  • 盐（salt）：每个用户随机生成的一段数据，和密码混在一起再哈希。原书的测试 test_password_salts_are_random 验证的就是：两个用户即使密码相同，哈希也不同。
  • 慢：普通的哈希（如 MD5、SHA-256）为速度而生，显卡一秒能算几十亿次，暴力破解太容易。密码哈希要选故意很慢、而且吃内存的算法：scrypt、Argon2、bcrypt。
  • 不要自己发明：原书强调密码哈希很难写对，要用经过社区审查的库。Node.js 的 crypto 模块内置了 scrypt，我们直接用它。

用 Node.js 的 scrypt 哈希密码

原书用 Werkzeug 的两个函数：generate_password_hash() 和 check_password_hash()。我们也写两个： 

import { randomBytes, scrypt, timingSafeEqual } from 'node:crypto'

// node:crypto 的 scrypt 是回调风格的，包一层变成 Promise
function scryptAsync(password: string, salt: Buffer, keylen: number): Promise<Buffer> {
  return new Promise((resolve, reject) => {
    scrypt(password, salt, keylen, { N: 16384, r: 8, p: 1 }, (err, key) => (err ? reject(err) : resolve(key)))
  })
}

export async function hashPassword(password: string): Promise<string> {
  const salt = randomBytes(16)                         // 每次都是新的随机盐
  const key = await scryptAsync(password, salt, 64)
  return `scrypt$${salt.toString('hex')}$${key.toString('hex')}`   // 盐和哈希存在一起
}

export async function verifyPassword(hash: string | null, password: string): Promise<boolean> {
  if (!hash) return false
  const [algorithm, saltHex, keyHex] = hash.split('$')
  if (algorithm !== 'scrypt' || !saltHex || !keyHex) return false
  const expected = Buffer.from(keyHex, 'hex')
  const actual = await scryptAsync(password, Buffer.from(saltHex, 'hex'), expected.length)
  return timingSafeEqual(actual, expected)             // 不用 ===，见下文
}
🔎 深入：为什么比较要用 timingSafeEqual

普通的比较遇到第一个不同的字节就会返回，所以“前 10 个字节都对”比“第 1 个字节就错”要多花一点点时间。 攻击者理论上可以通过测量响应时间，一个字节一个字节地猜出哈希。timingSafeEqual 不管哪里不同，都比较完所有字节才返回，时间恒定。 这种攻击叫时序攻击，现实中很难实施，但防御它几乎零成本。

原书用 Python 的 @property 做了一个“只写”的 password 属性：赋值时自动哈希，读取时报错。 Drizzle 的行就是普通对象，没有这种魔法。我们的约定更直接：表里只有 passwordHash 列，写入前一律调用 hashPassword()。 明文密码从来不会出现在 users 对象上，自然也就没有“读出明文”的可能。

登录状态：自己实现 Flask-Login

用户登录后，“已登录”这个状态必须被记住，否则每换一个页面都要重新输密码。原书用 Flask-Login 管理它，并在“理解 Flask-Login 的工作原理”一节里拆解了整个流程。 核心其实只有两件事：

  1. 登录时：把用户的 ID 写进会话（第 4 章的签名 Cookie）。
  2. 之后每个请求：从会话里读出 ID，去数据库查出用户，放在一个大家都能用的地方（Flask 里是 current_user，我们是 c.var.user）。

每个请求加载当前用户

先准备一个按 ID 查用户的函数。第 9 章加入角色之后，它会顺便把用户的权限查出来，所以这里用了一个左连接；现在你可以先把它当作“按 ID 查一行”： 

export type User = typeof users.$inferSelect

export async function findUserById(db: Db, id: number) {
  const [user] = await db.select().from(users).where(eq(users.id, id)).limit(1)
  return user ?? null
}

export async function findUserByEmail(db: Db, email: string) {
  const [user] = await db.select().from(users).where(eq(users.email, email.toLowerCase())).limit(1)
  return user ?? null
}

然后是加载当前用户的中间件，它就是 Flask-Login 的 user_loader + current_user：

import { createMiddleware } from 'hono/factory'
import { findUserById } from '../models/users.js'
import type { AppEnv } from '../types.js'

export const loadCurrentUser = createMiddleware<AppEnv>(async (c, next) => {
  const id = c.var.session.userId
  const user = id ? await findUserById(c.var.db, id) : null
  if (id && !user) delete c.var.session.userId       // 会话里的用户已经被删了
  c.set('user', user)                                  // 没登录就是 null
  await next()
})

别忘了在 types.ts 里声明 user 变量，在会话数据里加上 userId，并在 createApp() 里把中间件挂在会话之后：

ⓘ 原书的 UserMixin 和 AnonymousUser

Flask-Login 要求用户模型提供 is_authenticated、is_active、is_anonymous、get_id() 四个成员， 未登录时 current_user 是一个特殊的“匿名用户”对象。我们用更简单的约定：登录了，c.var.user 是用户对象；没登录，就是 null。 if (c.var.user) 就相当于 current_user.is_authenticated。TypeScript 会强制你在使用前检查它是不是 null。

保护路由

原书用 @login_required 装饰器让某个视图只允许登录用户访问，未登录的人会被送到登录页。 在 Hono 里，这就是一个挂在具体路由上的中间件： 

export const loginRequired = createMiddleware<AppEnv>(async (c, next) => {
  if (!c.var.user) {
    const url = new URL(c.req.url)
    // 记下原本想去的地址，登录成功后再送回去（对应 Flask-Login 的 next 参数）
    return c.redirect(`/auth/login?next=${encodeURIComponent(url.pathname + url.search)}`)
  }
  await next()
})

import type { FieldErrors, FormValues } from '../lib/forms.js'

interface FieldProps { name: string; label: string; values?: FormValues; errors?: FieldErrors }

export function Field({ name, label, values, errors, type = 'text' }: FieldProps & { type?: string }) {
  const error = errors?.[name]?.[0]
  const value = type === 'password' ? '' : String(values?.[name] ?? '')   // 密码框永远不回填
  return (
    <div class="mb-3">
      <label class="form-label" for={name}>{label}</label>
      <input class={`form-control${error ? ' is-invalid' : ''}`} id={name} name={name} type={type} value={value} />
      {error && <div class="invalid-feedback">{error}</div>}
    </div>
  )
}

export function Checkbox({ name, label, values }: FieldProps) {

      <input class="form-check-input" type="checkbox" id={name} name={name} checked={checked} />
      <label class="form-check-label" for={name}>{label}</label>
    </div>
  )
}

export function Submit({ label = '提交' }: { label?: string }) {
  return <button type="submit" name="submit" class="btn btn-primary">{label}</button>

对应 Flask-Login 的 login_user() 和 logout_user()，就是往会话里写入和删除 ID：

export function loginUser(c: Context<AppEnv>, user: User, remember: boolean) {
  c.var.session.userId = user.id
  c.var.session.remember = remember      // 会话中间件据此决定 Cookie 的有效期
}

export function logoutUser(c: Context<AppEnv>) {
  delete c.var.session.userId
  delete c.var.session.remember
}

“保持登录”是怎么实现的？原书解释：不勾选时，会话 Cookie 在浏览器关闭时失效；勾选后，Flask-Login 会设置一个长期有效的 Cookie。 在我们的会话中间件里，这只是设置 Cookie 时的一个 maxAge： 

await setSignedCookie(c, COOKIE_NAME, after, secret, {
  path: '/',
  httpOnly: true,
  sameSite: 'Lax',
  secure: !c.var.config.debug && !c.var.config.testing,          // 生产环境只通过 HTTPS 发送
  maxAge: c.var.session.remember ? 60 * 60 * 24 * 30 : undefined,  // 不设 maxAge = 关浏览器就失效
})

next 参数与开放重定向

登录成功后要回到用户原本想访问的页面，这个地址放在查询参数 next 里。 原书特别指出：必须验证 next 是一个站内的相对路径，否则攻击者可以构造 https://flasky.com/auth/login?next=https://evil.com 这样的链接，用户在真网站上登录后，却被送到了钓鱼网站。 

export function safeNext(next: string | undefined): string {
  return next && next.startsWith('/') && !/^\/[/\\]/.test(next) ? next : '/'
}

💡 改动了什么，为什么

原书的退出是一个普通链接（GET 请求）。我们改成了一个只有按钮的小表单（POST 请求），前面导航栏的代码里已经看到了。 原因是 HTTP 规定 GET 请求应该是“安全”的 —— 只读取，不改变状态。 用 GET 做退出，别的网站放一张 <img src="https://flasky.com/auth/logout"> 就能把你的用户踢下线，浏览器的链接预加载也可能误触发。 改成 POST 后，还顺带受到了 CSRF 中间件的保护。后面的“关注”“屏蔽评论”等操作我们也都会用 POST。

    flash(c, '确认邮件已发送到你的邮箱。')
    return c.redirect('/auth/login')
  },
)

export async function createUser(db: Db, input: { email: string; username: string; password: string }) {
  const [user] = await db.insert(users).values({
    email: input.email.toLowerCase(),
    username: input.username,
    passwordHash: await hashPassword(input.password),   // 明文密码到此为止
  }).returning()
  return user
}
🔎 深入：查重和插入之间的“空隙”

先 $count 查重、再 insert，中间有一小段时间。两个人同时用同一个邮箱注册，可能都通过了查重。 好在 email 列有 unique 约束，第二个 insert 一定会被数据库拒绝（抛出错误码 23505 的异常），不会产生脏数据。 查重的意义是给正常用户一个友好的提示；真正的保证来自数据库约束。这是一个值得记住的原则。

📌 原书检查点 8d：注册新用户

确认账户

为了确认用户填的邮箱真的属于他，注册后发一封带确认链接的邮件，用户点了链接才算确认。 原书分析了最简单的做法 —— 链接是 /auth/confirm/<用户id> —— 为什么不行：谁都能猜出别人的 ID，随手就能确认任何账户。 链接里需要一个只有服务器才能生成的令牌。

用 JWT 生成确认令牌

原书用 itsdangerous 生成带过期时间的 JSON Web 签名。它的原理和第 4 章的签名 Cookie 一模一样：数据 + 用密钥算出的签名。 这种“带签名的 JSON 令牌”有一个通用的标准格式，叫 JWT（JSON Web Token），Hono 内置了 hono/jwt： 

import { sign, verify } from 'hono/jwt'

type TokenPurpose = 'confirm' | 'reset' | 'change_email' | 'api'

export async function generateToken(
  secret: string, purpose: TokenPurpose, data: Record<string, string | number>, expiresIn = 3600,
): Promise<string> {
  const exp = Math.floor(Date.now() / 1000) + expiresIn        // 默认一小时后过期
  return sign({ ...data, purpose, exp }, secret, 'HS256')
}

export async function readToken(secret: string, token: string, purpose: TokenPurpose) {
  try {
    const payload = await verify(token, secret, 'HS256')      // 签名不对、已过期都会抛异常
    return payload.purpose === purpose ? payload : null
  } catch {
    return null
  }
}

purpose 字段防止令牌“串用”：确认账户的令牌不能拿去重置密码。原书用不同的键名（confirm、reset）达到同样的目的。 在它们之上，确认账户的两个函数对应原书 User 模型的 generate_confirmation_token() 和 confirm()： 

export const generateConfirmationToken = (secret: string, userId: number, expiresIn = 3600) =>
  generateToken(secret, 'confirm', { id: userId }, expiresIn)

export async function confirmUser(db: Db, secret: string, user: User, token: string) {
  const data = await readToken(secret, token, 'confirm')
  if (!data || data.id !== user.id) return false      // 别人的令牌不能确认我的账户
  await db.update(users).set({ confirmed: true }).where(eq(users.id, user.id))
  return true
}

export function requireUser(c: Context<AppEnv>) {
  const user = c.var.user
  if (!user) throw new HTTPException(401)
  return user

拦截未确认的用户

未确认的用户可以登录，但只能看到一个“请先确认账户”的页面。原书用蓝本的 before_app_request 钩子实现，它对所有请求生效。 我们在 loadCurrentUser 之后再挂一个全局中间件： 

export const confirmedGuard = createMiddleware<AppEnv>(async (c, next) => {
  const user = c.var.user
  if (user) {
    const path = c.req.path
    // 认证相关的页面（确认、重发、退出）和静态文件要放行，否则用户永远确认不了
    const exempt = path.startsWith('/auth/') || path.startsWith('/static/')
    if (!user.confirmed && !exempt) return c.redirect('/auth/unconfirmed')
  }
  await next()
})

// src/app.tsx
app.use('*', session, loadCurrentUser, confirmedGuard)

重置密码

忘记密码的用户没法登录，所以要借助邮件和令牌，流程和确认账户很像：

export const generateResetToken = (secret: string, userId: number, expiresIn = 3600) =>
  generateToken(secret, 'reset', { id: userId }, expiresIn)

export async function resetPassword(db: Db, secret: string, token: string, newPassword: string) {
  const data = await readToken(secret, token, 'reset')
  if (!data || typeof data.id !== 'number') return false
  const updated = await db.update(users)
    .set({ passwordHash: await hashPassword(newPassword) })
    .where(eq(users.id, data.id))
    .returning({ id: users.id })
  return updated.length === 1
}

修改邮箱

新邮箱要先验证确实属于用户才能生效。原书提到两种做法：把待确认的新邮箱存在数据库的一个字段里，或者直接把它放进令牌。 原书选了后者，我们也一样 —— 令牌签了名，新邮箱在里面不会被篡改： 

export const generateEmailChangeToken = (secret: string, userId: number, newEmail: string, expiresIn = 3600) =>
  generateToken(secret, 'change_email', { id: userId, newEmail }, expiresIn)

export async function changeEmail(db: Db, secret: string, user: User, token: string) {
  const data = await readToken(secret, token, 'change_email')
  if (!data || data.id !== user.id || typeof data.newEmail !== 'string') return false
  if (await findUserByEmail(db, data.newEmail)) return false        // 这期间被别人注册了
  await db.update(users).set({ email: data.newEmail }).where(eq(users.id, user.id))
  return true
}

处理函数要求用户输入密码（防止别人趁你离开电脑时改掉你的邮箱），然后把令牌发到新邮箱：

小结

  • 数据库只存加盐的慢哈希：scrypt + 随机盐，用 timingSafeEqual 比较；明文密码只在 hashPassword() 里出现一次。
  • 认证路由放在 routes/auth.tsx，挂载到 /auth。
  • Flask-Login 的本质：登录时 session.userId = id；loadCurrentUser 中间件每次按 ID 查出 c.var.user；loginRequired 中间件保护路由。
  • “保持登录” = 会话 Cookie 带 maxAge；next 参数必须用 safeNext() 验证，防开放重定向。
  • 修改状态的操作（包括退出）用 POST；业务规则（邮箱是否已注册）写在处理函数里，最终保证靠数据库的唯一约束。
  • JWT = 头部.载荷.签名，带 exp 过期时间；用 purpose 区分用途；确认、重置、改邮箱三个流程都建立在它之上。
