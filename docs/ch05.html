第 5 章

数据库

会话只能记住一个用户的一点点东西，而且关掉浏览器就可能消失。真正需要长期保存、所有用户共享的数据，要放进数据库。 这一章介绍关系型数据库的基本概念，然后用 Drizzle ORM 定义表、增删改查， 最后用 drizzle-kit 管理数据库结构的变更（迁移）。

本章目标

  • 理解表、行、主键、外键和“一对多”关系，知道 SQL 与 NoSQL 的取舍
  • 知道为什么选 Drizzle，以及为什么开发用 PGlite、生产用 PostgreSQL
  • 用 Drizzle 的 pgTable 定义模型，并从中自动得到 TypeScript 类型
  • 熟练地插入、修改、删除、查询数据，会看 Drizzle 生成的 SQL
  • 在处理函数和交互式 shell 里使用数据库
  • 用 drizzle-kit 生成、审查、应用迁移

SQL 数据库

关系型数据库把数据存在表（table）里，每张表对应应用里的一类东西 —— 用户、角色、文章。 表有固定的列（column，定义了“这类东西有哪些属性”）和不定数量的行（row，每一行就是一个具体的东西）。

每张表有一个特殊的列叫主键（primary key），它的值在表内唯一，用来标识每一行。 表还可以有外键（foreign key）列，存的是另一张表（或同一张表）某一行的主键。 这种行与行之间的链接叫关系（relationship），是“关系型”数据库名字的由来。

这种设计的好处是没有重复：角色名只存在 roles 表里一处，把 “Admin” 改名为 “Administrator”， 所有引用它的用户立刻就“看到”了新名字。代价是想列出“用户及其角色名”时，得把两张表连接（join）起来查。 好在关系数据库很擅长做这件事。

NoSQL 数据库

不遵循关系模型的数据库统称 NoSQL。常见的一类用集合（collection）代替表、用文档（document）代替行。 它们通常不支持连接，所以会把数据反规范化（denormalize）：直接把角色名抄进每个用户文档里。

开发用 PGlite，生产用 PostgreSQL

原书开发时用 SQLite（一个文件就是一个数据库，不用装服务器），上线后换成 MySQL 或 Postgres。 这个思路很实用，但有个隐患：SQLite 和 Postgres 毕竟是两种数据库，行为有差异， 而且在 Drizzle 里，两种数据库的表要用不同的函数定义（sqliteTable 和 pgTable）。

PGlite 完美地解决了这个问题：它是编译成 WebAssembly 的真正的 PostgreSQL， 以一个 npm 包的形式运行在你的 Node 进程里，数据存在一个目录中 —— 和 SQLite 一样免安装，但和生产环境是同一种数据库。

安装需要的包：

npm install drizzle-orm @electric-sql/pglite pg
npm install -D drizzle-kit @types/pg

原书表 5-1 列出了不同数据库的连接 URL，我们用到的是这些：

PGlite（磁盘）./data/dev一个目录，PGlite 会自动创建

先写一个最简单的数据库模块。第 7 章会把它改造成能根据配置切换 PGlite 和 PostgreSQL 的版本：

import { PGlite } from '@electric-sql/pglite'
import { drizzle } from 'drizzle-orm/pglite'
import * as schema from './schema.js'

// 数据存在项目目录的 data/dev 下（记得把 data/ 加进 .gitignore）
export const db = drizzle(new PGlite('./data/dev'), { schema })

定义模型

模型（model）指应用里需要持久保存的实体。在原书里，模型是一个继承 db.Model 的 Python 类； 在 Drizzle 里，模型就是一个用 pgTable() 定义的表对象：

Flask-SQLAlchemy
class Role(db.Model):
    __tablename__ = 'roles'
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(64), unique=True)

class User(db.Model):
    __tablename__ = 'users'
    id = db.Column(db.Integer, primary_key=True)
    username = db.Column(db.String(64),
                         unique=True, index=True)
Drizzle
import { pgTable, serial, varchar } from 'drizzle-orm/pg-core'

export const roles = pgTable('roles', {
  id: serial('id').primaryKey(),
  name: varchar('name', { length: 64 }).notNull().unique(),
})

export const users = pgTable('users', {
  id: serial('id').primaryKey(),
  username: varchar('username', { length: 64 }).notNull().unique(),
})
  • pgTable('roles', …) 的第一个参数就是表名（相当于 __tablename__）。原书建议表名用复数，我们照做。
  • 每个属性写成 代码里的名字: 类型('数据库里的列名')。两边可以不同：后面会看到 roleId: integer('role_id')，代码用驼峰，数据库用下划线。
  • serial 是 PostgreSQL 的自增整数，插入时不用给值，数据库自动分配 1、2、3……
  • .unique() 会自动建立唯一索引，所以不用再单独写 index=True。

从模型得到类型

Drizzle 最让人愉快的一点：不需要手写任何类型，表定义就是类型的来源：

export type Role = typeof roles.$inferSelect      // 查出来的一行：{ id: number; name: string }
export type NewUser = typeof users.$inferInsert   // 插入时需要的：{ id?: number; username: string; … }

注意 $inferInsert 里 id 是可选的（数据库会自动生成），而 username 是必填的（notNull() 且没有默认值）。 以后给表加一列，这些类型会自动跟着变，所有用到的地方编辑器都会检查。

ⓘ 原书的 __repr__ 呢？

原书给每个模型写了 __repr__()，方便在 shell 里打印时看得清楚。Drizzle 查出来的是普通 JavaScript 对象， console.log() 直接就能看到所有字段，不需要额外做什么。

关系

给 users 表加一个外键列，指向 roles.id：

Flask-SQLAlchemy
class Role(db.Model):
    # ...
    users = db.relationship('User', backref='role')

class User(db.Model):
    # ...
    role_id = db.Column(db.Integer,
                        db.ForeignKey('roles.id'))
Drizzle
import { integer } from 'drizzle-orm/pg-core'

export const users = pgTable('users', {
  id: serial('id').primaryKey(),
  username: varchar('username', { length: 64 }).notNull().unique(),
  roleId: integer('role_id').references(() => roles.id),
})

.references(() => roles.id) 定义了真正的数据库外键约束 —— 它保证 role_id 里只能放存在的角色 ID。 写成箭头函数是为了允许“引用在后面才定义的表”（相当于原书用字符串 'User' 来引用后面的类）。

原书的 db.relationship() 还提供了“面向对象”的访问方式：role.users 得到这个角色的所有用户，user.role 得到用户的角色。 Drizzle 里对应的是 relations()，它不改变数据库结构，只是告诉 Drizzle 两张表怎么连，供“关系查询”使用： 

import { relations } from 'drizzle-orm'

export const rolesRelations = relations(roles, ({ many }) => ({
  users: many(users),                    // role.users —— “一对多”的“多”
}))

export const usersRelations = relations(users, ({ one }) => ({
  role: one(roles, { fields: [users.roleId], references: [roles.id] }),   // user.role
}))

除了一对多，还有别的关系类型：一对一可以看作“多”的一方最多只有一个； 多对一是站在“多”那一方看的一对多；最复杂的多对多需要一张额外的“关联表”，第 12 章会详细讲。

数据库操作

原书在 flask shell 里演示各种数据库操作。我们也可以这么做（本章后面会搭一个 shell）， 这里先把每种操作的写法过一遍。

创建表

原书先用 db.create_all() 按模型建表，并提醒：表已存在时它不会更新表结构，想改表只能 drop_all() 再重建，数据全丢。 Drizzle 里对应的“快速原型”工具是 drizzle-kit push：它比较 schema.ts 和数据库的实际结构，直接把差异同步过去。 先在项目根目录写一个 drizzle-kit 的配置文件： 

import { defineConfig } from 'drizzle-kit'

export default defineConfig({
  dialect: 'postgresql',
  schema: './src/db/schema.ts',
  out: './drizzle',                       // 迁移文件放在这里（本章最后一节）
  driver: 'pglite',                       // 开发时连接的是 PGlite
  dbCredentials: { url: './data/dev' },
})

npx drizzle-kit push
# [✓] Changes applied
⚠ push 只适合开发初期

push 很方便，但它不留记录：生产数据库是怎么一步步变成现在这样的，没有任何文件能说清楚。 和原书一样，本章最后我们会换成正规的迁移。另外，PGlite 同一时间只能被一个进程打开， 运行 drizzle-kit 之前要先停掉开发服务器。

插入行

Flask-SQLAlchemy
>>> admin_role = Role(name='Admin')
>>> mod_role = Role(name='Moderator')
>>> user_role = Role(name='User')
>>> user_john = User(username='john', role=admin_role)
>>> db.session.add_all([admin_role, mod_role,
...                     user_role, user_john])
>>> db.session.commit()
>>> admin_role.id
1
Drizzle
const [adminRole, modRole, userRole] = await db
  .insert(roles)
  .values([{ name: 'Admin' }, { name: 'Moderator' }, { name: 'User' }])
  .returning()            // 让数据库把插入后的行（含 id）返回来

adminRole.id              // 1

await db.insert(users).values([
  { username: 'john', roleId: adminRole.id },
  { username: 'susan', roleId: userRole.id },
  { username: 'david', roleId: userRole.id },
])

原书演示了一个细节：Python 对象在 commit() 之前 id 是 None，提交之后数据库才分配 ID。 Drizzle 没有“先创建对象、再提交”这一步：insert 语句一执行，行就已经在数据库里了，.returning() 把数据库分配的 ID 带回来。

“数据库会话”与事务

原书说：Flask-SQLAlchemy 的 db.session（和 Flask 的用户会话毫无关系！）会把多次修改攒起来，commit() 时原子地一次写入； 中途出错就整体回滚，保证数据库不会停留在“改了一半”的状态。数据库会话也叫事务（transaction）。

Drizzle 默认每条语句单独执行、单独生效。需要“几条语句要么全成功、要么全失败”时，显式地开一个事务： 

await db.transaction(async (tx) => {
  await tx.insert(users).values({ username: 'eve', roleId: userRole.id })
  await tx.insert(users).values({ username: 'john' })   // 用户名重复 → 抛异常
})
// 第二条失败，第一条也被回滚：数据库里没有 eve

修改和删除行

Flask-SQLAlchemy
>>> admin_role.name = 'Administrator'
>>> db.session.add(admin_role)
>>> db.session.commit()

>>> db.session.delete(mod_role)
>>> db.session.commit()
Drizzle
import { eq } from 'drizzle-orm'

await db.update(roles)
  .set({ name: 'Administrator' })
  .where(eq(roles.id, adminRole.id))

await db.delete(roles)
  .where(eq(roles.name, 'Moderator'))
⚠ 别忘了 where

db.update(roles).set({ name: 'X' }) 如果漏了 .where()，会把所有角色都改名； db.delete(roles) 会删光整张表。SQL 本身就是这么规定的，Drizzle 只是忠实地翻译。写修改和删除语句时，先写 where。

查询行

最基本的查询，取出整张表：

Flask-SQLAlchemy
>>> Role.query.all()
[<Role 'Administrator'>, <Role 'User'>]
>>> User.query.filter_by(role=user_role).all()
[<User 'susan'>, <User 'david'>]
Drizzle
await db.select().from(roles)
// [{ id: 3, name: 'User' }, { id: 1, name: 'Administrator' }]
// 注意：没写 orderBy 时，数据库不保证返回顺序（刚被修改过的行常常跑到后面）

await db.select().from(users).where(eq(users.roleId, userRole.id))
// [{ id: 2, username: 'susan', roleId: 3 },
//  { id: 3, username: 'david', roleId: 3 }]

原书演示了把查询对象转成字符串来看 SQLAlchemy 生成的 SQL。Drizzle 用 .toSQL()：

db.select().from(users).where(eq(users.roleId, 3)).toSQL()
// {
//   sql: 'select "id", "username", "role_id" from "users" where "users"."role_id" = $1',
//   params: [3]
// }

注意 $1 和 params：值是作为参数单独发给数据库的，而不是拼进 SQL 字符串。 这让 SQL 注入攻击无从下手 —— 和 JSX 自动转义防 XSS 是一个道理。

原书表 5-5 的查询过滤器，在 Drizzle 里是 select() 之后链式调用的方法：

SQLAlchemy 过滤器Drizzle
filter_by(name='x') / filter(...).where(eq(t.name, 'x'))；多个条件用 and(…) / or(…)；还有 ne、gt、lt、like、inArray……
limit(n).limit(n)
offset(n).offset(n)
order_by(...).orderBy(asc(t.col)) / desc(t.col)
group_by(...).groupBy(t.col)

原书表 5-6 的“查询执行器”（真正触发数据库查询的方法）。Drizzle 的查询写好后 await 就会执行，所以对应关系是：

SQLAlchemyDrizzle
all()await db.select().from(t)…，得到数组
first()const [row] = await ….limit(1)，没有结果时 row 是 undefined
get(id)await db.query.t.findFirst({ where: eq(t.id, id) })
first_or_404() / get_or_404()先查，再 if (!row) throw new HTTPException(404)

paginate()用 limit + offset + $count 自己写（第 11 章）

关系查询

原书用 user_role.users 取出一个角色的所有用户，还演示了 lazy='dynamic'： 让关系返回“还没执行的查询”，以便继续加排序等条件。Drizzle 的关系查询在一次调用里就能指定这些： 

import { asc } from 'drizzle-orm'

const role = await db.query.roles.findFirst({
  where: eq(roles.name, 'User'),
  with: { users: { orderBy: asc(users.username) } },   // 相当于 user_role.users.order_by(User.username)
})
// { id: 3, name: 'User', users: [{ id: 3, username: 'david', … }, { id: 2, username: 'susan', … }] }

const john = await db.query.users.findFirst({ with: { role: true } })
// { id: 1, username: 'john', roleId: 1, role: { id: 1, name: 'Administrator' } }

db.query.xxx 这套 API 就是靠前面写的 relations() 知道怎么连表的。 只要计数的话，用 await db.$count(users, eq(users.roleId, 3))，相当于原书的 user_role.users.count()。

在处理函数里使用数据库

现在把数据库接进上一章的“你叫什么名字”应用：每次提交名字时查一下数据库， 没见过的名字就存进去，并在页面上说“很高兴认识你”；见过的就说“欢迎回来”。

原书的 Flask 版本：

if form.validate_on_submit():
    user = User.query.filter_by(username=form.name.data).first()
    if user is None:
        user = User(username=form.name.data)
        db.session.add(user)
        db.session.commit()
        session['known'] = False
    else:
        session['known'] = True
    session['name'] = form.name.data
    return redirect(url_for('index'))

Hono + Drizzle 版本，处理函数变成了 async：

import { eq } from 'drizzle-orm'
import { db } from './db/index.js'
import { users } from './db/schema.js'

app.post('/', zValidator('form', nameSchema, hook), async (c) => {
  const { name } = c.req.valid('form')

  const [user] = await db.select().from(users).where(eq(users.username, name)).limit(1)
  if (!user) {
    await db.insert(users).values({ username: name })
    c.var.session.known = false
  } else {
    c.var.session.known = true
  }

  c.var.session.name = name
  return c.redirect('/')
})

模板里根据 known 显示不同的第二行：

function IndexPage({ name, known, value = '', errors }: {
  name?: string; known?: boolean; value?: string; errors?: FieldErrors
}) {
  return (
    <>
      <div class="page-header">
        <h1>你好，{name ?? '陌生人'}！</h1>
        {name && (known ? <p>欢迎回来！</p> : <p>很高兴认识你！</p>)}
      </div>
      {/* …表单和上一章一样… */}
    </>
  )
}

app.get('/', (c) => c.render(<IndexPage name={c.var.session.name} known={c.var.session.known} />))
ⓘ 处理函数变成了 async

数据库查询要通过网络（或者至少跨越进程内的边界），需要时间，所以 Drizzle 的每个操作都返回 Promise，要用 await 等它完成。 用了 await 的函数必须声明成 async。忘了写 await 是新手最常见的 bug 之一： 你拿到的会是一个 Promise 对象，而不是查询结果。TypeScript 通常能帮你发现这种错误。

集成交互式 shell

原书用 @app.shell_context_processor 让 flask shell 启动时自动导入 db 和各个模型，省得每次手动 import。 Node.js 自带 REPL（交互式解释器），我们写个小脚本做同样的事： 

import repl from 'node:repl'
import * as drizzle from 'drizzle-orm'
import { db } from '../src/db/index.js'
import * as schema from '../src/db/schema.js'

console.log('Flasky shell。可用：db、roles、users、eq、and、desc……')
const r = repl.start({ prompt: 'flasky> ' })
Object.assign(r.context, { db, ...schema, ...drizzle })   // 相当于 shell context processor

npm pkg set scripts.shell="tsx scripts/shell.ts"
npm run shell

flasky> await db.select().from(users)
[ { id: 1, username: 'john', roleId: 1 }, … ]
flasky> await db.$count(users)
3

Node 的 REPL 支持顶层 await，所以可以直接执行查询。 如果更喜欢图形界面，drizzle-kit 还自带一个网页版数据库浏览器：运行 npx drizzle-kit studio，在浏览器里查看和编辑表中的数据。

用 drizzle-kit 做数据库迁移

开发过程中模型一定会变：加一列、改一个类型、建一张新表。数据库必须跟着变，而且不能丢数据。 原书介绍的解决方案是数据库迁移框架：就像 Git 跟踪源代码的变化一样，迁移框架跟踪数据库结构（schema）的变化， 每次变化生成一个迁移脚本，可以按顺序依次应用到任何一个数据库上。原书用的是 Alembic（通过 Flask-Migrate），我们用 drizzle-kit。

生成迁移

原书先要 flask db init 建立迁移仓库。drizzle-kit 不需要这一步 —— 前面写的 drizzle.config.ts 里的 out: './drizzle' 就是迁移目录。 如果你前面用 push 建过表，先删掉 data/dev 目录，从一个空数据库开始（原书在这里也给了同样的建议）。然后： 

npx drizzle-kit generate --name initial_migration
# 2 tables

drizzle/ 目录里还有一个 meta/ 子目录，保存着每次迁移后的 schema“快照”。 下次 generate 时，drizzle-kit 就是拿当前的 schema.ts 和最新快照比较，算出需要哪些 ALTER TABLE。 所以原书那句话同样适用：迁移目录必须和代码一起提交到版本控制。

应用迁移

生成迁移只是写出了 SQL 文件，还要在数据库上执行才算“升级”。drizzle-orm 提供了 migrate() 函数， 它会在数据库里建一张 __drizzle_migrations 表，记录哪些迁移已经执行过，每次只执行新增的部分： 

import { migrate } from 'drizzle-orm/pglite/migrator'
import { db } from '../src/db/index.js'

await migrate(db, { migrationsFolder: './drizzle' })
console.log('数据库已迁移到最新版本')
process.exit(0)

npm pkg set scripts.db:generate="drizzle-kit generate" scripts.db:migrate="tsx scripts/migrate.ts"
npm run db:migrate
# 数据库已迁移到最新版本
💡 为什么自己写 migrate 脚本

drizzle-kit 本身也有 drizzle-kit migrate 命令，开发时直接用也完全没问题。 自己写脚本的好处是：它和应用用的是同一个 db 对象，第 7 章切换到“按配置选数据库”之后，同一个脚本在开发、测试、生产环境都能用； 第 17 章的部署脚本也会调用同一个 migrate()。

⚠ 自动生成的迁移不一定对

原书警告：如果你重命名了一列，自动迁移可能会理解成“删掉旧列、新建一列”，旧数据就没了。 drizzle-kit 在遇到这种模棱两可的情况时会停下来问你：“这一列是新建的，还是从某列改名来的？”—— 认真回答它。 但其他意图（比如把字符串列改成整数列时，已有数据该怎么转换）它无从得知，所以每个迁移都要人工审查，必要时手动编辑 SQL 文件。

🔎 深入：原书“合并迁移”的技巧

原书介绍了一个技巧：开发一个功能时模型改了好几次，不想留下一堆零碎的迁移，可以 downgrade 撤掉最后一个迁移、删掉脚本、再重新生成一个。 drizzle-kit 里对应的做法是：在迁移还没提交、也没应用到别人的数据库之前，运行 npx drizzle-kit drop 删掉最新的迁移（它会同时更新快照）， 然后删掉本地开发库重新 migrate，再 generate 一个合并后的新迁移。已经上线的迁移永远不要改。

小结

  • 关系数据库用表、主键和外键组织数据，避免重复；NoSQL 用反规范化换取免连接的读取速度。
  • Drizzle 是“贴近 SQL 的 ORM”：表用 pgTable 定义，类型用 $inferSelect / $inferInsert 自动推导。
  • 开发和测试用 PGlite（进程内的 PostgreSQL），生产用 PostgreSQL 服务器，schema 只写一份。
  • .references() 定义数据库外键；relations() 只服务于 db.query.xxx 关系查询。
  • 增删改查：insert().values().returning()、update().set().where()、delete().where()、select().from().where()；多条语句要原子执行时用 db.transaction()。
  • 值总是作为参数传给数据库（$1），天然防 SQL 注入；.toSQL() 可以看生成的语句。
  • 表结构的变更走迁移：drizzle-kit generate → 审查 → 提交 → migrate()。

动手练习
