第 10 章

用户资料

每个社交网站都会给用户一个资料页，展示这个人在网站上的活动。用户也会把自己资料页的链接分享出去，所以地址要短、要好记。 这一章做出资料页、两个资料编辑器（用户自己的、管理员的），再加上 Gravatar 头像。

本章目标

  • 给用户表加上姓名、所在地、自我介绍、注册时间、最后访问时间
  • 理解“列默认值”的三种写法，以及为什么最后访问时间要限制写入频率
  • 做出 /user/:username 资料页，找不到用户时返回 404
  • 实现用户级和管理员级两个资料编辑器，处理好“下拉框的值是字符串”和“改了才查重”
  • 用 Gravatar 生成头像，并把邮箱的 MD5 哈希缓存进数据库

资料信息

原书给 User 模型加了五个新字段（例 10-1）：

Flask-SQLAlchemy
name = db.Column(db.String(64))
location = db.Column(db.String(64))
about_me = db.Column(db.Text())
member_since = db.Column(db.DateTime(),
                         default=datetime.utcnow)

                      default=datetime.utcnow)
Drizzle
name: varchar('name', { length: 64 }),
location: varchar('location', { length: 64 }),
aboutMe: text('about_me'),
memberSince: timestamp('member_since', { withTimezone: true })
  .notNull().defaultNow(),
lastSeen: timestamp('last_seen', { withTimezone: true })
  .notNull().defaultNow(),
  • varchar 有长度上限，text 没有 —— 自我介绍可能很长，所以用 text（原书用 db.Text，道理一样）。
  • timestamp(…, { withTimezone: true }) 对应 PostgreSQL 的 timestamptz：存储时统一换算成 UTC，读出来是 JavaScript 的 Date。第 3 章说过，服务器端一律用 UTC。
🔎 深入：列默认值的三种写法

原书特别解释了 default=datetime.utcnow 后面没有括号：传的是函数本身，SQLAlchemy 每次插入时调用它。 Drizzle 里有三种选择：

  • .default(值)：固定值，写进数据库的表定义里，如 .default(false)。
  • .defaultNow()：数据库端的 DEFAULT now()，由数据库在插入时取当前时间。最推荐 —— 即使有人绕过应用直接写 SQL，也能得到正确的默认值。
  • .$defaultFn(() => …)：由 Drizzle 在应用端每次插入时调用函数计算，最接近原书的写法，适合生成 UUID 这类数据库不方便算的值。

刷新“最后访问时间”

memberSince 靠默认值就够了，但 lastSeen 需要在用户每次访问时刷新。原书写了一个 ping() 方法， 在第 8 章那个每个请求都会运行的 before_app_request 钩子里调用它。我们对应地放进 confirmedGuard 中间件： 

export async function ping(db: Db, userId: number) {
  await db.update(users).set({ lastSeen: new Date() }).where(eq(users.id, userId))
}

export const confirmedGuard = createMiddleware<AppEnv>(async (c, next) => {
  const user = c.var.user
  if (user) {
    // 刷新最后访问时间，但一分钟内最多写一次数据库
    if (Date.now() - user.lastSeen.getTime() > 60_000) await ping(c.var.db, user.id)

    const path = c.req.path
    const exempt = path.startsWith('/auth/') || path.startsWith('/static/') || path.startsWith('/api/')
    if (!user.confirmed && !exempt) return c.redirect('/auth/unconfirmed')
  }
  await next()
})

资料页

资料页的路由没什么新东西（原书例 10-4）：

Flask
@main.route('/user/<username>')
def user(username):
    user = User.query.filter_by(
        username=username).first_or_404()
    return render_template('user.html', user=user)
Hono
main.get('/user/:username', async (c) => {
  const profile = await findUserByUsername(
    c.var.db, c.req.param('username'))
  if (!profile) throw new HTTPException(404)
  return c.render(
    <UserPage profile={profile} viewer={c.var.user} />,
    { title: profile.username })
})

first_or_404() 把“查询”和“找不到就 404”合成了一步。Drizzle 没有这个便捷方法，两行代码写得也很清楚。 注意变量名：页面上有两个用户 —— 被查看的人（profile）和正在看的人（viewer，即当前登录用户，可能是 null）， 起不同的名字能避免很多混淆。原书模板里的 user 和 current_user 就是这两个。 

export function UserPage({ profile, viewer }: { profile: User; viewer: CurrentUser | null }) {
  const isSelf = viewer?.id === profile.id
  return (
    <div class="page-header">
      <h1>{profile.username}</h1>
      {(profile.name || profile.location) && (
        <p>
          {profile.name}{profile.name && <br />}
          {profile.location && (
            <>来自 <a href={`https://www.openstreetmap.org/search?query=${encodeURIComponent(profile.location)}`}>
              {profile.location}</a></>
          )}
        </p>
      )}
      {isAdministrator(viewer) && <p><a href={`mailto:${profile.email}`}>{profile.email}</a></p>}
      {profile.aboutMe && <p>{profile.aboutMe}</p>}
      <p>
        注册于 <Moment ts={profile.memberSince} format="L" />。
        最后访问 <Moment ts={profile.lastSeen} />。
      </p>
      {isSelf && <a class="btn btn-outline-secondary" href="/edit-profile">编辑资料</a>}
    </div>
  )
}

原书指出了这个模板的几个细节，在 JSX 里一一对应：

  • 姓名和所在地放在同一个 <p> 里，只有至少一个有值时才输出这个段落（(a || b) && …）。
  • 所在地做成地图链接。原书链接到 Google 地图，这里换成了开放的 OpenStreetMap。注意用 encodeURIComponent 把地名编进 URL。
  • 只有管理员能看到用户的邮箱（isAdministrator(viewer)），方便管理员联系用户。
  • 两个时间用第 3 章的 <Moment> 组件，由浏览器按本地时区显示。

大多数用户会想快速打开自己的资料页，所以在导航栏里加一个链接（原书例 10-6）。登录了才显示：

{user && <li class="nav-item"><a class="nav-link" href={`/user/${user.username}`}>个人资料</a></li>}

资料编辑器

原书分析了两种不同的编辑需求：用户要编辑自己的公开信息；管理员要能编辑任何人的资料，包括用户自己不能碰的字段（邮箱、用户名、确认状态、角色）。 需求差别很大，所以做成两个表单。

用户自己的编辑器

三个字段都是可选的，所以只限制最大长度（原书用 Length(0, 64)）：

const profileSchema = z.object({
  name: z.string().trim().max(64, '最多 64 个字符'),
  location: z.string().trim().max(64, '最多 64 个字符'),
  aboutMe: z.string().trim(),
})

main.get('/edit-profile', loginRequired, (c) => {
  const user = requireUser(c)
  // 用现有的值预先填好表单（原书：form.name.data = current_user.name）
  const values = { name: user.name ?? '', location: user.location ?? '', aboutMe: user.aboutMe ?? '' }
  return c.render(<EditProfilePage values={values} />, { title: '编辑资料' })
})

main.post(
  '/edit-profile',
  loginRequired,
  validateForm(profileSchema, (c, values, errors) => c.render(<EditProfilePage values={values} errors={errors} />)),
  async (c) => {
    const user = requireUser(c)
    const data = c.req.valid('form')                      // { name, location, aboutMe }
    await c.var.db.update(users).set(data).where(eq(users.id, user.id))
    flash(c, '个人资料已更新。')
    return c.redirect(`/user/${user.username}`)
  },
)

原书用同一个视图函数处理 GET 和 POST，并通过 form.xxx.data 在两个方向上传递数据：GET 时把用户的现有值放进表单，POST 时从表单取出新值。 我们拆成了两个路由，数据流更直观：GET 把现有值作为 values 传给页面；POST 从 c.req.valid('form') 拿到新值。 而且因为 schema 的键和表的列名一致，set(data) 一行就能完成更新。 

export function EditProfilePage({ values, errors }: FormState) {
  return (
    <>
      <div class="page-header"><h1>编辑个人资料</h1></div>
      <form method="post" class="col-md-6">
        <Field name="name" label="真实姓名" values={values} errors={errors} />
        <Field name="location" label="所在地" values={values} errors={errors} />
        <TextArea name="aboutMe" label="自我介绍" values={values} errors={errors} />
        <Submit />
      </form>
    </>
  )
}

TextArea 和第 8 章的 Field 是一个模式，只是输出 <textarea>。资料页上“编辑资料”按钮只在查看自己的资料时显示，前面的 UserPage 里已经写了。

管理员的编辑器

管理员的表单多了四个字段，其中两个需要特别处理：

const adminProfileSchema = profileSchema.extend({
  email: z.email('请输入有效的邮箱地址').max(64),
  username: z.string().trim().min(1).max(64)
    .regex(/^[A-Za-z][A-Za-z0-9_.]*$/, '用户名只能包含字母、数字、点和下划线，并以字母开头'),
  confirmed: checkbox(),
  roleId: z.coerce.number().int(),          // 相当于 SelectField(coerce=int)
})

角色下拉框：原书用 SelectField，选项是 (角色 id, 角色名) 的列表，并用 coerce=int 把提交上来的值转成整数。 问题的根源在于：HTML 表单提交的一切都是字符串，<option value="3"> 提交上来就是 "3"。 Zod 的 z.coerce.number() 做的就是同一件事：先 Number("3")，再校验是不是整数。

下拉框的选项来自数据库，按名字排序（原书在表单的构造函数里查询）：

async function roleOptions(c: { var: AppEnv['Variables'] }): Promise<[number, string][]> {
  const rows = await c.var.db.select({ id: roles.id, name: roles.name }).from(roles).orderBy(roles.name)
  return rows.map((r) => [r.id, r.name])
}

邮箱和用户名的查重：原书在 EditProfileAdminForm 的 validate_email 里先判断值有没有变， 只有变了才去检查新值是否被别人占用 —— 否则管理员不改邮箱直接保存，会因为“邮箱已被注册”（被他自己）而失败。为此原书的表单构造函数还要接收被编辑的用户。 在处理函数里写这个逻辑就简单多了： 

main.post(
  '/edit-profile/:id{[0-9]+}',
  loginRequired,
  adminRequired,
  validateForm(adminProfileSchema, async (c, values, errors) =>
    c.render(<EditProfileAdminPage values={values} errors={errors} roles={await roleOptions(c)} />)),
  async (c) => {
    const db = c.var.db
    const id = Number(c.req.param('id'))
    const target = await findUserById(db, id)
    if (!target) throw new HTTPException(404)            // 相当于 get_or_404(id)
    const data = c.req.valid('form')
    const email = data.email.toLowerCase()

    // 改了才需要查重
    const errors: Record<string, string[]> = {}
    if (email !== target.email && (await db.$count(users, eq(users.email, email)))) errors.email = ['该邮箱已被注册']
    if (data.username !== target.username && (await db.$count(users, eq(users.username, data.username)))) {
      errors.username = ['该用户名已被使用']
    }
    if (Object.keys(errors).length) {
      return c.render(<EditProfileAdminPage values={data} errors={errors} roles={await roleOptions(c)} />)
    }

    await db.update(users).set({ ...data, email, avatarHash: gravatarHash(email) }).where(eq(users.id, id))
    flash(c, '资料已更新。')
    return c.redirect(`/user/${data.username}`)
  },
)

GET 路由用被编辑用户的现有值填好表单，roleId 决定下拉框默认选中哪一项：

main.get('/edit-profile/:id{[0-9]+}', loginRequired, adminRequired, async (c) => {

用户头像

资料页有了文字，还缺一张头像。原书用的是 Gravatar：用户在 Gravatar 网站上把头像和邮箱绑定， 任何网站只要知道用户的邮箱，就能拼出头像的地址 —— 地址里用的是邮箱的 MD5 哈希，而不是邮箱本身。

原书表 10-1 列出了 Gravatar 的查询参数：

参数说明
s图片尺寸（像素）
r图片分级：g、pg、r、x
d没有注册头像时的默认图：404（返回 404 错误）、一个图片 URL，或者 mp、identicon、monsterid、wavatar、retro、blank 等生成器
f强制使用默认头像

Node.js 的 crypto 模块可以直接算 MD5：

import { createHash } from 'node:crypto'

export function gravatarHash(email: string) {
  return createHash('md5').update(email.trim().toLowerCase()).digest('hex')
}

export function gravatar(
  user: { email: string; avatarHash: string | null }, size = 100, defaultImage = 'identicon', rating = 'g',
) {
  const hash = user.avatarHash ?? gravatarHash(user.email)
  return `https://secure.gravatar.com/avatar/${hash}?s=${size}&d=${defaultImage}&r=${rating}`
}
ⓘ MD5 在这里是安全的吗？

MD5 早已不能用于密码哈希（太快、有碰撞攻击），但这里它只是生成一个“邮箱的代号”，用不着抗碰撞。 Gravatar 近年也开始支持 SHA-256 哈希，把 'md5' 换成 'sha256' 同样可用，列的长度要相应改成 64。 本教程保持和原书一致。另外要知道：邮箱的 MD5 可以被字典攻击反推，所以严格注重隐私的网站会让用户自己上传头像。

在资料页上显示 256 像素的大头像，导航栏里显示 18 像素的小头像：

// src/views/pages.tsx —— 资料页
<img class="rounded profile-thumbnail" src={gravatar(profile, 256)} alt="" />
<div class="profile-header">…</div>

// src/views/layout.tsx —— 导航栏里的账户菜单
<a class="nav-link dropdown-toggle" href="#" data-bs-toggle="dropdown">
  <img src={gravatar(user, 18)} alt="" /> 账户
</a>

头像的定位靠 static/styles.css 里的两个 CSS 类（和原书一样）：

.profile-thumbnail { position: absolute; }
.profile-header { min-height: 260px; margin-left: 280px; }

缓存头像哈希

原书指出：MD5 是 CPU 密集的运算，一个页面要显示几十个头像时，这些计算会累积起来。 而用户的邮箱不变，哈希就不会变，所以可以算一次，存进数据库。给 users 表加一列： 

avatarHash: varchar('avatar_hash', { length: 32 }),     // MD5 的十六进制是 32 个字符

然后在所有“邮箱可能改变”的地方同步更新它：

// createUser() 里
avatarHash: gravatarHash(email),

// changeEmail() 里
await db.update(users)
  .set({ email: newEmail, avatarHash: gravatarHash(newEmail) })
  .where(eq(users.id, user.id))

gravatar() 优先使用缓存的 avatarHash，没有时（比如缓存列加上之前注册的老用户）才现算 —— 前面的代码里已经写了 user.avatarHash ?? gravatarHash(user.email)。

🔎 深入：这个缓存值得吗？

说实话，现代 CPU 上算一次 MD5 大约只要一微秒，一个页面算一百次也就 0.1 毫秒，远远比不上一次数据库查询。 原书这一节真正的价值，是演示“把可推导的数据缓存进数据库”这个模式，以及它带来的同步负担。 以后你会遇到值得这么做的场景（比如第 11 章把 Markdown 渲染结果存进 body_html，第 13 章的评论数），权衡的方式是一样的： 计算越贵、读得越多、写得越少，就越值得缓存。

小结

  • 资料字段：varchar 限长、text 不限长；时间用 timestamp withTimezone + defaultNow()。
  • lastSeen 在每个请求的中间件里刷新，但限制为每分钟最多写一次。
  • 资料页 /user/:username：查不到就 throw new HTTPException(404)；区分被查看的 profile 和正在看的 viewer。
  • 编辑器拆成 GET（用现有值填表单）和 POST（校验、更新、Flash、重定向）；管理员编辑器的 roleId 用 z.coerce.number()，查重只在值改变时进行。
  • Gravatar 头像 = 小写邮箱的 MD5 + 查询参数；哈希缓存在 avatarHash 列，所有改邮箱的地方都要同步更新。
