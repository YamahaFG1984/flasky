第 11 章

博客文章

这一章实现 Flasky 的核心功能：写文章和读文章。途中会学到几个非常通用的技术： 用一条 JOIN 查询代替成百上千次小查询、复用页面片段、给长列表分页、 以及安全地处理用户写的富文本（Markdown）。

本章目标

  • 定义 posts 表，在首页发布和展示文章
  • 理解 N+1 查询问题，用 JOIN 和子查询一次取出文章、作者和评论数
  • 把文章列表做成可复用的组件，同时用在首页和资料页
  • 用 Faker 生成大量假数据，实现分页查询和分页导航
  • 支持 Markdown：浏览器端实时预览，服务器端转换并清洗 HTML
  • 给每篇文章一个永久链接，并允许作者和管理员编辑

发布和展示文章

一篇文章有正文、时间和作者。作者是一个指向 users 的外键，所以用户和文章之间是一对多关系：

Flask-SQLAlchemy

                          default=datetime.utcnow)
    author_id = db.Column(db.Integer,

Drizzle
export const posts = pgTable('posts', {
  id: serial('id').primaryKey(),
  body: text('body').notNull(),
  timestamp: timestamp('timestamp', { withTimezone: true })
    .notNull().defaultNow(),
  authorId: integer('author_id').notNull()

  • timestamp 加了索引：文章列表总是按时间倒序排列，有了索引数据库就不必每次都把全表排一遍序。

一次查询取出文章和作者

文章列表里每一条都要显示作者的用户名和头像。原书的模板直接写 post.author.username，SQLAlchemy 会在访问 author 时自动去查一次用户。 方便，但藏着一个性能陷阱：

Drizzle 从不在背后自动查询 —— 你要什么数据，就在查询里明确地写出来。 下面这个函数一次取出文章、作者的几个字段，还用一个子查询顺便算出评论数（评论在第 13 章实现，这里先把列准备好）： 

const authorColumns = {
  id: users.id,
  username: users.username,
  email: users.email,
  avatarHash: users.avatarHash,
}

function selectPosts(db: Db) {
  return db.select({
    id: posts.id,
    body: posts.body,
    bodyHtml: posts.bodyHtml,
    timestamp: posts.timestamp,
    authorId: posts.authorId,
    author: authorColumns,                 // 嵌套对象：结果里是 post.author.username
    commentCount: sql<number>`(select count(*) from ${comments} where ${comments.postId} = ${posts.id})`
      .mapWith(Number),
  })
    .from(posts)
    .innerJoin(users, eq(posts.authorId, users.id))
}

// 结果的类型直接从查询推导出来，不用手写
export type PostWithAuthor = Awaited<ReturnType<typeof selectPosts>>[number]

sql`…` 是 Drizzle 写原生 SQL 片段的方式（第 5 章说过：好的 ORM 要允许你随时下沉到 SQL）。 里面的 ${comments.postId} 会被正确地展开成带引号的列名，.mapWith(Number) 把 PostgreSQL 返回的 bigint 计数转成 JavaScript 数字。

生成假数据

要开发分页，就需要大量文章。手动录入太慢，原书用 Faker 这个包生成看起来很真实的名字、邮箱、段落。JavaScript 有同名的 @faker-js/faker。它只在开发时需要，所以装成开发依赖（原书为此把 requirements 拆成了 dev.txt 和 prod.txt，第 7 章讲过 npm 里对应的是 -D）： 

npm install -D @faker-js/faker

import { faker } from '@faker-js/faker'
import { count } from 'drizzle-orm'
import type { Db } from './db/index.js'
import { users } from './db/schema.js'
import { createPost } from './models/posts.js'
import { createUser } from './models/users.js'

// 用户名或邮箱撞车时，PostgreSQL 报错码 23505（唯一约束冲突）
function isUniqueViolation(err: unknown): boolean {
  const e = err as { code?: string; cause?: { code?: string } }
  return e?.code === '23505' || e?.cause?.code === '23505'
}

export async function fakeUsers(db: Db, total = 100) {
  let created = 0
  while (created < total) {
    try {
      await createUser(db, {
        email: faker.internet.email(),
        username: faker.internet.username().replace(/[^A-Za-z0-9_.]/g, '') || 'user',
        password: 'password',
        confirmed: true,
        name: faker.person.fullName(),
        location: faker.location.city(),
        aboutMe: faker.lorem.sentence(),
        memberSince: faker.date.past(),
      })
      created++
    } catch (err) {
      if (!isUniqueViolation(err)) throw err       // 重复了就跳过重来，其他错误照常抛出
    }
  }
}

export async function fakePosts(db: Db, total = 100) {
  const [{ n }] = await db.select({ n: count() }).from(users)
  for (let i = 0; i < total; i++) {
    // 随机跳过若干行再取一行 = 随机挑一个作者（原书同样用 offset）
    const [author] = await db.select({ id: users.id }).from(users)
      .offset(faker.number.int({ min: 0, max: n - 1 })).limit(1)
    await createPost(db, author.id, faker.lorem.paragraphs(2), faker.date.past())
  }
}

Faker 是随机生成的，用户名可能重复。原书的做法是提交时捕获 IntegrityError 并回滚，然后重试 —— 我们捕获数据库的“唯一约束冲突”错误，思路完全一样。 配一个命令脚本： 

import { loadConfig } from '../src/config.js'
import { createDb } from '../src/db/index.js'
import { fakePosts, fakeUsers } from '../src/fake.js'

try { process.loadEnvFile() } catch { /* 没有 .env 也行 */ }

// 用法：npm run fake -- users 100   或   npm run fake -- posts 100
const [what, n = '100'] = process.argv.slice(2)
const db = createDb(loadConfig().databaseUrl)

else if (what === 'posts') await fakePosts(db, Number(n))

分页

网站越来越大，把所有文章一次显示出来会越来越慢：生成慢、传输慢、浏览器渲染也慢。解决办法是分页：每次只取一页的数据。

在数据库里分页：LIMIT 和 OFFSET

原书用 Flask-SQLAlchemy 的 paginate()，它在底层做了两件事：用 LIMIT 和 OFFSET 只取出一页，再用 COUNT 算出总数（用来计算一共多少页）。 我们自己写一个小小的 paginate()，把这两件事包起来： 

export async function paginate<T>(
  page: number,
  perPage: number,
  count: () => Promise<number>,
  fetch: (limit: number, offset: number) => Promise<T[]>,
): Promise<Pagination<T>> {
  const current = Math.max(1, page)
  const [total, items] = await Promise.all([count(), fetch(perPage, (current - 1) * perPage)])
  return new Pagination(items, current, perPage, total)
}

// ?page=3 → 3；缺省或乱写 → 1（相当于 request.args.get('page', 1, type=int)）
export function pageParam(c: Context): number {
  const n = Number.parseInt(c.req.query('page') ?? '1', 10)
  return Number.isNaN(n) ? 1 : n
}

paginate() 不关心查的是什么，只要调用方给它两个函数：一个算总数，一个按 limit/offset 取数据。 原书的 error_out=False（页码超出范围时返回空列表而不是 404）在这里是默认行为：OFFSET 超出了，数据库自然返回空数组。

文章的分页查询，同时支持“全部文章”和“某个作者的文章”（第 12 章还会加上“关注的人的文章”）：

export async function getPostsPage(db: Db, page: number, perPage: number, filter: { authorId?: number } = {}) {
  let query = selectPosts(db).$dynamic()                        // $dynamic()：允许后面按条件追加子句
  let countQuery = db.select({ n: count() }).from(posts).$dynamic()

  if (filter.authorId !== undefined) {
    const where = eq(posts.authorId, filter.authorId)
    query = query.where(where)
    countQuery = countQuery.where(where)
  }

  return paginate(
    page,
    perPage,
    async () => (await countQuery)[0].n,
    // 时间相同时再按 id 排，保证翻页时顺序稳定、不重不漏
    (limit, offset) => query.orderBy(desc(posts.timestamp), desc(posts.id)).limit(limit).offset(offset),
  )
}

每页的数量放进配置（原书的 FLASKY_POSTS_PER_PAGE），首页的处理函数就变成：

main.get('/', async (c) => {
  const pagination = await getPostsPage(c.var.db, pageParam(c), c.var.config.postsPerPage)
  return c.render(<IndexPage user={c.var.user} pagination={pagination} />)
})
🔎 深入：OFFSET 的代价

OFFSET 100000 意味着数据库要先数过十万行再丢掉它们，页码越靠后越慢。 对于“无限滚动”这类只需要“下一页”的场景，更好的做法是键集分页（keyset / cursor pagination）： 记住上一页最后一条的时间和 id，下一页查 WHERE (timestamp, id) < (上次的值) ORDER BY … LIMIT 20，走索引直接定位，不管翻多深都一样快。 它的缺点是没法直接跳到“第 37 页”，所以原书这种带页码的导航仍然用 OFFSET。

分页导航

原书的 paginate() 返回一个 Pagination 对象，里面有模板生成页码链接需要的一切。我们照着写一个同名的类：

Flask-SQLAlchemy 属性 / 方法我们的 Pagination说明
itemsitems当前页的记录
page / per_page / total同名（驼峰）当前页码、每页条数、总条数
pagespages总页数
has_prev / has_nexthasPrev / hasNext有没有上一页 / 下一页
prev_num / next_numprevNum / nextNum上一页 / 下一页的页码
iter_pages()iterPages()分页导航里要显示哪些页码
 
export class Pagination<T> {
  constructor(public items: T[], public page: number, public perPage: number, public total: number) {}

  get pages() { return Math.max(1, Math.ceil(this.total / this.perPage)) }
  get hasPrev() { return this.page > 1 }
  get hasNext() { return this.page < this.pages }
  get prevNum() { return this.hasPrev ? this.page - 1 : null }
  get nextNum() { return this.hasNext ? this.page + 1 : null }

  // null 表示“这里省略了一段”，导航里显示成 …
  *iterPages(leftEdge = 2, leftCurrent = 2, rightCurrent = 5, rightEdge = 2): Generator<number | null> {
    let last = 0
    for (let num = 1; num <= this.pages; num++) {
      if (
        num <= leftEdge ||                                                  // 最左边的几页
        (num >= this.page - leftCurrent && num < this.page + rightCurrent) ||  // 当前页附近
        num > this.pages - rightEdge                                        // 最右边的几页
      ) {
        if (last + 1 !== num) yield null
        yield num
        last = num
      }
    }
  }
}

原书把分页导航写成一个 Jinja2 宏 pagination_widget(pagination, endpoint, **kwargs)，额外的关键字参数原样传给 url_for()，这样资料页这种带 username 参数的地址也能用。 我们的组件更直接：让调用方传一个 href 函数，告诉组件“第 n 页的地址是什么”： 

export function PaginationWidget<T>({ pagination: p, href, fragment = '' }: {
  pagination: Pagination<T>
  href: (page: number) => string
  fragment?: string                      // 第 13 章用来加上 #comments
}) {
  return (
    <nav aria-label="分页">
      <ul class="pagination">
        <li class={`page-item${p.hasPrev ? '' : ' disabled'}`}>
          <a class="page-link" href={p.hasPrev ? href(p.page - 1) + fragment : '#'}>&laquo;</a>
        </li>
        {[...p.iterPages()].map((n) =>
          n === null ? (
            <li class="page-item disabled"><span class="page-link">&hellip;</span></li>
          ) : (
            <li class={`page-item${n === p.page ? ' active' : ''}`}>
              <a class="page-link" href={href(n) + fragment}>{n}</a>
            </li>
          ),
        )}
        <li class={`page-item${p.hasNext ? '' : ' disabled'}`}>
          <a class="page-link" href={p.hasNext ? href(p.page + 1) + fragment : '#'}>&raquo;</a>
        </li>
      </ul>
    </nav>
  )
}

服务器端：转换并清洗

原书讲得很清楚：表单提交时只发送 Markdown 源文本，浏览器里的预览 HTML 直接扔掉。 因为攻击者完全可以绕过浏览器，直接提交任意 HTML。服务器必须自己把 Markdown 再转换一次，并用白名单清洗结果： 

import { marked } from 'marked'
import sanitizeHtml from 'sanitize-html'

const POST_TAGS = ['a', 'abbr', 'acronym', 'b', 'blockquote', 'code', 'em', 'i',
  'li', 'ol', 'pre', 'strong', 'ul', 'h1', 'h2', 'h3', 'p']

function renderMarkdown(source: string, allowedTags: string[]) {
  const html = marked.parse(source, { async: false, gfm: true })      // gfm：裸网址自动变链接
  return sanitizeHtml(html, {
    allowedTags,
    allowedAttributes: { a: ['href', 'title'] },
  }).trim()
}

export const postBodyHtml = (body: string) => renderMarkdown(body, POST_TAGS)

转换每次显示都做一遍太浪费，原书把结果缓存在新的 body_html 列里，并用 SQLAlchemy 的事件监听器实现“正文一变，HTML 自动重新生成”。 Drizzle 没有这种隐式的事件机制，我们在写入正文的两个函数里显式地同时写入 HTML —— 所有修改正文的代码都经过这两个函数，效果一样，而且一眼就能看出发生了什么： 

// schema.ts 的 posts 表里加一列：bodyHtml: text('body_html'),

export async function createPost(db: Db, authorId: number, body: string, timestamp?: Date) {
  const [post] = await db.insert(posts)
    .values({ body, bodyHtml: postBodyHtml(body), authorId, timestamp })
    .returning()
  return post
}

export async function updatePost(db: Db, id: number, body: string) {
  await db.update(posts).set({ body, bodyHtml: postBodyHtml(body) }).where(eq(posts.id, id))
}

文章列表里优先显示 bodyHtml；它是服务器清洗过的，所以可以用 raw() 原样输出（相当于原书的 {{ post.body_html | safe }}）：

<div class="post-body">
  {/* body_html 是服务器清洗过的，才能用 raw() 原样输出 */}
  {post.bodyHtml ? raw(post.bodyHtml) : post.body}
</div>
⚠ raw() 的安全，完全建立在“写入时清洗过”之上

如果以后有人写了一段新代码，绕过 createPost / updatePost 直接往 body_html 里写东西，XSS 漏洞就出现了。 所以请把“只能通过这两个函数修改文章”当成一条团队规则；第 14 章的 API 也会复用它们。 另外，post.body 作为兜底（旧文章还没有 body_html）时没有用 raw()，会被正常转义，是安全的。

文章的永久链接

用户会想把某篇文章分享给朋友，所以每篇文章都需要一个独立的页面和固定的地址。用文章的 id 构造 URL 最简单：

main.get('/post/:id{[0-9]+}', async (c) => {
  const post = await getPost(c.var.db, Number(c.req.param('id')))
  if (!post) throw new HTTPException(404)
  return c.render(<PostList posts={[post]} user={c.var.user} />, { title: '文章' })
})

export async function getPost(db: Db, id: number) {
  const [post] = await selectPosts(db).where(eq(posts.id, id))
  return post ?? null
}

原书这里用了一个小技巧：给详情页模板传一个只有一个元素的列表 posts=[post]，这样就能直接复用 _posts.html。 我们同样把 [post] 传给 PostList 组件。然后在每篇文章底部加上永久链接： 

<div class="post-footer">
  <a href={`/post/${post.id}`}><span class="badge text-bg-secondary">永久链接</span></a>
</div>
💡 用 slug 代替数字 id

原书提到，有些网站喜欢用可读的地址，比如 /post/learning-drizzle-relations。这个可读的部分叫 slug，通常由标题转换而来。 实现方法：给 posts 表加一个 slug 列并加唯一索引，路由改成 /post/:slug。 常见的折中是两者都要：/post/42/learning-drizzle，按 id 查找，slug 只是给人看的。

编辑文章

最后一个功能：作者可以编辑自己的文章，管理员可以编辑任何人的文章。编辑页和首页一样有 Markdown 预览：

async function loadEditablePost(c: Context<AppEnv>) {
  const post = await getPost(c.var.db, Number(c.req.param('id')))
  if (!post) throw new HTTPException(404)
  const user = requireUser(c)
  // 不是作者、也不是管理员 → 403
  if (user.id !== post.authorId && !can(user, Permission.ADMIN)) throw new HTTPException(403)
  return post
}

main.get('/edit/:id{[0-9]+}', loginRequired, async (c) => {
  const post = await loadEditablePost(c)
  return c.render(<EditPostPage values={{ body: post.body }} />,     // 编辑的是 Markdown 源文本
    { title: '编辑文章', scripts: <MarkdownPreviewScripts /> })
})

main.post(
  '/edit/:id{[0-9]+}',
  loginRequired,
  validateForm(postSchema, (c, values, errors) =>
    c.render(<EditPostPage values={values} errors={errors} />, { scripts: <MarkdownPreviewScripts /> })),
  async (c) => {
    const post = await loadEditablePost(c)             // POST 时也要再检查一次权限！
    await updatePost(c.var.db, post.id, c.req.valid('form').body)
    flash(c, '文章已更新。')
    return c.redirect(`/post/${post.id}`)
  },
)

最后在文章底部加上“编辑”链接。作者看到蓝色的“编辑”，管理员看到红色的“编辑 [管理员]”，用不同样式提示这是管理功能（原书例 11-22）：

{user?.id === post.authorId ? (
  <a href={`/edit/${post.id}`}><span class="badge text-bg-primary">编辑</span></a>
) : isAdministrator(user) ? (
  <a href={`/edit/${post.id}`}><span class="badge text-bg-danger">编辑 [管理员]</span></a>
) : null}

小结

  • posts 表通过 authorId 外键和 users 形成一对多；timestamp 加索引，删用户时级联删除文章。
  • Drizzle 不会自动懒加载，用 innerJoin + 嵌套选择 + 子查询一次取齐列表需要的所有数据，避免 N+1。
  • 重复的页面片段做成组件（PostList），相当于 {% include %}；详情页传 [post] 复用它。
  • 分页 = LIMIT/OFFSET + COUNT；Pagination 类提供导航需要的属性，iterPages() 决定显示哪些页码。
  • Markdown：浏览器端 marked + DOMPurify 预览；服务器端只信任源文本，marked 转换后用 sanitize-html 白名单清洗，结果缓存在 bodyHtml。
  • 编辑权限在 GET 和 POST 两处都要检查。
