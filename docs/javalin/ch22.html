第三方登录与两步验证

第 8 章的认证只有一样东西：密码。这一章加两条路 —— 用 GitHub 账号登录（少记一个密码）， 和两步验证（密码泄露了也进不来）。 两个功能都是「照着抄很容易、抄错了很难发现」的典型， 所以本章花很多篇幅在每一步防的是什么攻击上。

本章目标

  • 讲清 OAuth2 授权码流程的每一步，以及 state 和 PKCE 各自防什么
  • 知道第三方登录最危险的那一步是「按邮箱关联已有账号」
  • 自己实现 TOTP，并用 RFC 6238 的官方向量验证它
  • 理解「密码过了但第二步没过」这个中间态为什么绝不能等于登录态
  • 知道为什么必须有恢复码，以及为什么必须防重放
  • 在测试里自己起一个假的服务商，把所有失败分支都覆盖掉

OAuth2：到底在干什么

先把名词理清楚，因为这是最容易混的地方：

☀ OAuth2 是授权协议，不是认证协议

OAuth2 回答的问题是「这个应用能不能代表用户去访问某些资源」。 「这个用户是谁」是我们借用它顺便做的 —— 拿到令牌之后再调一次「给我看看你是谁」的接口。

真正为认证设计的是 OpenID Connect（OIDC）， 它在 OAuth2 上加了一个签名的 id_token。 Google、微软、Keycloak 都支持 OIDC；GitHub 只有纯 OAuth2。 本章走的是通用的 OAuth2 路线，因为它到哪都能用。

⚠ 为什么要绕这么一大圈：code 和 token 的区别

最直观的设计是 GitHub 直接把 access_token 放在跳转地址里送回来 （历史上确实有这种模式，叫 implicit flow，现在已经不推荐了）。 问题是跳转地址会出现在：浏览器历史、Referer 头、 服务器访问日志、代理日志……令牌等于到处都是。

授权码流程把它拆成两半：跳转地址里只有一个一次性、短期有效的 code，拿它换令牌时还要出示只有服务端知道的 client_secret。所以就算 code 泄露了，别人也换不走。

两个防护：state 和 PKCE

statePKCE（code_verifier）
防什么 登录 CSRF：攻击者把自己的授权码塞给受害者， 让受害者在不知情的情况下登进攻击者的账号（之后受害者填的信息都进了攻击者手里） 授权码被截获：移动端/SPA 的回调可能被别的应用抢注， 拿到 code 就能换令牌
怎么工作 发起时生成随机串存会话，回调时比对 发起时送 SHA256(verifier)，换令牌时出示 verifier 原文
后端应用也要吗 必须 理论上有 client_secret 就够了，但 OAuth 2.1 要求所有客户端都用， 而且加上几乎零成本
private void oauthStart(Context ctx) {
    var provider = providerOrNull(ctx.pathParam("provider"));
    if (provider == null) throw new NotFoundResponse("没有配置这个登录方式");

    // state 防 CSRF：回调时必须带回同一个值，证明这次回调是我们发起的。
    // 少了它，攻击者可以把自己的授权码塞给受害者，把受害者的账号绑到自己头上。
    String state = OAuthClient.randomUrlSafe();
    // PKCE 的 verifier 防「授权码被截获」：换令牌时要出示它
    String verifier = OAuthClient.randomUrlSafe();

    ctx.sessionAttribute(OAUTH_STATE, state);
    ctx.sessionAttribute(OAUTH_VERIFIER, verifier);
    ctx.sessionAttribute(OAUTH_NEXT, safeNext(ctx, Routes.INDEX));

    ctx.redirect(services.oauth().authorizeUrl(
        provider, redirectUri(ctx, provider.name()),
        state, OAuthClient.codeChallenge(verifier)));
}
⚠ 回调地址必须从配置里取，不能从请求里拼
// ❌ 看着很聪明，实际是个洞
String redirectUri = ctx.scheme() + "://" + ctx.host() + "/auth/oauth/github/callback";

// ✅
private String redirectUri(Context ctx, String providerName) {
    return cfg.siteBaseUrl() + "/auth/oauth/" + providerName + "/callback";
}

Host 头是客户端可控的。攻击者伪造一个 Host: evil.com，你就把回调地址拼成了他的域名 —— 授权码直接送上门。（服务商那边登记的回调白名单能挡住一部分， 但不是所有服务商都严格匹配。）

这和第 17 章「behindProxy 必须是显式配置」是同一类问题： 凡是从请求头推导出来的「自己的身份」，都是不可信的。

最危险的一步：找到或创建本地账号

拿到 {id, email, login} 之后，怎么对应到本地账号？ 顺序决定安全性。 

/**
 * 找到或创建本地账号。
 * 顺序很重要：先按服务商 id 找，找不到才考虑按邮箱关联。
 */
private User linkOrCreate(Context ctx, String providerName,
                          OAuthClient.ExternalUser external) {
    var em = Db.em(ctx);

    // ① 这个 GitHub 账号以前绑过吗
    var existing = em.createQuery("""
            select i.user from OAuthIdentity i
             where i.provider = :p and i.providerUserId = :id
            """, User.class)
        .setParameter("p", providerName)
        .setParameter("id", external.providerId())
        .getResultStream().findFirst();
    if (existing.isPresent()) return existing.get();

    String email = external.email() == null ? null : external.email().toLowerCase();
    if (email == null || email.isBlank()) {
        // 很多服务商默认不给邮箱（GitHub 的邮箱可以设为私密）。
        // 没有邮箱就没法安全地关联已有账号 —— 让用户先用密码登录再去绑定。
        Flash.danger(ctx, "没能从第三方拿到你的邮箱，请先用密码登录后在设置里绑定。");
        return null;
    }

    // ② 本地有同邮箱的账号吗
    var byEmail = services.users(ctx).findByEmail(email);
    if (byEmail.isPresent()) {
        User user = byEmail.get();
        if (!user.isConfirmed()) {
            Flash.danger(ctx, "这个邮箱对应的账号还没有验证，请先完成邮箱验证。");
            return null;
        }
        em.persist(new OAuthIdentity(user, providerName, external.providerId()));
        return user;
    }

    // ③ 全新用户
    String username = uniqueUsername(ctx, external.name(), email);
    User user = new User(email, username);
    user.setPassword(OAuthClient.randomUrlSafe());   // 随机密码 = 只能用第三方登录
    user.setConfirmed(true);
    user.setRole(services.roles(ctx).defaultRole());
    /* ... */
}
⚠ 「按邮箱自动关联」是一个真实存在的账号接管手法

想象这个攻击：

  1. 攻击者知道受害者的邮箱是 victim@example.com
  2. 攻击者用这个邮箱在你的站上注册 —— 但不去验证邮箱 （他也收不到验证信）
  3. 一段时间后，受害者用自己的 GitHub 登录。GitHub 返回的邮箱正是 victim@example.com
  4. 如果你无条件「按邮箱关联」，受害者的 GitHub 就被绑到了攻击者创建的那个账号上。 攻击者用他当初设的密码随时能登进去，看到受害者之后的一切活动

所以代码里那一句 if (!user.isConfirmed()) 不是在挑剔， 它是这段逻辑里最重要的一行。 配套测试里专门有一条 不会关联到未验证邮箱的已有账号 盯着它。

更严格的做法是完全不自动关联：发现同邮箱就要求用户 「先用密码登录，再到设置里手动绑定」。GitHub 和 Google 自己用的就是这种。 本章选了「已验证邮箱才自动关联」这个折中， 因为它在体验和安全之间的位置比较常见 —— 但你要知道它是个取舍。

ⓘ 为什么用服务商的 id 而不是邮箱当主键

oauth_identities 表上那条唯一索引是 (provider, provider_user_id)，不是邮箱。原因： 邮箱会变，用户名会变，只有数字 id 不变。

用邮箱当关联键的后果是：用户在 GitHub 上改了邮箱， 下次登录你的站就认不出他了，于是又建了一个新账号。

两步验证：TOTP 是怎么算出来的

认证器 App 里那个每 30 秒跳一次的六位数，原理比想象中简单得多 —— 而且手机和服务器之间不需要任何通信： 

public static String code(byte[] key, long counter, int digits) {
    byte[] data = new byte[8];
    for (int i = 7; i >= 0; i--) {          // 计数器按大端写成 8 字节
        data[i] = (byte) (counter & 0xFF);
        counter >>>= 8;
    }

    Mac mac = Mac.getInstance("HmacSHA1");
    mac.init(new SecretKeySpec(key, "HmacSHA1"));
    byte[] hash = mac.doFinal(data);

    // 「动态截断」：用最后一个字节的低 4 位决定从哪里取 4 个字节。
    // 这一步是为了让结果均匀，不要总是取同一段。
    int offset = hash[hash.length - 1] & 0x0F;
    int binary = ((hash[offset]     & 0x7F) << 24)
               | ((hash[offset + 1] & 0xFF) << 16)
               | ((hash[offset + 2] & 0xFF) << 8)
               |  (hash[offset + 3] & 0xFF);

    int mod = (int) Math.pow(10, digits);
    return String.format("%0" + digits + "d", binary % mod);
}
☀ 自己实现密码学相关的东西，必须拿官方向量对一遍

「我这边跑着像是对的」完全不算数：算法差一位，结果照样是六位数字， 看不出任何异常，但用户永远登不进来 —— 而且你会先怀疑用户的手机时间。

RFC 6238 附录 B 给了一张表，照抄成测试就行： 

/** RFC 6238 附录 B 规定的种子：ASCII 的 "12345678901234567890" */
private static final byte[] RFC_SEED =
    "12345678901234567890".getBytes(StandardCharsets.US_ASCII);

@Test
void 符合RFC6238的官方测试向量() {
    assertCode("94287082", 59L);
    assertCode("07081804", 1111111109L);
    assertCode("14050471", 1111111111L);
    assertCode("89005924", 1234567890L);
    assertCode("69279037", 2000000000L);
    assertCode("65353130", 20000000000L);
}

这六行测试的价值，超过其余所有 TOTP 测试加起来 —— 它们证明的是「我的实现和全世界的认证器 App 算的是同一个东西」。

⚠ 比较验证码必须用常量时间
// ❌ 第一个字符不同就返回 —— 耗时泄露了「前几位对了」
if (expected.equals(input)) { ... }

// ✅
if (MessageDigest.isEqual(expected.getBytes(UTF_8), input.getBytes(UTF_8))) { ... }

攻击者反复提交、测量响应时间的微小差异，理论上能一位一位地把码试出来 —— 六位数从 10⁶ 次尝试降到 10×6 次。这叫计时攻击。

网络抖动会让这件事在真实环境里很难做成，但这是一行代码的成本。 凡是比较密钥、令牌、哈希、验证码，都用 MessageDigest.isEqual。

真正难的是状态机

算法有 RFC 兜底，容易写错的是「密码过了、第二步还没过」这个中间态。 

// 第 22 章：开了两步验证的话，密码只是第一步。

☀ 一个经典的真实漏洞：第二步形同虚设

有一类反复出现的 2FA 漏洞是这样的：登录成功后就先把用户登录了， 然后跳到验证码页面「挡」一下。于是攻击者只要 不访问那个页面，直接去 /edit-profile，就进去了 —— 两步验证完全没起作用。

所以配套测试里第一条就是盯这个的： 

var res = postFormWithCsrf(client, "/auth/login", "/auth/login",
    form("email", "john@example.com", "password", "cat12345"));
assertThat(res.headers().get("Location").get(0)).contains("/auth/2fa");

// 关键断言：这时候还不是登录态
var home = client.get("/edit-profile", req -> req.header("Accept", "text/html"));
assertThat(home.code())
    .as("待验证状态绝不能等于已登录")
    .isIn(302, 401);

另外两个容易漏的：待验证状态要有超时（这里是 5 分钟）， 以及验证码也要限流 —— 六位数只有一百万种可能，不限流的话几分钟就能爆破完， 那还不如不开两步验证。

防重放：同一个码不能用两次

long slot = Totp.verify(user.getTotpSecret(), cleaned, now.getEpochSecond());
if (slot != -1) {
    Long last = user.getTotpLastSlot();
    // 同一个时间片只认一次。不做这一步的话，攻击者在用户登录后的
    // 30 秒内拿到同一个码（肩窥、中间人、剪贴板）就能再登一次。
    if (last != null && slot <= last) return Result.REPLAYED;
    user.setTotpLastSlot(slot);
    return Result.OK;
}

Totp.verify 返回的不是布尔值，而是匹配上的那个时间片编号 —— 就是为了让调用方能记下来。这个设计上的小决定，是防重放能成立的前提。

恢复码：必须有的那条后路

测试：自己起一个假的服务商

第三方登录看起来「必须连外网才能测」。其实不是 —— 所谓服务商就是几个 HTTP 端点，在测试里用 Javalin 自己起一个就行。 

/** 假服务商：记下收到的参数，好断言我们发出去的请求是对的 */
private void startFakeProvider() {
    fakeProvider = Javalin.create(config -> {
        config.routes.post("/token", ctx -> {
            received.put("code", String.valueOf(ctx.formParam("code")));
            received.put("code_verifier", String.valueOf(ctx.formParam("code_verifier")));
            received.put("client_secret", String.valueOf(ctx.formParam("client_secret")));
            ctx.status(tokenStatus).contentType("application/json").result(tokenResponse);
        });
        config.routes.get("/userinfo", ctx -> {
            received.put("authorization", String.valueOf(ctx.header("Authorization")));
            ctx.status(userStatus).contentType("application/json").result(userResponse);
        });
    }).start(0);
    providerPort = fakeProvider.port();
}
☀ 这个做法的三个好处
  1. 能断言「我们发出去的请求对不对」。 code_verifier 有没有带上？client_secret 对不对？ 用 mock 库也能做，但假服务商测的是真实的 HTTP 报文， 连「GitHub 默认返回表单编码、要显式要 JSON」这种细节都能覆盖。
  2. 失败分支随便造。换令牌返回 401、用户信息里 email 是 null、对方超时 —— 改一个字段就行。 这些分支在真实环境里几乎没法复现， 但线上恰恰是它们出问题。
  3. 不需要网络，不需要密钥。CI 上能跑，而且永远不会因为 GitHub 抽风而变红。

为此 OAuthClient.Provider 把四个 URL 做成了配置项 （而不是写死常量）。「为了能测而留的接缝」几乎总是也让代码更灵活 —— 这里顺带就支持了 GitLab、Gitea 这些自托管的服务商。
