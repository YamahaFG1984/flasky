TypeScript 对照

很多人是从 TypeScript 过来的，而不是 Python。 对这些人来说 Java 的障碍不是「静态类型」—— 那个早就熟了 —— 而是两套类型系统在哲学上的差别： 结构 vs 名义、擦除 vs 具化、strictNullChecks vs 一个三十年的历史包袱。 这份附录把同一个问题用两边各写一遍。

ⓘ 一句话先定调

TypeScript 的类型是「写给编译器看的注解」，运行时全部消失； Java 的类型是「运行时真实存在的东西」—— 除了泛型参数，它也擦除。

这一句能解释这份附录里八成的差别。

同题一：定义一个数据结构

TypeScript
interface Post {
  id: number;
  body: string;
  authorName: string;
  commentCount: number;
}

// 任何「形状对得上」的对象都是 Post
const p: Post = {
  id: 1, body: "...",
  authorName: "john", commentCount: 3
};
Java
public record Post(
    long id,
    String body,
    String authorName,
    long commentCount
) {}

// 必须显式 new 这个类型
var p = new Post(1, "...", "john", 3);

// 字段访问没有 get 前缀
p.body();
☀ 最根本的差别：结构类型 vs 名义类型

TypeScript 是结构类型（structural）：只要字段对得上就是同一个类型， 不管它叫什么、从哪来。

Java 是名义类型（nominal）：record UserId(long v) 和 record PostId(long v) 字段完全一样，但互相不能赋值。

这听起来像是 Java 更啰嗦，但它换来一个 TS 要费劲才能做到的事： 

// Java：天然不会把 userId 传给要 postId 的方法
void deletePost(PostId id) { ... }
deletePost(userId);        // ❌ 编译不过

// TypeScript：要靠 branded type 这种技巧才能模拟
type PostId = number & { readonly __brand: 'PostId' };

反过来，TS 的结构类型让「临时拼一个对象传进去」非常自然， Java 这边你得先有一个类。两种风格各有代价。

同题二：处理「可能没有」

TypeScript（开了 strictNullChecks）
function findUser(email: string): User | undefined

const u = findUser(e);
u.name;              // ❌ 编译器拦住你

u?.name ?? "匿名";    // ✅

if (u) {
  u.name;            // ✅ 收窄之后就安全了
}
Java
Optional<User> findByEmail(String email)

var u = users.findByEmail(e);
u.getName();         // ❌ 但错在「Optional 没这方法」

u.map(User::getName).orElse("匿名");     // ✅

if (u.isPresent()) {
    u.get().getName();                   // ✅ 但没有类型收窄
}
⚠ Java 的空安全是约定，不是类型系统

这是 TS 程序员最容易踩的地方。TS 的 strictNullChecks 把 null | undefined 做进了类型系统，编译器真的拦得住。

Java 没有。String name 这个类型随时可能是 null， 编译器一个字都不会说。Optional<T> 只是一个普通的类， 而且它自己也可能是 null（Optional<User> u = null; 完全合法）。

Java 这边的现实做法是靠约定：

  • 返回值可能没有 → 用 Optional<T> （本教程的仓储层都是这样，见第 5 章）
  • 参数和字段 → 不要用 Optional， 用 @Nullable 注解表达意图，再靠 IDE 和 SpotBugs 检查
  • 靠 Java 14+ 的有用的 NPE 消息兜底： Cannot invoke "User.getName()" because "user" is null —— 至少它会告诉你是哪个变量

另外注意：Java 没有类型收窄。 if (u != null) 之后 u 的类型还是原来那个， 编译器不会因此放宽任何检查 —— 因为它本来就没检查。

同题三：泛型

TypeScript
interface Page<T> {
  items: T[];
  total: number;
}

// 类型在运行时不存在，但也没人需要它
function isStringArray(x: unknown): x is string[] {
  return Array.isArray(x)
      && x.every(i => typeof i === "string");
}
Java
public record Page<T>(
    List<T> items,
    long total
) {}

// 泛型参数在运行时被擦除了
List<String> a = new ArrayList<>();
List<Integer> b = new ArrayList<>();
a.getClass() == b.getClass();   // true !

if (x instanceof List<String>) {}   // ❌ 编译不过
ⓘ 两边都擦除，但 Java 的擦除更让人难受

TS 擦除得彻底，所以大家从一开始就不指望运行时有类型，习惯了用 zod 这类库在边界上做校验。

Java 擦除得不彻底 —— 类是具化的（instanceof User 没问题）， 只有泛型参数被擦掉了。这个不一致会在几个地方咬你： 

new T()                       // ❌ 不能这么干
new List<String>[10]          // ❌ 不能创建泛型数组
catch (MyException<T> e)      // ❌ 不能捕获泛型异常

// 所以 API 里经常要多传一个 Class<T> —— 看着冗余，是擦除逼的
ctx.bodyAsClass(PostDto.class)
ctx.queryParamAsClass("page", Integer.class)
em.createQuery(jpql, Post.class)

每次你在 Java API 里看到一个 Xxx.class 参数， 基本都是在给擦除打补丁。

同题四：等一个慢操作

TypeScript / Node
async function handler(req, res) {
  const user  = await db.findUser(id);
  const posts = await db.findPosts(user.id);
  res.json({ user, posts });
}

// 并行
const [user, posts] = await Promise.all([
  db.findUser(id),
  db.findPosts(id),
]);
Java（虚拟线程）
void handler(Context ctx) {
    var user  = users.findById(id).orElseThrow();
    var posts = postRepo.findByAuthor(user);
    ctx.json(Map.of("user", user, "posts", posts));
}
// 没有 async，没有 await —— 就是普通的阻塞代码

// 并行
try (var scope = new StructuredTaskScope
                     .ShutdownOnFailure()) {
    var u = scope.fork(() -> users.findById(id));
    var p = scope.fork(() -> postRepo.findByAuthor(id));
    scope.join().throwIfFailed();
    // u.get() / p.get()
}
☀ 虚拟线程消灭了「函数颜色」问题

TS/Node 里一个函数是不是 async 会传染： 调用 async 函数的函数也得是 async，一路往上。 这就是著名的 "What Color is Your Function"。

Java 21 的虚拟线程把调度做在了 JVM 层：阻塞的是虚拟线程， 不是操作系统线程。所以你写最朴素的阻塞代码， JDBC、InputStream、Thread.sleep() 一行不改， 就拿到了和 async 一样的吞吐。没有颜色，也没有生态分裂。

代价在第 19 章：Node 是单线程事件循环， 你几乎不用想数据竞争；Java 是真并发， 共享可变状态必须自己同步。两边各自放弃了一样东西。

同题五：处理一个列表

TypeScript
const names = users
  .filter(u => u.confirmed)
  .map(u => u.name)
  .sort();

const byId = new Map(users.map(u => [u.id, u]));

const total = posts.reduce((s, p) => s + p.views, 0);

const grouped = Object.groupBy(posts, p => p.authorId);
Java
var names = users.stream()
    .filter(User::isConfirmed)
    .map(User::getName)
    .sorted()
    .toList();

var byId = users.stream()
    .collect(Collectors.toMap(User::getId, u -> u));

long total = posts.stream().mapToLong(Post::getViews).sum();

var grouped = posts.stream()
    .collect(Collectors.groupingBy(Post::getAuthorId));
TypeScriptJava Stream注意
.filter().filter()一样
.map().map()一样
.find().filter(...).findFirst()返回 Optional
.some() / .every().anyMatch() / .allMatch()—
.reduce().reduce() 或 .collect()数值用 mapToLong().sum() 更快
.flatMap().flatMap()Java 要返回 Stream 不是数组
.sort().sorted(Comparator.comparing(...))TS 的 sort 原地改，Java 不改原集合
[...a, ...b]Stream.concat(a.stream(), b.stream())Java 没有展开语法
arr.lengthlist.size() / arr.length数组是字段，集合是方法
⚠ 三个会绊一下的差别
  1. Stream 只能用一次。 var s = list.stream(); 之后用两次会抛 IllegalStateException: stream has already been operated upon or closed。 它不是集合，是一次性的管道。
  2. 必须有终结操作。.filter() 本身什么都不做， 要 .toList() / .forEach() / .collect() 才真正执行。 少写一个，整条链路静悄悄地不跑。
  3. List.of() 造出来的是不可变的。 往里 add 会抛 UnsupportedOperationException。 要可变的用 new ArrayList<>(List.of(...))。

同题六：错误处理

TypeScript
try {
  await save(post);
} catch (e) {
  // e 的类型是 unknown，要自己收窄
  if (e instanceof ValidationError) { ... }
}

// 函数签名里看不出会抛什么
function save(p: Post): Promise<void>
Java
try {
    save(post);
} catch (ValidationException e) {   // 类型直接写在这
    ...
} catch (IOException | SQLException e) {   // 可以合并
    ...
}

// 受检异常必须写进签名
void save(Post p) throws IOException
ⓘ 受检异常：Java 独有，而且争议很大

Java 把异常分成两类：受检（IOException 这种， 必须 catch 或者在签名里声明）和非受检 （RuntimeException 的子类，随便抛）。

设计初衷是「强迫你处理可恢复的错误」，实践中招来的抱怨多过好处 —— 最常见的结果是满屏的 catch (Exception e) { throw new RuntimeException(e); }。 后来的语言（C#、Kotlin、TypeScript）都没有抄这个设计。

本教程的做法和主流一致：业务异常一律用非受检的 （NotFoundResponse、ForbiddenResponse 都是 RuntimeException 的子类）， 让它们一路冒泡到 Javalin 的异常处理器。

⚠ 没有锁文件这件事值得单独警惕

package-lock.json 保证「今天装的和上个月装的一模一样」。 Maven 没有这个概念：只要你的依赖声明了一个版本范围， 或者某个传递依赖更新了，两次构建的 classpath 就可能不同。

Java 这边的替代方案：

  • 永远写死版本号，不要用 [1.0,2.0) 这种范围
  • 用 BOM 统一管理一组相关依赖的版本（第 8 章的 jackson-bom）
  • mvn dependency:tree 定期看一眼仲裁结果
  • 严格要求可复现的话，用 maven-enforcer-plugin 的 dependencyConvergence 规则， 让「同一个库出现两个版本」直接构建失败

☀ 从 TS 过来，真正要调整的是三件事
  1. 不要指望编译器帮你管 null。 这是最大的落差，而且是单向的 —— 你会怀念 strictNullChecks。 把「返回值用 Optional、参数不用」变成肌肉记忆。
  2. 开始想并发。 Node 替你挡掉了数据竞争，Java 不会。 任何一个 static 字段、任何一个传进构造器的对象， 都可能被多个线程同时读写。第 19 章整章在讲这个。
  3. 依赖冲突是一种新病。 NoSuchMethodError 在 npm 世界里几乎不存在 （因为同名库可以共存），在 Java 里是家常便饭。 见到它先想版本，别怀疑自己的代码。

反过来，你会立刻喜欢上的：一个 JAR 就能部署 （不用 node_modules、不用管 Node 版本）、 IDE 的重构是真的可靠（名义类型 + 具化的类）， 以及模板在编译期就查错（第 3 章的 JTE）。
