Flask → Javalin 对照

“我在 Flask 里是这么写的，Javalin 怎么写？”——这份附录就是回答这个问题的。 按功能点排列，每一条都给出两边的写法和对应的章节。 第三列「不只是换语法」标记的是那些观念上真有差别的地方， 别只照着抄语法，那几条值得回去读原章节。

ⓘ 怎么用这份表

表里的 Flask 写法以原书《Flask Web 开发》用到的为准 （Flask 2.x + Flask-SQLAlchemy + Flask-WTF + Flask-Login）。 Javalin 一侧的写法全部来自本教程的配套代码，版本是 Javalin 7.2.3 / JTE 3.2.4 / Hibernate 7.4.2。

⚠ 不只是换语法：url_for 没有对应物

Flask 的 url_for 是运行时反查：改了 @app.route 的路径，所有 url_for 自动跟着变， 但写错端点名要到运行时才报错。

Javalin 没有这个机制。本教程的做法是自己写一个 Routes 常量类（第 3 章），用编译期检查换掉运行时反查： 改了路径只需要改一处，而写错名字当场编译不过。 这是 Java 这边一个典型的取舍 —— 少一点魔法，多一点编译器帮忙。

☀ 最大的手感差别：处理器不返回响应

Flask 的处理器 return 一个值，框架拿去变成响应。 Javalin 的处理器签名是 void handle(Context ctx) —— 响应是通过往 ctx 上写来构造的。

实际影响有两个。一是 return 在 Javalin 里只表示「这个方法结束了」， 不表示「响应定了」—— 所以写校验分支时必须记得 return， 漏了就会继续往下执行并覆盖掉刚写的响应。二是任何拿到 ctx 的地方（过滤器、异常处理器）都能改响应，比 Flask 灵活， 但也意味着「谁最后写的谁说了算」。

☀ 不只是换语法：JTE 的模板是编译成 Java 类的

Jinja2 的模板是运行时解释的字符串，变量名写错、字段不存在， 要等到那个页面被访问时才报错 —— 而且往往是在生产环境。

JTE 把每个 .jte 编译成一个 Java 类，@param 就是方法参数。 拼错字段名、传错类型、漏传参数，mvn compile 当场失败并指出模板的行号。 代价是模板里不能随便发明过滤器 —— 想要什么逻辑，写成 Java 方法再调。

这也是为什么本教程到处在用「页面模型 record」（PostListPage、 UserProfilePage）：把展示用的数据先算好，模板只负责摆放。

⚠ 不只是换语法：三个真会咬人的差别
  1. 没有 db.session 这个全局对象。 Flask-SQLAlchemy 的 session 是一个和请求绑定的代理，随手就能用。 JPA 的 EntityManager 不是线程安全的， 必须每个请求一个 —— 这就是 UnitOfWork 过滤器存在的原因（第 5、19 章）。
  2. 改了就会写回去。托管状态的实体，改一个字段在事务提交时 就会发 UPDATE，你没调任何 save。 这叫脏检查，很方便，但也意味着「临时改一下用来显示」会真的进库。
  3. create_all() 这条路本教程直接封死了。 让 ORM 建表在开发时很爽，上线后就没法演进 schema。 validate 模式 + Flyway 的组合是：实体和表对不上就启动失败， 逼着你写迁移。

☀ 不只是换语法：权限检查从「装饰器」变成了「路由上的标注」

Flask 的 @login_required 贴在函数上， 漏贴一个就是一个安全洞，而且没有任何办法发现 —— 你只能靠人眼 review 每个新加的视图函数。

Javalin 的做法是把角色写在路由注册处 （get("/moderate", this::moderate, Permission.MODERATE)）， 再由一个 beforeMatched 过滤器统一检查。 好处是整张权限表集中在一个地方，一眼能看完； 而且 path() 块上挂的角色会被块内所有路由继承， 往里加新路由自动受保护（第 9 章）。

☀ 部署这一行是整份表里差别最大的

Flask 应用上线要准备：Python 运行时、虚拟环境、 pip install -r requirements.txt、一个 WSGI 服务器（Gunicorn）、 通常还要一个 Nginx 在前面。任何一环的版本对不上都会出问题。

Javalin 这边是 scp target/javalinky.jar 然后 java -jar javalinky.jar。目标机器上只需要一个 JRE。 服务器（Jetty）、所有依赖、预编译的模板，全在这一个文件里。

代价是这个文件有 45MB，以及你得接受「一个进程」这个模型 —— 它不能像多进程那样靠操作系统隔离故障，一个 OutOfMemoryError 会带走所有正在处理的请求。

没有对应物的东西

最后列一些找不到直接对应的，省得你白找：

Flask 生态里的Javalin 这边的情况
url_for 没有。自己写常量类（第 3 章），用编译期检查换运行时反查
current_app / g 没有全局代理。要什么就传什么 —— ctx、services 都是显式参数
current_user（全局） CurrentUser.get(ctx)。Java 也有 ThreadLocal 能做成全局， 但虚拟线程下不划算，而且显式传更容易测（第 19 章）
Jinja2 过滤器 没有。写成 Java 方法，或者在页面模型 record 里算好
Flask-Bootstrap 的 quick_form 没有现成的。第 4 章自己写了 tag/field.jte，大约 25 行
Flask-Moment 没有。第 3 章自己写了 tag/timeago.jte + 一小段 JS
Celery 简单异步用 ExecutorService；要持久化队列和重试， 看 JobRunr 或 Quartz（第 18 章有提）
pip freeze 的扁平依赖 Maven 是传递依赖 + 版本仲裁，完全不同的模型。 冲突怎么查怎么治，见第 8 章的 jackson-bom 那一节和附录 C
💡 一句总结

这份表里反复出现同一个模式：Flask 用运行时的魔法换开发时的简洁， Java 这边用一点样板换编译期的确定性。

url_for 对 Routes 常量、Jinja2 对 JTE、 装饰器对路由标注 —— 每一对都是这个取舍。 习惯之后你会发现多出来的那点样板，换回来的是「能跑起来基本就是对的」。
