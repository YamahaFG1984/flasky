第 14 章

应用编程接口

到现在 Javalinky 只能用浏览器访问。这一章给它加一套 REST API， 让手机应用、单页前端、或者别人的程序也能读写数据。 Javalin 在这件事上特别顺手 —— 它本来就是为写 API 而生的框架。

本章目标

  • 理解 REST 的六个约束，尤其是“无状态”对设计的影响
  • 会设计资源 URL 和选对 HTTP 方法与状态码
  • 理解为什么绝不能把实体类直接序列化成 JSON
  • 实现 HTTP Basic + 令牌两种认证
  • 给集合资源做分页，并用 Javalin 的内容协商统一错误格式
  • 会用 HTTPie / curl 测接口

为什么要有 API

原书这一章开头描述的趋势今天已经是常态：业务逻辑越来越多地跑在客户端， 服务端主要负责数据的存取。

REST 的六个约束

REST 不是协议也不是标准，而是 Roy Fielding 在博士论文里提出的一种架构风格。 它由六个约束定义：

约束含义对我们的实际影响
客户端-服务器界面和数据存储分离API 不返回 HTML
无状态每个请求必须自带全部信息，服务器不保存客户端状态API 不能用会话，要用令牌 —— 见下面
可缓存响应要标明自己能不能被缓存用 ETag / Cache-Control 响应头
统一接口资源用 URL 标识，用标准 HTTP 方法操作最复杂的一条，下面详细说
分层系统客户端和服务器之间可以插代理、缓存、网关要正确处理 X-Forwarded-* 头（第 17 章）
按需代码（可选）服务器可以发可执行代码给客户端基本不用
☀ “无状态”是最重要也最容易违反的一条

前 13 章我们一直用会话：浏览器带一个 Cookie，服务器内存里存着 userId。这是有状态的 —— 服务器记着你。

它在浏览器场景下工作得很好，但对 API 不行，原因有三个：

  1. 手机应用、脚本、第三方程序不方便管理 Cookie；
  2. 要扩容到多台服务器时，会话必须共享存储（否则第二个请求打到另一台机器就不认你了）；
  3. REST 的缓存和分层约束都依赖"请求自包含"。

所以 API 用令牌：每个请求都在 Authorization 头里带上凭证，服务器不记任何东西。

资源与 URL 设计

REST 的核心概念是资源：应用领域里值得被单独引用的东西。 Javalinky 的资源有用户、文章、评论。每个资源有唯一的 URL， 操作用 HTTP 方法表达。

版本化

原书强调了一个重要的现实：网页能随服务端一起更新，手机应用不能。 你发布了新版 API，用户手机上还装着三个月前的旧版本。 所以 API 的变更必须非常谨慎，惯例是把版本号放进 URL： 

/api/v1/posts     ← 老客户端继续用
/api/v2/posts     ← 新客户端用，可以改 JSON 结构
ⓘ 什么算“破坏性变更”
变更破坏吗
新增一个响应字段不破坏（老客户端忽略它）
新增一个可选请求字段不破坏
删除或重命名响应字段破坏
改字段类型（数字 → 字符串）破坏
新增一个必填请求字段破坏
收紧校验规则破坏（老客户端的请求开始被拒）

所以尽量只做"新增"。一个实用技巧：响应里永远不要删字段， 只是把它标记为废弃并保持返回一个合理的值。

序列化：绝不要直接序列化实体

这是本章最重要的一条安全建议。假设偷懒写成这样： 

// ✗ 千万不要这么做
config.routes.get("/api/v1/users/{id}", ctx -> {
    User user = users.findById(id).orElseThrow();
    ctx.json(user);         // 把实体直接交给 Jackson
});

package com.example.javalinky.api.dto;

import com.example.javalinky.model.User;
import java.time.Instant;

/** 用户资源的公开表示。字段是手工挑的 —— 这就是重点。 */
public record UserDto(
    String url,
    long id,
    String username,
    String name,
    String location,
    String aboutMe,
    Instant memberSince,
    Instant lastSeen,
    String postsUrl,
    String timelineUrl,
    long postCount
) {
    public static UserDto from(User user, String baseUrl, long postCount) {
        return new UserDto(
            baseUrl + "/api/v1/users/" + user.getId(),
            user.getId(),
            user.getUsername(),
            user.getName(),
            user.getLocation(),
            user.getAboutMe(),
            user.getMemberSince(),
            user.getLastSeen(),
            baseUrl + "/api/v1/users/" + user.getId() + "/posts",
            baseUrl + "/api/v1/users/" + user.getId() + "/timeline",

        // 注意这里没有 email、没有 passwordHash、没有 role、没有 confirmed
    }
}

package com.example.javalinky.api.dto;

import com.example.javalinky.model.Post;
import java.time.Instant;

public record PostDto(
    String url,
    long id,
    String body,          // Markdown 原文，客户端可能想自己渲染
    String bodyHtml,      // 已清洗的 HTML，方便直接显示
    Instant timestamp,
    String authorUrl,
    String authorUsername,
    String commentsUrl,
    long commentCount
) {
    public static PostDto from(Post post, String baseUrl, long commentCount) {
        String self = baseUrl + "/api/v1/posts/" + post.getId();
        return new PostDto(
            self,
            post.getId(),
            post.getBody(),
            post.getBodyHtml(),
            post.getTimestamp(),
            baseUrl + "/api/v1/users/" + post.getAuthor().getId(),
            post.getAuthor().getUsername(),
            self + "/comments",
            commentCount);
    }
}
💡 为什么响应里到处放完整 URL

注意 url、authorUrl、commentsUrl 这些字段 —— 原书也是这么设计的。这叫 HATEOAS （把超链接作为应用状态的引擎）。

好处是客户端不需要知道 URL 的拼法： 拿到一篇文章，想看评论就跟着 commentsUrl 走。 这样服务端以后改 URL 结构也不会破坏客户端 —— 就像你浏览网页时从不手打 URL，而是点链接。

ⓘ 时间格式：又回到第 3 章的话题

API 返回时间一律用 ISO-8601 + UTC（2026-10-21T08:30:00Z）。 理由和第 3 章一样：服务端不知道客户端在哪个时区，让客户端自己转换。

不要返回 "2026-10-21 16:30:00" 这种没有时区信息的格式 —— 客户端无法判断它是哪个时区的，这是真实世界里 bug 的高发区。

API 认证

原书的方案（我们沿用）是两段式：

package com.example.javalinky.api;

import com.example.javalinky.db.Db;
import com.example.javalinky.db.UserRepository;
import com.example.javalinky.model.User;
import com.example.javalinky.service.AuthService;
import com.example.javalinky.util.Tokens;
import io.javalin.http.Context;
import io.javalin.http.ForbiddenResponse;
import io.javalin.http.UnauthorizedResponse;

public class ApiAuth {

    public static final String CTX_USER = "apiUser";
    private static final String PURPOSE_API = "api";

    private final AuthService auth;

    public ApiAuth(AuthService auth) {
        this.auth = auth;
    }

    /** 装在 /api/* 上的认证过滤器 */
    public void authenticate(Context ctx) {
        // 换令牌那个接口自己处理认证，这里跳过
        if (ctx.path().endsWith("/tokens") && ctx.method().name().equals("POST")) return;

        String header = ctx.header("Authorization");
        if (header == null || !header.startsWith("Bearer ")) {
            throw new UnauthorizedResponse("需要在 Authorization 头里提供 Bearer 令牌");
        }

        var jwt = auth.tokens().verify(header.substring(7), PURPOSE_API)
            .orElseThrow(() -> new UnauthorizedResponse("令牌无效或已过期"));

        User user = new UserRepository(Db.em(ctx))
            .findById(Tokens.userIdOf(jwt))
            .orElseThrow(() -> new UnauthorizedResponse("令牌对应的用户不存在"));

        if (!user.isConfirmed()) {
            throw new ForbiddenResponse("账号尚未确认");
        }

        ctx.attribute(CTX_USER, user);
    }

    /** 当前 API 调用者 */
    public static User user(Context ctx) {
        User user = ctx.attribute(CTX_USER);
        if (user == null) throw new UnauthorizedResponse();
        return user;
    }

    /** POST /api/v1/tokens —— 用 HTTP Basic 换令牌 */
    public void issueToken(Context ctx) {
        var credentials = ctx.basicAuthCredentials();
        if (credentials == null) {
            throw new UnauthorizedResponse("需要 HTTP Basic 认证");
        }

        User user = new UserRepository(Db.em(ctx))
            .findByEmail(credentials.getUsername().toLowerCase())
            .filter(u -> u.checkPassword(credentials.getPassword()))
            .orElseThrow(() -> new UnauthorizedResponse("邮箱或密码错误"));

        if (!user.isConfirmed()) {
            throw new ForbiddenResponse("账号尚未确认");
        }

        long ttlSeconds = 3600;
        String token = auth.tokens().issue(PURPOSE_API, user.getId(),
            java.time.Duration.ofSeconds(ttlSeconds));

        ctx.json(new TokenResponse(token, "Bearer", ttlSeconds));
    }

    public record TokenResponse(String token, String tokenType, long expiresIn) {}
}
⚠ HTTP Basic 的凭证不是加密的

Authorization: Basic am9obkBleGFtcGxlLmNvbTpjYXQ= 里那串东西只是 Base64 编码，任何人都能一秒解开。它不提供任何保密性。

所以用 Basic 认证的前提是必须走 HTTPS（由 TLS 提供加密）。 第 17 章会配好这一点。在生产环境用 HTTP 跑 Basic 认证等于把密码明文广播出去。

统一的错误格式

原书为此写了一堆辅助函数（bad_request()、unauthorized()……）， 还要在错误处理器里手动判断 request.accept_mimetypes。

Javalin 把这件事做掉了：第 2 章那些 NotFoundResponse 之类的异常 本来就会按 Accept 头返回 JSON 或文本。 所以我们只需要补两件事： 

package com.example.javalinky.api;

import io.javalin.config.JavalinConfig;
import io.javalin.validation.ValidationException;

public final class ApiErrors {

    public static void install(JavalinConfig config) {

        // ① 校验失败 → 400 + 字段级错误明细
        config.routes.exception(ValidationException.class, (e, ctx) -> {
            ctx.status(400).json(new ErrorBody(
                "validation_failed", "请求数据校验失败", e.getErrors()));
        });

        // ② 给 API 路径补上 JSON 格式的 404 / 405
        //    （HTML 页面的错误页在 ErrorPages 里，用 "html" 内容类型区分）
        config.routes.error(404, "json", ctx ->
            ctx.json(new ErrorBody("not_found", "资源不存在", null)));
        config.routes.error(405, "json", ctx ->
            ctx.json(new ErrorBody("method_not_allowed", "这个资源不支持该方法", null)));
    }

    public record ErrorBody(String error, String message, Object details) {}

    private ApiErrors() {}
}
☀ 内容协商：同一个异常，两种响应

这是 Javalin 一个很优雅的设计。config.routes.error(404, "html", ...) 和 error(404, "json", ...) 可以同时存在， Javalin 按请求的 Accept 头挑一个： 

# 浏览器
curl -H "Accept: text/html" localhost:7070/nope
→ 你的 404 HTML 页面

# API 客户端
curl -H "Accept: application/json" localhost:7070/api/v1/posts/99999
→ {"error":"not_found","message":"资源不存在","details":null}

于是一套业务代码同时服务两种客户端—— 处理器里只需要 throw new NotFoundResponse()，不用管调用者是谁。

API 路由模块

package com.example.javalinky.web.routes;

import com.example.javalinky.api.*;
import com.example.javalinky.api.dto.*;
import com.example.javalinky.config.AppConfig;
import com.example.javalinky.db.Page;
import com.example.javalinky.model.*;
import com.example.javalinky.web.Services;
import io.javalin.config.JavalinConfig;
import io.javalin.http.*;

import static io.javalin.apibuilder.ApiBuilder.*;

public class ApiRoutes implements RouteModule {

    private final AppConfig cfg;
    private final Services services;
    private final ApiAuth apiAuth;

    public ApiRoutes(AppConfig cfg, Services services) {
        this.cfg = cfg;
        this.services = services;
        this.apiAuth = new ApiAuth(services.auth());
    }

    @Override
    public void register(JavalinConfig config) {

        // API 不用会话，所以也不需要 CSRF —— 在 Csrf 过滤器里排除 /api/*
        config.routes.before("/api/*", apiAuth::authenticate);

        ApiErrors.install(config);

        config.routes.apiBuilder(() -> path("/api/v1", () -> {

            post("/tokens", apiAuth::issueToken);

            path("/posts", () -> {
                get("", this::listPosts);
                post("", this::createPost);
                path("/{id}", () -> {
                    get("", this::getPost);
                    patch("", this::updatePost);
                    get("/comments", this::listPostComments);
                    post("/comments", this::createComment);
                });
            });

            path("/users/{id}", () -> {
                get("", this::getUser);
                get("/posts", this::listUserPosts);
                get("/timeline", this::listUserTimeline);
            });

            get("/comments/{id}", this::getComment);
        }));
    }

    // ---------------- 文章 ----------------

    private void listPosts(Context ctx) {
        int page = Page.clampPage(ctx.queryParamAsClass("page", Integer.class)
                                     .allowNullable().get());
        var source = services.postRepo(ctx).findAll(page, cfg.postsPerPage());
        ctx.json(PagedResponse.of(source, p -> toDto(ctx, p),
                                  cfg.siteBaseUrl() + "/api/v1/posts"));
    }

    private void getPost(Context ctx) {
        Post post = services.postRepo(ctx)
            .findById(ctx.pathParamAsClass("id", Long.class).get())
            .orElseThrow(NotFoundResponse::new);
        ctx.json(toDto(ctx, post));
    }

    private void createPost(Context ctx) {
        User author = ApiAuth.user(ctx);
        if (!author.can(Permission.WRITE)) {
            throw new ForbiddenResponse("没有发布文章的权限");
        }

        // bodyValidator：反序列化 + 校验，失败自动 400
        var request = ctx.bodyValidator(PostRequest.class)
            .check(r -> r.body() != null && !r.body().isBlank(), "body 不能为空")
            .check(r -> r.body().length() <= 20000, "body 最长 20000 个字符")
            .get();

        Post post = services.postRepo(ctx).save(new Post(request.body(), author));
        com.example.javalinky.db.Db.em(ctx).flush();   // 要拿到自增 id

        // 201 Created 必须带 Location 头，指向新建的资源
        ctx.status(HttpStatus.CREATED)
           .header(Header.LOCATION, cfg.siteBaseUrl() + "/api/v1/posts/" + post.getId())
           .json(toDto(ctx, post));
    }

    private void updatePost(Context ctx) {
        User me = ApiAuth.user(ctx);
        Post post = services.postRepo(ctx)
            .findById(ctx.pathParamAsClass("id", Long.class).get())
            .orElseThrow(NotFoundResponse::new);

        // 和第 11 章一样：角色权限之外还要查归属
        boolean isAuthor = me.getId().equals(post.getAuthor().getId());
        if (!isAuthor && !me.can(Permission.ADMIN)) {
            throw new ForbiddenResponse("不能修改别人的文章");
        }

        var request = ctx.bodyValidator(PostRequest.class)
            .check(r -> r.body() != null && !r.body().isBlank(), "body 不能为空")
            .get();

        post.setBody(request.body());
        ctx.json(toDto(ctx, post));
    }

    // ---------------- 辅助 ----------------

    private PostDto toDto(Context ctx, Post post) {
        return PostDto.from(post, cfg.siteBaseUrl(),
            services.commentRepo(ctx).countByPost(post));
    }

    /** 请求体的形状。注意它和 PostDto 是两个不同的类 —— 见下面说明 */
    public record PostRequest(String body) {}
}
💡 请求 DTO 和响应 DTO 要分开

PostRequest 只有 body 一个字段，而 PostDto 有九个。 为什么不复用一个类？

因为客户端能提供的字段和服务端返回的字段本来就不一样。 id、timestamp、authorUrl 都是服务端决定的； 如果用同一个类接收请求，客户端就可能尝试传一个 "id": 999 或 "authorUrl": "..."—— 这叫批量赋值漏洞（mass assignment）。

规则：请求 DTO 只声明客户端应该能设置的字段。 多出来的 JSON 字段会被 Jackson 忽略（或者配置成报错）。

集合资源的分页

package com.example.javalinky.api.dto;

import com.example.javalinky.db.Page;
import java.util.List;
import java.util.function.Function;

/** 集合资源的统一响应格式 */
public record PagedResponse<T>(
    List<T> items,
    long total,
    int page,
    int pageSize,
    int totalPages,
    String prev,      // 没有上一页时是 null
    String next
) {
    public static <E, T> PagedResponse<T> of(Page<E> source,
                                             Function<E, T> mapper,
                                             String baseUrl) {
        return new PagedResponse<>(
            source.items().stream().map(mapper).toList(),
            source.total(),
            source.page(),
            source.size(),
            source.totalPages(),
            source.hasPrevious() ? baseUrl + "?page=" + source.previousPage() : null,
            source.hasNext()     ? baseUrl + "?page=" + source.nextPage()     : null);
    }
}

ⓘ 另一种惯例：用 Link 响应头

GitHub 等 API 把分页链接放在响应头里，响应体就是一个纯数组： 

Link: <https://api.example.com/posts?page=3>; rel="next",
      <https://api.example.com/posts?page=13>; rel="last"
X-Total-Count: 247

两种做法都很常见。放在响应体里对调用者更友好（不用解析头）， 放在头里更"纯粹"（响应体就是资源本身）。挑一种，然后全站一致。

用 HTTPie 测接口

原书推荐 HTTPie，确实比 curl 好用得多（彩色高亮、自动 JSON、语法简洁）： 

# 安装
pip install httpie      # 或 brew install httpie / apt install httpie

# 1. 用邮箱密码换令牌
http -a john@example.com:cat12345 POST :7070/api/v1/tokens

# 输出：
# {
#     "token": "eyJhbGciOiJIUzI1NiJ9...",
#     "tokenType": "Bearer",
#     "expiresIn": 3600
# }

# 2. 存进 shell 变量
TOKEN=$(http -a john@example.com:cat12345 POST :7070/api/v1/tokens | jq -r .token)

# 3. 读列表
http :7070/api/v1/posts "Authorization: Bearer $TOKEN"

# 4. 发一篇文章（HTTPie 的 key=value 会自动变成 JSON）
http POST :7070/api/v1/posts "Authorization: Bearer $TOKEN" \
     body='这是通过 **API** 发的文章'

# 5. 改一篇文章
http PATCH :7070/api/v1/posts/42 "Authorization: Bearer $TOKEN" \
     body='改过的内容'

# 6. 看分页
http :7070/api/v1/posts page==3 "Authorization: Bearer $TOKEN"

对应的 curl 写法（没有 HTTPie 时用）：

# 换令牌
curl -u john@example.com:cat12345 -X POST http://localhost:7070/api/v1/tokens

# 发文章
curl -X POST http://localhost:7070/api/v1/posts \
     -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"body": "通过 curl 发的文章"}'
⚠ 别忘了 Content-Type: application/json

Javalin 7 有一个 config.http.strictContentTypes 选项。 打开它之后，如果请求想被解析成 JSON 却没带正确的 Content-Type，会直接报错 —— 这能帮你早点发现客户端的问题。HTTPie 会自动带上这个头，curl 需要手写。

加分项：自动生成 API 文档

手写 API 文档一定会和代码脱节。Javalin 有一个 OpenAPI 插件， 能从注解生成 OpenAPI 规范，再配上 Swagger UI 就有了可交互的文档页： 

<dependency>
  <groupId>io.javalin.community.openapi</groupId>
  <artifactId>javalin-openapi-plugin</artifactId>
  <version>（和 Javalin 主版本对应的版本）</version>
</dependency>
<dependency>

和原书的差异小结

原书的做法本章的做法为什么
Flask-HTTPAuth 的 @auth.login_requiredbefore("/api/*", ...) 过滤器Javalin 的过滤器就够用，不需要扩展
一个接口同时支持 Basic 和令牌（verify_password 里判断）Basic 只用于换令牌，其他接口只认 Bearer职责清楚；也避免每个请求都跑 bcrypt
to_json() / from_json() 写在模型类上独立的 DTO record模型不该知道 JSON 的存在；也防止字段泄露
手写 bad_request() 等辅助函数抛 Javalin 的标准异常框架自带内容协商
分页信息放在响应体里（prev / next / count）一样原书这个设计很好，直接沿用

动手练习

  1. 用 HTTPie 走完整个流程：换令牌 → 列文章 → 发一篇 → 改它 → 看它的评论。 注意观察 201 响应的 Location 头。
  2. 不带 Authorization 头访问 /api/v1/posts，确认返回 401 和 JSON 格式的错误体。再带一个胡乱改过的令牌试一次。
  3. 故意违反第 ③ 节的建议：加一条路由直接 ctx.json(user)（传实体）， 然后访问它。看看响应里出现了什么（passwordHash？递归？栈溢出？） 看完立刻删掉这条路由。
  4. 试试批量赋值：往 POST /api/v1/posts 的 JSON 里加上 "id": 9999 和 "authorUsername": "admin"。 确认它们被忽略了。然后想一想：如果 PostRequest 里有这些字段会怎样？
  5. 把令牌有效期改成 10 秒，换一个令牌，等 15 秒后再用。确认收到 401。
  6. 用 A 用户的令牌去修改 B 用户的文章，确认返回 403。 （这是第 11 章 IDOR 检查的 API 版本。）
  7. 给 API 加一条 DELETE /api/v1/posts/{id}，返回 204 No Content。 注意：删除要检查归属，而且应该是幂等的 （删一个已经不存在的 id 应该返回 204 还是 404？两种设计都有人用，想清楚你选哪个、为什么）。
  8. （进阶）给 GET /api/v1/posts/{id} 加上 ETag 支持： 用 config.http.generateEtags = true 打开， 然后用 http :7070/api/v1/posts/1 "If-None-Match: <上次的 ETag>" 验证返回 304 Not Modified。这就是 REST 第三个约束"可缓存"的实际应用。
