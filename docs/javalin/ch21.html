第 21 章

实时：SSE 与 WebSocket

到现在为止，页面上的一切都是用户主动刷出来的。这一章让服务器能主动推： 有人评论了你的文章，立刻弹一条通知。 两种技术都做一遍 —— 先用 SSE 做通知（单向，而且就是普通 HTTP）， 再用 WebSocket 做「正在输入」提示（双向，所以 SSE 做不了）。

本章目标

  • 说得清 SSE 和 WebSocket 各自适合什么，以及为什么别一上来就选 WebSocket
  • 用 sse() 做服务器推送，理解 keepAlive() 改变了什么
  • 知道为什么没有心跳的 SSE 连接池一定会泄漏（本章有实测）
  • 用 ws() 做双向通信，并在 WebSocket 里正确拿到登录用户
  • 知道实时功能在多实例部署下会怎样失效
📦 本章代码

本章是第 19 章的直接延续：LiveHub 和 PostPresence 都是「应用级共享且可变」的对象，而且比限流器更难 —— 连接会在任意时刻消失。

先选对工具

☀ 决策很简单：只有「浏览器也要频繁往上发」才用 WebSocket
场景选什么为什么
通知、未读数、进度条、股价、日志流SSE全是服务器单向推
聊天、协同编辑、游戏、「正在输入」WebSocket两边都要主动发
几十个用户、数据几秒钟不变也没事轮询复杂度最低，别过度设计

常见的误区是「要实时 = 上 WebSocket」。实际上大部分「实时」需求是单向的， 而 SSE 在单向场景下几乎全面占优：它是普通 HTTP，所以 Cookie、认证、压缩、HTTP/2 多路复用、反向代理配置全都照旧， 而且断线重连是浏览器内置的 —— WebSocket 那边得自己写。

用 SSE 做通知

服务端：一个不会结束的处理器

// SSE 也是普通的 HTTP GET，所以路由上的角色约束照常生效
sse(Routes.LIVE, this::liveFeed, Access.AUTHENTICATED);

private void liveFeed(SseClient client) {
    User me = CurrentUser.require(client.ctx());

    client.keepAlive();
    services.live().register(me.getId(), client);

    // 先打个招呼：浏览器收到任意一条数据才会认为连接真的建立了
    client.sendEvent("hello", Map.of("connections",
        services.live().connectionCount(me.getId())));
}
⚠ keepAlive() 是这段代码的全部关键

默认情况下，处理器方法一返回，Javalin 就关掉连接 —— 那样客户端只会收到 hello 然后立刻断开重连，变成一个很昂贵的轮询。

client.keepAlive() 告诉 Javalin：这个连接我还要用，别关。 之后就由别的请求线程（比如处理「发评论」那个请求的线程） 往这个 client 上写数据。

所以 SseClient 一定是跨线程共享的对象 —— 第 19 章讲的所有东西在这里全部适用。

连接登记处：LiveHub

public final class LiveHub implements AutoCloseable {

    /**
     * newKeySet() 给出的是一个并发安全的 Set（底层就是 ConcurrentHashMap）。
     * 普通的 HashSet 在这里会直接出问题：一边遍历推送，一边有人断开连接。
     */
    private final Map<Long, Set<SseClient>> clients = new ConcurrentHashMap<>();

    public void register(long userId, SseClient client) {
        clients.computeIfAbsent(userId, id -> ConcurrentHashMap.newKeySet()).add(client);
        client.onClose(() -> unregister(userId, client));
    }

    public void unregister(long userId, SseClient client) {
        // compute 保证「删成员」和「删空集合」是一个原子动作。
        // 分成 get + remove 两步的话，正好有人在这中间往空集合里 add，
        // 那个连接就永远收不到消息了。
        clients.compute(userId, (id, set) -> {
            if (set == null) return null;
            set.remove(client);
            return set.isEmpty() ? null : set;    // 返回 null = 把这个 key 删掉
        });
    }

    public void send(long userId, String event, Object data) {
        Set<SseClient> set = clients.get(userId);
        if (set == null) return;

        for (SseClient client : set) {
            if (client.terminated()) { unregister(userId, client); continue; }
            try {
                client.sendEvent(event, data);
            } catch (Exception e) {
                // 推送失败就当这个连接废了。绝不能让它影响请求本身 ——
                // 「通知没发出去」比「发评论失败」轻得多。
                unregister(userId, client);
            }
        }
    }
}

一个用户可能开着好几个标签页，所以 userId → 一组连接。 到这里为止，这个类看起来是对的。

实测：上面那个版本会泄漏连接

写到这里我给它配了一个测试：连上 → 断开 → 再连上，断言「连接数还是 1」。 它失败了，显示 2。下面是查这个问题的完整过程， 因为结论比代码本身更值得记住。

⚠ 第一个假设：「断开应该立刻被发现」—— 错

直觉是客户端关掉连接，服务端马上就知道了。TCP 不是这样工作的。 对端发一个 FIN 只表示「我不再发数据了」，连接进入半关闭状态； 服务端这边还能继续写。

所以 client.onClose(...) 这个回调不保证会被及时调用， 容器要先察觉到 I/O 出问题才会触发它。

⚠ 第二个假设：「那就推一次消息，写失败自然会发现」—— 还是错

这就是 send() 里那段 try/catch 的设想。 于是我写了个探针：断开连接，然后连推 4 次消息，每次之后看连接数。 

[probe] 连上后:              {"connections":1}
[probe] 第 1 次推送后再连:    {"connections":2}
[probe] 第 2 次推送后再连:    {"connections":2}
[probe] 第 3 次推送后再连:    {"connections":2}
[probe] 第 4 次推送后再连:    {"connections":2}

死连接纹丝不动。原因还是 TCP： 往一个对端已关闭的 socket 写数据是会成功的 —— 数据进了内核发送缓冲区，write() 就返回了。 要等对方回 RST、而且本地再写一次，才会真正报错。

也就是说：那段 try/catch 在这个场景下一次都不会被触发。 它不是没用（网络真断了时有用），但指望它来回收连接是靠不住的。

☀ 正确答案：心跳。这就是为什么所有 SSE 实现都有心跳

办法是主动、定期地往每个连接写一点东西。 SSE 协议规定以 : 开头的行是注释，客户端会忽略 —— 正好拿来当心跳。 

public LiveHub(Duration interval) {
    this.heartbeat = Executors.newSingleThreadScheduledExecutor(r -> {
        Thread t = new Thread(r, "sse-heartbeat");
        t.setDaemon(true);      // 别拦着 JVM 退出
        return t;
    });
    long millis = Math.max(1, interval.toMillis());
    heartbeat.scheduleWithFixedDelay(this::ping, millis, millis, TimeUnit.MILLISECONDS);
}

/**
 * 心跳：往每个连接写一行 SSE 注释（": ping"）。
 * 浏览器会忽略注释行，但这次写会让已经断掉的连接暴露出来。
 * 顺带还能穿过某些代理的空闲超时。
 */
void ping() {
    clients.forEach((userId, set) -> {
        for (SseClient client : set) {
            if (client.terminated()) { unregister(userId, client); continue; }
            try {
                client.sendComment("ping");
            } catch (Exception e) {
                unregister(userId, client);
            }
        }
    });
}

加上之后，同一个探针：

[probe] 连上后:              {"connections":1}
[probe] 第 1 次推送后再连:    {"connections":1}
[probe] 第 2 次推送后再连:    {"connections":1}
[probe] 第 3 次推送后再连:    {"connections":1}
[probe] 第 4 次推送后再连:    {"connections":1}

心跳还顺带解决了另外两个问题：穿过代理的空闲超时 （nginx 默认 60 秒没数据就断开），以及 让客户端能及时发现服务器挂了（收不到心跳就重连）。

所以心跳不是优化，是 SSE 的必需品。 生产环境 15~30 秒比较合适；本教程的测试档位配成 200ms，好让测试跑得快。

ⓘ 测试要照着真实机制写，而不是照着直觉写

最终那个测试长这样 —— 注释里把踩过的坑留下了： 

/**
 * 断开的连接必须被摘掉，否则 LiveHub 就是个内存泄漏。
 *
 * 这个测试的写法是实测出来的，过程值得记一下：
 *   - 「关掉连接就立刻断言数量变了」不成立 —— TCP 对端关闭不会被服务端立刻感知
 *   - 「推一次消息就会发现」也不成立 —— 往半关闭的 socket 写是成功的，
 *     数据进了内核缓冲区。实测推 4 次，死连接依然挂在那里
 *   - 真正有效的是心跳：定期写一行注释，写不动的才暴露出来
 * 所以这里等的是一个心跳周期（测试档位配成 200ms）。
 */
@Test
void 断开的连接会被心跳清理掉() throws Exception { /* ... */ }

如果当初把第一个失败的测试「改成通过」（比如加个 sleep 再断言 ≤ 2）， 这个泄漏就会一直留在代码里。测试失败时先问「是测试错了还是代码错了」， 这次两个都错了。

浏览器端

// 只有登录用户才有这个流。用 body 上的标记判断，省得未登录时白连一次。
if (!document.body.dataset.authenticated) return;

var source = new EventSource('/live');

source.addEventListener('comment', function (e) {
  var d = JSON.parse(e.data);
  toast('<a href="' + d.postUrl + '">' +
        escapeHtml(d.author) + ' 评论了你的文章：' + escapeHtml(d.excerpt) + '</a>');
});

// EventSource 自带重连（默认 3 秒），所以这里什么都不用做。
// 真正需要处理的是「服务器明确说别再连了」—— 那种情况下要 close()。
source.addEventListener('error', function () {
  if (source.readyState === EventSource.CLOSED) {
    console.info('实时通知已断开，不再重连');
  }
});
⚠ 推送来的数据照样要转义

注意上面那个 escapeHtml()。推送的内容最终来自另一个用户的输入 （评论正文、用户名），而这里是用 innerHTML 拼出来的 —— 不转义就是一个标准的存储型 XSS。

服务端 JTE 模板的自动转义（第 3 章）管不到这里， 因为这段 HTML 是浏览器里拼的。 凡是自己拼 innerHTML 的地方，转义都得自己做 （或者改用 textContent，那样天然安全）。

用 WebSocket 做「正在输入」

这个功能 SSE 做不了，因为浏览器要主动往上发「我在打字」。 

// WebSocket：双向的那种。浏览器要往上报「我在输入」，
// 所以 SSE 不够用 —— 这正是两者的分界线。
ws("/ws/post/{id}", this::postSocket);

private void postSocket(WsConfig ws) {
    ws.onConnect(ctx -> {
        long postId = ctx.pathParamAsClass("id", Long.class).get();
        ctx.enableAutomaticPings();        // 协议级心跳，穿代理用的
        services.presence().join(postId, ctx);
    });

    ws.onMessage(ctx -> {
        long postId = ctx.pathParamAsClass("id", Long.class).get();
        // 只认一种消息，别的一律忽略 —— WebSocket 没有路由，
        // 所有消息都挤在这一个入口，解析要严格
        if (!"typing".equals(ctx.message())) return;

        String username = wsUsername(ctx);
        if (username != null) {
            services.presence().typing(postId, ctx, username);
        }
    });

    ws.onClose(ctx -> { /* leave */ });
    ws.onError(ctx -> { /* leave */ });
}
☀ WebSocket 的心跳不用自己写

ctx.enableAutomaticPings() 一行就够了。 和 SSE 不同，WebSocket 协议本身定义了 ping/pong 帧， 还有明确的关闭帧 —— 所以 onClose 是可靠的， 不需要 LiveHub 那套心跳兜底。

这是 WebSocket 相对 SSE 实打实的一个优势。 但也别忘了代价：它不是 HTTP 了，Javalin 的 before 过滤器、error 处理器、UnitOfWork 事务， 在 WebSocket 回调里一个都不生效。

在 WebSocket 里拿到登录用户

/**
 * 从 WebSocket 握手时带过来的 HTTP 会话里取当前用户名。
 *
 * 关键点：用户身份只能从服务端会话取。
 * WebSocket 升级用的还是普通 HTTP 请求，Cookie 照常带过来，
 * 所以 ctx.sessionAttribute() 读得到 —— 千万别去信消息体里的用户名。
 */
private String wsUsername(WsContext ctx) {
    Long userId = ctx.sessionAttribute(CurrentUser.SESSION_KEY);
    if (userId == null) return null;

    // 用户名在连接期间不会变，握手时查一次缓存在 ws 的属性里就够了，
    // 不必每条消息都查库
    String cached = ctx.attribute("username");
    if (cached != null) return cached;

    String username = Db.withEntityManager(em ->
        new UserRepository(em).findById(userId).map(User::getUsername).orElse(null));
    if (username != null) ctx.attribute("username", username);
    return username;
}
⚠ 两个必须注意的点

一、身份只能从会话取。 让客户端在消息里自报 {"user":"admin"} 是一个典型的越权漏洞 —— WebSocket 连接建立之后就没有「每个请求再认证一次」这回事了， 所有消息都来自同一条连接，身份必须在握手时确定并锁死。

二、WebSocket 回调里没有 EntityManager。 第 5 章的 UnitOfWork 是一个 HTTP before 过滤器， WebSocket 的消息回调不经过它。 所以 Db.em(ctx) 在这里会抛「当前请求没有 EntityManager」。 要自己开一个： 

/**
 * 自己开一个 EntityManager 用完就关。
 * 给不走 HTTP 请求流程的地方用：WebSocket 的回调、定时任务、Cli。
 */
public static <T> T withEntityManager(Function<EntityManager, T> work) {
    try (EntityManager em = emf().createEntityManager()) {
        return work.apply(em);
    }
}

又一个实测发现：WsContext 每次事件都是新对象

⚠ ctx != sender 不能用来判断「是不是发起者」

「转发给别人，不回给自己」听起来只要比一下对象就行： 

// ❌ 发起者也会收到自己的消息
public void typing(long postId, WsContext sender, String username) {
    each(postId, ctx -> {
        if (ctx != sender) ctx.send(...);
    });
}

测试直接抓住了这个：断言「发起者不该收到自己的 typing」失败了。 原因是 Javalin 为每个事件新建一个 WsContext —— onConnect 时存进 Set 的那个，和 onMessage 回调里拿到的那个不是同一个实例，所以引用比较永远不相等。

正确的做法是按 sessionId() 比，它在一条连接的生命周期里是稳定的： 

public void typing(long postId, WsContext sender, String username) {
    String senderId = sender.sessionId();
    each(postId, ctx -> {
        if (!ctx.sessionId().equals(senderId)) {
            ctx.send(Map.of("type", "typing", "username", username));
        }
    });
}

顺带一提：WsContext 重写了 equals/hashCode （按 sessionId），所以放进 Set 里去重是对的 —— 只有 == 这种引用比较会出问题。这种「集合语义对、引用语义错」 的组合特别容易蒙混过关。

实时功能在多实例下会碎掉

☀ 解法：把推送从「进程内的 Map」换成「所有实例都订阅的频道」
做法怎么工作代价
粘性会话 让同一个用户总是落到同一个实例 最省事，但实例重启时连接全断；扩缩容也会打乱
Redis Pub/Sub 发评论的实例 PUBLISH，所有实例 SUBSCRIBE 并推给本地连着的人 最常见的方案。多一个依赖；消息不持久（实例重启期间的会丢）
消息队列 同上，但用 Kafka / RabbitMQ，消息可持久化 重得多，适合通知本身就要可靠投递的场景
托管服务 Pusher、Ably、Supabase Realtime 之类 连接管理全交出去；花钱，而且多一个外部依赖

改造的范围其实很小：LiveHub.send() 从「直接写本地连接」 改成「PUBLISH 到频道」，再加一个订阅者在收到消息时写本地连接。 调用方一行都不用改。 这正是当初把推送收口到一个 LiveHub 里的价值。

动手练习

  1. 亲眼看看 SSE 的报文。登录后 curl -N -H "Cookie: JSESSIONID=..." http://localhost:7070/live， 保持着，然后在另一个浏览器里评论你的文章。 注意 -N（不缓冲）—— 少了它你什么都看不到。 观察心跳的 : ping 行。
  2. 复现那个泄漏。把 LiveHub 的心跳停掉 （heartbeat.shutdownNow() 提前调）， 跑 LiveNotificationTest，确认「断开的连接会被心跳清理掉」变红。
  3. 打开两个标签页，看 hello 事件里的 connections 变成 2。 关掉一个，等一个心跳周期，再开一个 —— 确认又回到 2 而不是 3。
  4. 验证 EventSource 的自动重连。连上之后把服务器 Ctrl+C，看浏览器控制台每 3 秒重试一次； 再把服务器起回来，确认它自己接上了 —— 这件事 WebSocket 要自己写几十行。
  5. 给通知加一个未读计数：在导航栏放一个小红点， 收到 comment 事件就 +1，点开通知列表清零。 想清楚一个问题：用户不在线时收到的通知怎么办？ （提示：实时推送和持久化通知是两件事，大多数系统两个都要）
  6. WebSocket 的「正在输入」接到页面上。 在文章页连 /ws/post/{id}，评论框 input 事件时 节流发送 typing，收到别人的 typing 就显示 「xxx 正在输入…」并在 3 秒后消失。
  7. 故意往 WebSocket 发一条超大的消息（比如 10MB 的字符串）。 看会发生什么，然后查一下怎么配置消息大小上限。
  8. （进阶）把 LiveHub 改成基于 Redis Pub/Sub。 本地用 docker run -p 6379:6379 redis， 起两个实例（不同端口），确认在实例 1 上登录的用户 能收到实例 2 上产生的通知。
