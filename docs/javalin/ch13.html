第 13 章

用户评论

评论是第二部分的最后一块功能。技术上它和文章很像（Markdown、分页、权限）， 所以这一章短一些。但它多出了一个新东西：内容协管—— 任何允许用户发内容的网站都绕不开这件事。

本章目标

  • 建 Comment 实体，理解它和 Post、User 的双重关联
  • 在文章页实现评论的提交与展示
  • 实现“评论后自动跳到最后一页”
  • 做一个协管后台，支持隐藏/恢复评论
  • 理清“谁能看到被隐藏的评论”这个权限矩阵

Comment 实体

CREATE TABLE comments (
    id        BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    body      TEXT         NOT NULL,
    body_html TEXT,
    timestamp TIMESTAMP(6) WITH TIME ZONE NOT NULL,
    disabled  BOOLEAN      NOT NULL DEFAULT FALSE,
    post_id   BIGINT       NOT NULL REFERENCES posts (id) ON DELETE CASCADE,
    author_id BIGINT       NOT NULL REFERENCES users (id)
);

-- 文章页按时间正序列这篇文章的评论
CREATE INDEX ix_comments_post_timestamp ON comments (post_id, timestamp);
-- 协管后台按时间倒序列全站评论
CREATE INDEX ix_comments_timestamp ON comments (timestamp DESC);

package com.example.javalinky.model;

import com.example.javalinky.util.Markdown;
import jakarta.persistence.*;
import java.time.Instant;

@Entity
@Table(name = "comments")
public class Comment {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, columnDefinition = "text")
    private String body;

    @Column(name = "body_html", columnDefinition = "text")
    private String bodyHtml;

    @Column(name = "timestamp", nullable = false)
    private Instant timestamp = Instant.now();

    /** 被协管员隐藏了。注意是"隐藏"而不是"删除"——见本章最后的讨论 */
    @Column(nullable = false)
    private boolean disabled = false;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "post_id", nullable = false)
    private Post post;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "author_id", nullable = false)
    private User author;

    protected Comment() {}

    public Comment(String body, Post post, User author) {
        this.body = body;
        this.post = post;
        this.author = author;
    }

    /** 评论用更严格的标签白名单（第 11 章的 COMMENT_POLICY） */
    @PrePersist
    @PreUpdate
    private void renderBody() {
        this.bodyHtml = Markdown.toSafeCommentHtml(body);
    }

    public Long getId() { return id; }
    public String getBody() { return body; }
    public void setBody(String body) { this.body = body; }
    public String getBodyHtml() { return bodyHtml; }
    public Instant getTimestamp() { return timestamp; }
    public boolean isDisabled() { return disabled; }
    public void setDisabled(boolean disabled) { this.disabled = disabled; }
    public Post getPost() { return post; }
    public User getAuthor() { return author; }
}
ⓘ 为什么评论的白名单比文章更严

文章允许标题、表格、代码块；评论只允许加粗、斜体、行内代码和链接。 理由很简单：评论区不该有人能发一个巨大的 h1 标题霸占版面。

这是一个产品决定，但它正好说明白名单机制的好处： 同一个渲染器配两套策略，几行代码的事。

仓储与提交

package com.example.javalinky.db;

import com.example.javalinky.model.Comment;
import com.example.javalinky.model.Post;
import com.example.javalinky.model.User;
import jakarta.persistence.EntityManager;
import java.util.Optional;

public class CommentRepository {

    private final EntityManager em;

    public CommentRepository(EntityManager em) {
        this.em = em;
    }

    public Comment save(Comment comment) {
        em.persist(comment);
        return comment;
    }

    public Optional<Comment> findById(long id) {
        return Optional.ofNullable(em.find(Comment.class, id));
    }

    public long countByAuthor(User author) {
        return em.createQuery(
                "select count(c) from Comment c where c.author = :a", Long.class)
            .setParameter("a", author)
            .getSingleResult();
    }

    public long countByPost(Post post) {
        return em.createQuery(
                "select count(c) from Comment c where c.post = :p", Long.class)
            .setParameter("p", post)
            .getSingleResult();
    }

    /**
     * 某篇文章的评论，按时间正序（对话要顺着读）。
     * 注意：本章后面讲"隐藏评论"时会给它加一个 includeDisabled 参数，
     * 最终只保留那一个版本。
     */
    public Page<Comment> findByPost(Post post, int page, int size) {
        long total = countByPost(post);
        var items = em.createQuery("""
                select c from Comment c
                  join fetch c.author
                 where c.post = :p
                 order by c.timestamp asc
                """, Comment.class)
            .setParameter("p", post)
            .setFirstResult((page - 1) * size)
            .setMaxResults(size)
            .getResultList();
        return Page.of(items, page, size, total);
    }

    /** 协管后台：全站评论，最新的在前 */
    public Page<Comment> findAllForModeration(int page, int size) {
        long total = em.createQuery("select count(c) from Comment c", Long.class)
            .getSingleResult();
        var items = em.createQuery("""
                select c from Comment c
                  join fetch c.author
                  join fetch c.post
                 order by c.timestamp desc
                """, Comment.class)
            .setFirstResult((page - 1) * size)
            .setMaxResults(size)
            .getResultList();
        return Page.of(items, page, size, total);
    }
}

private void createComment(Context ctx) {
    User me = CurrentUser.require(ctx);
    long postId = ctx.pathParamAsClass("id", Long.class).get();

    Post post = services.postRepo(ctx).findById(postId)
        .orElseThrow(() -> new NotFoundResponse("文章不存在"));

    var form = new CommentForm(ctx.formParam("body"));
    var errors = Forms.validate(form);
    if (!errors.isEmpty()) {
        Flash.danger(ctx, errors.values().iterator().next().get(0));
        ctx.redirect(Routes.post(postId) + "#comment-form");
        return;
    }

    services.commentRepo(ctx).save(new Comment(form.body(), post, me));
    Flash.success(ctx, "评论已发布。");

    // 跳到最后一页，这样用户能立刻看到自己的评论
    ctx.redirect(Routes.post(postId, LAST_PAGE) + "#comments");
}

“跳到最后一页”

用户刚发的评论在时间上是最后一条，所以应该跳到评论的最后一页。 但处理器在重定向时还不知道总共有几页。 原书用了一个小技巧：用 page=-1 表示“最后一页”， 由渲染文章页的处理器去算。 

/** 约定：page=-1 表示"最后一页" */
private static final int LAST_PAGE = -1;

private void showPost(Context ctx) {
    long id = ctx.pathParamAsClass("id", Long.class).get();
    Post post = services.postRepo(ctx).findById(id)
        .orElseThrow(() -> new NotFoundResponse("文章不存在"));

    // 协管员能看到被隐藏的评论，普通读者不能 —— 下面每一处计数和查询都要带上它
    User me = CurrentUser.get(ctx);
    boolean canModerate = me != null && me.can(Permission.MODERATE);

    var comments = services.commentRepo(ctx);
    int size = cfg.commentsPerPage();
    Integer requested = ctx.queryParamAsClass("page", Integer.class)
                           .getOrNull();

    int page;
    if (requested != null && requested == LAST_PAGE) {
        long total = comments.countByPost(post, canModerate);
        page = (int) Math.max(0, total - 1) / size + 1;
    } else {
        page = Page.clampPage(requested);
    }

    var commentPage = comments.findByPost(post, page, size, canModerate);

    View.render(ctx, "post.jte", "文章",
        "post", PostListPage.of(Page.of(List.of(post), 1, 1, 1), me,
            Map.of(post.getId(), comments.countByPost(post, canModerate))),
        "comments", CommentListPage.of(commentPage, me, post.getId()),
        "form", FormView.empty());
}
💡 一个更现代的做法

page=-1 能用，但它是个"魔法值"，别人读代码时会愣一下。 更清楚的写法是用一个命名参数：?page=last，或者干脆 /post/5/comments/last。

另外，现在的做法通常是不跳页 —— 用 AJAX 提交评论，然后把新评论插到列表底部，页面根本不刷新。 那需要前端代码，超出本教程范围，但你应该知道这是目前的主流。

谁能看到被隐藏的评论

协管的核心是一个 disabled 标记。但“隐藏”到底对谁隐藏？ 这个权限矩阵必须想清楚，否则很容易写出 bug： 

/**
 * 文章页的评论列表。
 * @param includeDisabled 协管员传 true，其他人传 false
 */
public Page<Comment> findByPost(Post post, int page, int size, boolean includeDisabled) {
    String filter = includeDisabled ? "" : " and c.disabled = false";

    long total = em.createQuery(
            "select count(c) from Comment c where c.post = :p" + filter, Long.class)
        .setParameter("p", post)
        .getSingleResult();

    var items = em.createQuery("""
            select c from Comment c
              join fetch c.author
             where c.post = :p%s
             order by c.timestamp asc
            """.formatted(filter), Comment.class)
        .setParameter("p", post)
        .setFirstResult((page - 1) * size)
        .setMaxResults(size)
        .getResultList();

    return Page.of(items, page, size, total);
}

/** countByPost 同样要带可见性参数，否则分页的总数和列表对不上 */
public long countByPost(Post post, boolean includeDisabled) {
    String filter = includeDisabled ? "" : " and c.disabled = false";
    return em.createQuery(
            "select count(c) from Comment c where c.post = :p" + filter, Long.class)
        .setParameter("p", post)
        .getSingleResult();
}

/**
 * 批量查"每篇文章有多少条评论"（第 11 章的列表页要用）。
 * 列表页千万别在循环里逐篇查 —— 那就是 N+1，第 16 章会用测试把它钉死。
 */
public Map<Long, Long> countCommentsByPost(List<Long> postIds) {
    if (postIds.isEmpty()) return Map.of();
    return em.createQuery("""
            select c.post.id, count(c)
              from Comment c
             where c.post.id in :ids
               and c.disabled = false
             group by c.post.id
            """, Object[].class)
        .setParameter("ids", postIds)
        .getResultStream()
        .collect(Collectors.toMap(row -> (Long) row[0], row -> (Long) row[1]));
}
ⓘ 两个版本只留一个

上面这一版 findByPost / countByPost 替换本章前面那个不带 includeDisabled 的版本， 不是和它共存。Java 允许重载，所以留着两个也能编译 —— 但那样迟早有人在某个页面上调了不过滤的那个， 把隐藏的评论原样显示给普通读者，而且这种 bug 测试很难覆盖到。

一个有用的习惯：涉及可见性和权限的查询，不要提供"不过滤"的重载。 让调用方必须显式写出 true 或 false， code review 时一眼能看出谁在看什么。

⚠ 这里用字符串拼接 JPQL，安全吗？

安全 —— 因为拼进去的是代码里写死的常量字符串， 不是用户输入。includeDisabled 是一个布尔值， 它只能在两个固定的 JPQL 片段之间二选一。

判断标准是：拼进 SQL 的内容是否可能来自外部？ 来自外部 → 必须用参数绑定；来自代码常量 → 拼接没问题。 

package com.example.javalinky.web.page;

import com.example.javalinky.db.Page;
import com.example.javalinky.model.Comment;
import com.example.javalinky.model.Permission;
import com.example.javalinky.model.User;
import java.time.Instant;
import java.util.List;

public record CommentListPage(long postId, Page<Item> page, boolean canModerate) {

    public record Item(
        long id,
        String bodyHtml,
        Instant timestamp,
        String authorUsername,
        String authorAvatarHash,
        boolean disabled
    ) {}

    public static CommentListPage of(Page<Comment> source, User viewer, long postId) {
        boolean canModerate = viewer != null && viewer.can(Permission.MODERATE);

        List<Item> items = source.items().stream()
            .map(c -> new Item(
                c.getId(),
                c.getBodyHtml(),
                c.getTimestamp(),
                c.getAuthor().getUsername(),
                c.getAuthor().avatarHash(),
                c.isDisabled()))
            .toList();

        return new CommentListPage(postId,
            Page.of(items, source.page(), source.size(), source.total()),
            canModerate);
    }
}

协管员需要一个能看到全站最新评论的页面。 第 9 章我们已经把路由声明好了（整个 /moderate 前缀需要 Permission.MODERATE），现在填上实现： 

private void moderate(Context ctx) {
    int page = Page.clampPage(ctx.queryParamAsClass("page", Integer.class)
                                 .getOrNull());

    var source = services.commentRepo(ctx)
        .findAllForModeration(page, cfg.commentsPerPage());

    View.render(ctx, "moderate.jte", "协管评论",
        "comments", CommentListPage.of(source, CurrentUser.get(ctx), 0));
}

private void disableComment(Context ctx) {
    setCommentDisabled(ctx, true);
}

private void enableComment(Context ctx) {
    setCommentDisabled(ctx, false);
}

private void setCommentDisabled(Context ctx, boolean disabled) {
    long id = ctx.pathParamAsClass("id", Long.class).get();
    Comment comment = services.commentRepo(ctx).findById(id)
        .orElseThrow(() -> new NotFoundResponse("评论不存在"));

    comment.setDisabled(disabled);     // 托管对象，提交时自动 UPDATE
    Flash.success(ctx, disabled ? "评论已隐藏。" : "评论已恢复显示。");

    // 操作完回到原来那一页，别让协管员每次都从第 1 页重新找
    String page = ctx.formParam("page");
    ctx.redirect(page == null
        ? Routes.MODERATE
        : Routes.MODERATE + "?page=" + page);
}

顺便讨论：评论计数

第 11 章我们绕开了 post.getComments().size() 这个 N+1 陷阱， 改成把评论数当参数传进 PostListPage.of。 现在 countCommentsByPost 有了，那条链路才算接完整 —— 列表页先收齐这一页的文章 id，查一次，再渲染。

当时还提到另一个方案（在 posts 表加计数列）。现在正式比较一下：

方案 A：每次聚合查询方案 B：在 posts 表加计数列
做法select post_id, count(*) … group by post_idposts.comment_count，发/删评论时 ±1
读性能一条额外查询（已经不是 N+1 了）零额外开销
写复杂度无每个改评论的地方都要记得更新计数
准确性永远准确有可能漂移（漏更新、并发、手工改库）
并发无问题需要 update … set c = c + 1 而不是先读后写
☀ 该选哪个

先用方案 A。它正确、简单，而且一条 group by 查询 在几十万条评论的规模下也只要几毫秒。

等到你有真实数据证明这条查询是瓶颈时，再上方案 B， 并且同时准备一个对账任务（定期用方案 A 重算一遍，修正漂移的计数）。

这是性能优化的通用顺序：先正确，再测量，最后优化。 第 16 章就是讲怎么"测量"。

ⓘ 如果真要做方案 B，关键的一行是这样
// ✗ 错：两个人同时评论时会丢一次计数（经典的竞态）
post.setCommentCount(post.getCommentCount() + 1);

// ✓ 对：把加法交给数据库，它会在行锁的保护下执行
em.createQuery("update Post p set p.commentCount = p.commentCount + 1 where p.id = :id")
  .setParameter("id", postId)
  .executeUpdate();

注意第二种写法会绕过一级缓存—— 内存里那个 Post 对象的 commentCount 还是旧值。 必要时用 em.refresh(post) 重新加载。

动手练习

  1. 发一篇文章，给它评论 35 条（每页 30 条）。确认第 36 次评论之后， 页面自动跳到了第 2 页，而且你的新评论在最底下。
  2. 用协管员账号隐藏一条评论。然后：
    • 用匿名浏览器（无痕窗口）打开那篇文章，确认看不到那条评论；
    • 确认评论总数也相应少了 1（这验证了 count 查询也过滤了）；
    • 用那条评论的作者登录，确认他也看不到自己被隐藏的评论。
  3. 在评论里输入 # 巨大标题 和一个表格，确认它们没有被渲染成标题和表格 （因为评论的白名单不允许）—— 对比在文章里输入同样内容的效果。
