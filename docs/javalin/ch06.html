电子邮件

第 8 章的“注册后发确认邮件”“忘记密码”都需要先有发邮件的能力。 这一章用 Jakarta Mail 把它搭起来，用 JTE 渲染邮件正文， 并且解决一个性能问题：发邮件很慢，不能让用户的浏览器干等着。

本章目标

  • 搞清楚 SMTP 在整条邮件链路里的位置
  • 配好 Jakarta Mail，会发一封纯文本 + HTML 的双版本邮件
  • 用本地假 SMTP 服务器做开发（比用真邮箱更快更安全）
  • 用 JTE 渲染邮件正文，复用第 3 章的模板能力
  • 把发送丢到后台线程，不阻塞请求

SMTP 在哪一环

先把概念理清楚：你的应用不"发送"邮件，它只是把邮件交给一台 SMTP 服务器， 剩下的投递工作由邮件系统接力完成。

Jakarta Mail

Python 标准库自带 smtplib，原书用 Flask-Mail 把它包了一层。 Java 的情况是：标准只定义了接口（jakarta.mail）， 实现要另外加（Eclipse 的 Angus Mail，前身是 JavaMail）。

<dependency>

  <artifactId>angus-mail</artifactId>
  <version>2.0.3</version>
</dependency>

开发环境：用本地假 SMTP 服务器

原书让读者配 Gmail，还要去开“允许不够安全的应用”。 今天 Gmail 已经关掉了这个开关（必须用应用专用密码或 OAuth2），而且用真邮箱开发有几个实际问题： 发信慢、有频率限制、测试邮件可能真的发给了别人、密码容易误提交到 Git。

☀ 强烈推荐：Mailpit

Mailpit（或它的前辈 MailHog）是一个“假” SMTP 服务器： 它接收邮件但从不真的投递，而是存下来给你在网页上看。 一个命令就能跑起来： 

docker run -d --name mailpit -p 1025:1025 -p 8025:8025 axllent/mailpit
  • 1025 是 SMTP 端口 —— 应用往这里发，不需要认证、不需要 TLS
  • 8025 是网页界面 —— 打开 http://localhost:8025 就能看到所有邮件， 包括 HTML 版、纯文本版和原始源码

开发第 8 章的“注册确认邮件”时，这东西会让你省下大量时间 —— 点一下注册，立刻在网页上看到邮件，直接复制确认链接。

如果你坚持用 Gmail，现在的正确做法是：开启两步验证，然后生成一个应用专用密码（16 位），用它代替账号密码。

Mailer 类

先把配置抽成一个 record（第 7 章会统一管配置）：

package com.example.javalinky.mail;

public record MailConfig(
    String host,
    int port,
    boolean startTls,
    String username,       // 不需要认证时传 null
    String password,
    String from,           // 如 "Javalinky <no-reply@javalinky.example>"
    String subjectPrefix   // 如 "[Javalinky] "
) {
    /** 开发默认值：对准本地 Mailpit */
    public static MailConfig fromEnv() {
        var env = System.getenv();
        return new MailConfig(
            env.getOrDefault("MAIL_HOST", "localhost"),
            Integer.parseInt(env.getOrDefault("MAIL_PORT", "1025")),
            Boolean.parseBoolean(env.getOrDefault("MAIL_STARTTLS", "false")),
            env.get("MAIL_USERNAME"),
            env.get("MAIL_PASSWORD"),
            env.getOrDefault("MAIL_FROM", "Javalinky <no-reply@javalinky.example>"),
            env.getOrDefault("MAIL_SUBJECT_PREFIX", "[Javalinky] ")
        );
    }
}

package com.example.javalinky.mail;

import jakarta.mail.*;
import jakarta.mail.internet.*;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import java.nio.charset.StandardCharsets;
import java.util.Properties;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class Mailer {

    private static final Logger log = LoggerFactory.getLogger(Mailer.class);

    private final MailConfig config;
    private final Session session;
    private final ExecutorService executor;

    public Mailer(MailConfig config) {
        this.config = config;
        this.session = buildSession(config);
        // Java 21 的虚拟线程：每封邮件一个线程，廉价到可以随便创建
        this.executor = Executors.newVirtualThreadPerTaskExecutor();
    }

    private static Session buildSession(MailConfig c) {
        Properties props = new Properties();
        props.put("mail.smtp.host", c.host());
        props.put("mail.smtp.port", String.valueOf(c.port()));
        props.put("mail.smtp.starttls.enable", String.valueOf(c.startTls()));
        props.put("mail.smtp.connectiontimeout", "10000");  // 别让它无限期挂着
        props.put("mail.smtp.timeout", "10000");
        props.put("mail.smtp.writetimeout", "10000");

        if (c.username() == null || c.username().isBlank()) {
            props.put("mail.smtp.auth", "false");
            return Session.getInstance(props);
        }

        props.put("mail.smtp.auth", "true");
        return Session.getInstance(props, new Authenticator() {
            @Override
            protected PasswordAuthentication getPasswordAuthentication() {
                return new PasswordAuthentication(c.username(), c.password());
            }
        });
    }

    /** 同步发送：会阻塞到 SMTP 服务器返回（几百毫秒到几秒） */
    public void sendNow(String to, String subject, String textBody, String htmlBody) {
        try {
            var message = new MimeMessage(session);
            message.setFrom(new InternetAddress(config.from()));
            message.setRecipients(Message.RecipientType.TO, InternetAddress.parse(to));
            message.setSubject(config.subjectPrefix() + subject, "UTF-8");

            // multipart/alternative：同一封信的两个版本，客户端自己挑
            var textPart = new MimeBodyPart();
            textPart.setText(textBody, StandardCharsets.UTF_8.name());

            var htmlPart = new MimeBodyPart();
            htmlPart.setContent(htmlBody, "text/html; charset=UTF-8");

            var multipart = new MimeMultipart("alternative");
            multipart.addBodyPart(textPart);   // 顺序重要：后面的优先级更高
            multipart.addBodyPart(htmlPart);
            message.setContent(multipart);

            Transport.send(message);
            log.info("邮件已投递给 SMTP：to={} subject={}", to, subject);

        } catch (MessagingException e) {
            // 故意不往上抛：发邮件失败不该让用户的注册流程失败
            log.error("发送邮件失败：to={} subject={}", to, subject, e);
        }
    }

    /** 异步发送：立刻返回，真正的发送在后台线程里跑 */
    public void send(String to, String subject, String textBody, String htmlBody) {
        executor.submit(() -> sendNow(to, subject, textBody, htmlBody));
    }

    public void close() {
        executor.close();   // Java 19+：等待已提交的任务跑完
    }
}
ⓘ 为什么要发两个版本

multipart/alternative 里放纯文本和 HTML 两份内容相同的正文， 邮件客户端挑自己能显示的那个。

  • 纯文本版服务于命令行邮件客户端、屏幕阅读器、以及“关闭了图片和 HTML”的用户。
  • 而且只有 HTML 没有纯文本的邮件更容易被判为垃圾邮件。

加上纯文本版的成本就是多写一个模板，很值。

用 JTE 渲染邮件正文

原书用 render_template('auth/email/confirm.txt', user=user, token=token) 渲染邮件，和渲染网页用的是同一套模板引擎。我们也一样 —— 但有个细节要处理： 纯文本邮件不能做 HTML 转义（否则用户名里的 & 会变成 &amp;）。

JTE 的转义策略由 ContentType 决定，所以要建两个 TemplateEngine： 

package com.example.javalinky.web;

import gg.jte.ContentType;
import gg.jte.TemplateEngine;
import gg.jte.output.StringOutput;
import gg.jte.resolve.DirectoryCodeResolver;

import java.nio.file.Path;
import java.util.Map;

public final class Templates {

    private static final Path JTE_ROOT = Path.of("src", "main", "jte");

    /** 网页和 HTML 邮件用：会做按上下文的 HTML 转义 */
    public static final TemplateEngine HTML = TemplateEngine.create(
        new DirectoryCodeResolver(JTE_ROOT),
        Path.of("jte-classes", "html"),
        ContentType.Html);

    /** 纯文本邮件用：不做任何转义 */
    public static final TemplateEngine TEXT = TemplateEngine.create(
        new DirectoryCodeResolver(JTE_ROOT),
        Path.of("jte-classes", "text"),
        ContentType.Plain);

    /** 渲染成字符串（而不是直接写进 HTTP 响应） */
    public static String render(TemplateEngine engine, String template, Map<String, Object> model) {
        var output = new StringOutput();
        engine.render(template, model, output);
        return output.toString();
    }

    private Templates() {}
}

然后让 Javalin 用同一个 HTML 引擎，而不是自己再建一个：

config.fileRenderer(new JavalinJte(Templates.HTML));

💡 为什么 HTML 邮件里全是 style=""

邮件客户端对 CSS 的支持停留在二十年前： Outlook 会丢掉 <style> 块、Gmail 会重写类名、几乎没人支持 flex 和 grid。 所以 HTML 邮件的通行做法是行内样式 + 表格布局。 不要试图在邮件里复用网页的 CSS。

把它包成一个服务

package com.example.javalinky.mail;

import com.example.javalinky.web.Templates;
import java.util.Map;

/** 业务语义的邮件发送入口。处理器只调这里的方法，不碰 Mailer。 */
public class MailService {

    private final Mailer mailer;
    private final String siteBaseUrl;   // 如 "http://localhost:7070"

    public MailService(Mailer mailer, String siteBaseUrl) {
        this.mailer = mailer;
        this.siteBaseUrl = siteBaseUrl;
    }

    public void sendConfirmation(String to, String username, String token) {
        var model = Map.<String, Object>of(
            "username", username,
            "confirmUrl", siteBaseUrl + "/auth/confirm/" + token
        );
        mailer.send(to, "确认你的账号",
            Templates.render(Templates.TEXT, "mail/confirm.txt.jte", model),
            Templates.render(Templates.HTML, "mail/confirm.html.jte", model));
    }

    public void sendPasswordReset(String to, String username, String token) {
        var model = Map.<String, Object>of(
            "username", username,
            "resetUrl", siteBaseUrl + "/auth/reset/" + token
        );
        mailer.send(to, "重置你的密码",
            Templates.render(Templates.TEXT, "mail/reset.txt.jte", model),
            Templates.render(Templates.HTML, "mail/reset.html.jte", model));
    }

    /** 第 17 章：有新用户注册时通知管理员 */
    public void notifyAdminNewUser(String adminEmail, String username) {
        var model = Map.<String, Object>of("username", username);
        mailer.send(adminEmail, "新用户注册",
            Templates.render(Templates.TEXT, "mail/new_user.txt.jte", model),
            Templates.render(Templates.HTML, "mail/new_user.html.jte", model));
    }
}
⚠ 邮件里的链接必须是绝对 URL

第 3 章说过：站内链接用相对路径，但邮件是唯一必须用绝对 URL 的场景 —— 邮件客户端没有“当前站点”这个概念。

所以 siteBaseUrl 必须从配置来（第 7 章会把它放进 AppConfig）， 不能从请求里猜。原书用 _external=True 让 Flask 自动拼， 但那依赖 SERVER_NAME 配置，本质上也是同一件事。

异步发送：为什么必须这么做

原书也遇到了这个问题：“如果你发了几封测试邮件，大概注意到 mail.send() 会阻塞几秒， 浏览器在这段时间里看起来没反应。”

☀ 这里 Javalin 比 Flask 省事

原书在这一节踩了一个坑：把发送挪到后台线程之后，mail.send() 用到了 current_app，而新线程里没有应用上下文，于是必须手动 with app.app_context():，还得把 app 当参数传进线程。

Javalin 没有这个问题 —— 因为它压根没有“上下文”这种线程局部状态。 Mailer 就是一个普通对象，在哪个线程调都一样。 这就是第 2 章说的“显式传参”带来的好处之一。

虚拟线程还是线程池？

传统线程池（固定大小）
// 并发发信上限 = 4
Executors.newFixedThreadPool(4);
虚拟线程（Java 21）
// 每个任务一个虚拟线程，无上限
Executors.newVirtualThreadPerTaskExecutor();

发邮件是典型的 IO 阻塞任务，虚拟线程正好对症。 但注意：“无上限”在这里未必是好事 —— 如果某一刻涌入一万个注册请求，你会同时开一万个 SMTP 连接，服务商会直接限流封你。 真要上量，就该换成下一节说的队列。

🔎 深入：后台线程发邮件的三个固有缺陷

原书在这一节末尾提了一句“量大的话应该用 Celery 任务队列”。具体缺陷是：

  1. 进程一死就丢。部署重启、崩溃、容器被杀 —— 排队中的邮件没了，没人知道。
  2. 失败没有重试。SMTP 服务器临时抽风，这封邮件就永远发不出去了。 我们的 Mailer 只是记了条日志。
  3. 无法观测。“有多少封在排队、哪些失败了”没有任何地方能查。

正确的做法是持久化队列：把“要发的邮件”写进数据库表（或 Redis、SQS）， 由一个独立的 worker 进程取出来发，失败则按指数退避重试。 Java 生态可以用 Quartz、JobRunr、db-scheduler，或者最简单的 —— 自己建一张 outbox 表 + 一个定时任务。

教程里不做这一步（会偏离主线），但上线前请认真考虑： “确认邮件没发出去”意味着用户永远无法完成注册。

接到应用里

public static void main(String[] args) {
    Db.init(/* ... */);

    var mailer = new Mailer(MailConfig.fromEnv());
    var mail = new MailService(mailer,
        System.getenv().getOrDefault("SITE_BASE_URL", "http://localhost:7070"));

    Runtime.getRuntime().addShutdownHook(new Thread(() -> {
        mailer.close();   // 等待排队中的邮件发完
        Db.close();
    }));

    Javalin.create(config -> {
        config.fileRenderer(new JavalinJte(Templates.HTML));
        // ...

        // 临时的试验路由，第 8 章会换成真正的注册流程
        config.routes.post("/", ctx -> {
            // ... 第 5 章的建用户逻辑 ...
            if (!known) {
                mail.notifyAdminNewUser(
                    System.getenv().getOrDefault("ADMIN_EMAIL", "admin@example.com"),
                    form.name());
            }
            ctx.redirect(Routes.INDEX);
        });
    }).start(port);
}

⚠ 三条底线
  1. .env 必须在 .gitignore 里（第 1 章已经加了）。
  2. 仓库里放一份 .env.example，列出需要哪些变量但不填真值，方便新同事。
  3. 密码一旦提交过就算泄露了，必须换新的 —— 删掉那次提交没用，Git 历史里还在，而且可能已经被爬虫抓走。

动手练习

  1. 跑起 Mailpit，发一封测试邮件。在 Mailpit 的网页界面里切换 HTML / Text / Raw 三个标签页， 看看一封 multipart/alternative 邮件的原始样子。
  2. 把 Mailer.send() 临时换成 sendNow()， 在 sendNow 开头加一句 Thread.sleep(3000) 模拟慢 SMTP， 然后提交表单 —— 亲自感受一下那三秒。改回异步再试一次。
  3. 把 MAIL_PORT 改成一个没人监听的端口（比如 1099），再发一次。 确认用户的请求照常成功，而错误只出现在日志里。 思考：这个设计在什么场景下是对的，什么场景下是错的？
  4. 写一个 mail/reset.txt.jte 和 mail/reset.html.jte （第 8 章会用到）。注意纯文本版里不要出现 HTML 标签。
  5. 在纯文本模板里写一个包含 & 和 < 的用户名， 确认它没有被转义成 &amp;。 然后故意用 Templates.HTML 去渲染那个 .txt.jte， 对比结果 —— 这就是为什么要两个引擎。
  6. 给 MailService 加一个开关：当环境变量 MAIL_ENABLED=false 时， 只把邮件内容打到日志而不真发。这在跑自动化测试时很有用（第 15 章）。
