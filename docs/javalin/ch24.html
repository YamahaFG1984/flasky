第 24 章

依赖治理

这个项目的 pom.xml 里有二十来条依赖， 而 mvn dependency:tree 展开之后是一百多个 jar。 这一章讲怎么管住它们：版本冲突怎么查、哪些工具可信哪些会误报、 以及怎么把「已经治好的问题」钉住不让它退回去。 本章所有的输出都是在这个项目上真跑出来的，不是编的例子。

本章目标

  • 搞清 Maven 的「最近者优先」仲裁规则，以及它什么时候会选错
  • 会用 dependency:tree / analyze，并知道后者一半的警告是误报
  • 用 maven-enforcer-plugin 把规则变成构建门槛
  • 分清 dependencyConvergence 和 requireUpperBoundDeps，知道该用哪个
  • 知道怎么查依赖里的已知漏洞，以及怎么决定升不升级
📦 本章代码

这一章结束时的完整项目在仓库的 javalinky/ 目录里，对应标签 jv-ch24： 

git checkout jv-ch24
cd javalinky && mvn validate      # 看 enforcer 跑起来

本章在 pom.xml 上加了 maven-enforcer-plugin， 并修掉了它报出来的 4 条真实问题。

Maven 怎么决定用哪个版本

这是一切的起点。npm 可以让同一个库的多个版本共存（嵌套 node_modules），Java 不行 —— 一个 classpath 上同一个类只能有一份。所以 Maven 必须挑一个。

☀ 出事的形状永远是同一个：NoSuchMethodError

第 8 章我们已经撞过一次：引入 java-jwt 之后运行时抛 

java.lang.NoSuchMethodError:
  'void com.fasterxml.jackson.core.util.BufferRecycler.releaseToPool()'

原因就是仲裁选了一个比某个使用者要求的还低的 jackson-core。编译期完全正常 —— 因为编译时用的是另一个模块的字节码，运行时才发现方法不存在。

这是 Java 依赖地狱的标准症状，值得单独记住： NoSuchMethodError / NoSuchFieldError 几乎总是版本冲突； ClassNotFoundException 才是「压根没这个依赖」。

第一个工具：dependency:tree

mvn dependency:tree                                       # 整棵树（一百多行）
mvn dependency:tree -Dincludes=com.fasterxml.jackson      # 只看某个 groupId
mvn dependency:tree -Dincludes=:::*:jar                   # 过滤语法：group:artifact:type:version
mvn dependency:tree -Dverbose                             # 连被淘汰的版本一起显示
ⓘ -Dverbose 才是排查冲突真正要用的那个

默认输出只显示赢家，所以你看到的是一棵「干净」的树 —— 冲突已经被悄悄解决掉了。加上 -Dverbose 会把 (omitted for conflict with 2.20.0) 这类注记也打出来， 那才是你要找的东西。

⚠ 下面那一组几乎全是误报，照着删会把应用删崩

「Unused declared」里的每一个都是必需的， 原因是同一个： 它们是通过 ServiceLoader 或反射在运行时加载的， 我们的代码里一行都不会 import 它们， 而分析器只会扫字节码里的引用。

被判「没用」的实际怎么被用到删了会怎样
logback-classicSLF4J 在启动时通过 ServiceLoader 找实现 日志全部消失，只剩一句「没有日志实现」的警告
h2 / postgresqlJDBC 驱动，按 URL 前缀自动注册 启动时「No suitable driver」
hibernate-validator
expressly		 Bean Validation 的实现，我们只 import 了 jakarta.validation 的接口 校验直接抛「找不到实现」
angus-mailJakarta Mail 的实现，同上发不出邮件
hibernate-hikaricp连接池集成，persistence.xml 里按类名配的启动失败
flyway-database-postgresqlFlyway 的 PG 方言插件连 PG 时迁移失败

这就是「接口和实现分开」这种设计的代价： 静态分析看不见运行时的连线。遇到这类误报，正确做法是 标注出来而不是删掉： 

<plugin>
  <artifactId>maven-dependency-plugin</artifactId>
  <configuration>
    <ignoredUnusedDeclaredDependencies>
      <!-- 这些是运行时实现，靠 ServiceLoader 加载，分析器看不见 -->
      <ignoredUnusedDeclaredDependency>ch.qos.logback:logback-classic</ignoredUnusedDeclaredDependency>
      <ignoredUnusedDeclaredDependency>com.h2database:h2</ignoredUnusedDeclaredDependency>
      <!-- ... -->
    </ignoredUnusedDeclaredDependencies>
  </configuration>
</plugin>
☀ 上面那一组（Used undeclared）倒是真问题

我们的代码直接 import org.eclipse.jetty...、 import jakarta.persistence...、org.slf4j...， 但 pom.xml 里一条都没声明 —— 它们是跟着 javalin 和 hibernate-core 蹭进来的。

风险很具体：哪天 Javalin 换掉 Jetty（比如上 Jetty 13）， 我们的代码会毫无预警地编译不过， 而我们从来没主动选择过依赖 Jetty。

「我 import 它，我就该声明它」 —— 这条规矩让「我依赖什么」变成一个显式的决定。 不过也要权衡：全部声明意味着多出十几条，而且每条都要自己管版本。 实践中的折中是：稳定的 API 包（jakarta.*、 slf4j-api）显式声明； 框架内部的实现细节（Jetty）就让它跟着框架走， 并接受「框架换引擎时我要改代码」这个事实。

把规则变成构建门槛

上面两个命令要人记得去跑。maven-enforcer-plugin 能让违规直接构建失败 —— 这才叫治理。

两条容易混的规则

dependencyConvergencerequireUpperBoundDeps
要求所有路径请求的版本完全一致 仲裁结果不低于任何一条路径的要求
在本项目上7 条失败4 条失败
失败的性质大多是无害的补丁号差异每一条都是真问题
适合当门槛吗太严，会被噪音淹没适合

dependencyConvergence 在本项目上报的 7 条，长这样： 

Dependency convergence error for gg.jte:jte:jar:3.2.3 paths to dependency are:
+-com.example:javalinky:jar:1.0-SNAPSHOT
  +-io.javalin:javalin-rendering-jte:jar:7.2.3:compile
    +-gg.jte:jte:jar:3.2.3:compile
and
+-com.example:javalinky:jar:1.0-SNAPSHOT
  +-gg.jte:jte:jar:3.2.4:compile
ⓘ 这一条其实完全没问题

我们在 pom.xml 里直接写了 JTE 3.2.4， 而 javalin-rendering-jte 依赖的是 3.2.3。 仲裁选了 3.2.4（直接声明胜出）， 比谁要求的都高 —— 向后兼容的补丁版本，安全。

另外 6 条是 slf4j-api 2.0.17 vs 2.0.18 之类，同理。 如果把 dependencyConvergence 设成门槛， 你每周都要处理这种噪音，最后的结果一定是把规则关掉。

四条全都是「拿到的版本比某个使用者要求的低」。 目前没出问题，只是因为那几个补丁版本之间碰巧没有 新增必需的 API。

这就是这个规则的价值：它在事故发生之前就把隐患标出来了。 第 8 章那个 NoSuchMethodError 是线上炸了才去查的； 这四条是构建时就被拦住的。

修法：在 dependencyManagement 里钉住

<dependencyManagement>
  <dependencies>
    <!-- 第 24 章：把被「最近者优先」仲裁到偏低版本的依赖钉回去。
         这几条是 mvn enforcer requireUpperBoundDeps 真实报出来的，不是凭空加的。 -->
    <dependency>
      <groupId>jakarta.activation</groupId>
      <artifactId>jakarta.activation-api</artifactId>
      <version>2.1.4</version>
    </dependency>
    <dependency>
      <groupId>jakarta.xml.bind</groupId>
      <artifactId>jakarta.xml.bind-api</artifactId>
      <version>4.0.5</version>
    </dependency>
    <dependency>
      <groupId>org.eclipse.angus</groupId>
      <artifactId>angus-activation</artifactId>
      <version>2.0.3</version>
    </dependency>
    <dependency>
      <groupId>org.jboss.logging</groupId>
      <artifactId>jboss-logging</artifactId>
      <version>3.6.3.Final</version>
    </dependency>

    <!-- 第 8 章就加的：用 BOM 统一整个 Jackson 家族 -->
    <dependency>
      <groupId>com.fasterxml.jackson</groupId>
      <artifactId>jackson-bom</artifactId>
      <version>${jackson.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

ⓘ 优先用 BOM，不得已才一条条钉

上面四条是手写的，因为它们来自不同的项目、没有共同的 BOM。 只要有 BOM 就用 BOM（第 8 章的 jackson-bom）：手写版本号意味着你从此要自己盯着它们升级， 而 BOM 是上游维护的。

最终的 enforcer 配置

<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-enforcer-plugin</artifactId>
  <version>3.5.0</version>
  <executions>
    <execution>
      <id>enforce-dependencies</id>
      <phase>validate</phase>        <!-- 最早的阶段，几秒就跑完 -->
      <goals><goal>enforce</goal></goals>
      <configuration>
        <rules>
          <requireMavenVersion><version>[3.9,)</version></requireMavenVersion>
          <requireJavaVersion><version>[21,)</version></requireJavaVersion>

          <!-- 仲裁结果不能低于任何一条路径要求的版本。
               这正是第 8 章 jackson 那个 NoSuchMethodError 的形状 -->
          <requireUpperBoundDeps/>

          <!-- 同一个依赖在 pom 里写了两遍（版本还不同）—— 纯粹的人为失误 -->
          <banDuplicatePomDependencyVersions/>

          <!-- 版本范围让构建不可复现：今天和下周拉到的可能不是同一个 jar -->
          <requireReleaseDeps>
            <message>不要用 SNAPSHOT 依赖</message>
            <onlyWhenRelease>true</onlyWhenRelease>
          </requireReleaseDeps>
        </rules>
      </configuration>
    </execution>
  </executions>
</plugin>
☀ 治理的要点是「修完之后钉住」

手工跑一次 dependency:tree 把冲突解决掉，是一次性的劳动 —— 下次有人加一条依赖，问题就回来了，而且没人会发现。

把它变成构建门槛之后，「引入冲突」这件事会在提交 PR 的那一刻 就被挡住，成本从「线上排查两小时」降到「改一行版本号」。

放在 validate 阶段是因为它几秒钟就跑完 —— 在编译和测试之前失败，开发者不用等。

已知漏洞：查，然后判断

# OWASP Dependency-Check：对着 NVD 数据库扫
mvn org.owasp:dependency-check-maven:check

# 第一次要下载整个 NVD 数据库，很慢（而且现在需要 NVD API key）
# CI 上记得缓存 ~/.m2/repository/org/owasp/dependency-check-data
工具特点
OWASP Dependency-Check 开源、本地跑、不传代码出去。误报较多（靠文件名猜构件）
GitHub Dependabot 免费、自动提 PR 升级。公开仓库基本没理由不开
Snyk / Sonatype 商业，数据质量和可达性分析更好，要钱
⚠ 「有 CVE」不等于「你被影响」

最著名的例子是 Log4Shell 时期的集体恐慌：很多人在 根本没用 log4j 的项目里疯狂升级， 也有人升级了 log4j-api（没有漏洞的那个）而漏掉了 log4j-core。

判断一个 CVE 是否影响你，问三个问题：

  1. 这个有漏洞的类/方法，在你的代码路径上吗？ （很多 CVE 只影响某个你从没调过的解析器）
  2. 攻击者能控制到达那里的输入吗？
  3. 升级的代价是什么？有没有破坏性变更

但也别滑到另一个极端。默认动作应该是升级 —— 只有当升级代价确实很大时，才花时间做上面的分析。 「我分析过了，不影响」这句话需要有人为它负责， 而且下次依赖变动时结论可能就变了。

升级这件事

mvn versions:display-dependency-updates     # 哪些依赖有新版
mvn versions:display-plugin-updates         # 插件也要升，很多人忘了这条
mvn versions:display-property-updates       # 用 property 管的版本号

mvn versions:set -DnewVersion=1.1.0         # 改自己项目的版本
☀ 小步快跑，比攒着一次升强得多

「等不忙了一次性升级」听着合理，实际是最糟的策略：

  • 攒了两年再升，一次要跨越十几个破坏性变更， 而且出了问题不知道是哪一个造成的
  • 中间的 CVE 全都在你身上挂着
  • 最后往往升不动了，变成「这个项目不能动」

可行的节奏：开 Dependabot，补丁版本自动合（测试绿就行）， 次版本每月看一眼，主版本当成一个正经任务排期。 前提是你的测试套件足够可信 —— 这就是第 15 章那 120 个测试在这里的价值： 它们让「升级」从一件需要勇气的事，变成一件看 CI 红绿的事。

ⓘ 关于「没有锁文件」这件事

npm 有 package-lock.json 保证每次装的一模一样， Maven 没有对应物。替代方案是三件事一起用：

  • 永远写死版本号，不要用 [1.0,2.0) 这种范围
  • 用 BOM 统一一组相关依赖
  • enforcer 把仲裁结果钉住

要更强的可复现性，可以看 maven-dependency-plugin 的 dependency:list -DoutputFile=， 把完整的解析结果提交进版本库，再加一个测试比对 —— 这是穷人版的锁文件，但确实管用。

一张检查清单

什么时候做什么
加一条新依赖前 看它的传递依赖（dependency:tree）； 看它最近一次发布是什么时候；想想能不能不加
加完之后 mvn validate 看 enforcer 有没有红； dependency:tree -Dverbose 看有没有把别人挤下去
遇到 NoSuchMethodError 先想版本冲突，dependency:tree -Dincludes=<那个 groupId>
每月 versions:display-dependency-updates， 升补丁和次版本
CI 里常驻 enforcer（已配）+ Dependabot + 漏洞扫描
打 fat jar 时 记得 shade 的 <filters>（第 7 章）和 ServicesResourceTransformer —— 依赖合并会出各种怪事

动手练习

  1. 看看被淘汰的版本。跑 mvn dependency:tree -Dverbose -Dincludes=org.slf4j， 找出 (omitted for conflict with ...) 那几行。
  2. 亲手制造一次冲突。在 pom.xml 里显式加一条 org.slf4j:slf4j-api:1.7.36（一个老得多的版本）， 然后 mvn validate。看 enforcer 怎么拦你。
  3. 把 requireUpperBoundDeps 换成 dependencyConvergence， 跑一次，数一数报了几条，判断一下其中几条是真问题。 体会为什么本章选了前者。
  4. 验证「误报」真的是误报。按 dependency:analyze 的建议把 com.h2database:h2 删掉，mvn test。 看报错长什么样，想清楚为什么分析器看不见它。
  5. 反过来，按它的建议显式声明 org.slf4j:slf4j-api 和 jakarta.persistence:jakarta.persistence-api。 再跑 dependency:analyze，看警告少了几条。
  6. 给仓库开 Dependabot：加一个 .github/dependabot.yml，package-ecosystem: maven， 每周检查。看它第一周提了几个 PR。
  7. 跑一次 mvn org.owasp:dependency-check-maven:check （要耐心，第一次很慢）。对报出来的每一条问那三个问题。
  8. （进阶）做一个穷人版锁文件： 用 dependency:list -DoutputFile=deps.txt -DoutputScope=false 把解析结果存进版本库，再写一个测试比对当前结果和文件是否一致。 然后故意升一个依赖，看测试怎么告诉你 classpath 变了。
