第 4 章

Web 表单

前三章的数据都是从服务器流向用户。这一章让数据反向流动：用户填表单，服务器接收、校验、保存。 听起来简单，但里面藏着四个绕不开的问题：怎么优雅地报校验错误、刷新页面为什么会重复提交、 怎么在两次请求之间记住东西、以及怎么防住 CSRF 攻击。

本章目标

  • 会用 Javalin 的 Validator 读取并校验表单字段
  • 会用 Jakarta Bean Validation 注解声明式地校验整个表单对象
  • 写出一个可复用的表单字段模板片段（相当于 Flask-Bootstrap 的 quick_form）
  • 理解并实现 Post/Redirect/Get 模式
  • 配好服务端会话，理解它和 Flask 签名 Cookie 会话的区别
  • 实现 Flash 一次性消息
  • 理解 CSRF 攻击的原理，并亲手写一套防护

表单的两次请求

一个表单从出现在屏幕上到数据进库，至少经过两次 HTTP 请求。 这是本章所有复杂性的根源，先把它看清楚：

原书用 Flask-WTF + WTForms 把这整套流程包了起来：一个 FlaskForm 子类同时负责 声明字段、校验、渲染 HTML、CSRF 防护四件事。 Java 没有一个这样的大一统方案 —— 我们要把这四件事分开做。 好消息是分开之后每一块都很简单，而且你能看清每一块在干什么。

ⓘ Validator 适合什么、不适合什么

适合：URL 查询参数、API 的单个字段 —— 校验失败直接返回 400 就够了。

不适合：网页表单。因为网页表单失败时不能只返回 400， 得把表单连同错误和用户已填的内容一起重新渲染。 所以下面我们换一套做法。

常用约束注解

注解作用WTForms 的对应
@NotNull不能为 nullInputRequired
@NotBlank字符串不能为 null / 空 / 全空白DataRequired
@NotEmpty集合或字符串不能为空—
@Size(min=, max=)长度范围Length
@Email邮箱格式Email
@Pattern(regexp=)正则匹配Regexp
@Min / @Max数值范围NumberRange
@Positive / @PositiveOrZero正数 / 非负数—
@Past / @Future日期在过去 / 未来—
@AssertTrue布尔值必须为 true（“我已阅读条款”）—
💡 跨字段校验（“两次密码必须一致”）

WTForms 用 EqualTo('password2')。Bean Validation 的注解是单字段的， 跨字段校验最简单的办法是在 record 里加一个 @AssertTrue 的派生属性： 

public record RegisterForm(
    @NotBlank @Email String email,
    @NotBlank @Pattern(regexp = "^[A-Za-z][A-Za-z0-9_.]*$",
        message = "用户名只能包含字母、数字、点和下划线，且必须以字母开头")
    String username,
    @NotBlank @Size(min = 8, message = "密码至少 8 位") String password,
    @NotBlank String password2
) {
    @AssertTrue(message = "两次输入的密码不一致")
    public boolean isPasswordsMatch() {
        return password != null && password.equals(password2);
    }
}

校验器会把这个属性的错误挂在字段名 passwordsMatch 上。 至于“邮箱是否已被注册”这类需要查数据库的校验，不要写进注解 —— 放在处理器里，第 8 章会这么做。

把校验结果包装成一个好用的东西

原书的 form.validate_on_submit() 返回一个布尔值，失败时 form.errors 里有错误。 我们做一个等价的小工具类： 

package com.example.javalinky.web;

import jakarta.validation.ConstraintViolation;
import jakarta.validation.Validation;
import jakarta.validation.Validator;
import java.util.*;

public final class Forms {

    // Validator 是线程安全的，创建一次全局复用（创建开销不小）
    private static final Validator VALIDATOR =
        Validation.buildDefaultValidatorFactory().getValidator();

    /**
     * 校验一个表单对象。
     * @return 字段名 → 该字段的全部错误信息。没有错误时返回空 Map。
     */
    public static <T> Map<String, List<String>> validate(T form) {
        Map<String, List<String>> errors = new LinkedHashMap<>();
        for (ConstraintViolation<T> v : VALIDATOR.validate(form)) {
            String field = v.getPropertyPath().toString();
            errors.computeIfAbsent(field, k -> new ArrayList<>()).add(v.getMessage());
        }
        return errors;
    }

    private Forms() {}
}

再定义一个“表单 + 错误”的容器，传给模板用。 它承担了 WTForms 里“回填用户输入”和“显示错误”两个职责： 

package com.example.javalinky.web;

import java.util.List;
import java.util.Map;

/**
 * 传给模板的表单状态。
 * values：要回填到 input 里的值（键是字段名）
 * errors：字段名 → 错误信息
 */
public record FormView(Map<String, String> values, Map<String, List<String>> errors) {

    public static FormView empty() {
        return new FormView(Map.of(), Map.of());
    }

    /** 模板里取回填值，没有就返回空串（不会是 null，模板省一层判断） */
    public String value(String field) {
        return values.getOrDefault(field, "");
    }

    public boolean hasError(String field) {
        return errors.containsKey(field);
    }

    /** 该字段的第一条错误，没有则返回 null */
    public String error(String field) {
        List<String> list = errors.get(field);
        return list == null || list.isEmpty() ? null : list.get(0);
    }

    public boolean ok() {
        return errors.isEmpty();
    }
}

  @endif

⚠ 密码框永远不要回填

注意上面那行 type.equals("password") ? "" : form.value(name)。 把密码写回 HTML 会让它出现在页面源码、浏览器缓存、甚至某些代理日志里。 校验失败时让用户重新输密码是业界通行做法。

ⓘ novalidate 是故意加的

<form novalidate> 关掉浏览器自带的 HTML5 校验弹泡， 这样你能在开发时看到服务端的校验结果。 上线时可以去掉它 —— 浏览器校验是很好的即时反馈。 但无论如何，服务端校验不能省： 任何人都能绕过浏览器直接 curl 你的接口。

处理器：一个路由，两种方法

原书的视图函数同时处理 GET 和 POST（methods=['GET','POST']）， 用 form.validate_on_submit() 区分。 Javalin 的路由是按方法注册的，所以写成两个处理器 —— 其实更清楚： 

// GET：渲染一个空表单
config.routes.get(Routes.LOGIN, ctx ->
    View.render(ctx, "auth/login.jte", "登录", "form", FormView.empty()));

// POST：接收、校验、处理
config.routes.post(Routes.LOGIN, ctx -> {
    var form = new LoginForm(
        ctx.formParam("email"),
        ctx.formParam("password"),
        ctx.formParam("remember") != null
    );

    var errors = Forms.validate(form);
    if (!errors.isEmpty()) {
        // 校验失败：回填 + 显示错误，重新渲染（HTTP 200，不是重定向）
        var values = new HashMap<String, String>();
        values.put("email", form.email() == null ? "" : form.email());
        if (form.remember()) values.put("remember", "1");

        View.render(ctx, "auth/login.jte", "登录",
                    "form", new FormView(values, errors));
        return;
    }

    // 校验通过：业务逻辑（第 8 章会真的验证密码）
    ctx.sessionAttribute("flash", "登录成功！");
    ctx.redirect(Routes.INDEX);     // ← 关键：重定向，不是渲染
});
💡 校验失败时该返回什么状态码？

严格说应该是 422 Unprocessable Content。但实践中返回 200 更常见， 因为我们返回的是一个完整可用的 HTML 页面，不是错误。 如果是 JSON API，就该用 400 / 422（第 14 章）。

Post/Redirect/Get

上面那行 ctx.redirect(...) 看着不起眼，它解决的是一个很烦人的真实问题。 试一下：如果成功之后直接渲染页面（而不是重定向），然后按浏览器的刷新按钮 —— 浏览器会问你“要重新提交表单吗？”，确认之后，数据被提交了两遍。

☀ 一条可以当纪律执行的规则

任何修改了服务器状态的 POST 处理器，结束时必须 ctx.redirect(...)， 不能 ctx.render(...)。 唯一的例外是校验失败 —— 那时什么都没改，重新渲染是安全的。

会话

HTTP 是无状态的：服务器处理完一个请求就把一切忘了。 要“记住”用户登录了、购物车里有什么、刚才提交成功了，就需要会话。

这里 Flask 和 Javalin 走的是两条完全不同的路，必须讲清楚：

用起来

Javalin 默认已经有一个内存会话，直接就能用：

ctx.sessionAttribute("userId", 7L);          // 写
Long userId = ctx.sessionAttribute("userId"); // 读（类型由左边推断，取不到是 null）
ctx.sessionAttribute("userId", null);         // 删
ctx.consumeSessionAttribute("flash");         // 读一次然后删掉（Flash 消息就用它）
ctx.req().getSession().invalidate();          // 整个会话作废（登出时用）

调一下会话 Cookie

默认配置能跑，但 Cookie 名字和安全属性值得自己定：

package com.example.javalinky;

import org.eclipse.jetty.ee10.servlet.SessionHandler;
import org.eclipse.jetty.http.HttpCookie;

public final class Sessions {

    public static SessionHandler handler(boolean httpsOnly) {
        SessionHandler h = new SessionHandler();
        h.setSessionCookie("JAVALINKY_SESSION");
        h.setHttpOnly(true);                                 // JS 读不到
        h.setSameSite(HttpCookie.SameSite.LAX);              // 挡掉跨站请求携带
        h.setSecureRequestOnly(httpsOnly);                   // 生产环境 true
        h.setMaxInactiveInterval(60 * 60 * 24 * 7);          // 7 天不活动就过期
        return h;
    }

    private Sessions() {}
}

Javalin.create(config -> {
    config.jetty.modifyServletContextHandler(handler ->
        handler.setSessionHandler(Sessions.handler(false)));
    // ...
});
ⓘ 关于 SessionHandler 的 import

Jetty 12 把 Servlet 相关的类放进了 ee10 模块，所以包名是 org.eclipse.jetty.ee10.servlet.SessionHandler。 如果你的 IDE 提示找不到，让它自动补全 import 就行 —— 这个类随 Javalin 的 Jetty 依赖一起进来，不用额外加依赖。

默认的会话数据存在内存里，所以重启应用会把所有人踢下线。 开发时无所谓；第 17 章我们会讲生产环境怎么把会话放到文件或数据库里（或者干脆不用会话，改用 JWT）。

Flash 消息

Flash 消息就是“显示一次就消失的提示”：操作成功、密码错误、权限不足。 它必须跨越一次重定向存活，所以要存在会话里 —— 而且读完就删。

Javalin 的 consumeSessionAttribute() 正是为此而生（读取并置空）。 做一个小类把它包起来，支持多条消息和不同级别： 

package com.example.javalinky.web;

import io.javalin.http.Context;
import java.util.ArrayList;
import java.util.List;

/** 一条一次性提示消息。level 直接用 Bootstrap 的样式名。 */
public record Flash(String level, String message) {

    private static final String KEY = "flash";

    public static void success(Context ctx, String msg) { add(ctx, "success", msg); }
    public static void info(Context ctx, String msg)    { add(ctx, "info", msg); }
    public static void warning(Context ctx, String msg) { add(ctx, "warning", msg); }
    public static void danger(Context ctx, String msg)  { add(ctx, "danger", msg); }

    private static void add(Context ctx, String level, String msg) {
        List<Flash> list = ctx.sessionAttribute(KEY);
        if (list == null) {
            list = new ArrayList<>();
            ctx.sessionAttribute(KEY, list);
        }
        list.add(new Flash(level, msg));
    }

    /** 取出全部消息并清空。相当于 Flask 的 get_flashed_messages()。 */
    public static List<Flash> consume(Context ctx) {
        List<Flash> list = ctx.consumeSessionAttribute(KEY);
        return list == null ? List.of() : list;
    }
}

消息要在每一个页面上都能显示，所以让 Layout 带上它， 在布局模板里统一渲染 —— 和原书把 get_flashed_messages() 放在 base.html 里是同一个思路： 

package com.example.javalinky.web;

import java.util.List;

public record Layout(String title, String csrfToken, List<Flash> flashes) {}

public static void render(Context ctx, String template, String title, Object... pairs) {
    Map<String, Object> model = new HashMap<>();
    model.put("layout", new Layout(
        title,
        ctx.attribute("csrfToken"),   // 由 CSRF 过滤器放进来，见下一节
        Flash.consume(ctx)            // 注意：读取即清空
    ));
    for (int i = 0; i < pairs.length; i += 2) {
        model.put((String) pairs[i], pairs[i + 1]);
    }
    ctx.render(template, model);
}

<div class="container py-4">

    <div class="alert alert-${flash.level()} alert-dismissible fade show" role="alert">
      ${flash.message()}

⚠ 一个容易踩的坑

Flash.consume() 是破坏性读取。 如果某次请求渲染了页面但消息没被显示出来（比如模板里忘了那段 @for）， 消息就永久丢了。所以：只在真正要渲染页面时调用 View.render， 不要在 before 钩子之类的地方提前取。

CSRF 防护

原书说“Flask-WTF 需要 SECRET_KEY，因为它要给所有表单生成 CSRF 令牌”， 然后就没再深入。但这个攻击值得你真正理解一次 —— 因为 Javalin 不替你做，得你自己写。 （好消息：写完你就永远懂了。）

攻击是怎么发生的

实现

package com.example.javalinky.web;

import io.javalin.config.JavalinConfig;
import io.javalin.http.Context;
import io.javalin.http.ForbiddenResponse;

import java.security.MessageDigest;
import java.security.SecureRandom;
import java.util.Base64;
import java.util.Set;

public final class Csrf {

    private static final String SESSION_KEY = "csrfToken";
    private static final String FORM_FIELD = "_csrf";
    private static final String HEADER = "X-CSRF-Token";

    /** 不会改变服务器状态的方法，不需要校验 */
    private static final Set<String> SAFE = Set.of("GET", "HEAD", "OPTIONS", "TRACE");

    private static final SecureRandom RANDOM = new SecureRandom();

    /** 在 Javalin 配置里调一次，装上两个过滤器 */
    public static void install(JavalinConfig config) {

        // ① 每个请求：确保会话里有令牌，并暴露给模板
        config.routes.before(ctx -> ctx.attribute(SESSION_KEY, tokenFor(ctx)));

        // ② 不安全的方法：校验令牌
        config.routes.before(ctx -> {
            if (SAFE.contains(ctx.method().name())) return;

            String sessionToken = ctx.sessionAttribute(SESSION_KEY);
            String submitted = ctx.formParam(FORM_FIELD);
            if (submitted == null) submitted = ctx.header(HEADER);   // AJAX 走请求头

            if (sessionToken == null || submitted == null || !constantTimeEquals(sessionToken, submitted)) {
                throw new ForbiddenResponse("CSRF 令牌缺失或不匹配，请刷新页面重试");
            }
        });
    }

    /** 取当前会话的令牌，没有就生成一个 */
    private static String tokenFor(Context ctx) {
        String token = ctx.sessionAttribute(SESSION_KEY);
        if (token == null) {
            byte[] bytes = new byte[32];
            RANDOM.nextBytes(bytes);
            token = Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);
            ctx.sessionAttribute(SESSION_KEY, token);
        }
        return token;
    }

    /**
     * 定长时间比较，避免"按字符逐个比较、不同就提前返回"泄露信息。
     * 普通的 equals() 比较越早失败返回越快，攻击者能据此一个字符一个字符地猜。
     */
    private static boolean constantTimeEquals(String a, String b) {
        return MessageDigest.isEqual(a.getBytes(), b.getBytes());
    }

    private Csrf() {}
}

之后每个 <form method="post"> 里都必须有 @template.tag.csrf(token = layout.csrfToken())。 忘了就会得到 403 —— 这个“失败很明显”的设计是故意的，总比默默不设防好。

💡 两层防御，不是一层
  1. SameSite=Lax Cookie（上一节配好了）：浏览器层面就不给跨站 POST 带 Cookie。 现代浏览器默认就是 Lax，这已经挡掉了绝大多数 CSRF。
  2. 令牌校验（这一节）：防住老浏览器、以及 SameSite 不生效的边缘情况 （比如同站的子域名被攻破）。

安全上这叫纵深防御。另外注意：第 14 章的 REST API 不需要 CSRF 令牌， 因为它用 Authorization 头认证，而浏览器不会自动帮攻击者加这个头。 届时我们会把 /api/* 排除掉。

把所有东西拼起来，App.java 现在是这样：

package com.example.javalinky;

import com.example.javalinky.web.*;
import io.javalin.Javalin;
import io.javalin.http.staticfiles.Location;
import io.javalin.rendering.template.JavalinJte;

import java.util.HashMap;

public class App {

    public static void main(String[] args) {
        int port = Integer.parseInt(System.getenv().getOrDefault("PORT", "7070"));

        Javalin.create(config -> {

            config.fileRenderer(new JavalinJte(JavalinJte.directoryTemplateEngine()));

            config.staticFiles.add(f -> {
                f.directory = "/public";
                f.location = Location.CLASSPATH;
                f.hostedPath = "/";
            });

            config.jetty.modifyServletContextHandler(h ->
                h.setSessionHandler(Sessions.handler(false)));

            Csrf.install(config);

            config.bundledPlugins.enableDevLogging();

            config.routes.error(404, "html", ctx ->
                View.render(ctx, "error/404.jte", "页面不存在"));
            config.routes.error(403, "html", ctx ->
                View.render(ctx, "error/403.jte", "没有权限"));
            config.routes.error(500, "html", ctx ->
                View.render(ctx, "error/500.jte", "服务器错误"));

            config.routes.get(Routes.INDEX, ctx ->
                View.render(ctx, "index.jte", "首页"));

            // --- 登录表单（第 8 章会接上真正的认证） ---
            config.routes.get(Routes.LOGIN, ctx ->
                View.render(ctx, "auth/login.jte", "登录", "form", FormView.empty()));

            config.routes.post(Routes.LOGIN, ctx -> {
                var form = new LoginForm(
                    ctx.formParam("email"),
                    ctx.formParam("password"),
                    ctx.formParam("remember") != null);

                var errors = Forms.validate(form);
                if (!errors.isEmpty()) {
                    var values = new HashMap<String, String>();
                    values.put("email", form.email() == null ? "" : form.email());
                    if (form.remember()) values.put("remember", "1");
                    View.render(ctx, "auth/login.jte", "登录",
                                "form", new FormView(values, errors));
                    return;
                }

                Flash.success(ctx, "表单校验通过！（真正的登录在第 8 章）");
                ctx.redirect(Routes.INDEX);
            });

        }).start(port);
    }
}

动手练习

  1. 提交一个空的登录表单，确认两个字段下面都出现了红色错误，并且邮箱框里你刚才填的内容被保留了。
  2. 临时把 login.jte 里的 @template.tag.csrf(...) 注释掉，再提交表单。 确认收到 403 和你写的那句提示 —— 这验证了防护真的在工作。
  3. 写一个注册表单（用上面的 RegisterForm），包括用户名正则和“两次密码一致”的检查。 故意填不一致的密码，看看错误挂在哪个字段名上，并在模板里把它显示出来。
  4. 把成功之后的 ctx.redirect(...) 改成 View.render(...)， 提交一次之后按 F5，观察浏览器的重复提交警告。然后改回来。
  5. 在首页加一个“访问计数器”：用 ctx.sessionAttribute("visits", ...) 记录你刷新了几次。 然后清掉浏览器 Cookie，确认计数归零。
  6. 打开浏览器开发者工具的 Application → Cookies，找到 JAVALINKY_SESSION， 确认它的 HttpOnly 和 SameSite 属性符合你的配置。然后在控制台里执行 document.cookie，确认看不到它。
