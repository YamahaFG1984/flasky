用户角色

上一章解决了“你是谁”（认证），这一章解决“你能干什么”（授权）。 我们会用位标志实现一套灵活的权限系统，然后接到 Javalin 的 路由角色机制上 —— 这是 Javalin 原生支持的功能，用起来比 Flask 的装饰器更清爽。

本章目标

  • 理解为什么用“权限位”而不是“角色名字符串”做判断
  • 会用位运算和 EnumSet 两种方式表达权限集合
  • 写一个可重复执行的角色播种任务
  • 用 Javalin 的 RouteRole + beforeMatched 实现声明式权限校验
  • 处理好“匿名用户”这个边界情况
  • 在模板里按权限显示/隐藏功能

为什么不是一个 isAdmin 布尔值

最朴素的做法是给 User 加一个 boolean admin。 但很快就不够用了：我们需要“能发文章但不能协管评论”的普通用户、 “能协管评论但不能改别人资料”的协管员、以及“什么都能干”的管理员。

第二种做法是存角色名字符串，然后到处写 if (user.getRole().equals("协管员"))。 这个做法的问题是：判断的是身份，而不是能力。 等你想加一个"高级会员"角色（也能协管评论）时， 得去代码里把所有相关的 if 找出来改一遍。

原书的做法（也是业界通行做法）是分成两层：

权限的表示：位标志

一个角色拥有一组权限。怎么把“一组”存进数据库的一列？ 原书的答案是位标志：给每个权限分配一个 2 的幂，整个集合就是它们的和。

Java 版：枚举 + EnumSet

原书用一组 int 常量。Java 可以做得更好：用枚举表达权限， 用 EnumSet 表达集合，只在存数据库时转成整数。 这样代码里拿到的是类型安全的枚举，不会把 8 和 16 写混。 

package com.example.javalinky.model;

import io.javalin.security.RouteRole;
import java.util.EnumSet;
import java.util.Set;

/**
 * 一项权限。
 * 实现 Javalin 的 RouteRole 接口，这样可以直接写在路由声明上 —— 见本章后面。
 */
public enum Permission implements RouteRole {

    FOLLOW(1),      // 关注别人
    COMMENT(2),     // 发表评论
    WRITE(4),       // 发布文章
    MODERATE(8),    // 协管别人的评论
    ADMIN(16);      // 管理员

    private final int bit;

    Permission(int bit) {
        this.bit = bit;
    }

    public int bit() {
        return bit;
    }

    // ---------- 整数 ↔ 集合 ----------

    /** 把数据库里的整数解析成权限集合 */
    public static EnumSet<Permission> fromBits(int bits) {
        EnumSet<Permission> set = EnumSet.noneOf(Permission.class);
        for (Permission p : values()) {
            if ((bits & p.bit) == p.bit) set.add(p);
        }
        return set;
    }

    /** 把权限集合打包成一个整数 */
    public static int toBits(Set<Permission> permissions) {
        int bits = 0;
        for (Permission p : permissions) bits |= p.bit;
        return bits;
    }
}
💡 为什么不直接用 @ElementCollection 存一张权限表

JPA 确实支持把集合映射成独立的表（role_permissions）。那样做更"范式化"， 而且加新权限不受 31 个的限制。

但位标志有一个决定性优势：判断权限不需要查数据库。 permissions 就是 roles 表里的一个 int 列， 随角色一起被加载，之后的每次判断都是纯内存的位运算。 权限判断在每个请求里都要做好几次，这个差别很实在。

Role 实体

package com.example.javalinky.model;

import jakarta.persistence.*;
import java.util.EnumSet;
import java.util.Set;

@Entity
@Table(name = "roles")
public class Role {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(length = 64, unique = true, nullable = false)
    private String name;

    @Column(name = "is_default", nullable = false)
    private boolean defaultRole;

    /** 权限位。数据库里是一个 int，代码里尽量别直接碰它 */
    @Column(nullable = false)
    private int permissions;

    @OneToMany(mappedBy = "role", fetch = FetchType.LAZY)
    private java.util.List<User> users = new java.util.ArrayList<>();

    protected Role() {}

    public Role(String name, Set<Permission> permissions) {
        this.name = name;
        this.permissions = Permission.toBits(permissions);
    }

    // ---------- 权限操作 ----------

    public EnumSet<Permission> permissions() {
        return Permission.fromBits(permissions);
    }

    public void setPermissions(Set<Permission> permissions) {
        this.permissions = Permission.toBits(permissions);
    }

    public boolean has(Permission permission) {
        return (permissions & permission.bit()) == permission.bit();
    }

    public void add(Permission permission) {
        permissions |= permission.bit();
    }

    public void remove(Permission permission) {
        permissions &= ~permission.bit();
    }

    public void resetPermissions() {
        permissions = 0;
    }

    // ---------- 普通访问器 ----------
    public Long getId() { return id; }
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    public boolean isDefaultRole() { return defaultRole; }
    public void setDefaultRole(boolean v) { this.defaultRole = v; }
    public int getPermissionBits() { return permissions; }

    @Override
    public String toString() { return "Role[" + name + "]"; }
}

角色播种

角色数据是“系统配置”而不是“用户数据”，所以应该由代码保证它存在。 原书用一个 Role.insert_roles() 静态方法，关键特性是 可以重复执行，每次都把角色调整到代码声明的状态 （这叫幂等）—— 这样部署新版本时直接跑一遍就行。 

package com.example.javalinky.service;

import com.example.javalinky.model.Permission;
import com.example.javalinky.model.Role;
import jakarta.persistence.EntityManager;

import java.util.EnumSet;
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.Set;

public class SeedService {

    /** 角色的唯一定义处。要改权限，改这里然后重新跑 seed-roles。 */
    private static final Map<String, Set<Permission>> ROLES = new LinkedHashMap<>();
    private static final String DEFAULT_ROLE = "普通用户";

    static {
        ROLES.put("普通用户", EnumSet.of(
            Permission.FOLLOW, Permission.COMMENT, Permission.WRITE));
        ROLES.put("协管员", EnumSet.of(
            Permission.FOLLOW, Permission.COMMENT, Permission.WRITE,
            Permission.MODERATE));
        ROLES.put("管理员", EnumSet.allOf(Permission.class));
    }

    private static EntityManager em;

    public static void use(EntityManager entityManager) {
        em = entityManager;
    }

    /**
     * 创建或更新全部角色。幂等：跑一次和跑一百次结果一样。
     * 相当于原书的 Role.insert_roles()。
     */
    public static void insertRoles() {
        ROLES.forEach((name, permissions) -> {
            Role role = em.createQuery("select r from Role r where r.name = :n", Role.class)
                .setParameter("n", name)
                .getResultStream().findFirst()
                .orElseGet(() -> {
                    Role fresh = new Role(name, Set.of());
                    em.persist(fresh);
                    return fresh;
                });

            // 每次都按代码里的定义重设，这样调整权限后重跑即可生效
            role.setPermissions(permissions);
            role.setDefaultRole(name.equals(DEFAULT_ROLE));
        });
    }
}

mvn -q compile exec:exec@cli -Dcli.args="seed-roles"
☀ “幂等”为什么这么重要

第 17 章部署时，Cli deploy 会在每次发版时执行这个方法。 如果它不幂等（比如无脑 persist 新角色）， 第二次部署就会因为唯一约束失败，或者产生重复数据。

判断一个任务是否幂等的方法很简单：连着跑两次，结果应该完全一样。 所有部署脚本都该满足这一条。

角色分配

package com.example.javalinky.db;

import com.example.javalinky.model.Role;
import jakarta.persistence.EntityManager;
import java.util.List;
import java.util.Optional;

public class RoleRepository {

    private final EntityManager em;

    public RoleRepository(EntityManager em) {
        this.em = em;
    }

    /** 新用户的默认角色 */
    public Role defaultRole() {
        return em.createQuery(
                "select r from Role r where r.defaultRole = true", Role.class)
            .getResultStream().findFirst()
            .orElseThrow(() -> new IllegalStateException(
                "没有默认角色，请先执行 Cli seed-roles"));
    }

    public Optional<Role> findByName(String name) {
        return em.createQuery("select r from Role r where r.name = :n", Role.class)
            .setParameter("n", name)
            .getResultStream().findFirst();
    }

    public Optional<Role> findById(long id) {
        return Optional.ofNullable(em.find(Role.class, id));
    }

    /** 管理员后台的角色下拉框要用（第 10 章） */
    public List<Role> findAll() {
        return em.createQuery("select r from Role r order by r.name", Role.class)
            .getResultList();
    }
}

Javalin 的路由角色

原书用两个自定义装饰器做权限校验： 

@main.route('/moderate')
@login_required
@permission_required(Permission.MODERATE)
def moderate():
    ...

Javalin 内置了这个概念，叫 路由角色（RouteRole）： 声明路由时把需要的角色作为最后一个参数传进去， 然后在一个统一的 beforeMatched 过滤器里检查。

ⓘ Javalin 6 的一个重要变更

Javalin 5 及以前有一个 AccessManager 接口专门做这件事。 它在 Javalin 6 被移除了，官方推荐改用 beforeMatched + ctx.routeRoles()——也就是本章的做法。 如果你在网上看到 config.accessManager(...) 的代码，那是旧版本的写法。

定义两组角色

Permission 已经实现了 RouteRole，但我们还需要表达 “只要登录就行，不关心具体权限”，所以再加一个枚举： 

package com.example.javalinky.web;

import io.javalin.security.RouteRole;

public enum Access implements RouteRole {
    /** 任何人都能访问（不写角色时的默认行为，写出来是为了可读性） */
    PUBLIC,
    /** 必须登录，但不要求任何具体权限 */
    AUTHENTICATED
}

校验过滤器

package com.example.javalinky.web;

import com.example.javalinky.model.Permission;
import com.example.javalinky.model.User;
import io.javalin.config.JavalinConfig;
import io.javalin.http.Context;
import io.javalin.http.ForbiddenResponse;
import io.javalin.http.UnauthorizedResponse;
import io.javalin.security.RouteRole;

import java.net.URLEncoder;
import java.nio.charset.StandardCharsets;
import java.util.Set;

public final class Authorization {

    public static void install(JavalinConfig config) {
        config.routes.beforeMatched(Authorization::check);
    }

    private static void check(Context ctx) {
        Set<? extends RouteRole> required = ctx.routeRoles();

        // 1. 没声明角色，或者显式声明公开 → 放过
        if (required.isEmpty() || required.contains(Access.PUBLIC)) return;

        User user = CurrentUser.get(ctx);

        // 2. 需要身份但没登录
        if (user == null) {
            denyAnonymous(ctx);
            return;
        }

        // 3. 逐个检查权限要求（声明了多个就必须全部满足）
        for (RouteRole role : required) {
            if (role instanceof Permission permission && !user.can(permission)) {
                throw new ForbiddenResponse("你没有执行这个操作的权限");
            }
        }
        // Access.AUTHENTICATED 到这里已经满足了（user != null）
    }

    /**
     * 未登录时的处理要分两种客户端：
     *   浏览器 → 跳到登录页，并记住他原本想去哪
     *   API    → 返回 401，让客户端自己处理
     */
    private static void denyAnonymous(Context ctx) {
        boolean wantsHtml = ctx.header("Accept") != null
            && ctx.header("Accept").contains("text/html");

        if (!wantsHtml || ctx.path().startsWith("/api/")) {
            throw new UnauthorizedResponse("请先登录");
        }

        Flash.warning(ctx, "请先登录。");
        String next = URLEncoder.encode(ctx.fullUrl(), StandardCharsets.UTF_8);
        ctx.redirect(Routes.LOGIN + "?next=" + next);
        ctx.skipRemainingHandlers();
    }

    private Authorization() {}
}
⚠ 注册顺序：Authorization 必须在 CurrentUser 之后

Authorization 要用 CurrentUser.get(ctx)， 所以加载用户的那个 before 过滤器必须先跑。 在 JavalinkyApp.create() 里的顺序是： 

UnitOfWork.install(javalin);     // ① 开事务（后面都要用数据库）
Csrf.install(javalin);           // ② 校验 CSRF 令牌
CurrentUser.install(javalin);    // ③ 加载当前用户（before）
Authorization.install(javalin);  // ④ 检查权限（beforeMatched）

注意 ③ 用的是 before、④ 用的是 beforeMatched—— 即使注册顺序写反了，Javalin 也保证所有 before 在所有 beforeMatched 之前执行。但写成符合逻辑的顺序更不容易出错。

用起来

@Override
public void register(JavalinConfig config) {
    config.routes.apiBuilder(() -> {

        // 公开页面
        get("/",               this::index);
        get("/user/{username}", this::userProfile);
        get("/post/{id}",       this::showPost);

        // 必须登录
        get("/edit-profile",   this::editProfileForm, Access.AUTHENTICATED);
        post("/edit-profile",  this::editProfile,     Access.AUTHENTICATED);

        // 需要 FOLLOW 权限
        post("/follow/{username}",   this::follow,   Permission.FOLLOW);
        post("/unfollow/{username}", this::unfollow, Permission.FOLLOW);

        // 需要 WRITE 权限
        post("/post",      this::createPost, Permission.WRITE);
        get("/edit/{id}",  this::editPostForm, Permission.WRITE);
        post("/edit/{id}", this::editPost,     Permission.WRITE);

        // 整个前缀都需要 MODERATE 权限 —— path 块可以挂角色
        path("/moderate", List.of(Permission.MODERATE), () -> {
            get("",                     this::moderate);
            post("/enable/{id}",        this::enableComment);
            post("/disable/{id}",       this::disableComment);
        });

        // 管理员专属
        path("/admin", List.of(Permission.ADMIN), () -> {
            get("/edit-profile/{id}",  this::adminEditProfileForm);
            post("/edit-profile/{id}", this::adminEditProfile);
        });
    });
}
⚠ 上面是全书最终的路由表，不是这一章的

把整张表列出来是为了让"权限怎么声明"一眼看全，但里面一大半处理器要到后面才写：

路由哪一章
/user/{username}、/edit-profile第 10 章
/post/{id}、/post、/edit/{id}第 11 章
/follow/{username}、/unfollow/{username}第 12 章
/moderate/*第 13 章

这一章只需要留下 get("/", this::index) 和 /admin 那一块（用来验证权限检查真的生效）。 其余等到对应章节再加 —— 否则 this::userProfile 这些方法引用会一路报 cannot find symbol。

☀ path() 上挂角色的两个好处
  1. 不会漏。往 /moderate 块里加新路由时， 权限自动继承 —— 不会出现"新加的那个接口忘了加装饰器"这种经典漏洞。
  2. 可叠加。外层 path 的角色会和内层的合并， 所以可以做"整个 /admin 要登录，其中删除操作还要额外权限"这种分层。

匿名用户

模板里写 layout.currentUser().can(Permission.WRITE)， 如果没登录就会 NullPointerException。 原书的解法是定义一个 AnonymousUser 类，它的 can() 永远返回 false， 这样模板里不用判空。

Java 里更简单：在 Layout 上加一个方法，把判空收在一处。

/** 当前用户是否有某权限。未登录一律返回 false —— 相当于原书的 AnonymousUser */
public boolean can(Permission permission) {
    return currentUser != null && currentUser.can(permission);
}

public boolean isAdmin() {
    return can(Permission.ADMIN);
}

/** 当前用户是否就是这个人（判断"编辑自己的资料"用） */
public boolean is(User other) {
    return currentUser != null && other != null
        && currentUser.getId().equals(other.getId());
}

⚠ 模板里隐藏按钮不是权限控制

藏起按钮只是为了界面干净。任何人都可以直接 curl -X POST https://你的站/moderate/disable/5。

真正的防线是路由上声明的 RouteRole，服务端强制执行。 模板判断和路由声明必须同时存在： 前者是体验，后者是安全。

别忘了迁移

roles 表在第 5 章的 V1 里已经有 permissions 列了， 所以本章不需要新迁移。但如果你当时没加，现在补一个： 

ALTER TABLE roles ADD COLUMN IF NOT EXISTS permissions INTEGER NOT NULL DEFAULT 0;
ALTER TABLE roles ADD COLUMN IF NOT EXISTS is_default  BOOLEAN NOT NULL DEFAULT FALSE;

CREATE INDEX IF NOT EXISTS ix_roles_is_default ON roles (is_default);
ⓘ 两件关于版本号的事，先说清楚免得你困惑

一、这个迁移在全新的库上其实什么都没做。 第 5 章的 V1__create_roles_and_users.sql 建 roles 表时已经带上了 permissions 和 is_default 两列（以及那个索引）。所以三条 IF NOT EXISTS 全部跳过。

那为什么还要它？因为已经按 V1 建好库并且在跑的环境 （比如你第 5 章就启动过一次开发库）未必有这两列 —— 迁移一旦执行过就不能再改，Flyway 会校验校验和。 所以增量只能写成新文件。这就是迁移和"直接改建表语句"的根本区别。

二、本书的迁移从 V1 跳到了 V3，没有 V2。 这是故意的：V2__add_user_about_me.sql 是第 5 章末尾 留给你的练习。Flyway 完全允许跳号（它只要求版本号递增）， 所以不做那道练习也不影响后面任何一章。

测试权限

权限逻辑是纯内存计算，不依赖 HTTP 也不依赖数据库 —— 这正是最值得写单元测试的那一类代码。

⚠ 从这一章起，所有涉及注册的测试都要先灌角色

RoleRepository.defaultRole() 查不到"默认角色"时会抛 IllegalStateException。注册处理器正好要调它，于是 任何没有预先灌入角色的测试，一注册就是 500， 而响应体里只有一句"服务器错误"，完全看不出和角色有关。

这相当于原书在 setUp() 里调的 Role.insert_roles()。 我们把它做成一个夹具方法，第 15 章会和其它夹具一起收进 TestFixtures： 

/** 相当于原书 setUp() 里的 Role.insert_roles() */
static void seedRoles(EntityManager em) {
    new SeedService(new RoleRepository(em)).seedRoles();
}

注意种子数据要灌在应用的那个内存库里。 第 7 章的 AppConfig.test() 给每次测试一个随机命名的库， 所以夹具必须用同一份 AppConfig —— 这也是第 15 章把配置收到 TestFixtures.config() 里的原因。 

package com.example.javalinky;

import com.example.javalinky.model.Permission;
import com.example.javalinky.model.Role;
import com.example.javalinky.model.User;
import org.junit.jupiter.api.Test;

import java.util.EnumSet;
import java.util.Set;

import static org.assertj.core.api.Assertions.assertThat;

class PermissionTest {

    @Test
    void 位标志能正确往返转换() {
        var set = EnumSet.of(Permission.FOLLOW, Permission.WRITE);
        int bits = Permission.toBits(set);

        assertThat(bits).isEqualTo(1 + 4);
        assertThat(Permission.fromBits(bits)).isEqualTo(set);
    }

    @Test
    void 普通用户不能协管评论() {
        var role = new Role("普通用户", EnumSet.of(
            Permission.FOLLOW, Permission.COMMENT, Permission.WRITE));
        var user = new User("u@example.com", "u");
        user.setRole(role);

        assertThat(user.can(Permission.WRITE)).isTrue();
        assertThat(user.can(Permission.MODERATE)).isFalse();
        assertThat(user.isAdministrator()).isFalse();
    }

    @Test
    void 管理员拥有全部权限() {
        var role = new Role("管理员", EnumSet.allOf(Permission.class));
        var user = new User("a@example.com", "a");
        user.setRole(role);

        for (Permission p : Permission.values()) {
            assertThat(user.can(p)).as("管理员应该有 %s", p).isTrue();
        }
    }

    @Test
    void 没有角色的用户什么都不能干() {
        var user = new User("x@example.com", "x");    // role 为 null
        for (Permission p : Permission.values()) {
            assertThat(user.can(p)).isFalse();
        }
    }

    @Test
    void 增删权限() {
        var role = new Role("测试", Set.of());
        assertThat(role.has(Permission.WRITE)).isFalse();

        role.add(Permission.WRITE);
        role.add(Permission.WRITE);       // 加两次应该等于加一次
        assertThat(role.has(Permission.WRITE)).isTrue();
        assertThat(role.getPermissionBits()).isEqualTo(Permission.WRITE.bit());

        role.remove(Permission.WRITE);
        assertThat(role.has(Permission.WRITE)).isFalse();
    }
}

  1. 跑一遍 Cli seed-roles，然后用 JShell 或数据库客户端查看 roles 表， 确认 permissions 列的值是 7 / 15 / 31。
  2. 把 SeedService 里"协管员"的权限去掉 WRITE， 重新跑 seed-roles，确认那一行的整数变了。这验证了幂等更新。
  3. 用一个普通用户登录，然后直接在地址栏访问 /moderate。 确认看到 403 页面。再把那个用户的角色改成协管员，刷新，确认能进去了。
  4. 给 Permission 加一个新权限 UPLOAD(32)，加进"管理员"角色， 重新播种。然后写一条需要 Permission.UPLOAD 的路由，验证只有管理员能访问。
  5. 在模板里不加@if(layout.can(...))， 但路由上保留 Permission.MODERATE。 用普通用户登录，点那个本不该看到的按钮，确认请求被服务端拒绝 —— 这就是"模板判断是体验、路由声明是安全"的实证。
