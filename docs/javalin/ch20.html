第 20 章

文件上传

第 10 章的头像用的是 Gravatar —— 省事，但要求用户去另一个网站注册。 这一章让用户直接传一张图。上传功能的代码量很小， 难的部分全在「怎么不被它害死」： 它是整个应用里攻击面最大的入口，没有之一。

本章目标

  • 用 ctx.uploadedFile() 接收文件，知道 enctype 为什么不能漏
  • 理解为什么扩展名和 Content-Type 一个都不能信，改用魔数识别
  • 知道文件名必须由服务端生成，以及目录穿越是怎么发生的
  • 在三个层次上限制大小，知道每一层挡住的是什么
  • 把文件发出去，并配对缓存头
  • 写出真正有价值的上传测试 —— 测的是恶意输入，不是正常路径
📦 本章代码

这一章结束时的完整项目在仓库的 javalinky/ 目录里，对应标签 jv-ch20： 

git checkout jv-ch20
cd javalinky && mvn -q compile exec:exec     # 打开 http://localhost:7070

先看清楚风险

上传功能的本质是：允许陌生人往你的服务器硬盘上写东西。 把这句话念两遍，下面每一条防护措施的必要性就都清楚了。

接收：ctx.uploadedFile()

Javalin 这边的 API 很小：

UploadedFile file = ctx.uploadedFile("avatar");   // 没传就是 null
List<UploadedFile> many = ctx.uploadedFiles("photos");

file.filename()      // 客户端给的原始文件名 —— ⚠ 不可信
file.extension()     // 从上面那个名字里切出来的 —— ⚠ 同样不可信
file.contentType()   // 客户端声明的 —— ⚠ 还是不可信
file.size()          // 客户端声明的长度 —— ⚠ 依然不可信
file.content()       // InputStream ← 只有这个是真的
☀ 这五个方法里只有最后一个值得信

上面四个全部来自 HTTP 请求体里的文本，是客户端写什么就是什么。 用 curl -F "avatar=@shell.jsp;filename=x.png;type=image/png" 就能让它们变成任何值。

所以本章后面所有的判断，都只基于 content() 读出来的真实字节。

表单那边：漏了 enctype 会静悄悄地失败

<%-- enctype 不能漏！默认的 urlencoded 不会传文件，
     服务端 ctx.uploadedFile() 会一直拿到 null，而且没有任何报错 --%>
<form method="post" novalidate enctype="multipart/form-data">
  @template.tag.csrf(token = layout.csrfToken())

  <input class="form-control" type="file" id="f-avatar" name="avatar"
         accept="image/png,image/jpeg,image/gif,image/webp">
</form>
⚠ 漏掉 enctype 是上传功能的头号坑

表单默认的编码是 application/x-www-form-urlencoded， 它只会把文件名当成一个普通文本字段发过去，文件内容根本不发。

结果是：浏览器正常提交，服务器返回 200，一切看起来都对 —— 只有 ctx.uploadedFile("avatar") 永远是 null。 没有任何一方报错。

另外注意 accept="image/png,..." 纯粹是个便利功能： 它只是让文件选择器默认过滤一下，一秒钟就能绕过。真正的校验必须在服务端。

识别类型：看内容，不看名字

这是本章的核心。判断「这是不是一张图」的唯一可靠办法是 读文件开头那几个字节 —— 业内叫魔数（magic number）。 每种格式都有固定的开头，这是文件格式规范的一部分，改不了。

格式开头的字节可打印形式
PNG89 50 4E 47 0D 0A 1A 0A.PNG....
JPEGFF D8 FF—
GIF47 49 46 38GIF8
WebP52 49 46 46 …… 第 8–11 字节 WEBPRIFF…WEBP
public enum ImageType {

    PNG ("png",  "image/png",  new int[]{0x89, 'P', 'N', 'G', 0x0D, 0x0A, 0x1A, 0x0A}),
    JPEG("jpg",  "image/jpeg", new int[]{0xFF, 0xD8, 0xFF}),
    GIF ("gif",  "image/gif",  new int[]{'G', 'I', 'F', '8'}),
    WEBP("webp", "image/webp", new int[]{'R', 'I', 'F', 'F'});   // 另需第 8..11 字节是 WEBP

    /** 够判断上面所有格式了 */
    public static final int MAGIC_BYTES = 12;

    /**
     * 认不出来就返回 null —— 调用方据此拒绝。
     * 注意是「白名单」：不在列表里的一律不收，而不是「黑名单」挡掉已知的坏格式。
     */
    public static ImageType detect(byte[] head) {
        for (ImageType type : values()) {
            if (matches(head, type.magic) && type.extraCheck(head)) return type;
        }
        return null;
    }

    private boolean extraCheck(byte[] head) {
        // RIFF 容器不只有 webp，还要看第 8..11 字节
        if (this != WEBP) return true;
        return head.length >= 12
            && head[8] == 'W' && head[9] == 'E' && head[10] == 'B' && head[11] == 'P';
    }

    private static boolean matches(byte[] head, int[] magic) {
        if (head.length < magic.length) return false;
        for (int i = 0; i < magic.length; i++) {
            if ((head[i] & 0xFF) != magic[i]) return false;
        }
        return true;
    }
}
☀ 白名单，不是黑名单

一个常见的错误思路是「禁止 .jsp、.php、.sh……」。 这永远列不全：.jspx？.phtml？大写的 .JSP？ 末尾带空格或点的 .jsp.？

白名单的逻辑是反的：认不出来就拒绝。 新出一种恶意格式，白名单天然就挡住了，不需要你更新任何东西。

凡是安全相关的判断，都要用白名单。 第 11 章的 HTML 清洗（owasp-sanitizer 的标签白名单）、 第 8 章登录后跳转的 URL 检查，用的都是同一个思路。

⚠ 为什么白名单里没有 SVG

SVG 是图片，浏览器也能显示，但它是 XML，而且可以内嵌 <script>。按 image/svg+xml 发出去的话， 浏览器会在你的域名下执行那段脚本 —— 这是一个标准的存储型 XSS，而且能拿到用户的会话 Cookie。

真要支持 SVG，有三条路：用 SVG 专用的清洗器（DOMPurify 之类）、 强制 Content-Disposition: attachment 让它只能下载， 或者把用户上传的内容放到另一个域名上 （这也是 GitHub 用 githubusercontent.com 的原因之一）。

存储：文件名和路径

public final class AvatarStore {

    public static final long MAX_BYTES = 2 * 1024 * 1024;   // 2 MB
    private static final SecureRandom RANDOM = new SecureRandom();

    private final Path root;

    public AvatarStore(Path root) {
        this.root = root.toAbsolutePath().normalize();
    }

    public Result store(InputStream in, long declaredSize) {
        if (declaredSize <= 0)        return new Result.Rejected(Rejection.EMPTY);
        if (declaredSize > MAX_BYTES) return new Result.Rejected(Rejection.TOO_LARGE);

        try {
            // 先落到临时文件：既能看头几个字节判类型，也能在真正写入前校验大小。
            // 注意不要先 readAllBytes() —— 那等于让任何人都能用一个大文件把堆撑爆。
            Files.createDirectories(root);
            Path temp = Files.createTempFile(root, "upload-", ".part");
            try {
                long written = Files.copy(in, temp, StandardCopyOption.REPLACE_EXISTING);

                // declaredSize 来自客户端，不能信。这里是真实落盘的字节数。
                if (written == 0)        return new Result.Rejected(Rejection.EMPTY);
                if (written > MAX_BYTES) return new Result.Rejected(Rejection.TOO_LARGE);

                ImageType type = ImageType.detect(readHead(temp));
                if (type == null) return new Result.Rejected(Rejection.NOT_AN_IMAGE);

                String filename = randomName() + "." + type.extension();
                Files.move(temp, root.resolve(filename), StandardCopyOption.REPLACE_EXISTING);
                return new Result.Stored(filename);
            } finally {
                Files.deleteIfExists(temp);    // move 成功的话这里是空操作
            }
        } catch (IOException e) {
            throw new UncheckedIOException("保存头像失败", e);
        }
    }

    /**
     * 按文件名取出路径。
     * 这里再校验一次 —— 就算数据库里的值被人改成了
     * "../../etc/passwd"，也出不了这个目录。
     */
    public Optional<Path> find(String filename) {
        if (filename == null || filename.isBlank()) return Optional.empty();

        Path candidate = root.resolve(filename).normalize();
        if (!candidate.startsWith(root)) return Optional.empty();   // ← 目录穿越在这里被挡住
        if (!Files.isRegularFile(candidate)) return Optional.empty();
        return Optional.of(candidate);
    }

    private static String randomName() {
        byte[] bytes = new byte[16];
        RANDOM.nextBytes(bytes);
        return HexFormat.of().formatHex(bytes);
    }
}

这段代码里有五个决定，逐个说。

☀ ① 文件名完全由服务端生成

randomName() 给出 32 个十六进制字符，扩展名来自 识别出来的真实类型，而不是用户给的。 客户端那个 filename() 我们一个字都没用。

这一下解决了三个问题：目录穿越（名字里不可能有 /）、 互相覆盖（随机名撞不上）、以及「传一个叫 .htaccess 的文件」。

用 SecureRandom 而不是 Random： 后者可预测，有人能算出别人的头像文件名。虽然头像不算机密， 但养成习惯 —— 凡是「不该被猜到」的标识，都用 SecureRandom。

☀ ② 先落临时文件，不要 readAllBytes()

最直观的写法是 byte[] data = in.readAllBytes();，然后随便处理。 问题是这等于把请求体整个读进堆内存 —— 十个人同时传 100MB，你的应用就 OOM 了。

Files.copy(in, temp) 是流式的，内存占用恒定。 而且临时文件就在目标目录里（Files.createTempFile(root, ...)）， 所以最后那一步 Files.move 是同一个文件系统上的原子重命名， 不会出现「写到一半被别人读到」的半截文件。

☀ ③ 大小校验做了两次，因为第一次不算数

declaredSize 来自 UploadedFile.size()， 而那个值来自 HTTP 头 —— 客户端说多少就是多少。 用它做早期拒绝是对的（省得白写一遍磁盘），但不能只有它。

Files.copy 的返回值是真实写入的字节数，那个才是事实。 配套测试里有一个专门的用例：声称 100 字节、实际发 2MB+，必须被拒。

☀ ④ find() 为什么还要再查一次路径

文件名是我们自己生成的，理论上不可能有 ../。 那为什么读的时候还要校验？

因为这叫纵深防御。那个文件名存在数据库里， 而数据库的值可能因为别的漏洞（SQL 注入、管理后台的疏忽、 一次手工改库）变成任何东西。find() 这三行 让「数据库被污染」不至于升级成「任意文件读取」。 

Path candidate = root.resolve(filename).normalize();
if (!candidate.startsWith(root)) return Optional.empty();

关键是 normalize() —— 它把 a/../../b 这类 路径真正算出来，之后 startsWith 才有意义。 少了 normalize() 这个检查形同虚设。

ⓘ ⑤ 用 sealed interface 表达「成功或失败」
public sealed interface Result {
    record Stored(String filename) implements Result {}
    record Rejected(Rejection reason) implements Result {}
}

比「返回 null 表示失败」好在：调用方拿不到失败原因就没法给用户 一句人话。比抛异常好在：被拒绝是正常的业务分支，不是异常情况。

sealed 的作用是告诉编译器「实现类只有这两个」， 于是 switch 模式匹配可以做穷尽检查 —— 以后加一种结果，所有处理它的地方都会编译失败。

三层大小限制，各挡各的

层在哪配挡住什么到达这一层时
① 反向代理 nginx client_max_body_size 4m; 根本不让大请求到达应用 —
② 容器 javalin.jetty.multipartConfig.maxFileSize(...) Jetty 解析时就中断，不占用你的代码 请求体没读完
③ 应用 AvatarStore 里的两次检查 业务规则（2MB），并给出友好的错误信息 已经流式写到临时文件 
// 第 20 章：multipart 的上限。这是比应用层校验更早的一道闸 ——
// 超了之后 Jetty 直接拒收，请求体根本不会被读完。
javalin.jetty.multipartConfig.maxFileSize(
    AvatarStore.MAX_BYTES, io.javalin.config.SizeUnit.BYTES);
javalin.jetty.multipartConfig.maxTotalRequestSize(
    AvatarStore.MAX_BYTES + 1024 * 1024, io.javalin.config.SizeUnit.BYTES);
ⓘ 为什么三层都要，不能只留最外面那层

外层挡得早但说不清楚。nginx 拒绝时返回的是一个 裸的 413 页面，用户看到的是「Request Entity Too Large」， 不知道是头像太大了。

内层说得清楚但代价高。到了应用层， 请求体已经传完了，带宽和磁盘 I/O 都花掉了。

所以配成：外层留宽一点（4MB）兜底防滥用， 内层卡业务值（2MB）给用户一句人话。 另外别忘了第 17 章部署时 nginx 的 client_max_body_size 默认只有 1MB —— 不改的话 2MB 的头像永远传不上来， 而且报错完全看不出和这个配置有关。

把文件发出去

private void serveAvatar(Context ctx) {
    String file = ctx.pathParam("file");

    // AvatarStore.find 会再做一次路径校验
    var path = services.avatars().find(file)
        .orElseThrow(() -> new NotFoundResponse("没有这个头像"));

    String ext = file.substring(file.lastIndexOf('.') + 1);
    var type = ImageType.byExtension(ext);
    ctx.contentType(type == null ? "application/octet-stream" : type.contentType());

    // 文件名是内容的随机标识，改了头像就是新文件名 —— 所以可以放心长期缓存
    ctx.header("Cache-Control", "public, max-age=31536000, immutable");
    ctx.result(Files.newInputStream(path));
}
☀ 两个细节

一、Content-Type 必须自己设。 不设的话浏览器会「嗅探」内容来猜类型，而嗅探是可以被诱导的 —— 一个精心构造的文件可能被当成 HTML 执行。 认不出类型时回落到 application/octet-stream（= 下载，不渲染）。 生产环境还应该加一个 X-Content-Type-Options: nosniff，彻底关掉嗅探。

二、immutable 这个缓存头是靠文件名换来的。 因为文件名是随机生成的，内容变了文件名一定也变， 所以同一个 URL 的内容永远不会改 —— 这正是 max-age=31536000, immutable 成立的前提。 如果用的是 /avatars/john.png 这种按用户名的地址， 就绝对不能这么缓存，否则用户换了头像一年内都看不到。

ⓘ 为什么不用 staticFiles

Javalin 的 config.staticFiles.add(...) 支持 Location.EXTERNAL，指向磁盘目录也能用。没走它的原因有三个：

  • 要自己控制 Content-Type 和缓存头
  • 要走 AvatarStore.find() 的路径校验
  • 以后要加权限（比如「只有登录用户能看」）时有地方加

真上了规模的话，这类文件应该交给对象存储（S3 / OSS）加 CDN， 应用只负责签发上传地址 —— 那时这个路由就不需要了。

换头像时记得删旧的

// 头像是可选的：没选文件就什么都不做
var upload = ctx.uploadedFile("avatar");
if (upload != null && upload.size() > 0) {
    var result = services.avatars().store(upload.content(), upload.size());
    if (result instanceof AvatarStore.Result.Rejected rejected) {
        // 校验失败要把已填的文字一起带回去，别让用户重打一遍
        View.render(ctx, "edit_profile.jte", "编辑资料",
                    "form", new FormView(formValues(form),
                        Map.of("avatar", List.of(rejected.reason().message))),
                    "admin", false, "targetUser", null);
        return;
    }
    String old = user.getAvatarFile();
    user.setAvatarFile(((AvatarStore.Result.Stored) result).filename());
    // 换了新的就把旧文件删掉，否则磁盘只增不减
    if (old != null) services.avatars().delete(old);
}
⚠ 文件和数据库是两套存储，它们会不一致

上面这段有一个没有完美解法的问题： setAvatarFile() 的效果要等事务提交才落库， 而 delete() 是立刻生效的。如果事务随后回滚了， 数据库里还指着旧文件，但旧文件已经被删了 —— 头像变成 404。

这类「数据库 + 外部存储」的不一致是分布式系统的常态， 文件系统、对象存储、第三方 API 都一样。常见的几种处理：

  • 容忍它（本章的选择）。头像丢了不是大事，回退到 Gravatar 即可
  • 只增不删，另开一个清理任务按数据库对账
  • 把删除推迟到事务提交之后（JPA 的 @PostCommit 之类的钩子）

重要的不是选哪个，而是知道这个问题存在并有意识地选。 悄悄写成上面那样然后没想过，才是问题。

💡 测试客户端怎么发 multipart

javalin-testtools 只给了 FormBody（urlencoded）， 没有 multipart 构造器。但 Request.Builder.post() 接受任意 BodyPublisher，所以自己拼字节就行 —— multipart 的格式本身很简单： 

static Response postMultipart(HttpClient client, String path,
                              Map<String, String> fields, FilePart file) {
    String boundary = "----JavalinkyTest" + System.nanoTime();
    var out = new ByteArrayOutputStream();

    for (var e : fields.entrySet()) {
        write(out, "--" + boundary + "\r\n");
        write(out, "Content-Disposition: form-data; name=\"" + e.getKey() + "\"\r\n\r\n");
        write(out, e.getValue() + "\r\n");
    }
    if (file != null) {
        write(out, "--" + boundary + "\r\n");
        write(out, "Content-Disposition: form-data; name=\"" + file.field()
                 + "\"; filename=\"" + file.filename() + "\"\r\n");
        write(out, "Content-Type: " + file.contentType() + "\r\n\r\n");
        out.write(file.bytes());
        write(out, "\r\n");
    }
    write(out, "--" + boundary + "--\r\n");

    byte[] body = out.toByteArray();
    return client.request(path, req -> req
        .header("Content-Type", "multipart/form-data; boundary=" + boundary)
        .post(HttpRequest.BodyPublishers.ofByteArray(body)));
}

注意换行必须是 \r\n，不是 \n —— 这是 RFC 规定的，用 \n 的话服务端解析不出任何字段， 而且同样是静悄悄地失败。

  1. 亲手绕过扩展名检查。随便找个文本文件，改名叫 avatar.png，用 curl -F "avatar=@x.png;type=image/png" 传上去。 确认被拒。然后把 ImageType.detect 的调用注释掉再试一次 —— 看看文件真的躺在了你的 data/avatars/ 里。
  2. 把表单上的 enctype="multipart/form-data" 删掉，提交。 观察：没有任何报错，但 ctx.uploadedFile() 是 null。 这就是正文说的「静悄悄地失败」。
  3. 传一个 3MB 的图片。看你撞到的是哪一层限制，报错长什么样。 然后把 Jetty 的 maxFileSize 调大，再试一次 —— 这次应该撞到应用层，错误信息友好多了。
  4. 做一次缩略图。现在是原图存原图发， 一张 2MB 的照片当 40×40 的头像显示很浪费。 用 javax.imageio.ImageIO 在存储时生成 64 和 256 两个尺寸， 让 Avatar.url(size) 挑合适的那张。 （提示：这还顺带解决了一个安全问题 —— 重新编码会丢掉原图里的一切非图像数据）
  5. 想清楚「图片炸弹」。一张 10KB 的 PNG 可以解压成 50000×50000 的位图，吃掉 10GB 内存。 上一题的 ImageIO 会中招。查一下怎么在解码前 读出图片的宽高（提示：ImageReader.getWidth()）， 超过阈值就直接拒绝。
  6. 给头像加删除功能的测试：上传一张，调 POST /edit-profile/avatar/delete，确认文件真的从磁盘上消失了、 而且页面回落到 Gravatar。
  7. 验证缓存头真的生效。上传头像，开浏览器开发者工具的 Network 面板刷新两次，确认第二次是 (from disk cache)。 然后换一张头像，确认立刻看到了新的 —— 想清楚为什么 immutable 在这里不会出问题。
  8. （进阶）把存储换成 S3 兼容的对象存储（本地可以用 MinIO）。 AvatarStore 抽成接口，实现两份。 你会发现路径穿越的检查不需要了， 但多出来一个新问题：上传失败时怎么保证不留下孤儿对象。
