性能

第一条纪律：先测量

慢查询日志

原书用 Flask-SQLAlchemy 的 get_debug_queries() 在 after_app_request 里检查每条查询的耗时。 Hibernate 自带这个功能，一个配置项就能开： 

<!-- 超过这个毫秒数的查询会被记录。Hibernate 6+ 的属性名 -->
<property name="hibernate.log_slow_query" value="500"/>

<!-- 老版本（5.4.5+）的属性名，两个都写上更保险 -->
<property name="hibernate.session.events.log.LOG_QUERIES_SLOWER_THAN_MS"
          value="500"/>

<!-- 顺便打开统计，后面的 N+1 检测器要用 -->
<property name="hibernate.generate_statistics" value="true"/>

然后让对应的 logger 输出到日志（第 17 章会完整配 Logback）：

<configuration>
  <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
    <encoder>
      <pattern>%d{HH:mm:ss.SSS} %-5level %logger{20} - %msg%n</pattern>
    </encoder>
  </appender>

  <!-- 慢查询单独一个 logger，方便在生产环境只开这一个 -->
  <logger name="org.hibernate.SQL_SLOW" level="INFO"/>

  <!-- 开发时想看全部 SQL 就把这个打开（生产千万别开，日志量巨大） -->
  <!-- <logger name="org.hibernate.SQL" level="DEBUG"/> -->

  <root level="INFO">
    <appender-ref ref="CONSOLE"/>
  </root>
</configuration>
☀ 原书指出了一个很重要的点：慢查询监控要开在生产环境

“数据库性能问题很少在开发时出现，因为开发用的数据库小得多。 正因为如此，在生产模式下开启这个选项要有用得多。”

第 7 章我们把阈值放进了 AppConfig.slowQueryMillis： 开发环境设得宽松（或者直接看全部 SQL），生产环境设 500ms 并当成告警来处理。

用 10 条测试数据永远发现不了"这个查询缺索引"—— 它在 100 万行的表上才会暴露。

请求耗时：Server-Timing

Javalin 有一个 requestLogger 回调，带着请求耗时。 我们可以把它写进日志，更有用的是写进 Server-Timing 响应头—— 浏览器开发者工具会直接把它画出来： 

package com.example.javalinky.db;

import org.hibernate.resource.jdbc.spi.StatementInspector;

/**
 * 统计"当前请求发了多少条 SQL、一共花了多久"。
 * 原理：Hibernate 每次要执行 SQL 都会先调用 inspect()，
 * 我们在这里数一下（并不修改 SQL，原样返回）。
 */
public class QueryStats implements StatementInspector {

    /** 用 ThreadLocal 是因为每个请求在自己的线程里（虚拟线程同样适用） */
    private static final ThreadLocal<Counter> CURRENT = new ThreadLocal<>();

    public static class Counter {
        public int count;
        public long nanos;
        public String slowest;
        public long slowestNanos;
    }

    public static void start() {
        CURRENT.set(new Counter());
    }

    public static Counter stop() {
        Counter counter = CURRENT.get();
        CURRENT.remove();
        return counter == null ? new Counter() : counter;
    }

    public static Counter current() {
        return CURRENT.get();
    }

    @Override
    public String inspect(String sql) {
        Counter counter = CURRENT.get();
        if (counter != null) counter.count++;
        return sql;         // 必须原样返回，否则就改了 SQL
    }

    /** 记录单条查询的耗时（由下面的计时包装调用） */
    public static void record(String sql, long nanos) {
        Counter counter = CURRENT.get();
        if (counter == null) return;
        counter.nanos += nanos;
        if (nanos > counter.slowestNanos) {
            counter.slowestNanos = nanos;
            counter.slowest = sql;
        }
    }
}

<property name="hibernate.session_factory.statement_inspector"
          value="com.example.javalinky.db.QueryStats"/>

package com.example.javalinky.web;

import com.example.javalinky.config.AppConfig;
import com.example.javalinky.db.QueryStats;
import io.javalin.config.JavalinConfig;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public final class Timing {

    private static final Logger log = LoggerFactory.getLogger(Timing.class);
    private static final String START = "requestStartNanos";

    public static void install(JavalinConfig config, AppConfig cfg) {

        config.routes.before(ctx -> {
            ctx.attribute(START, System.nanoTime());
            QueryStats.start();
        });

        config.routes.after(ctx -> {
            Long start = ctx.attribute(START);
            if (start == null) return;

            long totalMs = (System.nanoTime() - start) / 1_000_000;
            var stats = QueryStats.stop();
            long dbMs = stats.nanos / 1_000_000;

            // ① 写进响应头，开发者工具能直接看到
            ctx.header("Server-Timing", String.format(
                "total;dur=%d, db;dur=%d, queries;desc=\"%d\"",
                totalMs, dbMs, stats.count));

            // ② 慢请求写日志
            if (totalMs >= cfg.slowQueryMillis()) {
                log.warn("慢请求 {} {} 共 {}ms，其中数据库 {}ms（{} 条查询）。最慢的一条：{}",
                    ctx.method(), ctx.path(), totalMs, dbMs, stats.count, stats.slowest);
            }

            // ③ 查询条数异常多 → 很可能是 N+1
            if (stats.count > 20) {
                log.warn("疑似 N+1：{} {} 发了 {} 条 SQL",
                    ctx.method(), ctx.path(), stats.count);
            }
        });
    }

    private Timing() {}
}
💡 Javalin 自带的 requestLogger 也能用
config.requestLogger.http((ctx, ms) -> {
    log.info("{} {} → {} ({}ms)", ctx.method(), ctx.path(), ctx.status(), ms.longValue());
});

区别是：requestLogger 在响应写完之后才跑， 所以它的耗时包含了网络写出的时间，更接近"用户感受到的"； 但那时已经不能再改响应头了，所以 Server-Timing 必须在 after 里设置。两者可以同时用。

自动发现 N+1

第 11、12 章我们两次提到 N+1 问题，并说"第 16 章会讲怎么自动发现"。 上面的 Timing 里那段"查询条数 > 20 就告警"已经是一个朴素的检测器了。 更严格的做法是在测试里断言查询条数： 

package com.example.javalinky;

import com.example.javalinky.db.QueryStats;
import io.javalin.testtools.JavalinTest;
import org.junit.jupiter.api.Test;

import static org.assertj.core.api.Assertions.assertThat;

class NPlusOneTest {

    @Test
    void 首页列20篇文章时查询条数必须是常数() {
        var app = JavalinkyApp.create(TestFixtures.config());

        JavalinTest.test(app, (server, client) -> {
            // 准备 20 篇文章，作者各不相同
            TestFixtures.withTransaction(em -> {
                TestFixtures.seedRoles(em);
                for (int i = 0; i < 20; i++) {
                    var user = TestFixtures.user(em, "user" + i);
                    em.persist(new com.example.javalinky.model.Post("文章 " + i, user));
                }
            });

            client.get("/");      // 请求期间 QueryStats 在数

            // 这个上限是人工定的：count 查询 + 主查询 + 评论数聚合 + 当前用户
            // 如果有人不小心引入了 N+1，这个数字会变成 20+，测试立刻变红
            assertThat(lastQueryCount()).isLessThanOrEqualTo(6);
        });
    }
}
☀ 这类测试叫“性能回归测试”，很值得写

它不测"快不快"（那依赖机器性能，在 CI 上不稳定），而是测 "查询条数是不是常数"——这是个确定性的、可断言的性质。

价值在于：半年后有人在模板里加了一行 ${post.author.role.name}， N+1 就悄悄回来了。人眼 review 很难发现，但这个测试会当场变红。

Java 生态还有现成的工具：Hypersistence Utils 和 db-util 都提供了"断言某段代码只发了 N 条 SQL"的工具类。

☀ 索引的几条实用规则
  1. WHERE 和 JOIN 用到的列要有索引。这是 80% 的性能问题的答案。
  2. 复合索引遵循"最左前缀"。 (a, b, c) 这个索引能加速 where a=?、 where a=? and b=?，但不能加速 where b=?。
  3. 索引不是免费的。每个索引都会让 INSERT / UPDATE 变慢，并占磁盘。 不要给每一列都建索引。
  4. 对函数的查询用不上普通索引。 where lower(email) = ? 需要一个表达式索引： CREATE INDEX ... ON users (lower(email))。 （我们第 5 章的 findByEmail 就是这种情况！）
  5. 索引也要进迁移文件。千万不要手工在生产库上加索引 —— 下次部署一个新环境时就没有了。
⚠ 加索引时别锁住生产库

在 PostgreSQL 上，普通的 CREATE INDEX 会锁住整张表的写入， 几百万行的表可能锁好几分钟 —— 这段时间你的网站等于挂了。 

-- 生产环境加索引要用这个（不阻塞写入，代价是慢一些）
CREATE INDEX CONCURRENTLY ix_posts_author_timestamp
    ON posts (author_id, timestamp DESC);

注意 CONCURRENTLY 不能在事务里执行， 所以 Flyway 的迁移脚本要加一行标记： 

-- V8__add_post_index.sql
-- flyway:executeInTransaction=false
CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_posts_author_timestamp
    ON posts (author_id, timestamp DESC);

CPU 剖析：JFR

数据库之外的另一类性能问题是 CPU 消耗：某个方法在疯狂计算。 原书用 Python 的 cProfile，并提醒"剖析器会让应用显著变慢，不建议在生产环境用"。

Java 这边的情况好得多：JFR（Java Flight Recorder）是 JDK 自带的， 开销只有百分之一到几个百分点，设计上就是可以在生产环境常开的。 

# 方式一：启动时就开始记录 60 秒
java -XX:StartFlightRecording=duration=60s,filename=app.jfr,settings=profile \
     -jar target/javalinky.jar

# 方式二（更常用）：对一个已经在跑的进程动态开启
jps -l                                   # 找出进程号
jcmd <pid> JFR.start name=debug settings=profile
# ... 这时候去复现慢的操作 ...
jcmd <pid> JFR.dump name=debug filename=app.jfr
jcmd <pid> JFR.stop name=debug

# 不装 GUI 也能看个大概
jfr summary app.jfr
jfr print --events jdk.ExecutionSample app.jfr | head -50
ⓘ settings=profile 和 settings=default
设置开销用在
default约 1%生产环境常开，出问题时直接 dump 看历史
profile约 2–5%排查问题时临时开，采样频率高得多

一个很实用的生产配置：常开 default 并设置 disk=true,maxage=1h，这样问题发生后你还能 dump 出刚刚过去那一小时的数据。 这在排查"偶发的卡顿"时是救命的 —— 不需要复现。

💡 火焰图：async-profiler

JFR 的 GUI 不是每个人都喜欢。async-profiler 能直接生成 火焰图（一张 SVG，横轴是占用时间比例，纵轴是调用栈深度）， 看一眼就知道时间花在哪： 

# 采样 30 秒，生成火焰图
./asprof -d 30 -f flame.html <pid>

火焰图的读法：找最宽的那个"平台"—— 宽度代表占用的时间比例，所以最宽的格子就是热点。

指标：看趋势而不是看瞬间

日志回答"刚才那个请求怎么了"，指标回答"最近一小时整体怎么样"。 两者都需要。Javalin 有一个 Micrometer 模块： 

<dependency>
  <groupId>io.javalin</groupId>
  <artifactId>javalin-micrometer</artifactId>
  <version>${javalin.version}</version>
</dependency>
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-registry-prometheus</artifactId>
  <version>1.15.4</version>
</dependency>

var registry = new PrometheusMeterRegistry(PrometheusConfig.DEFAULT);

// JVM 层面的内置指标
new JvmMemoryMetrics().bindTo(registry);
new JvmGcMetrics().bindTo(registry);
new JvmThreadMetrics().bindTo(registry);
new ProcessorMetrics().bindTo(registry);

Javalin.create(config -> {
    config.registerPlugin(new MicrometerPlugin(cfg -> cfg.registry = registry));

    // 暴露给 Prometheus 抓取。注意要加访问控制！
    config.routes.get("/internal/metrics", ctx -> ctx.result(registry.scrape()));
});
☀ 最该先监控的四个指标

Google SRE 把它们叫“四个黄金信号”：

信号具体指标告警线的例子
延迟响应时间的 P50 / P95 / P99P95 > 500ms 持续 5 分钟
流量每秒请求数（通常不告警，用来理解其他指标）
错误5xx 响应的比例> 1% 持续 2 分钟
饱和度数据库连接池使用率、线程池、堆内存连接池使用率 > 90%

注意延迟要看百分位而不是平均值。 平均 100ms 可能意味着"99% 的人 50ms，1% 的人 5 秒"—— 而那 1% 正是会投诉的人。

⚠ /internal/metrics 不能公开

指标端点会暴露你的接口列表、流量规模、错误率、甚至堆内存布局。 必须做访问控制，至少三种选择：

  • 绑在另一个只对内网开放的端口上（config.jetty.addConnector）；
  • 加 Basic 认证（config.bundledPlugins.enableBasicAuth）；
  • 在 nginx 层按来源 IP 限制（第 17 章）。

最后：关于缓存

缓存是最诱人也最危险的优化手段。它能让某些操作快 100 倍， 同时引入"数据不一致"这类最难排查的 bug。

动手练习

  1. 造一批大数据：Cli fake 500 20000。然后访问首页的深页（?page=500）， 看浏览器开发者工具里的 Server-Timing，记下耗时。
  2. 把 hibernate.log_slow_query 设成 10（毫秒）， 浏览几个页面，看日志里冒出哪些查询。找出最慢的那一条。
  3. 连上数据库，对上一题找到的慢查询跑 EXPLAIN ANALYZE。 找出 Seq Scan。加一个索引（写成迁移文件），再跑一次对比。
  4. 故意制造一个 N+1：在 tag/posts.jte 里加一行 ${post.authorUsername()} 改成访问实体的 post.getAuthor().getRole().getName()。 访问首页，看 Server-Timing 里的 queries 数字从 5 变成多少。
  5. 写一个像正文里那样的"查询条数断言"测试，然后让上一题那个 N+1 把它弄红。
  6. 用 JFR 采一次：启动应用，用 ab 或 hey 压首页 （hey -n 2000 -c 20 http://localhost:7070/）， 同时 jcmd <pid> JFR.start settings=profile， 压完 dump 出来用 jfr print --events jdk.ExecutionSample 看热点。
  7. 给静态文件配上长期缓存头，然后在开发者工具的 Network 面板里确认 第二次访问时 CSS 和 JS 是 (from disk cache)。
  8. （进阶）给第 9 章的角色查询加一个 Caffeine 缓存 （角色几乎不变，但每个请求都要查）。 然后想清楚一个问题：管理员改了某个角色的权限之后，缓存怎么失效？ 这个问题的答案就是缓存复杂度的来源。
