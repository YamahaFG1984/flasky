💡 三个让开发体验质变的 IDE 设置
  1. 打开“自动构建项目”（Settings → Build → Compiler → Build project automatically）。配合 Debug 模式下的热交换， 改方法体之后保存就生效，不用重启 —— 这最接近 Flask 的自动重载体验。
  2. 配好运行配置：把 APP_PROFILE=dev 这些环境变量 填进 Run Configuration，以后点一下绿色三角就能跑，不用每次敲 mvn 命令。
  3. 学会条件断点：右键断点可以填条件（比如 user.getUsername().equals("john")）。 调试"只有某个用户会出错"这类问题时，比加 log.info 高效得多。

怎么找靠谱的 Java 库

原书这一节讲"怎么找 Flask 扩展"。Java 这边没有"官方扩展注册表"， 但有几个靠得住的入口：

去处适合找什么
central.sonatype.comMaven Central 的官方搜索。查某个库的最新版本、坐标、依赖
mvnrepository.com同上，界面更友好，还能看到"有多少项目在用它"
javalin.io/pluginsJavalin 的官方与社区插件清单
awesome-java按分类整理的精选库列表
Javalin 官方文档一页讲完整个框架。强烈建议通读一遍，大概一小时
☀ 判断一个库值不值得用：五个信号
  1. 最近一次发布是什么时候。超过两年没更新的库要谨慎 —— 尤其是 Jakarta EE 迁移（javax.* → jakarta.*）之后， 老库可能根本跑不起来。
  2. 传递依赖有多少。mvn dependency:tree 看一眼。 一个工具库拖进来 40 个 jar 是个坏信号。
  3. 许可证。Apache 2.0 / MIT / BSD 可以放心用； GPL / AGPL 要看清楚对你的项目有什么要求。
  4. issue 的响应情况。不是看有多少 issue， 而是看维护者回不回。
  5. 有没有安全公告记录。有 CVE 不一定是坏事（说明有人在审计）， 但要看修得快不快。
💡 一个必须做的自动化：依赖漏洞扫描

Java 生态出过 Log4Shell 这种级别的漏洞。不要靠人工关注安全新闻， 让工具每天帮你查： 

<!-- OWASP Dependency-Check：扫描已知 CVE -->
<plugin>
  <groupId>org.owasp</groupId>
  <artifactId>dependency-check-maven</artifactId>
  <version>（查当前版本）</version>
  <executions>
    <execution><goals><goal>check</goal></goals></execution>
  </executions>
</plugin>

或者更省事：在 GitHub 上打开 Dependabot—— 它会自动给有漏洞的依赖提升级 PR。免费，配置只要一个文件。

Javalin 和 Spring Boot 的关系

这是最多人问的问题，值得单独说清楚：

JavalinSpring Boot
定位一个库：你的 main 方法调用它一个框架：它调用你的代码
启动时间约 0.2 秒约 2–5 秒
依赖注入没有，手工 new（第 7 章）内置容器，注解驱动
事务管理自己写（第 5 章的 UnitOfWork）@Transactional 一个注解

出问题时调用栈是直的，能一路读到框架内部堆栈几十层代理，要懂框架才能读

☀ 本教程的真正用意

不是说 Javalin 比 Spring Boot 好 —— 大项目里 Spring Boot 的生态优势是压倒性的。

本教程的用意是：先在一个没有魔法的框架上，把 Web 开发的每一层亲手做一遍。

于是当你之后用 Spring Boot 时， @Transactional、HttpSession、 HandlerInterceptor、@PreAuthorize、 spring.jpa.open-in-view 这些东西对你来说不是黑盒—— 你知道它们在解决什么问题、代价是什么、出错时该往哪看。

这是直接从 Spring Boot 入门很难获得的视角。

💡 怎么问出一个能被回答的问题

这是一个被严重低估的技能。一个好问题包含：

  1. 最小可复现代码——不是贴你整个项目，而是删到只剩问题本身的二十行；
  2. 完整的错误信息——包括堆栈（而不是"报错了"）；
  3. 版本号——Java、Javalin、相关库；
  4. 你已经试过什么——这能避免别人重复建议你试过的方案。

有意思的是：整理最小复现的过程本身就能解决掉一半的问题。 所以这件事即使最后没发出去也不亏。

参与进来

原书最后这一节讲"回馈社区"，这里原样转述它的建议（都同样适用于 Java 生态）：

  • 读一读 Javalin（或你喜欢的任何库）的文档，提交修正或改进—— 文档的 typo、不清楚的措辞、过时的例子，维护者通常很乐意接受这类 PR。 这也是参与开源最容易的第一步。

  • 给你在用的库贡献 bug 修复或改进。
  • 写新的库并开源。
  • 把你的应用开源。
ⓘ Javalin 本身就是一个很适合读源码的项目

它只有一万多行 Kotlin 代码，而且结构清晰。 你现在已经知道 config.routes.get()、 beforeMatched、ctx.routeRoles() 这些 API 的语义了， 去看它们是怎么实现的会非常有收获 —— 这是把"会用"变成"懂了"的最快路径。

建议的切入顺序：JavalinServlet（请求怎么被分发） → Context（它到底包了什么） → 路由匹配的那棵树。

☀ 一句话总结整本教程

Javalin 应用就是“一张路由表 + 一串 ctx -> {} 处理器”， 过滤器是包在处理器外面的一层层洋葱皮。

十八章下来，这层层洋葱皮分别是：事务边界（第 5 章）、CSRF 校验（第 4 章）、 当前用户加载（第 8 章）、权限检查（第 9 章）、耗时统计（第 16 章）、 请求 ID（第 17 章）。而每个处理器都在做同一件事： 从 ctx 取出参数，调用不知道 HTTP 存在的业务代码，把结果设回 ctx。

这个结构简单到可以画在一张纸上 —— 但它足以支撑一个真实的产品。 而且这个结构和框架无关：换成 Spring Boot、Express、Rails、Django， 层次和职责都是一样的，只是名字不同。

还要说一句：本教程改编自 Miguel Grinberg 的《Flask Web Development》。 那本书的章节安排、知识递进顺序、以及"用一个贯穿全书的真实应用来教学"的思路， 都是经过验证的优秀设计 —— 我们只是把 Python 换成了 Java。 如果你以后要学 Python Web 开发，强烈推荐去读原书。
