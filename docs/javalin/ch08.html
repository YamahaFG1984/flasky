ⓘ “自己写认证”不是在教你造轮子

网上常见的建议是“认证千万别自己写”。这个建议针对的是密码哈希算法和 加密协议——那些确实必须用成熟实现（我们也在用：bcrypt 和 java-jwt 都是现成库）。

而“把哈希、会话、令牌这几个成熟零件组装成登录流程”是每个后端开发都该亲手做一遍的事。 做完你才能判断 Spring Security 的某个配置到底在保护什么。

密码安全

这是整章最重要的一节。假设你的数据库被导出了（这比你想象的常见： SQL 注入、备份文件放错位置、员工离职带走数据），用户的密码会怎样？

☀ 三条必须记住的规则
  1. 永远不存明文，也永远不"加密"密码。 加密是可逆的 —— 能解密就意味着你（或拿到密钥的人）能看到原始密码。要用单向哈希。
  2. 必须用专门为密码设计的慢哈希算法。 bcrypt、scrypt、Argon2 都行。MD5、SHA-1、SHA-256、SHA-512 都不行—— 它们是为"快"设计的。
  3. 盐必须每个密码独立随机。 好消息：bcrypt 自动生成盐并存进结果字符串，你不用操心。

package com.example.javalinky.util;

import at.favre.lib.crypto.bcrypt.BCrypt;

public final class Passwords {

    /**
     * 代价因子。每加 1，计算时间翻倍。
     * 12 在 2026 年的服务器上约 0.2–0.3 秒，是个合理的平衡点：
     * 用户登录时感觉不到，攻击者暴力破解的成本高得离谱。
     */
    private static final int COST = 12;

    /** bcrypt 只处理前 72 字节，超长的部分会被静默忽略 */
    private static final int MAX_BYTES = 72;

    public static String hash(String plaintext) {
        checkLength(plaintext);
        return BCrypt.withDefaults().hashToString(COST, plaintext.toCharArray());
    }

    public static boolean verify(String plaintext, String hash) {
        if (plaintext == null || hash == null || hash.isBlank()) return false;
        try {
            return BCrypt.verifyer().verify(plaintext.toCharArray(), hash).verified;
        } catch (IllegalArgumentException e) {
            return false;   // 哈希格式不对（比如数据库里是脏数据）
        }
    }

    private static void checkLength(String plaintext) {
        if (plaintext.getBytes(java.nio.charset.StandardCharsets.UTF_8).length > MAX_BYTES) {
            throw new IllegalArgumentException("密码过长（bcrypt 上限为 72 字节）");
        }
    }

    private Passwords() {}
}
⚠ bcrypt 的 72 字节上限是真实的坑

bcrypt 只看密码的前 72 字节，后面的直接丢掉。 这意味着一个 100 字符的密码和它的前 72 字节会被当成同一个密码。 如果你允许超长密码（比如来自密码管理器的随机串），必须显式处理 —— 上面的代码选择报错，另一种常见做法是先 SHA-256 再交给 bcrypt。

想完全避开这个问题，可以改用 Argon2id （de.mkammerer:argon2-jvm），它是现在的首选推荐。 本教程用 bcrypt 是因为它纯 Java、无原生依赖、部署最省心。

User 实体加上密码

/** 设置密码。注意：参数是明文，但存进字段的是哈希 */
public void setPassword(String plaintext) {
    this.passwordHash = Passwords.hash(plaintext);
}

/** 校验密码 */
public boolean checkPassword(String plaintext) {
    return Passwords.verify(plaintext, this.passwordHash);
}
💡 原书的一个巧妙设计，Java 里怎么表达

原书给 User 定义了一个 password 属性： 写它会自动哈希，读它会抛 AttributeError—— 用语言机制保证"没人能把密码读回来"。

Java 的等价做法更简单：只提供 setPassword()，不提供 getter。 passwordHash 字段是 private 的，外界根本没有读明文的途径。

另外注意：User.toString() 里绝对不要包含 passwordHash—— 否则某天一条调试日志就把全站哈希打进日志文件了。

会话登录

原书用 Flask-Login 管理登录状态，并专门有一节“理解 Flask-Login 是怎么工作的”。 我们直接实现，所以这一节就是那一节的内容：

CurrentUser：相当于 Flask 的 current_user

package com.example.javalinky.web;

import com.example.javalinky.db.Db;
import com.example.javalinky.db.UserRepository;
import com.example.javalinky.model.User;
import io.javalin.config.JavalinConfig;
import io.javalin.http.Context;
import io.javalin.http.UnauthorizedResponse;

public final class CurrentUser {

    private static final String SESSION_KEY = "userId";
    private static final String CTX_KEY = "currentUser";

    /** 装一个 before 过滤器，把当前用户加载进每个请求 */
    public static void install(JavalinConfig config) {
        config.routes.before(ctx -> {
            Long userId = ctx.sessionAttribute(SESSION_KEY);
            if (userId == null) return;                 // 未登录，留 null

            User user = new UserRepository(Db.em(ctx)).findById(userId).orElse(null);
            if (user == null) {
                // 用户被删了，但会话还在 → 清掉会话
                logout(ctx);
                return;
            }
            ctx.attribute(CTX_KEY, user);
            user.setLastSeen(java.time.Instant.now());  // 第 10 章：记录最后活跃时间
        });
    }

    /** 当前用户，未登录返回 null */
    public static User get(Context ctx) {
        return ctx.attribute(CTX_KEY);
    }

    public static boolean isAuthenticated(Context ctx) {
        return get(ctx) != null;
    }

    /** 必须登录，否则抛 401（第 9 章会把它换成更好的机制） */
    public static User require(Context ctx) {
        User user = get(ctx);
        if (user == null) throw new UnauthorizedResponse("请先登录");
        return user;
    }

    public static void login(Context ctx, User user) {
        // 关键一步：换一个新的会话 ID，防止"会话固定攻击"
        ctx.req().changeSessionId();
        ctx.sessionAttribute(SESSION_KEY, user.getId());
        ctx.attribute(CTX_KEY, user);
    }

    public static void logout(Context ctx) {
        ctx.sessionAttribute(SESSION_KEY, null);
        ctx.attribute(CTX_KEY, null);
        ctx.req().getSession().invalidate();   // 整个会话作废，连 Flash 也清掉
    }

    private CurrentUser() {}
}
🔎 深入：changeSessionId() 防的是什么

会话固定攻击（session fixation）：攻击者先访问你的网站拿到一个会话 ID， 然后用某种方式（钓鱼链接、XSS）让受害者的浏览器也用这个 ID， 等受害者登录之后，攻击者手里的那个 ID 就变成了已登录会话。

防御就一行：登录成功时换一个新的会话 ID， 让攻击者手里的旧 ID 作废。 这也是 Spring Security 默认行为之一 —— 现在你知道它在干什么了。

⚠ 登出为什么要用 POST

原书的登出是 GET /auth/logout。这其实有个问题： 任何能让你的浏览器发起 GET 的地方（<img src="/auth/logout">、 浏览器预取、聊天软件的链接预览）都能把你登出。

虽然“被登出”危害不大，但它违反了一条基本原则： GET 必须是安全的（不改变服务器状态）。 所以我们用带 CSRF 令牌的 POST。

登录与登出的处理器

private void loginForm(Context ctx) {
    if (CurrentUser.isAuthenticated(ctx)) {
        ctx.redirect(Routes.INDEX);
        return;
    }
    View.render(ctx, "auth/login.jte", "登录", "form", FormView.empty());
}

private void login(Context ctx) {
    var form = new LoginForm(
        ctx.formParam("email"),
        ctx.formParam("password"),
        ctx.formParam("remember") != null);

    var errors = Forms.validate(form);
    if (!errors.isEmpty()) {
        renderLoginWithErrors(ctx, form, errors);
        return;
    }

    var users = services.users(ctx);
    User user = users.findByEmail(form.email().toLowerCase()).orElse(null);

    if (user == null || !user.checkPassword(form.password())) {
        // 注意：不区分"用户不存在"和"密码错误"
        Flash.danger(ctx, "邮箱或密码错误。");
        renderLoginWithErrors(ctx, form, Map.of());
        return;
    }

    CurrentUser.login(ctx, user);
    Flash.success(ctx, "欢迎回来，" + user.getUsername() + "！");
    ctx.redirect(safeNext(ctx, Routes.INDEX));
}

private void logout(Context ctx) {
    CurrentUser.logout(ctx);
    // invalidate() 之后 Flash 也没了，所以这条消息要重新放进新会话
    Flash.info(ctx, "你已登出。");
    ctx.redirect(Routes.INDEX);
}

private void renderLoginWithErrors(Context ctx, LoginForm form,
                                   Map<String, List<String>> errors) {
    var values = new HashMap<String, String>();
    values.put("email", form.email() == null ? "" : form.email());
    if (form.remember()) values.put("remember", "1");
    View.render(ctx, "auth/login.jte", "登录",
                "form", new FormView(values, errors));
}

开放重定向：原书留下的一个漏洞

登录成功后要跳回用户原本想访问的页面，这个目标地址通常放在 ?next=/edit-profile 查询参数里。原书的代码是： 

next = request.args.get('next')
if next is None or not next.startswith('/'):
    next = url_for('main.index')
return redirect(next)
⚠ startswith('/') 不够

//evil.example.com/ 也是以 / 开头的， 但浏览器会把它解释成协议相对 URL，跳到 https://evil.example.com/。

这叫开放重定向漏洞。攻击者给你发 https://javalinky.example/auth/login?next=//evil.example/fake-login， 你在真网站上登录成功，然后被跳到一个长得一模一样的假网站， 它提示"会话过期，请重新登录"——你就把密码交出去了。 

/**
 * 安全地取 next 参数。只接受"本站的绝对路径"：
 *   /edit-profile        ✓
 *   /post/5?page=2       ✓
 *   //evil.example/x     ✗ 协议相对 URL，会跳到外站
 *   /\evil.example/x     ✗ 某些浏览器会把 \ 当成 /
 *   https://evil/x       ✗ 显然不行
 *   javascript:alert(1)  ✗
 */
private static String safeNext(Context ctx, String fallback) {
    String next = ctx.queryParam("next");
    if (next == null || next.isBlank()) return fallback;
    if (!next.startsWith("/")) return fallback;
    if (next.startsWith("//")) return fallback;
    if (next.length() > 1 && (next.charAt(1) == '\\' || next.charAt(1) == '/')) return fallback;
    return next;
}
💡 一个更彻底的做法

与其校验用户给的 URL，不如根本不接受 URL： 把目标地址存进会话（ctx.sessionAttribute("afterLogin", ctx.path())）， 登录后从会话里取。攻击者碰不到会话，所以天然安全。 代价是跨标签页的行为会怪一点。

新用户注册

package com.example.javalinky.web.form;

import jakarta.validation.constraints.*;

public record RegisterForm(
    @NotBlank(message = "请填写邮箱")
    @Size(max = 64, message = "邮箱最长 64 个字符")
    @Email(message = "邮箱格式不正确")
    String email,

    @NotBlank(message = "请填写用户名")
    @Size(max = 64, message = "用户名最长 64 个字符")
    @Pattern(regexp = "^[A-Za-z][A-Za-z0-9_.]*$",
             message = "用户名必须以字母开头，只能包含字母、数字、点和下划线")
    String username,

    @NotBlank(message = "请填写密码")
    @Size(min = 8, max = 72, message = "密码长度需在 8 到 72 之间")
    String password,

    @NotBlank(message = "请再输入一次密码")
    String password2
) {
    @AssertTrue(message = "两次输入的密码不一致")
    public boolean isPasswordsMatch() {
        return password != null && password.equals(password2);
    }
}

private void register(Context ctx) {
    var form = new RegisterForm(
        ctx.formParam("email"),
        ctx.formParam("username"),
        ctx.formParam("password"),
        ctx.formParam("password2"));

    // 1. 注解能查的先查
    var errors = new LinkedHashMap<String, List<String>>(Forms.validate(form));

    // 2. 需要查数据库的校验（注解做不到），相当于原书的 validate_email/validate_username
    var users = services.users(ctx);
    String email = form.email() == null ? "" : form.email().toLowerCase();
    if (!errors.containsKey("email") && users.emailExists(email)) {
        errors.put("email", List.of("这个邮箱已经注册过了"));
    }
    if (!errors.containsKey("username") && users.usernameExists(form.username())) {
        errors.put("username", List.of("这个用户名已被占用"));
    }

    if (!errors.isEmpty()) {
        var values = new HashMap<String, String>();
        values.put("email", email);
        values.put("username", nullToEmpty(form.username()));
        View.render(ctx, "auth/register.jte", "注册",
                    "form", new FormView(values, errors));
        return;
    }

    // 3. 创建用户
    var user = new User(email, form.username());
    user.setPassword(form.password());
    user.setRole(services.roles(ctx).defaultRole());   // 第 9 章实现
    users.save(user);

    // 4. 发确认邮件。注意：令牌要用 user.getId()，所以必须先 flush 拿到主键
    Db.em(ctx).flush();
    String token = services.auth().confirmationToken(user.getId());
    services.mail().sendConfirmation(user.getEmail(), user.getUsername(), token);

    Flash.info(ctx, "确认邮件已发送，请查收邮箱完成注册。");
    ctx.redirect(Routes.LOGIN);
}
ⓘ em.flush() 是干什么的

persist() 只是把对象纳入管理，INSERT 语句默认延迟到事务提交时才发。 但我们现在就需要自增主键（令牌里要带 userId）， 所以调 flush() 强制把挂起的 SQL 发到数据库 —— 注意这不是提交，事务还在，出错照样会回滚。

（用 GenerationType.IDENTITY 时 Hibernate 会在 persist() 时就插入以拿到 id， 所以这行 flush() 可能是多余的 —— 但写上它可以让代码不依赖主键生成策略。）

⚠ 唯一性检查有竞态，数据库约束是最后防线

两个人同时注册同一个邮箱时，两次 emailExists() 都可能返回 false， 然后两条 INSERT 都执行。这时救你的是数据库的唯一索引 （第 5 章的迁移里建了 ix_users_email）。

所以要把约束冲突也当成一种校验失败来处理：

config.routes.exception(jakarta.persistence.PersistenceException.class, (e, ctx) -> {
    if (isUniqueViolation(e)) {
        Flash.danger(ctx, "这个邮箱或用户名刚刚被别人注册了，请换一个。");
        ctx.redirect(Routes.REGISTER);
    } else {
        throw e;   // 其他数据库错误照常当 500
    }
});

“应用层检查给出友好提示 + 数据库约束保证绝对正确”是标准组合， 两者都要有。

签名令牌：确认邮件、重置密码、换邮箱

这三个功能的套路完全一样： 给用户发一个链接，链接里带一个只有服务器能验证真伪的字符串。

原书用 itsdangerous 库生成“带签名和过期时间的 JSON”。 Java 里对应的标准是 JWT（JSON Web Token）。 

<dependency>
  <groupId>com.auth0</groupId>
  <artifactId>java-jwt</artifactId>
  <version>4.5.0</version>
</dependency>

package com.example.javalinky.util;

import com.auth0.jwt.JWT;
import com.auth0.jwt.algorithms.Algorithm;
import com.auth0.jwt.exceptions.JWTVerificationException;
import com.auth0.jwt.interfaces.DecodedJWT;

import java.time.Duration;
import java.time.Instant;
import java.util.Optional;

public class Tokens {

    private static final String ISSUER = "javalinky";

    private final Algorithm algorithm;

    public Tokens(String secretKey) {
        this.algorithm = Algorithm.HMAC256(secretKey);
    }

    /** 签发一个有用途、有有效期、绑定某个用户的令牌 */
    public String issue(String purpose, long userId, Duration ttl) {
        return JWT.create()
            .withIssuer(ISSUER)
            .withSubject(String.valueOf(userId))
            .withClaim("purpose", purpose)
            .withIssuedAt(Instant.now())
            .withExpiresAt(Instant.now().plus(ttl))
            .sign(algorithm);
    }

    /** 带额外数据的令牌（换邮箱需要把新邮箱带上） */
    public String issue(String purpose, long userId, Duration ttl,
                        String extraKey, String extraValue) {
        return JWT.create()
            .withIssuer(ISSUER)
            .withSubject(String.valueOf(userId))
            .withClaim("purpose", purpose)
            .withClaim(extraKey, extraValue)
            .withIssuedAt(Instant.now())
            .withExpiresAt(Instant.now().plus(ttl))
            .sign(algorithm);
    }

    /** 校验并解析。任何问题（签名错、过期、用途不符）都返回 empty */
    public Optional<DecodedJWT> verify(String token, String expectedPurpose) {
        if (token == null || token.isBlank()) return Optional.empty();
        try {
            DecodedJWT jwt = JWT.require(algorithm)
                .withIssuer(ISSUER)
                .withClaim("purpose", expectedPurpose)
                .build()
                .verify(token);
            return Optional.of(jwt);
        } catch (JWTVerificationException e) {
            return Optional.empty();
        }
    }

    public static long userIdOf(DecodedJWT jwt) {
        return Long.parseLong(jwt.getSubject());
    }
}

package com.example.javalinky.service;

import com.example.javalinky.config.AppConfig;
import com.example.javalinky.mail.MailService;
import com.example.javalinky.util.Tokens;
import java.time.Duration;

public class AuthService {

    public static final String PURPOSE_CONFIRM = "confirm";
    public static final String PURPOSE_RESET   = "reset-password";
    public static final String PURPOSE_EMAIL   = "change-email";

    private final Tokens tokens;
    private final MailService mail;

    public AuthService(AppConfig config, MailService mail) {
        this.tokens = new Tokens(config.secretKey());
        this.mail = mail;
    }

    public String confirmationToken(long userId) {
        return tokens.issue(PURPOSE_CONFIRM, userId, Duration.ofHours(24));
    }

    public String resetToken(long userId) {
        // 重置密码的窗口要短 —— 这是高危操作
        return tokens.issue(PURPOSE_RESET, userId, Duration.ofMinutes(30));
    }

    public String emailChangeToken(long userId, String newEmail) {
        return tokens.issue(PURPOSE_EMAIL, userId, Duration.ofHours(2),
                            "newEmail", newEmail);
    }

    public Tokens tokens() { return tokens; }
}

确认账号

private void confirm(Context ctx) {
    var jwt = services.auth().tokens()
        .verify(ctx.pathParam("token"), AuthService.PURPOSE_CONFIRM);

    if (jwt.isEmpty()) {
        Flash.danger(ctx, "确认链接无效或已过期，请重新申请。");
        ctx.redirect(Routes.INDEX);
        return;
    }

    long userId = Tokens.userIdOf(jwt.get());
    User user = services.users(ctx).findById(userId).orElse(null);
    if (user == null) {
        Flash.danger(ctx, "确认链接无效。");
        ctx.redirect(Routes.INDEX);
        return;
    }

    if (user.isConfirmed()) {
        Flash.info(ctx, "这个账号已经确认过了。");
    } else {
        user.setConfirmed(true);        // 托管对象，改字段即入库
        Flash.success(ctx, "账号确认成功，欢迎加入 Javalinky！");
    }
    ctx.redirect(Routes.INDEX);
}

private void resendConfirmation(Context ctx) {
    User user = CurrentUser.require(ctx);
    if (user.isConfirmed()) {
        ctx.redirect(Routes.INDEX);
        return;
    }
    String token = services.auth().confirmationToken(user.getId());
    services.mail().sendConfirmation(user.getEmail(), user.getUsername(), token);
    Flash.info(ctx, "新的确认邮件已发送。");
    ctx.redirect(Routes.INDEX);
}
ⓘ 注意：确认路由不要求登录

原书给 confirm 加了 @login_required，于是流程是 “点邮件链接 → 要求先登录 → 登录后才确认”。

我们这里不要求登录，因为令牌本身已经证明了“持有者能收到那个邮箱的邮件”。 这样用户体验更顺（在手机上点开邮件链接就直接确认完了）。 代价是别人拿到你的确认链接也能帮你确认 —— 但这没有危害。

public static void installUnconfirmedGuard(JavalinConfig config) {
    config.routes.beforeMatched(ctx -> {
        User user = CurrentUser.get(ctx);
        if (user == null || user.isConfirmed()) return;

        String path = ctx.path();
        // 白名单：认证相关的路径必须放过
        if (path.startsWith("/auth/") || path.equals("/favicon.ico")) return;
        // API 走自己的规则（第 14 章）
        if (path.startsWith("/api/")) return;

        ctx.redirect("/auth/unconfirmed");
        ctx.skipRemainingHandlers();    // 别再执行后面的处理器
    });
}

private void changePassword(Context ctx) {
    User user = CurrentUser.require(ctx);
    var form = new ChangePasswordForm(
        ctx.formParam("oldPassword"),
        ctx.formParam("password"),
        ctx.formParam("password2"));

    var errors = new LinkedHashMap<String, List<String>>(Forms.validate(form));
    if (errors.isEmpty() && !user.checkPassword(form.oldPassword())) {
        errors.put("oldPassword", List.of("当前密码不正确"));
    }
    if (!errors.isEmpty()) {
        View.render(ctx, "auth/change_password.jte", "修改密码",
                    "form", new FormView(Map.of(), errors));
        return;
    }

    user.setPassword(form.password());

    // 改密码之后换一个会话 ID（和登录时同理）
    ctx.req().changeSessionId();

    Flash.success(ctx, "密码已更新。");
    ctx.redirect(Routes.INDEX);
}

private void requestPasswordReset(Context ctx) {
    String email = nullToEmpty(ctx.formParam("email")).toLowerCase();

    services.users(ctx).findByEmail(email).ifPresent(user -> {
        String token = services.auth().resetToken(user.getId());
        services.mail().sendPasswordReset(user.getEmail(), user.getUsername(), token);
    });

    // 关键：无论邮箱存不存在，都给同一句提示。
    // 否则这个接口就变成了"查询某邮箱是否注册过"的工具。
    Flash.info(ctx, "如果这个邮箱已注册，重置链接已经发送过去了。");
    ctx.redirect(Routes.LOGIN);
}

private void doPasswordReset(Context ctx) {
    var jwt = services.auth().tokens()
        .verify(ctx.pathParam("token"), AuthService.PURPOSE_RESET);
    if (jwt.isEmpty()) {
        Flash.danger(ctx, "重置链接无效或已过期。");
        ctx.redirect(Routes.LOGIN);
        return;
    }

    var form = new PasswordResetForm(ctx.formParam("password"), ctx.formParam("password2"));
    var errors = Forms.validate(form);
    if (!errors.isEmpty()) {
        View.render(ctx, "auth/reset_password.jte", "重置密码",
                    "form", new FormView(Map.of(), errors),
                    "token", ctx.pathParam("token"));
        return;
    }

    User user = services.users(ctx).findById(Tokens.userIdOf(jwt.get())).orElse(null);
    if (user == null) {
        Flash.danger(ctx, "重置链接无效。");
        ctx.redirect(Routes.LOGIN);
        return;
    }

    user.setPassword(form.password());
    Flash.success(ctx, "密码已重置，请用新密码登录。");
    ctx.redirect(Routes.LOGIN);
}
🔎 深入：JWT 做密码重置令牌的一个缺陷

JWT 是无状态的：签发之后服务器不记录它，所以没法作废。 这意味着一个重置令牌在有效期内可以用多次—— 如果邮箱被人看过一眼，攻击者可以在 30 分钟内反复重置你的密码。

更严格的做法有两种：

  1. 把令牌哈希存进数据库，用过就删（password_reset_tokens 表）。 这是最稳的做法，代价是多一张表。
  2. 把当前密码哈希的一部分放进令牌的 claim 里。 密码一改，哈希就变，旧令牌自动失效。零成本，很巧妙。

原书用 itsdangerous 也有同样的问题。生产系统请至少实现第二种。

修改邮箱

这里有个容易做错的地方：确认邮件要发给新邮箱，但在确认之前不能改数据库。 所以把新邮箱放进令牌： 

private void requestEmailChange(Context ctx) {
    User user = CurrentUser.require(ctx);
    String newEmail = nullToEmpty(ctx.formParam("email")).toLowerCase();
    String password = ctx.formParam("password");

    // 改邮箱是敏感操作，必须重新验证密码
    if (!user.checkPassword(password)) {
        Flash.danger(ctx, "密码不正确。");
        ctx.redirect(Routes.CHANGE_EMAIL);
        return;
    }
    if (services.users(ctx).emailExists(newEmail)) {
        Flash.danger(ctx, "这个邮箱已经被使用了。");
        ctx.redirect(Routes.CHANGE_EMAIL);
        return;
    }

    String token = services.auth().emailChangeToken(user.getId(), newEmail);
    services.mail().sendEmailChange(newEmail, user.getUsername(), token);

    Flash.info(ctx, "确认邮件已发送到新邮箱，请到那边完成确认。");
    ctx.redirect(Routes.INDEX);
}

private void confirmEmailChange(Context ctx) {
    var jwt = services.auth().tokens()
        .verify(ctx.pathParam("token"), AuthService.PURPOSE_EMAIL);
    if (jwt.isEmpty()) {
        Flash.danger(ctx, "链接无效或已过期。");
        ctx.redirect(Routes.INDEX);
        return;
    }

    User user = services.users(ctx).findById(Tokens.userIdOf(jwt.get())).orElse(null);
    String newEmail = jwt.get().getClaim("newEmail").asString();
    if (user == null || newEmail == null) {
        Flash.danger(ctx, "链接无效。");
        ctx.redirect(Routes.INDEX);
        return;
    }
    // 再查一次：令牌签发之后可能有人抢注了这个邮箱
    if (services.users(ctx).emailExists(newEmail)) {
        Flash.danger(ctx, "这个邮箱已经被使用了。");
        ctx.redirect(Routes.INDEX);
        return;
    }

    user.setEmail(newEmail);
    user.setAvatarHash(null);      // 第 10 章：Gravatar 哈希是按邮箱算的，要重算
    Flash.success(ctx, "邮箱已更新。");
    ctx.redirect(Routes.INDEX);
}

💡 测试里的 CSRF 令牌怎么弄

有两种做法，各有取舍：

  1. 从页面 HTML 里抠出来（上面 csrfTokenFrom() 的做法）—— 真实度最高，连 CSRF 防护本身都一起测了。
  2. 在测试配置里关掉 CSRF——原书就是这么做的 （WTF_CSRF_ENABLED = False）。代码干净，但漏测了一个安全机制。

建议：大部分测试用第 2 种（加一个 AppConfig.csrfEnabled 开关）， 然后专门写两三个测试用第 1 种来验证 CSRF 防护确实有效。

动手练习

  1. 在 JShell 里执行 Passwords.hash("cat") 三次，对比三个结果。 数一数 bcrypt 字符串的各个部分（$2a$12$ 开头）。 然后把 COST 改成 4 和 15，用 System.nanoTime() 测一下耗时差多少。
  2. 跑起 Mailpit，完整走一遍注册流程：填表 → 在 Mailpit 里看到邮件 → 点确认链接 → 账号变成已确认。
  3. 把确认令牌的有效期改成 Duration.ofSeconds(5)，注册一个账号， 等 10 秒再点链接，确认看到"链接已过期"。
  4. 拿一个确认令牌，到 jwt.io 上粘贴进去 （或者自己 Base64 解码中间那段），看看载荷里有什么。 然后手动改一个字符再去访问，确认服务器拒绝了它。
  5. 试试开放重定向：访问 /auth/login?next=//example.com，登录。 确认你没有被跳到外站。然后把 safeNext 里那几行检查注释掉，再试一次。
