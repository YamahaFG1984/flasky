测试

前面每一章我们都零散写了几个测试。这一章把它系统化： 三层测试怎么分工、怎么用 JaCoCo 看覆盖率、 怎么用 JavalinTest 测完整的 HTTP 请求、怎么用 Playwright 驱动真实浏览器。 最后回答原书那个问题：这么折腾值得吗？

本章目标

  • 理解测试金字塔，知道每一层该测什么
  • 用 JUnit 5 + AssertJ 写清晰的断言
  • 做好测试数据隔离，让测试之间互不影响
  • 用 JaCoCo 生成覆盖率报告，并正确解读它
  • 用 JavalinTest 测登录、表单、重定向、API
  • 用 Playwright 做端到端测试

为什么测试

原书给了两个理由，第二个才是关键：

  1. 确认新写的代码按预期工作 —— 手动点一遍也能达到同样效果；
  2. 确认改动没有破坏旧功能——这个没法手动做， 因为每改一行都要重测全部功能，人类做不到。
☀ 测试真正买到的东西：改代码的勇气

没有测试的项目，改动大一点你就会犹豫："这个重构会不会弄坏什么？" 于是代码越来越不敢动，只能一层层往上加补丁。

有一套能在 30 秒内跑完的测试，你可以放心大改 —— 跑一遍就知道有没有坏。这是测试最大的价值，而不是"找到 bug"。

JUnit 5 与 AssertJ

import org.junit.jupiter.api.*;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.ValueSource;

import static org.assertj.core.api.Assertions.*;

class 分页算法测试 {

    @Test
    void 空列表也要显示第一页() {
        var page = Page.of(List.of(), 1, 20, 0);
        assertThat(page.totalPages()).isEqualTo(1);
        assertThat(page.hasPrevious()).isFalse();
        assertThat(page.hasNext()).isFalse();
    }

    @Test
    void 省略号出现在该出现的位置() {
        var page = Page.of(List.of(), 7, 20, 400);   // 第 7 页，共 20 页
        assertThat(page.pageNumbers())
            .containsExactly(1, 0, 5, 6, 7, 8, 9, 0, 20);  // 0 代表省略号
    }

    @ParameterizedTest                       // 一个方法跑多组数据
    @ValueSource(ints = {-100, -1, 0})
    void 非法页码一律当成第一页(int bad) {
        assertThat(Page.clampPage(bad)).isEqualTo(1);
    }

    @Test
    void 越界访问会抛异常() {
        assertThatThrownBy(() -> Passwords.hash("x".repeat(100)))
            .isInstanceOf(IllegalArgumentException.class)
            .hasMessageContaining("72 字节");
    }
}
💡 AssertJ 为什么比 JUnit 自带的断言好
JUnit 的 Assertions
assertEquals(3, list.size());
assertTrue(list.contains("a"));
assertTrue(s.startsWith("Hello"));
// 失败信息：expected: <3> but was: <2>
AssertJ
assertThat(list).hasSize(3).contains("a");
assertThat(s).startsWith("Hello");
// 失败信息会打印出整个 list 的内容
// 和具体哪里不匹配

AssertJ 是链式的（一个对象上连着断言多个条件）， 而且失败信息详细得多——这在 CI 上只能看日志时非常重要。

测试数据隔离

这是集成测试最容易踩坑的地方：测试之间必须互不影响。 如果测试 A 建了一个用户 john，测试 B 又建一个 john，第二个会因为唯一约束失败 —— 而且失败与否取决于执行顺序，这是最难排查的那种问题。

    public static void withTransaction(java.util.function.Consumer<EntityManager> work) {
        EntityManager em = Db.emf().createEntityManager();
        try {
            em.getTransaction().begin();
            work.accept(em);
            em.getTransaction().commit();
        } catch (RuntimeException e) {
            if (em.getTransaction().isActive()) em.getTransaction().rollback();
            throw e;
        } finally {
            em.close();
        }
    }

ⓘ DB_CLOSE_DELAY=-1 很关键

H2 内存库默认在最后一个连接关闭时就销毁。 而 HikariCP 连接池会回收空闲连接 —— 结果是测试跑到一半数据库突然"消失"，报 Table not found。

DB_CLOSE_DELAY=-1 让库在 JVM 退出前一直存在。 这是用 H2 做测试时的必备参数，几乎每个人都会踩一次这个坑。

代码覆盖率：JaCoCo

原书用 Python 的 coverage 工具，给 flask test 加了一个 --coverage 选项。 Java 的对应工具是 JaCoCo，配成 Maven 插件就行，不需要改代码： 

<plugin>
  <groupId>org.jacoco</groupId>
  <artifactId>jacoco-maven-plugin</artifactId>
  <version>0.8.13</version>

    <!-- 测试前挂上探针 -->

      <id>prepare-agent</id>

    </execution>
    <!-- 测试后生成报告 -->
    <execution>
      <id>report</id>
      <phase>verify</phase>
      <goals><goal>report</goal></goals>

    <!-- 可选：覆盖率低于阈值就让构建失败 -->
    <execution>
      <id>check</id>
      <phase>verify</phase>
      <goals><goal>check</goal></goals>
      <configuration>
        <rules>
          <rule>
            <element>BUNDLE</element>
            <limits>
              <limit>
                <counter>LINE</counter>
                <value>COVEREDRATIO</value>
                <minimum>0.50</minimum>
              </limit>
            </limits>
          </rule>
        </rules>
      </configuration>
    </execution>
  </executions>
  <configuration>
    <excludes>
      <!-- 生成的模板类、入口类不计入 -->
      <exclude>gg/jte/generated/**</exclude>

☀ 该优先给哪些代码补测试

看着 JaCoCo 报告，按这个顺序挑：

  1. 安全相关：权限判断、归属检查、令牌校验、HTML 清洗。 这些出错的后果最严重。
  2. 算法性质的纯逻辑：分页、权限位、时间计算。 这些最好测（不需要任何环境），性价比最高。
  3. 容易写错的边界：空列表、第一页/最后一页、null、超长输入。
  4. 修过 bug 的地方：每修一个 bug 就补一个测试，保证它不再出现。

不值得测的：getter / setter、toString()、 只是转发一下的方法、以及配置类。

集成测试：JavalinTest

原书用 Flask 的测试客户端，它模拟一个请求环境而不真的起服务器。 Javalin 的 JavalinTest 更彻底：它真的在一个随机端口上启动服务器， 然后给你一个 HTTP 客户端。

class MainRoutesTest {

ⓘ JavalinTest.test() 替代了原书的 /shutdown 路由

原书为了做 Selenium 测试，不得不在应用里加一条 只在测试配置下生效的 /shutdown 路由—— 因为 Werkzeug 开发服务器只能靠一个 HTTP 请求来优雅关闭。

这是个无奈的妥协：生产代码里出现了一条专门给测试用的路由。 JavalinTest 帮我们避开了它 —— 它自己管服务器的启动和关闭，测完立刻 app.stop()。 所以我们的应用里没有任何测试专用代码。

测带会话的流程

登录之后的测试需要保持 Cookie。原书的做法是 app.test_client(use_cookies=True)。 JavalinTest 的客户端基于 OkHttp，默认不自动管理 Cookie， 所以我们自己记一下： 

package com.example.javalinky.web;

import com.example.javalinky.JavalinkyApp;
import com.example.javalinky.TestFixtures;
import com.example.javalinky.db.Db;
import io.javalin.testtools.HttpClient;
import io.javalin.testtools.JavalinTest;
import org.junit.jupiter.api.Test;

import java.util.Map;
import java.util.regex.Matcher;
import java.util.regex.Pattern;

import static org.assertj.core.api.Assertions.assertThat;

class LoginFlowTest {

    /** 从 HTML 里抠出 CSRF 隐藏字段的值 */
    private static final Pattern CSRF =
        Pattern.compile("name=\"_csrf\"\\s+value=\"([^\"]+)\"");

    @Test
    void 登录成功后首页显示用户名() {
        var app = JavalinkyApp.create(TestFixtures.config());

        JavalinTest.test(app, (server, client) -> {
            // 准备数据：建角色和一个用户
            TestFixtures.withTransaction(em -> {
                TestFixtures.seedRoles(em);
                TestFixtures.user(em, "john");
            });

            // ① GET 登录页，拿到 CSRF 令牌和会话 Cookie
            var loginPage = client.get("/auth/login");
            String cookie = loginPage.header("Set-Cookie");
            String token = extractCsrf(loginPage.body().string());

            // ② POST 登录
            var login = client.post("/auth/login",
                Map.of("email", "john@example.com",
                       "password", "cat12345",
                       "_csrf", token),
                builder -> builder.header("Cookie", sessionOf(cookie)));

            assertThat(login.code()).isEqualTo(302);
            assertThat(login.header("Location")).isEqualTo("/");

            // ③ 带着会话访问首页
            var home = client.get("/", builder ->
                builder.header("Cookie", sessionOf(cookie)));

            assertThat(home.body().string())
                .contains("john")
                .contains("登出");
        });
    }

    private static String extractCsrf(String html) {
        Matcher m = CSRF.matcher(html);
        assertThat(m.find()).as("页面里应该有 CSRF 隐藏字段").isTrue();
        return m.group(1);
    }

    /** 从 Set-Cookie 头里取出 name=value 部分，丢掉 Path/HttpOnly 等属性 */
    private static String sessionOf(String setCookieHeader) {
        return setCookieHeader.split(";", 2)[0];
    }
}
💡 更省事的办法：给测试配置加一个 CSRF 开关

上面那段抠令牌、传 Cookie 的代码写一次还行，写二十次就太烦了。 原书直接在测试配置里关掉 CSRF（WTF_CSRF_ENABLED = False）。

我们可以做得更好一点：给 AppConfig 加一个开关，

// AppConfig 新增字段
boolean csrfEnabled

// Csrf.install 里
if (!config.csrfEnabled()) return;   // 测试时整个跳过校验

然后：绝大多数测试用 csrfEnabled=false， 另外专门写两三个测试用 true 来验证 CSRF 防护本身有效。 这样既省事，又没有漏测安全机制。

package com.example.javalinky.api;

import com.example.javalinky.JavalinkyApp;
import com.example.javalinky.TestFixtures;
import com.fasterxml.jackson.databind.ObjectMapper;
import io.javalin.testtools.JavalinTest;
import org.junit.jupiter.api.Test;

import java.util.Base64;
import java.util.Map;

import static org.assertj.core.api.Assertions.assertThat;

class ApiTest {

    private static final ObjectMapper JSON = new ObjectMapper();

    @Test
    void 没有令牌时返回401() {
        JavalinTest.test(JavalinkyApp.create(TestFixtures.config()), (server, client) -> {
            var response = client.get("/api/v1/posts", b ->
                b.header("Accept", "application/json"));

            assertThat(response.code()).isEqualTo(401);
            assertThat(response.body().string()).contains("Bearer");
        });
    }

    @Test
    void 发文章并读回来() {
        JavalinTest.test(JavalinkyApp.create(TestFixtures.config()), (server, client) -> {
            TestFixtures.withTransaction(em -> {
                TestFixtures.seedRoles(em);
                TestFixtures.user(em, "john");
            });

            // ① 换令牌
            String basic = Base64.getEncoder().encodeToString(
                "john@example.com:cat12345".getBytes());
            var tokenResponse = client.post("/api/v1/tokens", null, b ->
                b.header("Authorization", "Basic " + basic));

            assertThat(tokenResponse.code()).isEqualTo(200);
            String token = JSON.readTree(tokenResponse.body().string())
                               .get("token").asText();
            assertThat(token).isNotBlank();

            // ② 发文章
            var created = client.post("/api/v1/posts",
                Map.of("body", "这是 **API** 发的文章"),
                b -> b.header("Authorization", "Bearer " + token));

            assertThat(created.code()).isEqualTo(201);
            String location = created.header("Location");
            assertThat(location).isNotNull().contains("/api/v1/posts/");

            // ③ 按 Location 读回来
            var fetched = client.get(location.replace("http://localhost", ""), b ->
                b.header("Authorization", "Bearer " + token));

            assertThat(fetched.code()).isEqualTo(200);
            var json = JSON.readTree(fetched.body().string());
            assertThat(json.get("body").asText()).isEqualTo("这是 **API** 发的文章");
            // 验证 Markdown 被渲染并清洗了
            assertThat(json.get("bodyHtml").asText())
                .contains("<strong>API</strong>");
            // 验证敏感字段没有泄露
            assertThat(fetched.body().string()).doesNotContain("passwordHash");
        });
    }

    @Test
    void 不能修改别人的文章() {
        JavalinTest.test(JavalinkyApp.create(TestFixtures.config()), (server, client) -> {
            // 建两个用户，john 发一篇文章，susan 去改它 → 应该 403
            // （完整代码略，思路和上面一样）
        });
    }
}

端到端测试：Playwright

原书用 Selenium。今天更推荐 Playwright，原因是：

SeleniumPlaywright
浏览器驱动要单独下载 chromedriver，版本必须匹配mvn 一条命令自动装好浏览器
等待元素要手写 WebDriverWait，否则随机失败自动等待，几乎不会出现"偶尔红"的测试
调试看日志自带追踪查看器，能回放每一步的截图和网络请求
生态老牌，什么都支持较新，但主流浏览器都覆盖

package com.example.javalinky.e2e;

import com.example.javalinky.JavalinkyApp;
import com.example.javalinky.TestFixtures;
import com.microsoft.playwright.*;
import io.javalin.Javalin;
import org.junit.jupiter.api.*;

import static com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;

@TestInstance(TestInstance.Lifecycle.PER_CLASS)
class EndToEndTest {

    private Javalin app;
    private int port;
    private Playwright playwright;
    private Browser browser;

    @BeforeAll
    void startEverything() {
        // 端到端测试比较贵，所以整个类共用一个应用和一个浏览器
        app = JavalinkyApp.create(TestFixtures.config());
        app.start(0);                       // 0 = 随机空闲端口
        port = app.port();

        TestFixtures.withTransaction(em -> {
            TestFixtures.seedRoles(em);
            TestFixtures.user(em, "john");
        });

        playwright = Playwright.create();
        browser = playwright.chromium().launch(
            new BrowserType.LaunchOptions().setHeadless(true));
    }

    @AfterAll
    void stopEverything() {
        if (browser != null) browser.close();
        if (playwright != null) playwright.close();
        if (app != null) app.stop();
    }

    private String url(String path) {
        return "http://localhost:" + port + path;
    }

    @Test
    void 用户能登录并发一篇文章() {
        try (BrowserContext context = browser.newContext()) {   // 每个测试一个干净的浏览器上下文
            Page page = context.newPage();

            // ① 打开首页
            page.navigate(url("/"));
            assertThat(page.locator("h1")).containsText("陌生人");

            // ② 点"登录"
            page.getByRole(com.microsoft.playwright.options.AriaRole.LINK,
                new Page.GetByRoleOptions().setName("登录")).click();

            // ③ 填表单。Playwright 会自动等元素出现，不需要 sleep
            page.getByLabel("邮箱").fill("john@example.com");
            page.getByLabel("密码").fill("cat12345");
            page.getByRole(com.microsoft.playwright.options.AriaRole.BUTTON,
                new Page.GetByRoleOptions().setName("登录")).click();

            // ④ 确认登录成功
            assertThat(page.locator("h1")).containsText("john");

            // ⑤ 发一篇文章（这一步会用到 EasyMDE，纯 JS，只有真浏览器能测）
            page.locator("textarea[name=body]").fill("端到端测试发的文章");
            page.getByRole(com.microsoft.playwright.options.AriaRole.BUTTON,
                new Page.GetByRoleOptions().setName("发布")).click();

            // ⑥ 确认文章出现在列表里
            assertThat(page.locator(".post-list")).containsText("端到端测试发的文章");
        }
    }
}
☀ 端到端测试该测什么、不该测什么

该测（只有它能测的）：

  • 涉及 JavaScript 的交互：Markdown 编辑器、时间本地化、Bootstrap 下拉菜单；
  • 跨页面的完整流程：注册 → 收邮件 → 确认 → 登录 → 发文章；
  • "页面真的能打开"这种最基本的健康检查。

不该测（放到下面两层去）：

  • 表单校验的每一种错误组合 —— 用集成测试，快一百倍；
  • 权限的每一种组合 —— 用集成测试；
  • 算法边界 —— 用单元测试。

一条经验：端到端测试超过 20 个就该反思了—— 大概有一半的内容可以下移到更快的层。

把测试接进 CI

测试只有每次提交都自动跑才有价值。GitHub Actions 的最小配置： 

name: test

on:
  push:
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'
          cache: maven          # 缓存 ~/.m2，能省掉大部分下载时间

      - name: 跑测试并生成覆盖率
        run: mvn --batch-mode clean verify
        env:
          APP_PROFILE: test

      - name: 上传覆盖率报告
        if: always()            # 即使测试失败也上传，方便排查
        uses: actions/upload-artifact@v4
        with:
          name: jacoco-report
          path: target/site/jacoco/
ⓘ 为什么端到端测试通常不进 CI 的主流程

Playwright 要下载浏览器、启动真实渲染，在 CI 上可能要几分钟。 常见的做法是分开：

  • 每次提交：单元 + 集成测试（目标：3 分钟内出结果）；
  • 合并到主分支 / 每晚：加上端到端测试。

Maven 里用 maven-failsafe-plugin 可以把 *Test（单元）和 *IT（集成/端到端）分开跑。

☀ 原书的结论

“不管你喜不喜欢，你的应用都会被测试。 如果你不自己测，那么你的用户就会成为不情愿的测试者 —— 他们会发现 bug，然后你得在压力下修。”

“像数据库模型这种能脱离应用环境执行的测试，总是应该写， 因为成本很低。端到端测试有时必要，但因为写起来复杂， 只应该用于那些无法隔离测试的功能。”

“应用代码应该组织成：把业务逻辑推进独立于应用上下文的模块，这样更容易测试。 视图函数里的代码应该简单，只做一层薄薄的转接—— 接收请求，然后调用封装了业务逻辑的类或函数。”

最后那段话值得对照一下我们的代码。回看第 2 章的建议： 

// 处理器只做三件事：取参数 → 调服务 → 设响应
config.routes.post("/posts", ctx -> {
    String body = ctx.formParam("body");
    long userId = ctx.sessionAttribute("userId");
    Post post = postService.publish(userId, body);   // ← 业务逻辑在这里
    ctx.redirect("/post/" + post.getId());
});

postService.publish() 不知道 HTTP 的存在， 所以它可以用最快的单元测试来覆盖所有边界情况； 处理器那三行只需要一个集成测试确认"接线正确"就够了。

可测试性不是测试工具带来的，是代码结构带来的。 如果你发现某段逻辑很难测，那通常不是测试的问题 —— 是那段代码该拆了。
