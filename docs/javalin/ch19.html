并发与线程安全

这一章讲 Python 程序员转 Java 时最容易摔跤、而且摔得最疼的地方。 前十八章你其实一直在写并发代码 —— Javalin 从第 2 章起就在用线程池同时处理多个请求 —— 只是因为我们的代码碰巧没有共享可变状态，所以一直相安无事。 这一章把那层窗户纸捅破：什么时候会出事、出事长什么样、怎么写才对、 以及怎么写一个真的能抓住它的测试。

本章给应用加了一个登录限流器：一个被所有请求线程共用的对象。 它不是为了讲并发硬造的例子 —— 没有它，任何人都能对你的登录接口不限次数地撞库。

先说清楚：你一直在写并发代码

回忆一下第 2 章启动应用时的那行日志：Javalin started in 213ms。 那一刻 Jetty 起了一个线程池。两个用户同时访问， 你的处理器方法会在两个线程里同时执行。 这不是「高并发场景」才有的事，是从第一行代码起就成立的事实。

Flask 下你很少需要想这件事，原因有三层，值得一条条拆开：

ⓘ 关于 GIL 的一句澄清

“Python 有 GIL 所以线程安全”是一句似是而非的话。 GIL 保证的是单条字节码指令不被打断， 而 counter += 1 是三条指令（读、加、写）， 所以多线程的 Flask（gunicorn --threads 4）照样会丢更新。

Python 程序员较少遇到这类 bug，真正的原因是默认部署是多进程的： 进程之间没有共享内存，想共享只能走 Redis 或数据库， 而那一步会强迫你正面思考并发。Java 把这一步省了。

三个不同的问题，别混成一个

“线程安全”这个词底下至少压着三件事。它们的症状和解法都不一样， 混在一起谈是大多数困惑的来源：

问题一句话典型症状解法
竞态条件
race condition		 「检查」和「行动」之间插进了别人 限流放行了 58 次而不是 50 次；两个人注册了同一个用户名 把检查和行动合成一个原子操作
可见性
visibility		 A 线程写了，B 线程永远看不到 改了配置开关，某些线程就是不生效；循环退不出来 volatile、final、或任何同步手段
原子性
atomicity		 一个「看起来是一步」的操作其实是好几步 count++ 丢更新；对象被看到「改了一半」的中间状态 Atomic* 类、不可变对象、锁
☀ 可见性是最反直觉的那个

竞态和原子性好歹符合直觉 —— 「两个人同时改，当然会乱」。 可见性不是：它说的是就算只有一个人写，另一个人也可能永远读不到。 

class Worker {
    private boolean running = true;         // 注意：没有 volatile

    void stop()  { running = false; }       // 由别的线程调用

    void loop() {
        while (running) { /* 干活 */ }      // 这个循环可能永远不退出
    }
}

原因不是「还没来得及同步」，而是 JIT 编译器看到 loop() 里 没人改 running，合法地把它提到循环外面只读一次， 变成了 if (running) while (true) {...}。 这是 Java 内存模型允许的优化 —— 没有同步手段，就没有任何跨线程可见性的承诺。

加一个 volatile 就对了。它的含义不是「原子」（volatile int i; i++ 照样丢更新），而是「每次都去主内存读写，别缓存，别重排」。

给自己的应用做一次盘点

理论说完，看实际的。把 JavalinkyApp.create() 里造出来的东西列一遍， 每一个都问一句：它是所有请求共用的，还是每个请求一份的？

对象生命周期为什么安全
AppConfig应用级，共享 不可变（record，字段全是 final）。启动后没人改，天然安全
TemplateEngine应用级，共享 JTE 明确保证线程安全；内部的模板类缓存自己做了同步
EntityManagerFactory应用级，共享 JPA 规范要求它线程安全（它造出来的 EntityManager 则完全不是）
Mailer 的线程池应用级，共享 ExecutorService 的实现本身是线程安全的
Services应用级，共享 record，只持有上面这些；仓储是方法里现造的，不是字段
EntityManager每请求一个 放在 ctx 属性里（第 5 章的 UnitOfWork）
QueryStats.Counter每线程一个 ThreadLocal（第 16 章）
RateLimiter应用级，共享且可变 ⚠ 本章要讨论的就是它
☀ 第 7 章那个「不用 Spring」的决定，在这里兑现了

回头看 Services 里这一行： 

public UserRepository users(Context ctx) { return new UserRepository(Db.em(ctx)); }

当时的说法是「仓储依赖当前请求的 EntityManager，不能提前造好」。 现在可以说得更准确：如果把它写成字段，整个应用就共用一个 EntityManager 了 —— 而 EntityManager 不是线程安全的。

症状会非常难查：一级缓存被几个请求混着用，A 请求查出来的实体在 B 请求里被改了， 偶尔抛 ConcurrentModificationException，偶尔只是数据串了。 低流量下几乎不复现，一上线就开始。

用 Spring 的话这件事由 @Scope("request") 之类的东西替你处理， 代价是作用域变成了一个你看不见的配置。 手写装配的好处就是：对象的生命周期在代码里一目了然。

写一个真的会被并发打到的东西：登录限流

到现在为止我们的共享状态都是只读的，所以一直没出事。 但有一个功能绕不开可变的共享状态：限流。

为什么需要它：第 8 章用 bcrypt 存密码，cost 12，验证一次大约 200 毫秒。 这挡得住离线爆破，但挡不住在线撞库 —— 拿一份泄露的「邮箱+常用密码」清单，对着你的 /auth/login 一个个试。 更糟的是每次尝试都要烧掉你 200 毫秒 CPU，攻击者几乎零成本， 这同时还是一个放大型的 DoS。

算法：令牌桶

先看错误的写法

下面这段，九成的人第一次都会这么写 —— 而且它看起来已经很小心了： 用的是 ConcurrentHashMap，不是普通的 HashMap。 

// ❌ 有竞态
private final ConcurrentHashMap<String, Double> buckets = new ConcurrentHashMap<>();

public boolean tryAcquire(String key) {
    double tokens = buckets.getOrDefault(key, (double) capacity);   // ① 读
    if (tokens >= 1.0) {                                            // ② 判断
        buckets.put(key, tokens - 1.0);                             // ③ 写
        return true;
    }
    return false;
}
⚠ ConcurrentHashMap 保证的是单个操作，不是你的那一串

get 是原子的，put 也是原子的， 但 ①②③ 合起来不是。两个线程完全可能都在 ① 读到 tokens = 1.0，都通过 ②，然后都在 ③ 写回 0.0 —— 一个令牌被用了两次。

这类 bug 有个通称叫 check-then-act（检查后行动）。 它的家族很大，长得都不一样但本质是同一个：

你写的隐含的竞态
if (!map.containsKey(k)) map.put(k, v);两个线程都没查到，都插入
if (!users.emailExists(e)) users.save(...)第 8 章就提过 —— 靠数据库唯一索引兜底
if (file.exists()) file.delete();中间文件被别人删了
if (x == null) x = create();造了两个对象（经典的双重检查锁问题）

识别方法：代码里出现「先问一句，再根据答案行动」，而问和行动之间 状态可能被别人改掉，那就是一个竞态。

正确的写法：让「检查并更新」成为一个操作

ConcurrentHashMap 早就想到了这件事，给了一组 原子的复合操作：compute、computeIfAbsent、 merge、putIfAbsent、replace。 它们会在这个 key 所在的桶上持锁，把你的「读—判断—写」整个包进去。 

package com.example.javalinky.web;

import java.util.Iterator;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicLong;
import java.util.function.LongSupplier;

public final class RateLimiter {

    /** 桶的状态。做成不可变记录，这样 compute() 里只能整体替换，不会改了一半 */
    private record Bucket(double tokens, long updatedAt) {}

    private final int capacity;           // 桶最多装多少个令牌 = 允许的突发量
    private final double tokensPerNano;   // 补充速度
    private final long idleNanos;         // 多久没动过的桶可以回收
    private final LongSupplier clock;     // 默认 System.nanoTime，测试里换成假时钟

    private final ConcurrentHashMap<String, Bucket> buckets = new ConcurrentHashMap<>();
    private final AtomicLong callsSincePrune = new AtomicLong();

    private static final long PRUNE_EVERY = 1000;

    public RateLimiter(int capacity, double perSecond) {
        this(capacity, perSecond, System::nanoTime);
    }

    /** 时钟可注入：测试里换成假时钟，就不用 sleep 了 */
    public RateLimiter(int capacity, double perSecond, LongSupplier clock) {
        if (capacity < 1) throw new IllegalArgumentException("capacity 至少是 1");
        if (perSecond <= 0) throw new IllegalArgumentException("perSecond 必须大于 0");
        this.capacity = capacity;
        this.tokensPerNano = perSecond / 1_000_000_000.0;
        this.idleNanos = (long) (capacity / tokensPerNano) * 2;
        this.clock = clock;
    }

    public boolean tryAcquire(String key) {
        long now = clock.getAsLong();

        boolean[] granted = new boolean[1];
        buckets.compute(key, (k, bucket) -> {
            double tokens = bucket == null
                ? capacity
                : refill(bucket.tokens(), now - bucket.updatedAt());

            if (tokens >= 1.0) {
                granted[0] = true;
                return new Bucket(tokens - 1.0, now);
            }
            return new Bucket(tokens, now);
        });

        if (callsSincePrune.incrementAndGet() % PRUNE_EVERY == 0) prune(now);
        return granted[0];
    }

    /** 登录成功之后把这个 key 的记录清掉，别让之前的失败次数拖累正常用户 */
    public void reset(String key) {
        buckets.remove(key);
    }

    private double refill(double tokens, long elapsedNanos) {
        if (elapsedNanos <= 0) return tokens;
        return Math.min(capacity, tokens + elapsedNanos * tokensPerNano);
    }

    /** 清掉长时间没动过的桶 —— 不清的话这个 map 本身就是一个 DoS 入口 */
    private void prune(long now) {
        for (Iterator<Map.Entry<String, Bucket>> it = buckets.entrySet().iterator(); it.hasNext(); ) {
            Map.Entry<String, Bucket> e = it.next();
            if (now - e.getValue().updatedAt() > idleNanos) it.remove();
        }
    }
}

这段代码里有四个决定值得单独说。

☀ ① 为什么 boolean[] granted 这个数组能用

在 lambda 里写一个单元素数组，看着像个 hack —— Java 不允许 lambda 改外部局部变量， 所以用数组绕过去。但这里不只是能用，而且是安全的， 原因藏在 compute 的契约里：

ConcurrentHashMap.compute 的映射函数「最多执行一次」。 它在桶上持锁，不存在重试。所以在里面写副作用是对的。

对照一下，换成看起来等价的 AtomicReference 就错了： 

// ❌ updateAndGet 在 CAS 失败时会重跑这个函数，granted 会被多加
ref.updateAndGet(b -> { granted[0] = true; return ... ; });

Atomic* 的 updateAndGet / accumulateAndGet 文档明确要求函数无副作用，因为竞争时会重算。 这是两个 API 一个很容易踩错的区别。

☀ ② 为什么 Bucket 是个 record

如果 Bucket 是个有 setter 的普通类，compute 里就会变成 「拿到对象，改它两个字段」。问题是 remaining() 这种不走 compute 的读取方可能正好看到「tokens 改了但 updatedAt 还没改」 的半截状态。

做成不可变记录之后，状态变更只能是「整体换一个新的」。 读到的要么是旧的完整状态，要么是新的完整状态，不存在中间态。 这是并发编程里最省力的一招：能用不可变对象就别用锁。

⚠ ③ 那个 prune() 不是洁癖，是在堵一个洞

map 的 key 是 IP 地址 —— 也就是攻击者可以控制的东西。 不清理的话，每来一个新 IP 就多一条记录，永不释放。 IPv6 下伪造来源地址几乎不要成本，几百万条记录就能把你的堆撑爆。

「用外部输入当 key 的缓存」必须有上界或过期策略， 否则限流器本身就成了最好用的那个攻击面。这一条适用于一切 Map 形态的缓存，不限于限流。

这里用的是最省事的办法：每 1000 次调用顺手扫一遍。 生产环境更推荐 Caffeine 的 expireAfterAccess + maximumSize，它用的是 W-TinyLFU，不需要你自己管。

ⓘ ④ 时钟为什么要能注入

LongSupplier clock 这个参数只有测试会用到。 没有它的话，「过 60 秒令牌补回来了吗」这种测试只能靠 Thread.sleep(60_000) —— 一个测试跑一分钟，而且在 CI 上还不稳。

凡是依赖「现在几点」的逻辑，都把时钟做成参数。 标准库里的 java.time.Clock 就是为这个存在的 （Clock.fixed()、Clock.offset()）； 这里因为只需要一个单调纳秒数，用 LongSupplier 更轻。

⚠ 用 ctx.ip() 当 key 有两个坑

一、在反向代理后面，ctx.ip() 是代理的地址。 那样所有用户共用一个桶，第 6 个人就被挡在门外了。 第 17 章加的 cfg.behindProxy() 开关就是为这个： 开启时要让 Jetty 信任 X-Forwarded-For。 而且这个开关必须是显式配置 —— 如果在没有代理时也信任这个头， 攻击者自己伪造一个就能绕过限流。

二、IP 不等于人。一栋楼、一个学校出口 NAT 共用一个 IP； 反过来一个攻击者可以有很多 IP。所以 IP 限流是提高成本，不是 杜绝。更完整的方案是多个维度叠加：IP 一个桶、 被攻击的账号一个桶，再加上「失败 N 次后要求验证码」。

怎么写一个真的能抓住竞态的测试

这是本章最值得带走的一节。并发 bug 的可怕之处不在于难修， 而在于你的测试大概率根本没在测并发。

第一步：让线程真的「同时」开始

循环里 start() 500 个线程是不够的 —— 第一个线程可能在第 500 个还没创建出来时就跑完了。 要用 CountDownLatch 把它们卡在同一条起跑线上： 

var ready = new CountDownLatch(threads);   // 所有线程都起来了吗
var start = new CountDownLatch(1);         // 发令枪
var done  = new CountDownLatch(threads);   // 都跑完了吗

for (int i = 0; i < threads; i++) {
    new Thread(() -> {
        ready.countDown();                 // 报到
        try {
            start.await();                 // ← 所有线程堵在这一行
            if (limiter.tryAcquire("同一个IP")) granted.incrementAndGet();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            done.countDown();
        }
    }).start();
}

ready.await(30, TimeUnit.SECONDS);         // 等所有线程就位
start.countDown();                         // 砰 —— 一起放出去
done.await(30, TimeUnit.SECONDS);

第二步：确认这个测试真的有检测力

写完之后别急着满意。把正确的实现换成错误的那版，跑一遍， 看测试会不会红。不会红的话，这个测试就是个摆设。

本章就实测了一次，结果出乎意料 —— 所以这段值得原样记下来。 测试机是一台 2 核的 Linux 机器，用上面那个错误实现， 每种配置跑 20~50 轮，统计「放行次数 ≠ 容量」的比例：

线程类型线程数抓到竞态的轮次最高放行（容量 50）
虚拟线程2000 / 20　(0%)—
平台线程2009 / 50　(18%)52
平台线程50042 / 50　(84%)58
正确实现在以上所有配置下都是 0 次超发（50 轮 × 4 组，无一例外）
⚠ 用虚拟线程写的并发测试，可能一个 bug 都抓不到

这个结果第一眼很反直觉 —— 虚拟线程不是更轻、更容易起几千个吗？ 问题恰恰在这里：虚拟线程要挂在载体线程上才能跑， 而载体线程池默认只有 CPU 核数那么大。

在 2 核机器上，再多的虚拟线程也只有 2 个在真正并行。 而我们那段临界区是纯内存操作，几十纳秒就结束了 —— 两个线程要正好在这几十纳秒里交错，概率低到 20 轮都碰不上一次。

平台线程就不一样：它们由操作系统调度，会被随时抢占， 包括在 ① 和 ③ 中间。所以 500 个平台线程能把发现率推到 84%。

结论：测竞态要用平台线程，并且线程数要显著超过核数。 这和「生产环境用虚拟线程」不矛盾 —— 生产要的是吞吐，测试要的是搅动。

☀ 更让人不安的推论

84% 已经是把参数调到最好的结果。也就是说，就算你认真写了并发测试， 单跑一轮仍有 16% 的概率漏掉一个真实存在的 bug。

所以最终的测试里套了一层 for (int round = 1; round <= 3; round++)： 3 轮全部漏掉的概率是 0.16³ ≈ 0.4%。整个测试仍然只要 0.6 秒。

这也解释了为什么并发 bug 能活着上线 —— 它在开发机上「测过了」，只是那次没抓到。 真正可靠的办法是从一开始就用对的工具（原子操作、不可变对象）， 把测试当成第二道防线而不是第一道。 

/**
 * 两个参数是量出来的，不是拍的：
 *   - 平台线程，不是虚拟线程。虚拟线程挤在少数几个载体线程上，
 *     纳秒级的临界区根本碰不到一起 —— 2 核机器上跑 20 轮，一次都没抓住。
 *   - 500 个，不是 200 个。同一台机器上 200 个的发现率是 18%，500 个是 84%。
 *     再叠加 3 轮，漏网概率降到约 0.4%。
 */
@Test
void 五百个线程同时抢五十个令牌只能放行五十次() throws Exception {
    for (int round = 1; round <= 3; round++) {
        int threads = 500;
        int capacity = 50;
        var clock = new FakeClock();                   // 时间不走，排除补充的干扰
        var limiter = new RateLimiter(capacity, 1.0, clock::now);

        var ready = new CountDownLatch(threads);
        var start = new CountDownLatch(1);
        var done = new CountDownLatch(threads);
        var granted = new AtomicInteger();

        for (int i = 0; i < threads; i++) {
            new Thread(() -> {
                ready.countDown();
                try {
                    start.await();
                    if (limiter.tryAcquire("同一个IP")) granted.incrementAndGet();
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    done.countDown();
                }
            }).start();
        }

        assertThat(ready.await(30, TimeUnit.SECONDS)).as("线程没起齐").isTrue();
        start.countDown();
        assertThat(done.await(30, TimeUnit.SECONDS)).as("不该有线程卡住").isTrue();

        assertThat(granted.get())
            .as("第 %d 轮：多放行一次，就是多漏一次撞库尝试", round)
            .isEqualTo(capacity);
    }
}
💡 专业工具：jcstress

如果你要写的是真正的并发基础设施（一个无锁队列、一个自定义锁）， 手写 latch 测试是不够的 —— 你需要 OpenJDK 的 jcstress（Java Concurrency Stress Tests）。

它会穷举线程交错、插入内存屏障扰动、跑上百万次， 然后告诉你「这个结果组合出现了 37 次」——包括那些只在特定 CPU 架构上 才可能出现的重排。写应用代码用不上它，但知道它存在很重要。

虚拟线程：改变了什么，没改变什么

第 7 章有这么一行，当时一笔带过： 

javalin.concurrency.useVirtualThreads = true;

现在把它说清楚。

☀ 对 Python 程序员：这大致就是 async/await，但不用改代码

Python 为了解决同一个问题引入了 async def / await， 代价是生态分裂：同步的库不能在异步代码里用， 于是有了 requests 和 httpx、 psycopg2 和 asyncpg、Flask 和 FastAPI。 这就是所谓的「函数颜色」问题。

虚拟线程把这件事做在了 JVM 层：阻塞的是虚拟线程，不是载体线程。 所以 JDBC、InputStream、Thread.sleep() 这些老代码 一行不改就享受到了收益 —— 没有颜色问题，也没有生态分裂。

⚠ 它没有解决的事情
  1. 共享可变状态仍然要同步。本章前面所有内容在虚拟线程下 一字不改地成立。虚拟线程让你更容易起几万个线程 —— 也就是让竞态更容易发生。
  2. CPU 密集的活一点没变快。虚拟线程的收益全部来自「等待时让出载体」。 bcrypt 验证那 200 毫秒是实打实在算，让不出去。
  3. ThreadLocal 的代价变了。几万个虚拟线程 = 几万份 ThreadLocal 副本。我们的 QueryStats 只存一个小 Counter，没问题；但如果你往 ThreadLocal 里塞大对象 （比如一个连接、一个缓冲区），在虚拟线程下就是内存灾难。 JDK 20+ 的 ScopedValue 是为此准备的替代品。
  4. 连接池仍然是瓶颈。一万个虚拟线程同时要数据库连接， 而 HikariCP 只有 10 个 —— 它们就在那里排队。 虚拟线程把瓶颈从线程池挪到了连接池，并没有变没。

pinning：唯一需要你操心的新问题

虚拟线程在阻塞时「卸载」载体线程。但有两种情况它卸载不了， 只能死死占住载体 —— 这叫 pinning（钉住）： 

// ⚠️ JDK 21 下：在 synchronized 块里阻塞，会把载体线程钉住
synchronized (lock) {
    var result = jdbcTemplate.query(...);    // 阻塞 I/O，但让不出去
}

// ✅ 改用 ReentrantLock，它是虚拟线程友好的
private final ReentrantLock lock = new ReentrantLock();

lock.lock();
try {
    var result = jdbcTemplate.query(...);    // 阻塞时正常卸载
} finally {
    lock.unlock();
}

另一种是本地方法（JNI）里的阻塞，那个没办法绕。 钉住的后果是：载体线程池（默认 = CPU 核数）被占光之后， 所有虚拟线程一起卡住，表现为应用突然整体没响应。

ⓘ 怎么查 pinning，以及一个好消息
# 启动时加上，被钉住就打栈
java -Djdk.tracePinnedThreads=full -jar target/javalinky.jar

# 或者用第 16 章的 JFR：jdk.VirtualThreadPinned 事件
jfr print --events jdk.VirtualThreadPinned recording.jfr

好消息是 JDK 24 的 JEP 491 基本消灭了 synchronized 引起的 pinning。本教程用的是 JDK 21，所以这一条仍然要注意； 如果你跑在 24 及以上，只剩 JNI 那一种了。

不管哪个版本，新代码一律优先用 ReentrantLock 总是没错的。

工具箱：什么场景用什么

最后给一张对照表。遇到共享状态时，从上往下找第一个够用的 —— 越靠上的越省心。

优先级手段适用我们在哪用了
1 不共享
每请求一份		 能不共享就不共享 —— 这是最彻底的解法 EntityManager（UnitOfWork）
2 不可变
record / final		 共享但从不修改。天然安全，不需要任何同步 AppConfig、Bucket、各种 DTO
3 ThreadLocal 每线程一份的上下文。注意虚拟线程下别放大对象 QueryStats、SLF4J 的 MDC
4 并发容器
ConcurrentHashMap 等		 共享的集合。复合操作一定要用它的原子方法 RateLimiter
5 Atomic* 单个计数器 / 引用。函数式更新方法里不能有副作用 RateLimiter.callsSincePrune
6 volatile 只要可见性、不要原子性的单个标志位 —
7 ReentrantLock 上面都不够用时。虚拟线程下优于 synchronized —
8 数据库
唯一索引 / 悲观锁		 跨进程的竞态 —— 多实例部署时 JVM 内的锁全部失效 ix_users_email（第 8 章）
⚠ 最后一行最容易被忘掉：多开一个实例，你的锁就没了

本章讲的所有手段 —— 原子操作、volatile、ReentrantLock —— 作用范围都只到一个 JVM 为止。 第 17 章部署时只要你起了两个实例（或者一个容器扩到两副本）， 这个 RateLimiter 就变成了两个独立的限流器，配额直接翻倍。

这不一定是问题（限流本来就是概率性的），但你必须知道它。 要跨实例一致，只能把状态放到进程之外：Redis 的 INCR + EXPIRE，或者数据库的行锁。

对「同一个邮箱只能注册一次」这种绝不能错的约束， 唯一可靠的答案从来都是数据库的唯一索引 —— 第 8 章说的「数据库约束是最后防线」，现在应该更有体会了。

动手练习

  1. 亲手制造一次竞态。把 RateLimiter.tryAcquire 换成本章「错误的写法」那一版，跑 RateLimiterTest。 没红的话多跑几次 —— 感受一下 84% 是什么体验。 然后把线程数从 500 改成 50，看发现率怎么掉下去。
  2. 验证虚拟线程抓不到。把那个测试里的 new Thread(...) 换成 Thread.ofVirtual().start(...)， 配合错误实现跑 20 次，数一数抓到几次。 再用 Runtime.getRuntime().availableProcessors() 看看你的核数， 对照正文那张表。
  3. 可见性的实验。照正文那个 Worker 写一个小程序： 一个线程空转 while (running)，主线程 1 秒后 stop()。 用 java -XX:+UnlockDiagnosticVMOptions -XX:-TieredCompilation 跑，看它会不会永远不退出。加上 volatile 再跑一次。
  4. RateLimiter 现在只按 IP 限流。加一个按邮箱的桶： 同一个账号被从很多 IP 攻击时也要能挡住。想清楚两个桶的关系 —— 是「任一超限就拒绝」还是「都超限才拒绝」？
  5. 把 prune() 换成 Caffeine （Caffeine.newBuilder().expireAfterAccess(...).maximumSize(...)）。 对比一下代码量，以及你因此少操心了什么。
