关注

“关注”让 Javalinky 从博客变成社交网络。这一章的技术含量集中在数据建模上： 我们需要一个多对多、自引用、还带额外字段的关系 —— 这三个修饰词叠在一起，正好把关系型建模的几个关键概念都覆盖了。 最后那个“查出我关注的人的全部文章”的 JOIN，值得你反复读几遍。

本章目标

  • 分清一对多、多对多、自引用三种关系
  • 理解为什么多对多需要关联表，以及什么时候关联表必须升级成实体
  • 会写 JPA 的复合主键（@IdClass）
  • 彻底搞懂那条 JOIN 查询是怎么工作的
  • 实现关注/取关、关注者列表、以及首页的“只看关注”

关系回顾

为什么关联表必须升级成实体

如果 follows 表只有两个外键，JPA 可以用 @ManyToMany 自动帮你管， 你甚至看不到那张表的存在： 

// 纯粹的多对多：JPA 自动维护 follows 表，代码里看不到它
@ManyToMany
@JoinTable(name = "follows",
    joinColumns = @JoinColumn(name = "follower_id"),
    inverseJoinColumns = @JoinColumn(name = "followed_id"))
private Set<User> following = new HashSet<>();

但我们想记录“什么时候关注的”。 一旦关联表需要额外的列，@ManyToMany 就不够用了 —— 因为它管理的是"用户的集合"，没地方放时间戳。

☀ 这是一个必须记住的建模规则

多对多关系一旦需要记录"关系本身的属性"，就要把关联表建成独立实体， 然后用两个一对多代替一个多对多。

而且现实中这种需求几乎总会出现：关注时间、是否特别关注、是否屏蔽动态…… 所以很多人的经验是：一开始就建成实体，省得以后改。 原书也是这么做的（Follow 模型）。

建表与建模

CREATE TABLE follows (
    follower_id BIGINT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    followed_id BIGINT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    timestamp   TIMESTAMP(6) WITH TIME ZONE NOT NULL,

    -- 复合主键：保证"同一对关系"只能有一条记录
    PRIMARY KEY (follower_id, followed_id)
);

-- 主键索引已经覆盖了"我关注了谁"的查询（最左前缀是 follower_id）
-- 但"谁关注了我"需要另一个索引
CREATE INDEX ix_follows_followed ON follows (followed_id);
ⓘ 复合主键顺便解决了两个问题
  1. 防重复关注。同一对 (follower, followed) 插第二次会违反主键约束， 数据库直接拒绝 —— 不用靠应用逻辑保证。
  2. 查询加速。主键自带索引，而 (follower_id, followed_id) 这个顺序正好能加速"我关注了谁"的查询。

ON DELETE CASCADE 则保证删用户时它的关注记录一起消失， 不会留下指向不存在用户的脏数据。

复合主键：@IdClass

JPA 表达复合主键有两种方式（@IdClass 和 @EmbeddedId）。 这里用 @IdClass，因为它让实体的字段声明保持直观： 

package com.example.javalinky.model;

import java.io.Serializable;
import java.util.Objects;

/**
 * Follow 的复合主键。
 * 规则：字段名必须和 Follow 里标了 @Id 的字段同名，
 *      类型是对应实体的主键类型（User 的主键是 Long）。
 * 另外必须有公开的无参构造器，并正确实现 equals/hashCode。
 */
public class FollowId implements Serializable {

    private Long follower;
    private Long followed;

    public FollowId() {}

    public FollowId(Long follower, Long followed) {
        this.follower = follower;
        this.followed = followed;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof FollowId other)) return false;
        return Objects.equals(follower, other.follower)
            && Objects.equals(followed, other.followed);
    }

    @Override
    public int hashCode() {
        return Objects.hash(follower, followed);
    }
}

package com.example.javalinky.model;

import jakarta.persistence.*;
import java.time.Instant;

@Entity
@Table(name = "follows")
@IdClass(FollowId.class)
public class Follow {

    /** 关注的发起者 */
    @Id
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "follower_id", nullable = false)
    private User follower;

    /** 被关注的人 */
    @Id
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "followed_id", nullable = false)
    private User followed;

    @Column(name = "timestamp", nullable = false)
    private Instant timestamp = Instant.now();

    protected Follow() {}

    public Follow(User follower, User followed) {
        this.follower = follower;
        this.followed = followed;
    }

    public User getFollower() { return follower; }
    public User getFollowed() { return followed; }
    public Instant getTimestamp() { return timestamp; }
}
💡 更简单的替代方案：代理主键

复合主键在 JPA 里写起来比较啰嗦（要多一个类、要手写 equals/hashCode）。 很多团队的做法是给关联实体一个普通的自增 id，再加唯一约束： 

@Entity
@Table(name = "follows", uniqueConstraints =
    @UniqueConstraint(columnNames = {"follower_id", "followed_id"}))
public class Follow {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    // ... follower / followed / timestamp
}

效果几乎一样（唯一约束同样防重复），代码少一半。 本教程用复合主键是为了跟原书的表结构一致，也为了让你见过这种写法。 实际项目里代理主键更省事，推荐。

User 上的两个集合

/** 我关注了谁（我是 follower） */
@OneToMany(mappedBy = "follower", fetch = FetchType.LAZY,
           cascade = CascadeType.ALL, orphanRemoval = true)
private List<Follow> following = new ArrayList<>();

/** 谁关注了我（我是 followed） */
@OneToMany(mappedBy = "followed", fetch = FetchType.LAZY,
           cascade = CascadeType.ALL, orphanRemoval = true)
private List<Follow> followers = new ArrayList<>();

public List<Follow> getFollowing() { return following; }
public List<Follow> getFollowers() { return followers; }
ⓘ cascade 和 orphanRemoval 分别管什么
设置含义这里为什么要
cascade = ALL对 User 做的操作（persist / remove / merge）传播到它的 Follow 记录删用户时它的关注记录一起删
orphanRemoval = true从集合里移除一个 Follow，就意味着删除它取关时直接 following.remove(f) 即可

注意数据库层面我们也写了 ON DELETE CASCADE。两层都配是有意的： JPA 的 cascade 只在"通过 JPA 删除"时生效， 而数据库约束对任何途径（包括手写 SQL、别的服务）都生效。

关注操作

package com.example.javalinky.db;

import com.example.javalinky.model.Follow;
import com.example.javalinky.model.FollowId;
import com.example.javalinky.model.User;
import jakarta.persistence.EntityManager;

import java.util.List;

public class FollowRepository {

    private final EntityManager em;

    public FollowRepository(EntityManager em) {
        this.em = em;
    }

    public boolean isFollowing(User follower, User followed) {
        if (follower == null || followed == null) return false;
        return em.find(Follow.class,
            new FollowId(follower.getId(), followed.getId())) != null;
    }

    public void follow(User follower, User followed) {
        if (isFollowing(follower, followed)) return;      // 幂等
        em.persist(new Follow(follower, followed));
    }

    public void unfollow(User follower, User followed) {
        Follow follow = em.find(Follow.class,
            new FollowId(follower.getId(), followed.getId()));
        if (follow != null) em.remove(follow);
    }

    /**
     * 关注数 / 粉丝数。
     * 注意要减去 1，因为每个人都关注了自己（见本章最后一节）。
     */
    public long countFollowing(User user) {
        return count("f.follower", user);
    }

    public long countFollowers(User user) {
        return count("f.followed", user);
    }

    private long count(String side, User user) {
        return em.createQuery(
                "select count(f) from Follow f where " + side + " = :u", Long.class)
            .setParameter("u", user)
            .getSingleResult();
    }

    /** 粉丝列表（分页）。join fetch 关注者本人，避免 N+1 */
    public Page<Follow> followersOf(User user, int page, int size) {
        long total = countFollowers(user);
        var items = em.createQuery("""
                select f from Follow f
                  join fetch f.follower
                 where f.followed = :u
                 order by f.timestamp desc
                """, Follow.class)
            .setParameter("u", user)
            .setFirstResult((page - 1) * size)
            .setMaxResults(size)
            .getResultList();
        return Page.of(items, page, size, total);
    }

    /** 关注列表（分页） */
    public Page<Follow> followingOf(User user, int page, int size) {
        long total = countFollowing(user);
        var items = em.createQuery("""
                select f from Follow f
                  join fetch f.followed
                 where f.follower = :u
                 order by f.timestamp desc
                """, Follow.class)
            .setParameter("u", user)
            .setFirstResult((page - 1) * size)
            .setMaxResults(size)
            .getResultList();
        return Page.of(items, page, size, total);
    }
}

private void follow(Context ctx) {
    User me = CurrentUser.require(ctx);
    User target = services.users(ctx).findByUsername(ctx.pathParam("username"))
        .orElseThrow(() -> new NotFoundResponse("没有这个用户"));

    if (me.getId().equals(target.getId())) {
        Flash.warning(ctx, "你不能关注自己。");
        ctx.redirect(Routes.user(target.getUsername()));
        return;
    }

    var follows = services.follows(ctx);
    if (follows.isFollowing(me, target)) {
        Flash.info(ctx, "你已经关注了 " + target.getUsername() + "。");
    } else {
        follows.follow(me, target);
        Flash.success(ctx, "已关注 " + target.getUsername() + "。");
    }
    ctx.redirect(Routes.user(target.getUsername()));
}

private void unfollow(Context ctx) {
    User me = CurrentUser.require(ctx);
    User target = services.users(ctx).findByUsername(ctx.pathParam("username"))
        .orElseThrow(() -> new NotFoundResponse("没有这个用户"));

    services.follows(ctx).unfollow(me, target);
    Flash.info(ctx, "已取消关注 " + target.getUsername() + "。");
    ctx.redirect(Routes.user(target.getUsername()));
}

核心：查出“我关注的人的文章”

这是本章真正的难点，也是原书花了最多篇幅解释的地方。 需求是：首页能切换成“只看我关注的人发的文章”，而且要能分页。

错误做法：N+1

// ✗ 千万别这么写
List<Post> timeline = new ArrayList<>();
for (Follow f : me.getFollowing()) {                // 1 条查询
    timeline.addAll(postRepo.findByAuthor(f.getFollowed()));   // 每个人 1 条
}
timeline.sort(comparing(Post::getTimestamp).reversed());       // 在内存里排序

原书把这个问题叫 N+1 问题：1 次查关注列表 + N 次查每个人的文章。它的致命缺陷不止是慢：

  • 关注 500 个人就是 501 条 SQL；
  • 没法分页——你必须把所有人的所有文章全查出来才能排序， 然后取前 20 条。关注的人越多，查出来的数据越多，内存越爆；
  • 排序和分页在应用内存里做，数据库的索引完全用不上。

正确答案是：用一条带 JOIN 的查询，让数据库一次搞定过滤、排序和分页。

JOIN 到底在干什么

原书用一组小表格把 JOIN 讲得非常清楚，这里完整复现一遍。 假设数据是这样的：

写成 JPQL

/**
 * 查出某用户关注的人发的全部文章（他的"时间线"）。
 *
 * 对应的 SQL 大致是：
 *   select p.* from posts p
 *     join follows f on f.followed_id = p.author_id
 *    where f.follower_id = ?
 *    order by p.timestamp desc
 *    limit ? offset ?
 */
public Page<Post> findTimeline(User user, int page, int size) {
    long total = em.createQuery("""
            select count(p)
              from Post p
              join Follow f on f.followed = p.author
             where f.follower = :me
            """, Long.class)
        .setParameter("me", user)
        .getSingleResult();

    var items = em.createQuery("""
            select p
              from Post p
              join fetch p.author
              join Follow f on f.followed = p.author
             where f.follower = :me
             order by p.timestamp desc
            """, Post.class)
        .setParameter("me", user)
        .setFirstResult((page - 1) * size)
        .setMaxResults(size)
        .getResultList();

    return Page.of(items, page, size, total);
}
☀ 注意这里有两种 join，别混了
写法作用影响结果集吗
join fetch p.author顺便把作者一起查出来，避免后面访问 post.getAuthor() 时 N+1不影响（只是多取了列）
join Follow f on f.followed = p.author用来过滤：只保留那些作者被我关注了的文章影响（这是筛选条件）

JPQL 支持 join … on … 这种"显式连接任意实体"的写法 （Jakarta Persistence 2.1 开始），正好对应原书那条 Post.query.join(Follow, Follow.followed_id == Post.author_id)。

⚠ JOIN 可能产生重复行

如果一个作者在 follows 里对应多行（我们的复合主键保证了不会）， JOIN 之后同一篇文章会出现多次。 遇到这种情况要加 select distinct p。

但 distinct 和 join fetch 一起用时要小心： Hibernate 6+ 默认会在 Java 层面去重，不会把 distinct 发给数据库（这正是我们想要的）。 老版本需要 .setHint("hibernate.query.passDistinctThrough", false)。

一个巧妙的技巧：让每个人关注自己

上面的查询有个问题：我自己的文章不在我的时间线里。 这不符合直觉 —— 刷社交网站首页时你肯定希望看到自己刚发的内容。

怎么解决？最直接的想法是改查询：where f.follower = :me or p.author = :me。 但原书用了一个更漂亮的办法：注册时让每个用户自动关注自己。 

users.save(user);
Db.em(ctx).flush();
services.follows(ctx).follow(user, user);    // ← 自己关注自己

已有用户需要补数据。写成一个幂等的任务，放进 Cli deploy：

/**
 * 确保每个用户都关注了自己。幂等，可以反复执行。
 * 相当于原书的 User.add_self_follows()。
 */
public static void addSelfFollows() {
    var follows = new FollowRepository(em);
    var users = em.createQuery("select u from User u", User.class).getResultList();

    int added = 0;
    for (User user : users) {
        if (!follows.isFollowing(user, user)) {
            follows.follow(user, user);
            added++;
        }
    }
    System.out.printf("为 %d 个用户补上了自关注%n", added);
}

然后把计数减 1，别让用户看到奇怪的数字：

/** 对外展示的关注数：减掉"自己关注自己"那一条 */
public long countFollowingVisible(User user) {
    return Math.max(0, countFollowing(user) - 1);
}

public long countFollowersVisible(User user) {
    return Math.max(0, countFollowers(user) - 1);
}
⚠ 别忘了把自己从列表里过滤掉

粉丝列表和关注列表也会出现自己。原书没处理这一点（列表里会看到自己）， 我们在查询里加个条件： 

where f.followed = :u and f.follower <> :u

这也顺便说明了方案 B 的代价：每一处用到关注数据的地方都要记得排除自己。

首页的“全部 / 关注”切换

原书用一个 Cookie 记住用户的选择（而不是会话）—— 这样即使会话过期，偏好还在。我们照做： 

private static final String COOKIE_SHOW_FOLLOWED = "show_followed";

private void index(Context ctx) {
    int page = Page.clampPage(ctx.queryParamAsClass("page", Integer.class)
                                 .allowNullable().get());
    User me = CurrentUser.get(ctx);

    // 只有登录用户才可能选"只看关注"
    boolean showFollowed = me != null
        && "1".equals(ctx.cookie(COOKIE_SHOW_FOLLOWED));

    var repo = services.postRepo(ctx);
    Page<Post> posts = showFollowed
        ? repo.findTimeline(me, page, cfg.postsPerPage())
        : repo.findAll(page, cfg.postsPerPage());

    View.render(ctx, "index.jte", "首页",
                "form", FormView.empty(),
                "posts", PostListPage.of(posts, me),
                "showFollowed", showFollowed);
}

/** 切换到"全部" */
private void showAll(Context ctx) {
    CurrentUser.require(ctx);
    ctx.cookie(COOKIE_SHOW_FOLLOWED, "", 0);     // maxAge=0 就是删除
    ctx.redirect(Routes.INDEX);
}

/** 切换到"只看关注" */
private void showFollowed(Context ctx) {
    CurrentUser.require(ctx);
    ctx.cookie(COOKIE_SHOW_FOLLOWED, "1", 30 * 24 * 60 * 60);   // 30 天
    ctx.redirect(Routes.INDEX);
}

💡 为什么是 Cookie 而不是会话或数据库
存法生存期适合
Cookie自己设（我们设了 30 天）纯界面偏好，丢了也没事
会话登出就没了临时状态（比如多步表单的中间数据）
数据库永久，跨设备真正的用户设置（语言、通知偏好）

“首页默认看哪个标签”属于第一类。注意 Cookie 里存的是 非敏感的界面偏好，所以不需要签名 —— 用户自己改成 show_followed=1 也没有任何危害。

粉丝 / 关注列表页

package com.example.javalinky.web.page;

import com.example.javalinky.db.Page;
import com.example.javalinky.model.Follow;
import java.time.Instant;
import java.util.List;

public record FollowListPage(
    String title,              // "xxx 的粉丝" / "xxx 关注的人"
    String ownerUsername,
    String baseUrl,
    Page<Item> page
) {
    public record Item(String username, String name, String avatarHash, Instant since) {}

    /** showFollower=true 表示列"关注者"，false 表示列"被关注者" */
    public static FollowListPage of(String title, String ownerUsername, String baseUrl,
                                    Page<Follow> source, boolean showFollower) {
        List<Item> items = source.items().stream()
            .map(f -> showFollower ? f.getFollower() : f.getFollowed())
            .map(u -> new Item(u.getUsername(),
                               u.getName() == null ? "" : u.getName(),
                               u.avatarHash(),
                               null))
            .toList();
        return new FollowListPage(title, ownerUsername, baseUrl,
            Page.of(items, source.page(), source.size(), source.total()));
    }
}

private void followers(Context ctx) {
    User user = loadUserByUsername(ctx);
    int page = Page.clampPage(ctx.queryParamAsClass("page", Integer.class)
                                 .allowNullable().get());

    var source = services.follows(ctx)
        .followersOf(user, page, cfg.followersPerPage());

    View.render(ctx, "follow_list.jte", user.getUsername() + " 的粉丝",
        "page", FollowListPage.of(
            user.getUsername() + " 的粉丝",
            user.getUsername(),
            Routes.followers(user.getUsername()),
            source, true));
}

关于“时间线”的现实

🔎 深入：这套做法能支撑多大规模

我们的时间线是读时聚合（read fanout）：每次打开首页， 现场 JOIN 算出结果。它的特点是：

  • 写很便宜：发文章就是一条 INSERT；
  • 读比较贵：每次都要 JOIN + 排序。

对中小型站点（几万用户、人均关注几百）这完全够用 —— 配上 ix_posts_author_timestamp 索引，这条查询是毫秒级的。

但如果某个用户被一千万人关注（明星账号），情况就不同了。 大型社交网络改用写时扩散（write fanout）： 发一条内容时，立刻把它推进所有粉丝的"收件箱"（一张预先算好的表或 Redis 列表）。 读首页变成一次简单的范围查询，但发一条内容可能要写一千万次。

真实系统往往是混合的：普通用户写时扩散，大 V 读时聚合。 这个话题超出本教程范围，但你应该知道 “时间线”是整个社交产品里最难做的技术点， 而我们这条 JOIN 是它最朴素也最正确的起点。

动手练习

  1. 造一批假数据，然后在 JShell 里手动建几条关注关系。 用 show_sql 打开 SQL 日志，访问"我关注的"标签页， 确认只发了两条 SQL（一条 count，一条取数据）。
  2. 按上面"错误做法"那段代码写一个 N+1 版本的时间线， 对比两者在关注 50 个人时的 SQL 条数和耗时。
  3. 试着重复关注同一个人（直接调两次 follows.follow(a, b) 并提交）， 确认数据库的主键约束把它挡住了。 然后把 follow() 里的 isFollowing 判断去掉，看看异常长什么样。
  4. 把 addSelfFollows() 连着跑两次，确认第二次输出"为 0 个用户补上了自关注"—— 这验证了幂等。
  5. 检查粉丝列表里有没有出现自己。如果有，按正文里的提示加上 f.follower <> :u 的过滤。
  6. 关掉"自己关注自己"的设计，改成在查询里加 or p.author = :me。 然后用 EXPLAIN（第 16 章会讲怎么用）对比两条查询的执行计划， 看看 OR 是不是真的影响了索引使用。
  7. （进阶）给 Follow 加一个 boolean muted 字段（“关注但不看他的动态”）， 写好迁移，并在时间线查询里加上 and f.muted = false。 体会一下"关联实体"相比"纯多对多"的扩展性优势。
