第 23 章

时区与国际化

这一章的内容有个特点：平时完全看不出问题， 到了某几个特定的时刻就集体出错 —— 跨年的那一夜、夏令时切换的那两个小时、用户出了一趟国。 好消息是我们从第 5 章起就把时间存成了 Instant， 地基是对的；要补的是「渲染的那一刻」。

本章目标

  • 分清 Instant / LocalDateTime / ZonedDateTime，知道什么时候用哪个
  • 理解「偏移量不是时区」，以及为什么这个区别会害死人
  • 知道「昨天」「今天」这类判断必须先转时区再比日历
  • 用 ResourceBundle 做多语言，并正确协商 Accept-Language
  • 把用户输入的时区名当成不可信数据

先分清三个类型

java.time 的设计非常好，但前提是你选对了类型。 选错的代价要很久以后才显现。

类型表示什么举例什么时候用
Instant 时间轴上的一个点。没有时区、没有日历， 就是「从 1970 年起过了多少纳秒」 某条评论被发出的那一瞬间 存数据库、记日志、算时长 —— 默认就用它
LocalDateTime 墙上挂钟的读数。没有时区，所以它不对应任何确定的时刻 「3 月 8 日上午 9 点」—— 但哪里的 9 点？ 生日、营业时间、闹钟这类「在当地几点」的概念
ZonedDateTime 时刻 + 时区 + 日历规则，三者齐全 「纽约时间 3 月 8 日上午 9 点」 要做日历运算的时候（加一天、取这一天的开始）
☀ 一条贯穿全书的规矩：存 UTC，渲染时才转
// 实体里（第 5 章起就是这样）
@Column(nullable = false)
private Instant timestamp = Instant.now();      // ✅ 没有时区的歧义

// ❌ 千万别这样
private LocalDateTime timestamp;                // 哪个时区的？谁也说不清

LocalDateTime 存进数据库，在服务器从上海迁到法兰克福的那天 会集体错 7 小时，而且历史数据无法修复 —— 因为你不知道每条记录当初是按哪个时区写的。

Instant 就没有这个问题：它本身就是绝对的， 服务器在哪、用户在哪，都只影响显示。

⚠ 偏移量不是时区

+08:00 和 Asia/Shanghai 看起来是一回事， 完全不是：

  • +08:00 是一个固定偏移，永远比 UTC 快 8 小时
  • Asia/Shanghai 是一套规则： 现在是 +08:00，但 1986–1991 年中国实行过夏令时，那几年夏天是 +09:00

对有夏令时的地区，这个区别每年咬你两次： 

@Test
void 偏移量不等于时区() {
    var realZone = ZoneId.of("America/New_York");
    var fixed    = ZoneId.of("-05:00");    // 纽约的冬季偏移

    Instant summer = Instant.parse("2026-07-01T12:00:00Z");
    assertThat(summer.atZone(realZone).getHour())
        .as("真时区懂夏令时，夏天是 -04:00")
        .isNotEqualTo(summer.atZone(fixed).getHour());
}

所以用户的时区偏好一定要存 IANA 的名字 （Asia/Shanghai），不能存偏移量。 浏览器那边用 Intl.DateTimeFormat().resolvedOptions().timeZone 就能拿到正确的名字。

夏令时：三个会咬人的事实

@Test
void 夏令时切换当天只有23小时() {
    ZoneId ny = ZoneId.of("America/New_York");

    ZonedDateTime before = ZonedDateTime.of(2026, 3, 8, 0, 30, 0, 0, ny);
    ZonedDateTime after  = ZonedDateTime.of(2026, 3, 9, 0, 30, 0, 0, ny);

    assertThat(java.time.Duration.between(before, after).toHours())
        .as("日历上过了一天，但只过了 23 小时 —— 所以『一天 = 86400 秒』是错的")
        .isEqualTo(23);
}

@Test
void 不存在的本地时间会被调整而不是抛异常() {
    ZoneId ny = ZoneId.of("America/New_York");
    // 2026-03-08 02:30 在纽约根本不存在（时钟从 2:00 跳到 3:00）
    ZonedDateTime ghost = ZonedDateTime.of(2026, 3, 8, 2, 30, 0, 0, ny);

    assertThat(ghost.getHour())
        .as("java.time 会把它顺延到 3:30，不会报错 —— 所以这种 bug 很难发现")
        .isEqualTo(3);
}
☀ 「加一天」有两种含义，而且结果不一样
ZonedDateTime t = ZonedDateTime.of(2026, 3, 7, 12, 0, 0, 0, ZoneId.of("America/New_York"));

t.plusDays(1)            // 3 月 8 日 12:00 —— 日历上的一天（实际过了 23 小时）
t.plus(Duration.ofDays(1))  // 3 月 8 日 13:00 —— 物理上的 24 小时

两个都对，看你要的是哪个。「每天上午 9 点发日报」要的是前者， 「24 小时后令牌过期」要的是后者。 把它们搞混，用户就会在每年两个特定的日子收到晚一小时的日报。

渲染：时区在最后一刻才参与

/**
 * 按「看的人是谁」来格式化时间。
 * 存的一律是 Instant（= UTC 的一个时刻，没有时区概念）；
 * 时区只在渲染的那一刻才参与进来。
 */
public record Formats(ZoneId zone, Locale locale) {

    /** 2026年3月14日 15:09 */
    public String dateTime(Instant at) {
        if (at == null) return "";
        return DateTimeFormatter.ofLocalizedDateTime(FormatStyle.LONG, FormatStyle.SHORT)
            .withLocale(locale).withZone(zone).format(at);
    }

    /**
     * 「3 分钟前」。
     * 注意「昨天」「今天」这类判断必须先转到用户时区再比日期 ——
     * 直接拿 Instant 相减得到的是绝对时长，不是日历上的天数。
     */
    public String relative(Instant at, Instant now) {
        if (at == null) return "";

        Duration elapsed = Duration.between(at, now);
        if (elapsed.isNegative()) return "刚刚";

        long seconds = elapsed.toSeconds();
        if (seconds < 60)   return "刚刚";
        if (seconds < 3600) return elapsed.toMinutes() + " 分钟前";

        // 跨不跨天是按用户所在时区的日历算的，不是按 24 小时
        LocalDate thatDay = at.atZone(zone).toLocalDate();
        LocalDate today   = now.atZone(zone).toLocalDate();

        if (thatDay.equals(today))                return elapsed.toHours() + " 小时前";
        if (thatDay.equals(today.minusDays(1)))   return "昨天";
        if (thatDay.isAfter(today.minusDays(7)))  return today.toEpochDay() - thatDay.toEpochDay() + " 天前";
        return date(at);
    }
}
⚠ 「昨天」不是「24 小时前」

最常见的写法是 if (elapsed.toHours() < 48) return "昨天";。 这在晚上会错得很明显： 

@Test
void 跨日判断要按用户时区算而不是按24小时() {
    ZoneId ny = ZoneId.of("America/New_York");
    var formats = new Formats(ny, Locale.SIMPLIFIED_CHINESE);

    // 纽约时间 1 月 1 日 23:00 和 1 月 2 日 01:00，只差 2 小时但跨了一天
    Instant lateNight = ZonedDateTime.of(2026, 1, 1, 23, 0, 0, 0, ny).toInstant();
    Instant nextDay   = ZonedDateTime.of(2026, 1, 2, 1, 0, 0, 0, ny).toInstant();

    assertThat(formats.relative(lateNight, nextDay))
        .as("只隔 2 小时，但日历上是昨天")
        .isEqualTo("昨天");
}

正确的做法是把两个 Instant 各自转到用户时区 拿到 LocalDate，再比日期。 「几分钟前」「几小时前」这类时长可以直接减， 「今天/昨天」这类日历概念不行。

模板那边

@param Layout layout
@param Instant at
@param boolean relative = true

<%-- datetime 属性里永远是 UTC 的 ISO 串（机器读），
     显示出来的才是用户时区的本地时间（人读） --%>
<time datetime="${layout.formats().iso(at)}"
      title="${layout.formats().dateTime(at)}">
    ${relative ? layout.formats().relative(at, Instant.now()) : layout.formats().dateTime(at)}
</time>
ⓘ 为什么从「前端 JS 格式化」改成了服务端

第 3 章那版是把 ISO 串扔给浏览器，让 JS 去转。那样有三个问题： 没有 JS 就看到一串 2026-03-14T07:09:00Z、 爬虫和邮件里不对、以及首屏会闪一下（先显示 UTC 再被改写）。

服务端渲染的代价是：用户换了时区要刷新页面才生效。 对博客来说这完全可以接受。 <time datetime> 属性仍然保留 UTC 的 ISO 串 —— 那是给机器看的（搜索引擎、阅读器、辅助技术），两边各取所需。

☀ 不要自己拼句子

最常见的国际化错误是这样写： 

// ❌ 这段代码无法翻译成很多语言
String text = count + " " + msg.get("comments") + (count == 1 ? "" : "s");

问题是语序和单复数规则是每种语言自己的事。 英语两种形式（1 / 其它），俄语三种，阿拉伯语六种， 中文一种但量词有很多个。把句子拆成零件在代码里拼， 等于假定所有语言都和英语一个结构。

正确做法是整句进文案文件，数字当参数传， 由 MessageFormat 的 choice 去选： 

var en = Messages.of(Locale.ENGLISH);
en.get("post.comments", 0);   // "No comments"
en.get("post.comments", 1);   // "1 comment"
en.get("post.comments", 5);   // "5 comments"

var zh = Messages.of(Locale.SIMPLIFIED_CHINESE);
zh.get("post.comments", 0);   // "还没有评论"
zh.get("post.comments", 5);   // "5 条评论"

同一个 key、同一个调用，两种语言给出各自自然的句子 —— 而调用处一个 if 都没有。

语言协商：别自己解析 Accept-Language

/**
 * 从 Accept-Language 头里挑一个我们支持的语言。
 * 自己解析这个头很容易写错，JDK 的 Locale.lookup 已经实现了 RFC 4647。
 */
public static Locale fromAcceptLanguage(String header) {
    if (header == null || header.isBlank()) return Formats.DEFAULT_LOCALE;
    try {
        List<Locale.LanguageRange> ranges = Locale.LanguageRange.parse(header);
        Locale match = Locale.lookup(ranges, SUPPORTED);
        return match == null ? Formats.DEFAULT_LOCALE : match;
    } catch (IllegalArgumentException e) {
        // 畸形的头不该让整个请求挂掉
        return Formats.DEFAULT_LOCALE;
    }
}

Accept-Language: zh-CN,zh;q=0.9,en;q=0.8 这个头比看起来复杂： 有权重、有通配、有「语言-地区」的层级回退规则。 JDK 已经按 RFC 4647 实现好了，自己写只会写出 bug。

⚠ 关掉 ResourceBundle 的默认回退
// 显式用 Control 关掉「找不到就回退到系统默认语言」这个行为 ——
// 服务器的系统语言和用户想看什么毫无关系
this.bundle = ResourceBundle.getBundle(BUNDLE, locale,
    ResourceBundle.Control.getNoFallbackControl(ResourceBundle.Control.FORMAT_PROPERTIES));

默认情况下 ResourceBundle 找不到 messages_fr.properties 时， 会回退到运行 JVM 的那台机器的默认语言。 开发机是中文、服务器是英文的话，同一份代码在两台机器上显示不同的语言 —— 而且在开发机上永远复现不出来。

用户给的时区名是不可信输入

/**
 * 时区名来自用户输入或 Cookie，一定要当成不可信的。
 * ZoneId.of 对非法值会抛异常，不接住的话任何人都能用一个
 * tz=../../ 的 Cookie 把整站打成 500。
 */
public static ZoneId parseZone(String raw) {
    if (raw == null || raw.isBlank()) return null;
    try {
        return ZoneId.of(raw.trim());
    } catch (DateTimeException e) {
        return null;
    }
}
⚠ 这是一个很容易被忽略的 DoS

时区偏好通常存在 Cookie 里，而 Cookie 是客户端完全可控的。 ZoneId.of("随便什么") 抛 DateTimeException， 不接住的话这个用户的每一个请求都会 500， 包括「去设置页把它改回来」那个请求 —— 他被自己锁死了， 而且不知道要去清 Cookie。

一般规律：凡是把外部输入喂给一个「解析」函数的地方， 都要问一句「它解析失败会怎样」。 ZoneId.of、Integer.parseInt、 UUID.fromString、Instant.parse 全都是这一类。

偏好从哪来：四级回退

优先级来源给谁用
1用户设置里选的（存数据库）登录用户，换设备也跟着走
2Cookie匿名用户也该能切语言
3Accept-Language 头第一次来的人，零配置就对
4站点默认兜底
ⓘ 算一次就缓存在 ctx 属性里

一个文章列表页可能渲染几十个时间。 每次都重新查用户、解析 Cookie、协商语言太浪费， 所以 Localization 把结果缓存在请求作用域里： 

public static Formats formats(Context ctx) {
    Formats cached = ctx.attribute(CTX_FORMATS);
    if (cached != null) return cached;

    Formats formats = new Formats(resolveZone(ctx), resolveLocale(ctx));
    ctx.attribute(CTX_FORMATS, formats);
    return formats;
}

ctx 属性是请求作用域的， 每个请求一份，所以不存在第 19 章那些并发问题。 这和 UnitOfWork 把 EntityManager 放进 ctx 是同一个模式。

动手练习

  1. 亲眼看看夏令时的坑。写个小程序打印 ZonedDateTime.of(2026, 3, 8, 2, 30, 0, 0, ZoneId.of("America/New_York"))。 它不会报错，但打出来是 3:30。想清楚如果这是一个「每天 2:30 跑的定时任务」会怎样。
  2. 把 relative() 里的跨日判断改成 elapsed.toHours() < 48， 跑 LocalizationTest，确认「跨日判断要按用户时区算」那条变红。
  3. 加一个时区选择器。用 ZoneId.getAvailableZoneIds() 生成下拉框， 并用 JS 的 Intl.DateTimeFormat().resolvedOptions().timeZone 自动选中用户当前的时区。
  4. 手动设一个 Cookie: tz=乱七八糟 再访问首页。 确认页面正常（回退到默认时区），不是 500。 然后把 parseZone 里的 try/catch 去掉，再试一次。
  5. 用 curl -H "Accept-Language: en-US,en;q=0.9" localhost:7070 确认页面变成英文。再试 fr-FR，确认回退到中文而不是报错。
  6. 把剩下的硬编码文案也抽出去。现在只抽了导航栏那几条。 搜一遍模板里的中文，挑一个页面全部换成 layout.t(...)， 体会一下工作量 —— 这就是为什么国际化要在项目早期就做。
  7. 给邮件也加上语言：第 6 章的确认邮件现在永远是中文。 注意一个难点：发邮件时没有 HTTP 请求， 所以语言只能来自用户的偏好字段。
  8. （进阶）messages_*.properties 很容易漏翻译。 写一个测试：遍历所有语言的文件，断言它们的 key 集合完全一致。 这比人工检查可靠得多。
