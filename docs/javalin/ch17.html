部署

把应用放到真实的服务器上，让真实的用户访问。 这一章先把“任何部署方式都要做的事”讲清楚（部署任务、日志、打包）， 再分别讲三条路：PaaS、Docker、传统服务器。 最后给一份上线前的检查清单。

第一步：部署任务

每次发新版本，服务器上都有一组固定动作要做：跑数据库迁移、更新角色定义、补数据。 手动执行既容易漏又容易错，所以第 7 章我们已经把它做成了一个命令： 

case "deploy" -> {
    // ① Db.init 里会先跑 Flyway 迁移
    // ② 创建/更新角色定义（第 9 章）
    // ③ 确保每个用户都关注了自己（第 12 章）
    run(cfg, () -> {
        SeedService.insertRoles();
        SeedService.addSelfFollows();
    });
}
☀ 部署任务必须幂等

原书强调了这一点：“这些函数的设计方式使得多次执行也不会有问题。 这样设计更新函数，就可以在每次安装或升级时直接运行 deploy 命令， 不用担心某个函数在错误的时机运行带来的副作用。”

为什么重要？因为部署会失败、会重试、会回滚重来。 一个"只能跑一次"的部署脚本会在第一次重试时就把你坑住。 验证方法：连着跑两次，结果应该一样。 

java -cp target/javalinky.jar com.example.javalinky.Cli deploy

生产环境的日志

开发时出错，你看到的是控制台里的完整堆栈。 生产环境用户只会看到一个 500 页面 —— 堆栈必须被记录到某个地方， 否则你永远不知道出了什么事。

⚠ 这份配置要放进新文件 logback-prod.xml，不要覆盖 logback.xml

直觉上应该直接改第 3 章那份 logback.xml，但那样会把下面的 SMTPAppender 挂到开发和测试上：每跑一次 mvn test，Logback 都要去连 SMTP；而且没设 ADMIN_EMAIL 时它会在启动阶段打一串配置错误。

所以保留两份，按启动参数选：

  • src/main/resources/logback.xml — 开发/测试用，就是第 3 章那份（只有控制台）
  • src/main/resources/logback-prod.xml — 下面这份，生产用
java -Dlogback.configurationFile=logback-prod.xml -jar target/javalinky.jar

Logback 默认只找 logback.xml，所以不加这个参数永远不会用到生产那份。 本章后面的 Dockerfile、systemd unit 和 Procfile 里都要带上它。 

<configuration>

  <!-- 用环境变量控制，不用改文件就能调整 -->
  <property name="LOG_DIR"   value="${LOG_DIR:-logs}"/>
  <property name="LOG_LEVEL" value="${LOG_LEVEL:-INFO}"/>

  <!-- ① 控制台（容器 / PaaS） -->
  <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
    <encoder>
      <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%X{requestId}] %logger{25} - %msg%n</pattern>
    </encoder>
  </appender>

  <!-- ② 滚动文件（传统服务器） -->
  <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
    <file>${LOG_DIR}/javalinky.log</file>
    <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
      <fileNamePattern>${LOG_DIR}/javalinky.%d{yyyy-MM-dd}.%i.log.gz</fileNamePattern>
      <maxFileSize>100MB</maxFileSize>
      <maxHistory>30</maxHistory>
      <totalSizeCap>3GB</totalSizeCap>
    </rollingPolicy>
    <encoder>
      <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%X{requestId}] %logger{25} - %msg%n</pattern>
    </encoder>
  </appender>

  <!-- ③ 严重错误发邮件。注意用 ERROR 过滤器，否则会被日志淹没 -->
  <appender name="EMAIL" class="ch.qos.logback.classic.net.SMTPAppender">
    <filter class="ch.qos.logback.classic.filter.ThresholdFilter">
      <level>ERROR</level>
    </filter>
    <smtpHost>${MAIL_HOST:-localhost}</smtpHost>
    <smtpPort>${MAIL_PORT:-1025}</smtpPort>
    <STARTTLS>${MAIL_STARTTLS:-false}</STARTTLS>
    <username>${MAIL_USERNAME:-}</username>
    <password>${MAIL_PASSWORD:-}</password>
    <to>${ADMIN_EMAIL}</to>
    <from>${MAIL_FROM:-javalinky@localhost}</from>
    <subject>[Javalinky] 应用错误：%logger{20} - %msg</subject>
    <!-- 一封邮件里带上出错前的若干条日志，便于还原现场 -->
    <cyclicBufferTracker class="ch.qos.logback.core.spi.CyclicBufferTracker">
      <bufferSize>20</bufferSize>
    </cyclicBufferTracker>
  </appender>
  <!-- 邮件发送比较慢，包一层异步，别拖慢请求 -->
  <appender name="ASYNC_EMAIL" class="ch.qos.logback.classic.AsyncAppender">
    <appender-ref ref="EMAIL"/>
    <discardingThreshold>0</discardingThreshold>
    <queueSize>256</queueSize>
  </appender>

  <logger name="org.hibernate.SQL_SLOW" level="INFO"/>

  <root level="${LOG_LEVEL}">
    <appender-ref ref="CONSOLE"/>
    <appender-ref ref="FILE"/>
    <appender-ref ref="ASYNC_EMAIL"/>
  </root>
</configuration>
⚠ 错误邮件一定要限流

想象一下：数据库挂了，每个请求都报 ERROR，每秒 50 个请求 —— 你的邮箱会在一分钟内收到 3000 封邮件， 而且邮件服务商可能直接封了你的账号。

上面的 AsyncAppender 的 queueSize=256 提供了一道粗糙的防线（队列满就丢弃）。 但真正的解法是：别用邮件做告警—— 用专门的错误聚合服务（Sentry、GlitchTip）或监控系统（Prometheus + Alertmanager）， 它们会把相同的错误归并成一条，并支持告警静默。

原书用邮件是因为它零依赖、人人都能跑通。本教程保留它，但请把它当成"最低配方案"。

请求 ID：把一次请求的所有日志串起来

注意上面日志格式里的 [%X{requestId}]。 %X 读的是 MDC（映射诊断上下文）—— 一个 ThreadLocal 的键值表。 给每个请求分配一个 ID 放进去，这一次请求产生的所有日志就都带着同一个 ID： 

package com.example.javalinky.web;

import io.javalin.config.JavalinConfig;
import org.slf4j.MDC;
import java.util.UUID;

public final class RequestId {

    public static final String HEADER = "X-Request-Id";
    private static final String MDC_KEY = "requestId";

    public static void install(JavalinConfig config) {
        config.routes.before(ctx -> {
            // 如果上游代理已经给了一个 ID 就沿用（便于跨服务追踪）
            String id = ctx.header(HEADER);
            if (id == null || id.isBlank() || id.length() > 64) {
                id = UUID.randomUUID().toString().substring(0, 8);
            }
            MDC.put(MDC_KEY, id);
            ctx.header(HEADER, id);      // 回给客户端，用户报错时能提供这个 ID
        });

        // 必须清理！线程是复用的，不清会把 ID 带到下一个请求里
        config.routes.after(ctx -> MDC.remove(MDC_KEY));
    }

    private RequestId() {}
}
⚠ RequestId.install 要排在 Timing.install 之后

上面那句 MDC.remove(MDC_KEY) 写在 after 里，而 Javalin 按注册顺序执行同类型的过滤器 —— after 也是注册顺序，不是倒序。 所以如果把 RequestId 装在第 16 章的 Timing 前面， 它的清理会先跑，Timing 打慢请求日志时 MDC 已经空了： 

10:42:07.113 WARN  [] c.e.javalinky.web.Timing - 慢请求 GET / 共 812ms ...
                   ↑ 本该是 [a3f91b02]

偏偏这正是最需要请求 ID 的那条日志。第 7 章的 JavalinkyApp 里，正确的顺序是： 

Timing.install(javalin, cfg);   // 量整个请求的耗时（它的 after 要读 MDC）
RequestId.install(javalin);     // 把请求 id 放进 MDC 和响应头
UnitOfWork.install(javalin);
Csrf.install(javalin);
CurrentUser.install(javalin);
Authorization.install(javalin);

一般的直觉是"请求 ID 要最先装，这样后面都能用"—— 对 before 来说没错，但 after 的方向正好相反。 凡是在 after 里做清理的过滤器，都要放在用它的人后面。

💡 为什么这个小东西价值很大

用户来报："我刚才提交的时候报错了。" 没有请求 ID 的话， 你要在一秒产生几百行的日志里靠时间戳猜是哪一条。

有了它：500 错误页上显示"错误编号 a3f91b02"，用户把这串字符发给你， grep a3f91b02 javalinky.log —— 整条链路的日志立刻全在眼前。 

<p class="text-secondary small">
  如果需要帮助，请把这个编号告诉我们：<code>${requestId}</code>
</p>

模板里凭空出现的 ${requestId} 得有人传进去。 第 7 章的 ErrorPages 现在要给 500 这一条多带一个参数： 

public static void install(JavalinConfig config) {
    config.routes.error(404, "html", ctx ->
        View.render(ctx, "error/404.jte", "页面不存在"));
    config.routes.error(403, "html", ctx ->
        View.render(ctx, "error/403.jte", "没有权限"));

    // 500 页把请求 id 显示出来，用户报错时能直接提供，方便在日志里定位
    config.routes.error(500, "html", ctx ->
        View.render(ctx, "error/500.jte", "服务器错误",
                    "requestId", String.valueOf(ctx.header(RequestId.HEADER))));
}
ⓘ 为什么从响应头读，而不是从 MDC 读

MDC.get("requestId") 看着更直接，但错误页有可能在 RequestId 的 after 清理之后才渲染 —— 那时 MDC 已经空了。 响应头是上面 install 里一进来就写好的，整个请求期间都在。

外面那层 String.valueOf(...) 不是多余的：JTE 的 @param String requestId 不接受缺失的参数， 真的拿不到时要给一个字符串（"null"）而不是 Java 的 null， 否则其它地方渲染 500 页会抛"参数缺失"，把一个 500 变成两个。

打包：一个 JAR 搞定

第 7 章已经配好了 maven-shade-plugin，但有个问题没解决： JAR 里没有 src/main/jte 目录， 所以运行时编译模板的方式在生产环境行不通。

解决办法是用 JTE 的 Maven 插件在打包时预编译模板。 注意要配两个执行 —— 第 6 章说过 HTML 和纯文本是两个源目录、 两种 ContentType，预编译时也必须分别处理： 

<plugin>
  <groupId>gg.jte</groupId>
  <artifactId>jte-maven-plugin</artifactId>
  <version>${jte.version}</version>
  <executions>
    <!-- ① 网页和 HTML 邮件 -->
    <execution>
      <id>jte-html</id>
      <phase>generate-sources</phase>
      <goals><goal>generate</goal></goals>
      <configuration>
        <sourceDirectory>${basedir}/src/main/jte</sourceDirectory>
        <contentType>Html</contentType>
        <!-- 把模板编译成 Java 源码，再由 javac 一起编译 -->
        <targetDirectory>${project.build.directory}/generated-sources/jte</targetDirectory>
      </configuration>
    </execution>

    <!-- ② 纯文本邮件：另一个源目录、另一个 ContentType、另一个包名 -->
    <execution>
      <id>jte-text</id>
      <phase>generate-sources</phase>
      <goals><goal>generate</goal></goals>
      <configuration>
        <sourceDirectory>${basedir}/src/main/jte-text</sourceDirectory>
        <contentType>Plain</contentType>
        <packageName>gg.jte.generated.text</packageName>
        <targetDirectory>${project.build.directory}/generated-sources/jte</targetDirectory>
      </configuration>
    </execution>
  </executions>
</plugin>
⚠ <packageName> 必须给第二个执行换掉

两个执行的产物都是 Java 源码，默认都生成在 gg.jte.generated.* 下。 如果不给纯文本那套换个包名，两边的类会撞在同一个包里 —— mvn package 不一定报错，但运行时 createPrecompiled 按包名扫描时只能看到一套， 于是生产环境一发邮件就报"找不到 mail/confirm.txt.jte"。

这个坑只在生产模式暴露：开发模式两个引擎各自运行时编译， 包名由各自的输出目录隔开，完全正常。 

/** 生产用：读 jar 里预编译好的模板类，启动快、不需要编译器 */
public static TemplateEngine precompiled() {
    return TemplateEngine.createPrecompiled(ContentType.Html);
}

/**
 * 纯文本那套在另一个包里，所以不能用上面那个单参数的重载 ——
 * 必须显式告诉它类加载器和包名。第一个参数是 classDirectory，
 * 预编译的类已经在 classpath 上了，传 null。
 */
public static TemplateEngine textPrecompiled() {
    return TemplateEngine.createPrecompiled(
        null, ContentType.Plain, Templates.class.getClassLoader(), "gg.jte.generated.text");
}

三种部署模型

路线一：PaaS

原书用的是 Heroku（当时有免费额度，现在没有了）。 今天同类的选择有 Fly.io、Render、Railway、Koyeb 等等。 它们的流程大同小异，这里以通用形式讲，概念可以直接套用。

声明怎么启动

release: java -cp target/javalinky.jar com.example.javalinky.Cli deploy
web: java -XX:MaxRAMPercentage=75 -Dlogback.configurationFile=logback-prod.xml -jar target/javalinky.jar
☀ release 这一行很关键

它声明了"每次部署新版本之后、新进程接管流量之前"要执行什么 —— 正是我们的 deploy 命令（跑迁移）。

为什么不能在应用启动时跑迁移？因为滚动部署时会同时启动多个实例， 它们会并发执行迁移 —— Flyway 有锁机制能挡住，但更干净的做法是 让迁移成为一个独立的、只跑一次的步骤。

ⓘ -XX:MaxRAMPercentage=75 是什么

JVM 默认最多用物理内存的 25% 当堆。在一个 512 MB 的容器里， 这意味着只用 128 MB —— 浪费了。

设成 75% 让它用到 384 MB，留下的部分给元空间、线程栈和堆外内存。 不要设成 100%，否则容器会因为超限被强杀（OOMKilled）。

设置环境变量

# 每个平台的命令不同，但要设的变量是一样的

SITE_BASE_URL=https://javalinky.example.com
SECRET_KEY=<openssl rand -hex 32 的输出>
ADMIN_EMAIL=you@example.com

# 但格式往往是 postgres://user:pass@host/db（不是 JDBC 格式），要转换一下

DATABASE_USER=...
DATABASE_PASSWORD=...

# 邮件：用专业的发信服务，不要用个人邮箱

HTTPS_ONLY=true
LOG_LEVEL=INFO
💡 很多平台给的连接串不是 JDBC 格式

形如 postgres://user:pass@host:5432/db 的 URL 是 libpq 风格，JDBC 驱动不认。加一个小工具函数转换： 

/** 把 postgres://user:pass@host:port/db 转成 JDBC 格式 */
static String toJdbcUrl(String url) {
    if (url.startsWith("jdbc:")) return url;
    var uri = java.net.URI.create(url);
    return "jdbc:postgresql://" + uri.getHost()
         + (uri.getPort() > 0 ? ":" + uri.getPort() : "")
         + uri.getPath();
}

用户名和密码要从 uri.getUserInfo() 里分别取出来。

HTTPS 与反向代理

PaaS 平台在你的应用前面有一层负载均衡器，它负责 TLS 终止。 这带来一个必须处理的问题： 

import org.eclipse.jetty.server.ForwardedRequestCustomizer;

// 只在明确知道自己跑在代理后面时才开
if (cfg.behindProxy()) {
    javalin.jetty.modifyHttpConfiguration(httpConfig ->
        httpConfig.addCustomizer(new ForwardedRequestCustomizer()));
}

if (cfg.httpsOnly()) {
    // 把 http:// 的请求 301 到 https://
    javalin.bundledPlugins.enableSslRedirects();
}
⚠ behindProxy 必须是一个显式配置，不能自动判断

X-Forwarded-For 只是一个普通的 HTTP 头，任何客户端都能随便填。 如果你无条件信任它： 

curl -H "X-Forwarded-For: 1.2.3.4" https://你的站/login
# → 你的限流和审计日志里记的是 1.2.3.4，攻击者真实 IP 不留痕迹

所以规则是：只有当请求确实经过了你控制的代理时才信这个头。 PaaS 和自己配的 nginx 都满足这个条件（它们会覆盖客户端传来的值）； 直接暴露在公网的应用绝对不能开。

路线二：Docker

多阶段构建

# ========== 阶段一：构建 ==========
FROM maven:3.9-eclipse-temurin-21 AS build

WORKDIR /build

# 先只拷 pom.xml 并下载依赖 —— 这一层会被缓存，
# 只要 pom 没变，改代码就不用重新下载几百个 jar
COPY pom.xml .
RUN mvn -B dependency:go-offline

# 再拷源码
COPY src ./src
RUN mvn -B clean package -DskipTests

# ========== 阶段二：运行 ==========
FROM eclipse-temurin:21-jre-alpine

# 不要用 root 跑应用
RUN addgroup -S javalinky && adduser -S -G javalinky javalinky

WORKDIR /app
COPY --from=build /build/target/javalinky.jar app.jar

# 日志目录要让应用用户能写
RUN mkdir -p /app/logs && chown -R javalinky:javalinky /app
USER javalinky

ENV APP_PROFILE=prod \
    PORT=8080 \
    LOG_DIR=/app/logs

EXPOSE 8080

# 健康检查：让编排系统知道容器是不是真的能服务
HEALTHCHECK --interval=30s --timeout=3s --start-period=20s --retries=3 \
    CMD wget -q --spider http://localhost:8080/healthz || exit 1

# exec 形式（不是 shell 形式）：这样 java 进程的 PID 是 1，
# 能直接收到 docker stop 发的 SIGTERM，从而优雅关闭
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", \
            "-Dlogback.configurationFile=logback-prod.xml", \
            "-jar", "app.jar"]

健康检查端点要自己加一个：

// 放在 MainRoutes 里，公开访问
get("/healthz", ctx -> {
    // 不只是返回 200 —— 要真的验证依赖可用
    try {
        Db.em(ctx).createNativeQuery("select 1").getSingleResult();
        ctx.json(Map.of("status", "ok"));
    } catch (Exception e) {
        ctx.status(503).json(Map.of("status", "degraded", "reason", "database"));
    }
});
💡 优雅关闭：Javalin 已经帮你做好了

收到 SIGTERM 时，理想行为是：停止接受新请求 → 等正在处理的请求做完 → 关掉数据库连接 → 退出。

Javalin 的默认 Jetty 配置带了 StatisticsHandler， 所以 app.stop() 会等活跃请求结束。 再加上第 7 章注册的 serverStopping 事件（关邮件线程池和数据库）， 这件事就齐了。 

var app = JavalinkyApp.create(config).start(config.port());
Runtime.getRuntime().addShutdownHook(new Thread(app::stop));

⚠ ${DB_PASSWORD:?...} 这个写法很值得学

冒号加问号表示"这个变量必须有值，否则报错退出"。 这和第 7 章 Env.require() 是同一个思路： 宁可启动失败，也不要带着默认密码上线。

没有它的话，忘记设 DB_PASSWORD 会让 compose 用空密码启动， 然后你有一个空密码的生产数据库。

🔎 深入：原书提到的 Docker 生产环境的局限

原书列了四条，今天依然准确：

  1. 监控告警。Docker 能重启挂掉的容器，但不会告诉你它挂了、也不会在它"活着但不正常"时报警。
  2. 日志。每个容器一个日志流，没有长期存储和检索。要配 ELK / Loki 这类系统。
  3. 密钥管理。环境变量会出现在 docker inspect 的输出里，不算真正的保密。 需要 Docker Secrets、Vault 或云平台的密钥服务。
  4. 可靠性与扩容。要跑多实例、要负载均衡、要滚动更新 —— 这些 Docker 本身不管，需要 Kubernetes、Swarm 或 Nomad。

所以 docker compose 很适合单机部署和开发环境， 但"容器化"和"有一套可运维的生产环境"是两件事。

ⓘ HTTPS_ONLY=false 但 BEHIND_PROXY=true，为什么

HTTP → HTTPS 的重定向交给 nginx 做（更靠前、更便宜）。 应用自己不做重定向，否则会和 nginx 打架造成循环。

但应用需要知道原始请求是 HTTPS 的（为了生成正确的绝对 URL 和设置 Secure Cookie），这就是 BEHIND_PROXY=true 的作用。

⑤ 升级流程

#!/usr/bin/env bash
set -euo pipefail

HOST="user@javalinky.example.com"

echo "==> 本地构建（包括跑测试）"
mvn clean verify

echo "==> 上传"
scp target/javalinky.jar "$HOST:/tmp/javalinky.jar"

ssh "$HOST" bash -s <<'REMOTE'
set -euo pipefail

echo "==> 备份当前版本（方便回滚）"
sudo cp /opt/javalinky/javalinky.jar \
        /opt/javalinky/javalinky.jar.bak-$(date +%Y%m%d-%H%M%S)

echo "==> 替换"
sudo mv /tmp/javalinky.jar /opt/javalinky/javalinky.jar
sudo chown javalinky:javalinky /opt/javalinky/javalinky.jar

echo "==> 跑部署任务（迁移 + 播种）"
sudo -u javalinky env $(grep -v '^#' /etc/javalinky.env | xargs) \
     java -cp /opt/javalinky/javalinky.jar com.example.javalinky.Cli deploy

echo "==> 重启"
sudo systemctl restart javalinky

echo "==> 等它起来"
for i in $(seq 1 30); do
  if curl -fsS http://127.0.0.1:8080/healthz > /dev/null; then
    echo "健康检查通过"
    exit 0
  fi
  sleep 1
done

echo "启动失败，最近的日志："
sudo journalctl -u javalinky -n 50 --no-pager
exit 1
REMOTE
☀ 这个脚本里有三个值得学的细节
  1. set -euo pipefail：任何一步失败就立刻中止。 没有它的话，上传失败了脚本还会继续重启服务，于是你重启了一个旧版本还以为部署成功了。
  2. 备份旧 jar：回滚就是 mv 回来再 restart，几秒钟的事。
  3. 部署后做健康检查：不验证就等于不知道部署成功没有。 失败时自动打印日志，省得你再 ssh 一次。
⚠ 这个流程有一次短暂的服务中断

systemctl restart 期间（约 1–3 秒）请求会被拒绝。 对个人项目完全可以接受。要做到零中断需要：

  • 起两个实例（javalinky@1、javalinky@2，systemd 模板单元）；
  • nginx 配置 upstream 指向两个端口；
  • 逐个重启，重启前先从 upstream 里摘掉。

另外注意：零中断部署要求数据库迁移是向后兼容的—— 新旧两个版本会同时连着同一个数据库。 所以不能在一次发版里"删一列"：要先发一个版本停止使用它，下一个版本再删。

上线检查清单

☀ 第一次上线前，照着过一遍

安全

  • SECRET_KEY 是随机生成的，不是默认值，而且没进版本库
  • 数据库密码是强密码，数据库不监听公网
  • 全站 HTTPS，HTTP 301 跳转，HSTS 头已设置
  • 会话 Cookie 带 Secure + HttpOnly + SameSite
  • CSRF 防护开启（第 4 章），并确认 /api/* 被正确排除
  • enableDevLogging 和 enableRouteOverview 已关闭
  • /internal/metrics 之类的内部端点不可公网访问
  • 应用不以 root 运行
  • 错误页不泄露堆栈信息

数据

  • 迁移在一个空库上从零跑通过（第 15 章的测试已经天天在验证这件事）
  • 有自动备份，而且验证过能恢复（没验证过的备份等于没有备份）
  • 连接池大小和数据库的 max_connections 匹配得上

可运维

  • 日志有地方存、能检索，而且带请求 ID
  • 有健康检查端点，并且真的检查了依赖
  • 进程挂了会自动重启
  • 错误有告警（哪怕只是邮件）
  • 有一条命令就能回滚
  • 慢查询日志已开启（第 16 章）

正确性

  • 生产配置下本地跑通过（APP_PROFILE=prod）
  • 邮件真的能发出去，而且链接是 https:// 的绝对地址
  • 反向代理后面 ctx.ip() 拿到的是真实客户端 IP
  • 静态文件有缓存头，而且更新后不会取到旧版本

动手练习

  1. 执行 mvn clean package，然后用生产配置在本地跑起打好的 jar。 确认模板能正常渲染（这验证了 JTE 预编译配置正确）。
  2. 把 SECRET_KEY 去掉再启动，确认它启动失败并明确告诉你缺什么。
  3. 按 Dockerfile 构建镜像，对比两个阶段镜像的大小： docker images。然后 docker compose up 把应用和 Postgres 一起跑起来。
  4. 在容器里执行 Cli deploy 两次，确认第二次也成功（幂等）。
  5. 用 docker compose stop app 停掉应用，再看 docker compose ps 里 db 的健康状态。 然后 docker compose up -d app，观察它是怎么等数据库就绪的。
  6. 给 RequestId 过滤器加上，然后故意触发一个 500 错误。 在日志里 grep 那个请求 ID，确认能看到这次请求的全部日志行。
  7. 模拟代理场景：用 curl -H "X-Forwarded-For: 1.2.3.4" -H "X-Forwarded-Proto: https" 访问一个会打印 ctx.ip() 和 ctx.scheme() 的调试路由。 分别在 BEHIND_PROXY 为 true 和 false 时试，对比结果 —— 然后想一想为什么这个开关不能默认开。
  8. （进阶）租一台最便宜的 VPS，按"路线三"完整部署一次， 包括申请 Let's Encrypt 证书。这个过程会让你对前 16 章的所有配置项 都有新的理解。
