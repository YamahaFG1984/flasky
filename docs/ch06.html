第 6 章

电子邮件

很多应用需要在特定事件发生时通知用户，最常用的渠道就是电子邮件：注册确认、找回密码、新评论提醒…… 这一章用 Nodemailer 从 Hono 应用里发邮件，用 JSX 写邮件模板，并且让发邮件不再拖慢页面响应。

本章目标

  • 知道一封邮件从应用到收件箱经过了哪些环节
  • 用环境变量配置 SMTP 服务器，并用 Ethereal 在开发时安全地测试
  • 写一个 sendEmail() 函数，同时发送纯文本和 HTML 两个版本
  • 理解“同步发送会拖慢响应”，用后台发送解决它，并处理好错误
  • 知道什么时候该换成邮件服务的 HTTP API 和任务队列

邮件是怎么发出去的

应用自己并不直接把邮件送到对方邮箱。它把邮件交给一台 SMTP 服务器（Simple Mail Transfer Protocol，简单邮件传输协议）， 由 SMTP 服务器负责投递。原书用的 Flask-Mail 是对 Python 标准库 smtplib 的封装；Node.js 生态里对应的是 Nodemailer，它是 Node 世界事实上的标准发信库。 

npm install nodemailer
npm install -D @types/nodemailer

配置 SMTP 服务器

原书表 6-1 列出了 Flask-Mail 的配置项，它们和 Nodemailer 的 createTransport() 选项一一对应：

Flask-Mail 配置Nodemailer 选项说明
MAIL_SERVERhostSMTP 服务器地址
MAIL_PORTport通常是 587（STARTTLS）或 465（SSL）
MAIL_USE_TLS / MAIL_USE_SSLsecuresecure: true 表示一连上就加密（465 端口）；587 端口设为 false，Nodemailer 会自动用 STARTTLS 升级为加密连接
MAIL_USERNAME / MAIL_PASSWORDauth: { user, pass }登录凭据
 
import nodemailer from 'nodemailer'

const transport = nodemailer.createTransport({
  host: process.env.MAIL_SERVER ?? 'smtp.googlemail.com',
  port: Number(process.env.MAIL_PORT ?? 587),
  secure: false,                      // 587 端口：先明文连接，再用 STARTTLS 升级加密
  auth: {
    user: process.env.MAIL_USERNAME,
    pass: process.env.MAIL_PASSWORD,
  },
})
⚠ 永远不要把账号密码写进代码

原书反复强调：凭据要从环境变量读取，尤其是你打算开源的时候。一旦密码进了 Git 历史，就算后来删掉，它也永远留在历史里了。 设置环境变量的方法： 

export MAIL_USERNAME=你的邮箱账号       # macOS / Linux
export MAIL_PASSWORD=你的应用专用密码
$env:MAIL_USERNAME="你的邮箱账号"      # Windows PowerShell

第 7 章会改成把它们写进一个不提交到 Git 的 .env 文件，让应用启动时自动读取。

ⓘ 关于 Gmail

原书当年的做法是在 Google 账户里打开“允许不够安全的应用”。这个选项 Google 已经彻底停用了。 现在要用 Gmail 的 SMTP，需要先给账户开启两步验证，再生成一个应用专用密码（App Password）， 把它填进 MAIL_PASSWORD。原书的另一条建议依然有效：别用个人主邮箱，专门注册一个测试用的账号。

开发时更好的选择：Ethereal

开发阶段其实不需要真的把邮件发出去 —— 你只想确认“邮件内容对不对”。Nodemailer 的作者提供了一个免费的假 SMTP 服务 Ethereal：发给它的邮件不会投递给任何人，但你能在网页上看到邮件的样子。 它甚至不需要注册，代码里就能临时生成一个账号： 

import nodemailer from 'nodemailer'

const account = await nodemailer.createTestAccount()     // 临时生成一个 Ethereal 账号
const transport = nodemailer.createTransport({
  host: 'smtp.ethereal.email',
  port: 587,
  auth: { user: account.user, pass: account.pass },
})

const info = await transport.sendMail({
  from: 'you@example.com',
  to: 'you@example.com',
  subject: 'test email',
  text: 'This is the plain text body',
  html: 'This is the <b>HTML</b> body',
})

console.log('在浏览器里查看这封邮件：', nodemailer.getTestMessageUrl(info))

npx tsx scripts/send-test-email.ts
# 在浏览器里查看这封邮件： https://ethereal.email/message/Zx…

这对应原书“在 Python shell 里发送测试邮件”的一节。原书还特别提到，Flask-Mail 的 send() 要在应用上下文里调用； Nodemailer 没有这种限制，它就是一个普通对象，在哪里调用都行。

把发邮件集成进应用

每次发邮件都手写 from、主题前缀、正文，很快就会变得重复。原书的做法是把公共部分抽成一个 send_email() 函数， 并且邮件正文也用模板生成，一封邮件两个模板：.txt 是纯文本版本，.html 是富文本版本。

邮件模板就是一个普通函数，接收数据，返回两个版本。HTML 版本用 JSX 写，和网页模板一样享受自动转义：

Jinja2：templates/mail/new_user.txt + .html
{# new_user.txt #}
User {{ user.username }} has joined.

{# new_user.html #}
User <b>{{ user.username }}</b> has joined.
一个 TSX 文件：src/views/emails.tsx
export type EmailTemplate<P> =
  (props: P) => { text: string; html: unknown }

export const newUserEmail: EmailTemplate<{ username: string }> =
  ({ username }) => ({
    text: `新用户 ${username} 刚刚注册了。`,
    html: <p>新用户 <b>{username}</b> 刚刚注册了。</p>,
  })

然后是 sendEmail() 本身。主题前缀和发件人，原书放在应用配置里，我们暂时先写成常量：

const MAIL_SUBJECT_PREFIX = '[Flasky]'
const MAIL_SENDER = 'Flasky Admin <flasky@example.com>'
const FLASKY_ADMIN = process.env.FLASKY_ADMIN        // 管理员的邮箱，新用户注册时通知他

async function sendEmail<P>(to: string, subject: string, template: EmailTemplate<P>, props: P) {
  const { text, html } = template(props)
  await transport.sendMail({
    from: MAIL_SENDER,
    to,
    subject: `${MAIL_SUBJECT_PREFIX} ${subject}`,
    text,
    html: String(await html),       // JSX 元素转成 HTML 字符串
  })
}
ⓘ <P> 是什么

这是 TypeScript 的泛型：P 代表“某个模板需要的数据类型”。 调用 sendEmail(to, '新用户', newUserEmail, { username }) 时，TypeScript 会从 newUserEmail 推断出 P 是 { username: string }， 于是你少传或传错字段都会被标红 —— 相当于原书 **kwargs 的类型安全版本。

最后，在处理函数里“见到新名字”时通知管理员：

异步发送邮件

试着提交几个新名字，你会发现：每次提交页面都要“卡”一两秒。原因是 await sendEmail(…) 要等 SMTP 服务器那边一来一回确认收下， 这段时间里浏览器一直在等响应。

原书的解决办法是开一个后台线程去发邮件，并且因为 Flask-Mail 需要应用上下文，还得在线程里手动 app.app_context()。 在 Node.js 里事情简单得多：I/O 本来就是异步的，只要不等它就行 —— 去掉 await，邮件就在后台继续发，响应立刻返回。

但“不等”有一个陷阱：如果后台发送失败了（密码错、网络断），这个错误没有人接住。在 Node.js 里，没有被处理的 Promise 拒绝会让整个进程崩溃。所以要改成这样：

function sendEmail<P>(to: string, subject: string, template: EmailTemplate<P>, props: P): Promise<void> {
  const task = (async () => {
    const { text, html } = template(props)
    await transport.sendMail({
      from: MAIL_SENDER,
      to,
      subject: `${MAIL_SUBJECT_PREFIX} ${subject}`,
      text,
      html: String(await html),
    })
  })().catch((err) => console.error('邮件发送失败：', err))   // ← 一定要接住错误

  return task      // 调用方想等可以 await，不想等就忽略
}

// 处理函数里：不加 await
if (FLASKY_ADMIN) sendEmail(FLASKY_ADMIN, '新用户', newUserEmail, { username: name })

⚠ 在 Cloudflare Workers 这类环境里

Node.js 服务器是一个长期运行的进程，响应发出去之后，后台任务可以继续跑。 但在 Serverless / 边缘环境里，运行时可能在响应发出后就立刻“冻结”这次调用，后台任务会被掐断。 Hono 为此提供了 c.executionCtx.waitUntil(promise)：告诉运行时“响应先发，但等这个 Promise 完成再收工”。 第 7 章的最终版 sendEmail 会顺手兼容这一点。另外，Workers 不支持 SMTP 连接，只能用下面说的 HTTP API 发信。

发得多了怎么办

原书在这一章结尾说：如果应用要发大量邮件，每封都开一个线程并不合适，应该交给专门的任务队列，比如 Celery。 这句话在 Node.js 里同样成立。后台 Promise 虽然轻量，但它活在进程的内存里：进程重启、部署新版本的那一刻，没发完的邮件就丢了。

💡 生产环境的发信服务

正式上线时，一般不用个人邮箱的 SMTP（原书第 17 章也提到 Gmail 的额度很低，而且禁止商用）， 而是用专门的事务性邮件服务：Amazon SES、Postmark、Resend、SendGrid、Mailgun…… 它们都提供 SMTP 接入（改改 createTransport 的配置就行），也提供更快的 HTTP API。以 Resend 为例，一次 fetch 就能发信，这种方式在任何 JavaScript 运行时都能用： 

await fetch('https://api.resend.com/emails', {
  method: 'POST',
  headers: { Authorization: `Bearer ${process.env.RESEND_API_KEY}`, 'Content-Type': 'application/json' },
  body: JSON.stringify({ from: MAIL_SENDER, to, subject, text, html }),
})

小结

  • 应用把邮件交给 SMTP 服务器投递；Nodemailer 的 createTransport() 配置服务器和凭据，凭据只能来自环境变量。
  • 开发时用 Ethereal 这样的假 SMTP 服务查看邮件，不会误发给真实用户。
  • sendEmail() 统一处理发件人和主题前缀；每封邮件同时提供纯文本和 HTML 两个版本，HTML 用 JSX 写。
  • 去掉 await 就能让邮件在后台发送、响应立刻返回；后台 Promise 一定要 .catch()，否则失败会让进程崩溃。
  • 边缘环境要用 waitUntil；邮件量大或不能丢时，换成任务队列和事务性邮件服务。
